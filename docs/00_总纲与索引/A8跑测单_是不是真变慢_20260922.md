## 补测失败的三轮全貌

```
17:50:41.6  首搜开始（进程刚起 1.9s）
17:50:46.667 第1轮：可搜站点=0 定论=false 等待次数=10  → 5s 预算用尽，放弃等待
17:50:46.667 Toast「正在初始化播放源，自动重试…」（FastSearchActivity.kt:510）
17:50:47.317 第2轮（自动重搜1）：等待次数=10 → **0 次等待**，2ms 空转
17:50:47.963 第3轮（自动重搜2）：等待次数=10 → **0 次等待**，3ms 空转 → 判定真空 → 空态
17:50:56.230 jar 首次装载落地（＝站点池此刻才算就绪）——**比放弃晚了 8.3 秒**
```

## 判定（本轮只判原因，不含方案）

**① 不是 DoH。** 三条独立证据：
- 失败窗口内 `DoH命中=0 失败=0` —— 那一轮 `jar装载序号=0/0`，**DoH 连一次都没被调用**；
- DoH **关**的那次冷启（块1）就绪 ≤ +8.75s，**并不比开的快**；
- DoH **开**的两次冷启分别是 ≤+5.8s 与 ≈+16.5s —— **同设置下自身差 10 秒以上** ⇒ 波动来自源站/网络，不来自开关。

**② 真机制 = 「站点池就绪时间」与「等待预算」不匹配。**
就绪实测 5s ~ 16.5s+，而等待预算固定 **5s**（`READY_RETRY_MAX=10 × 500ms`）。
「划掉→打开→立刻搜」（+1.9s 起搜）时，就绪还没到，必然踩空。

**③ S2 空转是放大器（实证）。** 第 2、3 轮 `等待次数=10` —— `readyRetry` 只在 `search()` 里清零，自动重搜轮**一次都没等**。
⇒ 名义上"三轮共 15s"，实际总预算只有 **5s + 1.3s 空转 ≈ 6.3s**。

**④ 我先前"建议 S1 不做"的判断被本组数据推翻，纠正：**
当时依据的是"就绪 4.7~13s ⇒ 只修 S2 的 16.2s 窗口够用"。现在实测就绪可到 **+16.5s**，而首搜可在 **+1.9s** 就发起 ⇒ 需要的窗口 ≈ **14s+**，S2 单改的 16.2s 只剩 2s 余量，太薄。

**⑤ 关键：抬高等待上限不会让正常搜索变慢 —— 机制上不可能慢。**
`FastSearchActivity.kt:647` 的条件是 `!isSitePoolSettled() && readyRetry < MAX`：**池子一旦有定论就立刻跳出等待**。
而上限**只作用在"池子确实还在途"的那段时间**；池子给出"0 站点"的**明确空态**时同样立即停等。
⇒ 正常路径（40 站可搜）**一行都不等**（热态首条 57~67ms、冷启首条 2.2s 均不受影响）；受影响的只有"**今天必然失败**"的那条路。

**⑥ 观感问题（独立于机制）**：`:510` 的 Toast 是在 **5s 预算用尽之后**才弹的
⇒ 用户看到的是「提示 → 马上失败」，而不是「提示 → 一直在等」。这解释了本次观感。

## 🎯 机制定案：就绪 = **一次网络拉订阅配置**，缓存只在失败时兜底

代码链条（`ApiConfig.java` / `HomeFragment.kt` / `MainActivity.kt`）：

1. 冷启进 `HomeFragment` → `loadConfig(onlyConfigChanged, …)`（`HomeFragment.kt:493`）；
2. `onlyConfigChanged = mainActivity.useCacheConfig`（`:304`），而 `useCacheConfig = intent.extras.getBoolean(CACHE_CONFIG_CHANGED, false)`（`MainActivity.kt:28`）
   ⇒ **只有"从设置页回来"才会带 true；从桌面正常冷启一律 false**；
3. `loadConfig(useCache=false)` 时 **跳过本地缓存**，直接走 `doLoadConfigRequest()` 发网络请求；
4. 请求超时＝ **`DEFAULT_MILLISECONDS = 10000`（10 秒／阶段）**（`OkGoHelper.java:39`）；
5. 失败才调 `useCacheFallback()`（"网络不佳，已使用缓存的订阅配置"）→ 并在那里 `sitePoolSettled = true`（`ApiConfig.java:357`）。

⇒ **`站点池定论=true` 的时刻 = 那次网络请求返回（或超时回退）的时刻。**
正常 <1s（#1~#3 都在 +1.6s 内定论）；**网络一抖，10 秒超时＋回退 ⇒ 就绪跑到 +16s**（补测实测 ≈+16.5s，jar 在 `17:50:56.23` 才首次装载）。
**而搜索的等待预算固定 5 秒** ⇒ +1.9s 起搜时必踩空。

## 本段结论

1. **搜索没有坏**：极速冷启 3/3 成功，首条 1.7~1.8s，热态 57~67ms。
2. **失败是"竞态"**：冷启那次网络拉配置慢到 10s 超时，而搜索 5 秒就认输。
3. **要修的是"认输太早"**，不是 DoH、不是搜索线、不是订阅解析。
