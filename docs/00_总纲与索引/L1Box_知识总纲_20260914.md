## 一、构建 / 签名 / 发布链路

| 问题 | 根因 | 最终修法 |
|---|---|---|
| CI 反复构建失败、无产物 | CI 环境不可控 | 放弃纯 CI，改本地构建；脚本固化多道闸门 |
| 老设备/部分机型装不上 | 缺 v1(JAR) 签名 | `apksigner --min-sdk-version 17` 强制 v1(SHA-1)+v2+v3；**验证也必须带此参数**，否则 v1 恒显示 false |

| 资源名混淆 | — | **禁止 apktool 重打包**（会破坏混淆资源名） |
| Guard 站点 `getSpider` 返回 null | 加固 jar 校验宿主签名白名单 | 切回官方 `TVBoxOSC.jks` 签名（部分闪退就此消失） |

**闸门体系**：构建脚本内多道闸门 + `check_l1box_regressions.sh`（源码静态断言，A~V 节 180+ 条）。**重构/改名后锚点必须同步更新**，否则误报。

## 二、架构铁律（违反必炸）

1. **首页源池与订阅站点池严格隔离**：`homeSiteList` ← assets（**永不被订阅覆盖**）；`sourceBeanList` ← 当前线路。
2. **首页.json 绝不能走 `parseJson`**（上一版因此被订阅覆盖，出致命 bug）。
3. **jar 缓存门槛须与上游逐字一致**：`useCache || !md5.isEmpty()`。**写反 → 下拉刷新 jar 永不更新**。
4. **`L1Executors` 是线程池唯一入口**，绝不 `shutdown`；饱和走 SAFE_REJECT（非主线程直跑 / 主线程转 overflow）。
5. **进度存独立 SP**（`util/ProgressStore.java`）；**勿塞回 cache 表**（换库文件＝历史收藏全丢）。
6. 旋转按钮显隐必须走 `applyRotateBtnVisibility(show)`，**勿裸 `setVisibility(VISIBLE)`**；判操作栏可见用 `mBottomVisible`。
7. 新浮层**勿用 `paddingHorizontal/Vertical`**（API26+，minSdk24 会静默丢内边距）。
8. 新增 Toast 文案**必须登记进** ToastSweeper `HOST_TEXTS`。
9. `ShadowLayout` 的 `hl_shapeMode="ripple"` **必须配** `hl_layoutBackground`，否则 NPE。
10. `sourceBeanList` 读写全 `synchronized`，搜索/详情**只用快照**（否则 CME 闪退）。

## 三、加固 jar 崩溃专题（项目最核心，占一半篇幅）

### 3.1 三条物理事实（决定了所有修法的形状）

1. **native abort 是进程级死亡，不是 Java 异常**。`Fatal signal 6` + `JNI DETECTED ERROR`，`catch(Throwable)` **拿不到控制权**
   → **只能"事前串行 + 事前门禁"，绝不可靠 try-catch 兜**。
2. **共享原生状态是进程级的**：`DexNative` 进程内一份；SDK 启动时 **`killall` 掉已在跑的实例**（固定二进制路径）
   → 多个加固 jar 共存＝**互杀链**。串行锁必须**全局**，`lockFor(jarKey)` 管不住 jar 之间。
3. **abort 只有两个出口**（无第三处）：
   - **入站**：`/proxy` → `Proxy.proxy` → `DexNative.proxyInvoke(obj == null)`
   - **初始化**：`Init.init` → `DexNative.getLoader(mid == null)`

### 3.2 真根因①：家族判据的**结构性盲区**（从 ab 起一直存在）

`scan()` 对每个 dex **独立**判定，且 `isProtected()` 要求 **`Init` 与 `DexNative` 同处一个 dex**
→ **"壳 + payload"多 dex 加固 jar** 恒判为普通 jar → 走普通路径直接调 `Init.init` → abort。

**行号级实证**：崩溃栈 `JarLoader.loadClassLoader(JarLoader.java:181)` 就是**普通路径的 `method.invoke`**
（受控路径 `ProtectedInitJar.init` 从不调用 `Init.init`）→ **崩溃 100% 是判据漏判，不是推断**。

### 3.3 真根因②：native **跨代失配**（`mid == null`）

`load()` 每次重进都 `classLoaders.clear()` + `new DexClassLoader`（新一代类），
而解出的 native 库**进程内常驻**（dlopen 不随 ClassLoader 释放）→ **跨代 jmethodID 失效** → abort。

**"退出软件 → 重进 → 搜索"几乎必崩，就是这条**（"退出"不杀进程，"重进"复用进程重新 loadConfig）。

### 3.4 两个反直觉事实（推翻过我的判断）

- **native 不在 jar 内**：Go 代理二进制 4,403,192B 从 `oss4liview.moji.com` / `zl.wpscdn.cn` 的**伪装 .png** URL 下载；
  `libdecjni.so` 解到 `cache/.<随机名>` 后 unlink，会话内出现 **15+ 个不同随机名**，每代重新抽解。
  → **"jar 内含 .so"不能当判据**。
- **jar 内部出站调用走 HTTP 是良性的**：`ConnectException 127.0.0.1:8964 ECONNREFUSED`
  → **代理在 jar 之间受控接力本身安全**。
- **ak 的"0 崩溃"是时序运气，不是机制正确**：其日志里同一 jar 已走普通路径 **13843 次**
  （当时成功进 native 且抛可捕获 Java 异常被吞）。al 的 `warmUp` 预热把跨代初始化密度顶上去，才兑现崩溃。

### 3.5 四道防线（全留，且**不占速度**）

| 防线 | 内容 |
|---|---|
| ① | `NATIVE_INIT_LOCK` 进程级串行（含 bindDexLoader） |
| ② | `GO_PROXY_STARTED` 进程级单飞 + `PROXY_HOLDER` |
| ③ | `JarLoader` 门禁 `isNativeWindow()`（initializing + `proxyQuietUntil` **800ms** → 事前 503；真机实测 exec→health ready 544~573ms） |
| ④ | 路由账本 `protectedJarKeys` / `proxyHolderKey` / `familyJarKeys` + `FAMILY_LOADERS` 身份终审（**必须 static**，主/home 两实例共享） |

> **⚠ 前提**：四道防线**全部以"判据正确"为前提**。判据漏 → 该 jar 不进账本 → **后面全部失效**。
> 这就是"加了四道防线还崩"的真正原因。

### 3.7 一次真实的代价核算（**最重要的一条认知修正**）

| 我早期以为 | 实际 |
|---|---|
| 多判家族 jar → 只是"少个网盘源" | **整个 jar 被拒载 → 该站点直接消失** |

ap 的 458 次拒载就是这么来的：判据放宽后 jar 首进受控路径，而**手写路径把"先起代理"漏了**
→ jar 取 loader 时连 `127.0.0.1:8964` 全 ECONNREFUSED（7738 次）→ 拿不到 loader → 拒载 → **搜索列表为空**。
修法：**两路初始化**（有代理可承接 → 手绑；否则/失败 → 交还 jar 自身 `Init.init`，jar 自己知道正确次序）。

### 3.8 已知边界（降级不崩）

- 家族 jar 无 `startGoProxy(Context)` → 无人成 holder → 其 `/proxy` 全 503（**降级不崩**）。
- init 结构不匹配 → 返 false 干净拒载。
- **首轮慢属正常税**：首次搜索集中创建 26 个 DexClassLoader，第 2 轮起仅 3（单线程池 + 全局串行锁 + 缓存命中）。每进程只交一次。

## 四、jar 中和器（JarKillNeutralizer）

| | 内容 |
|---|---|
| **错法（惨剧）** | 把 kill 方法 `name_idx` 改指**类描述符** `Landroid/os/Process;` → **dex verifier 加载即判非法** → 整 dex 拒载 → `ClassNotFoundException: Init` → **站点永久不可用**；且**就地写回磁盘**造成持久污染 |
| **正法（aj 落地）** | 改指字符串表里**已存在的合法方法名**（如 `toString`，签名不匹配）→ verifier 通过，运行期才抛 `NoSuchMethodError` |
| 配套 | `isLegacyBrokenAlias` 识别旧坏 jar 就地修复；patch 前 `setWritable(true)`；记账用**路径+大小+mtime**（防换版跳过中和） |

## 五、播放器与缓冲水位

### 5.1 播放失败阶梯
- 失败入口**唯一**：`PlayFragment.errReplay()` → `PlayerHelper.buildCompatFallbackPlan`（IJK 软解 → Exo），**每集 ≤ 2 次**。
- 自动切换**只准内置**（`switchToNextInternalPlayer()`）；`mPlayerBtn.performClick()` 会**唤起 MX/VLC**（错）。
- **`STATE_ERROR` 下 `VideoView.start()` 不重建播放器** → 重播**必须先 `release()`**。
- 连播倒计时共用 `showNextEpisodeTip()` + `mNextTipShowing` 防重；停表三处：`onDetachedFromWindow` / `onWindowVisibilityChanged` / `STATE_IDLE`。

### 5.2 缓冲水位定稿（09-12）

**关键认知**：水位与内存是同一物理量的两种写法（`水位秒数 = 字节 ÷ 码率`）。同码率想让水位翻倍，内存必须翻倍。

**默认水位真相**：不是 12.5MB，而是 `min(50 秒, 137.5MB ÷ 码率)`（`minBufferMs = maxBufferMs = 50000`）。

| 档位 | 触发 | 阶段一 | 阶段二 | 字节闸门 |
|---|---|---|---|---|
| **关闭** | `heap ≤ 128MB` 或 `isLowRamDevice()` | 默认 50 秒 | 不升级 | 默认 137.5MB |
| **保守** | `MemTotal ≤ 4608MB`（4GB 机） | 50 秒 | **150 秒** | **48MB** |
| **标准** | 其余 | 50 秒 | **240 秒** | **72MB** |
| **激进** | `heap ≥ 256MB` 且 `MemTotal ≥ 7168MB` | 50 秒 | **300 秒** | **96MB** |

**要点**：
- 升档点按**播放位置**（`playbackPositionUs >= 10s`）判定，**不可只靠 `onStopped()`**（切集走 release，第二集会直接吃深水位）。
- `L1LoadControl extends DefaultLoadControl`，只加一道自有字节闸门；**不反射、不动 Exo 源码**（2.18.7 留了扩展点）。
- **三级兜底**：① 5 条参数不变式（构建期断言）② 升档前可用堆须 ≥ 字节水位 × 3 ③ 内存压力回落 `setTargetBufferSize(24MB)` + **60 秒冷却**。
- 低档**不接管**；高码率源反而**更省内存**（96MB < 137.5MB）。
- **盲区**：4GB 机 `getMemoryClass()` 报 192/256MB，会被判中/高档 → 必须用 `MemTotal` 单开一档。

## 六、首页 / 搜索体验问题

### 6.1 首页"一直加载"（多轮反复，四个卡死点）
① `onPause` 只 `cancelHomeWatchdog()`；② spider 判空用 `isNullOrEmpty()`；
③ spider 空时 `loadJar` 无回调**需放行**；④ 30s 看门狗覆盖 `initData + reloadSitePool`。
另：**OkGo 3.0.4 默认超时/重试会挂住链路**，须显式设超时。

### 6.2 首页每次进入都自动刷新
ViewPager 相邻页销毁重建 → `offscreenPageLimit = fragments.size`（治本）+ `init()` 三分支（空源/有缓存/首次）。

### 6.3 反复进出详情页 → 搜索结果补全停止
`FastSearchActivity` 进详情页调 `searchExecutorService!!.shutdownNow()`：**只返回排队任务，打断在跑任务且永不回**；
`onResume` 仅重投队列余量（常已空）→ **在飞站点永久丢失**。
**修法（aq）**：删掉两处 `shutdownNow()` 与 `pauseRunnable` / `onResume` 重投 —— 让本轮搜索后台自然跑完（已有 30s 看门狗封顶）。

### 6.4 冷启动首搜"空源"（ar 修）
**根因**：把"**还没加载好**"误判成"**没有源**"。
订阅站点池与内置首页源**都是异步装载**，冷启动有一段**两者同时为空**的窗口；
而首页源兜底条件是"订阅池非空才加载" → 兜底也不生效 → `siteKey` 为空 → 直接空态。**点得越快越容易撞上。**
加剧因素：冷启动时"勾选站点"表回退成空表，而**空表被当成过滤条件**，把全部站点滤掉。

**修法（5 处）**：
1. 加"**装载已定论**"标志 `sitePoolSettled`，**四个出口全部置位**（订阅解析完 / 没订阅 / 首页源就绪 / 重试用尽）；
2. 搜索侧未定论就**先等**（`4 × 500ms` 重试），超时才给空态 → **不必再退回首页**；
3. **空勾选集合＝没有过滤意图＝全选**（不再当成"全都不选"）；
4. `DetailActivity` 换源搜索同一处判据对齐；
5. 闸门新增 **V 节 8 条**断言永久锁死。

### 6.5 其它已修体验项
启动画面双图标闪现（values-v31 覆盖 SplashTheme）、分类栏滑动、Tab 切换、全屏正倒序后"高亮集≠在播集"、空状态双入口、扫一扫样式、投屏 `CastDialog` 崩溃（改 `XPopup.Builder.asCustom().show()` + try/catch）、订阅本地导入改 SAF（删 MANAGE_EXTERNAL_STORAGE）。

## 七、被实验否掉的路（**别再走**）

| 路径 | 为什么否掉 |
|---|---|
| **`warmUp` 全量预热** | **密度放大器**：把"5 天一次"变成"每次退出重进一次"。al 崩 5 次即此 |
| **分源并发**（普通 16 / 家族 10） | 收益被预热与崩溃重启吃掉，**体感为负**；名义提速 ≠ 实际提速 |
| **全量 16 并发** | ae/ai 两次实证：提速揭开旧伤 |
| **启发式家族信号**（`nativeRef() && processRef()`） | 把大量普通 jar 误判进受控路径，**458 次误拒载的主因之一** |
| **旧中和器改指类描述符** | dex verifier 判非法 → **整 dex 拒载、站点永久不可用**、磁盘持久污染 |
| **猜 jar 取窗口的路径去拦弹窗** | q~u 五版全败，根因是**没先验证"视图里有 TextView"这个假设** |
| **固定豆瓣热播** | 依赖外链+加固链路，判定不值得修 → 主动降级为"站点推荐" |
| **甲方案＝提速方案**（误读） | **甲不含提速**。甲的目标是"**不崩 + 速度 = ab**"，即回到 ab 水平但不带 ab 的病 |

## 八、工具链与取证踩坑（跨全程复用）

| 坑 | 事实 | 对策 |
|---|---|---|
| **Git Bash PATH 损坏** | `grep/ls/head/dirname` 全 not found | `export PATH=".../PortableGit/.../usr/bin:.../cmd:$PATH"` 一行修复 |
| **后台任务同样需要** | 曾致 `logcat > file` 跑 1h54m 后崩于 `dirname` | **后台命令也必须先 export PATH** |
| **md 读写编码** | `Get-Content` 按 ANSI 读会乱码并写回 | 一律 `python io.open(encoding='utf-8')` |
| **adb 路径** | 不在 PATH、不认 `/c/...` | 用 `C://Users//Administrator//AppData//Local//Android//Sdk//platform-tools//adb.exe`，install/pull/push 必须传 `C://...` |
| **release 包不可 `run-as`** | 拿不到 `files/` 下的 jar | 取证改走反编译 / dex 结构 |
| **logcat 缓冲被挤掉** | 一加按进程配额限流（`LOGS OVER PROC QUOTA(420) DROPPED`） | `adb logcat -b all -v time > file &` 全程后台抓；硬证据走 **`dumpsys dropbox --print`** |
| **`logcat -c` 在 OPPO 上不清缓冲** | 09-14 ar 日志内含清空前的 19:19 内容（清空无效） | 别指望 `-c`；按时间戳切片分析 |
| **应用日志被限流** | 某一窗口 tvbox 的 `System.out` 被丢 125~137 次 | 用 window manager 事件流（`wm_on_resume_called`）还原操作轨迹 |

## 九、流程铁律 & 诚实边界

### 9.1 流程铁律
1. **先列根因与方案 → 用户确认 → 再动手**。
2. **"单机实测通过"不算结论**：要给**机制性兜底**（不依赖具体机型、不依赖某处恰好记得回收），并说明"换台低配机为什么会不同"。
3. **一批一变量，绝不混批**：al/am 的教训就是"分源并发 + 预热 + 判据改动同时上线"，崩了无法归因，白耗两版。
4. **减少崩溃必须，加速锦上添花**。
5. 修复动作**最小化**：隐藏（`alpha=0 / GONE / y=-6000`）优于 `removeView`（jar 后续 removeView 会 `IllegalArgumentException`）。
6. 修复后**必须回头 review**（多次"交付后自检"发现漏网分支）。

### 9.2 明确未证 / 边界
- ✅ **已证（aq 实测）**：手绑路径**能成**（29 次成功 / 28 次回退），此前只敢标"边界未证"。
- ⚠ **本轮测不出**：装载复用在"退出＝划掉杀进程"场景**用不上**，需"回桌面不划掉再进"才验。
- ⚠ **待装机验证**：ar 的"冷启动首搜空源"修复。
- ⚠ 重试上限 2 秒：弱网订阅拉取更久仍会空，但**文案准确、再搜一次即可**，不再有"必须回首页"的死结。
- ⚠ ab 期**无留存真机日志**，不能证明 ab 从未崩过，只能说机制当时同样存在、触发密度低得多。
