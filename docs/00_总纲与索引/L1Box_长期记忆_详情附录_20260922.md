## 一、缓存线要点（09-18~09-19 定稿）

用户目标：点开秒播 ＋ 10 秒后加深加载 ＋ 拖拉不卡 ＋ 不触发风控。

- 风控五维：并发连接数／请求速率／顺序特征／单位时间流量／命中缓存时的请求数。**A（Exo 落盘缓存）五维全不增**＝唯一零风控方案；**多线程尽速预取＝四维异常，不做**。
- 落点：`ExoCacheConfig`（默认 true／256MB／`isCacheableUrl`／`purgeStaleOnProcessStart` 延迟 10s 后台删、幂等、失败不抛）＋`CACHE_DIR_NAME` 创建点与清理点共用；`ExoMediaPlayer.setDataSource` 判开关；`HawkConfig.EXO_DISK_CACHE`＋设置页开关＋`PlayerHelper.init()` 同步（**两个同步点缺一不可**）；`App.onCreate` 调清理。**player 模块不能引用 App 的 HawkConfig ⇒ 开关必须由 App 注入。**
- **🔴 红线**：`127.0.0.1` 的 `/l1.m3u8`（净化）与 `/proxy`（网盘）每集同址，而 Exo 缓存 key 取 URI ⇒ 不排除必然"换集还在播上一集"。已排除：本机／localhost／[::1]／0.0.0.0 ＋ file/content/asset ＋ rtmp/rtsp。
- **升档守门修复（批一）**：原 `create()` 用创建时堆推 deepBytes、守门却比运行时堆 ⇒ 结构性不成立。现＝字节按 `maxMemory()/4` 夹取，守门 `可用堆 ≥ deepBytes+RESERVE(32MB)` 且 `≥ MIN_AVAIL(96MB)`；`AVAIL_FACTOR` 已删。
- **🔴 起播门槛对 HLS 是伪命题**：`bufferedDurationUs` 按整片跃升（实测 5/5 ≥3000ms）⇒ 1000/1500/2200 同一瞬间一起满足。**保留 1500ms 不动**；"自适应门槛"整批取消。Exo 官方默认缓冲 **137.6MB** ⇒ 128MB 比 Google 默认还低＝安全证据。
- 口径：没完全退出软件 → 缓存生效；完全划掉/强停 → **下次打开软件时**清缓存归还存储（残留 ≤256MB，在系统 cache 目录）。**⚠ 缓存类测试别在首页连按两次返回**（`MainActivity.confirmExit` 会 killProcess 清缓存）。
- 起播四段严格串行（中位 ~1058ms）；净化中位 138ms／>2000ms 占 36%，**用户拍板超时 2.5s 不动**；净化只动 m3u8 清单层、不碰画面。IJK 缓存默认关且排除 `.m3u8`。
- 验证脚本 `_l1_batch1/2/3_stats.py`；**清理类判据一律以 `adb shell ls .../cache/` 为准**（日志会丢行）。
- 产物流水：bk `6b457e71b22cf9e784149a53d768c76d`（批三缓存定版，**缓存线六项真机全绿**：命中/清理/水位128+升档/换集不串集/开关/稳定）／bj `ebf5b20ecde9eb8b7ab108bed735c0d0`（批二落盘缓存）／bi `66d658fde067947fe6e42dc085b768f8`（批一埋点+修升档守门）。

## 六、DoH 注入点机制（2026-09-22 第九次精简时移出）

- `DnsOverHttps.java:127` `if (url == null) return Dns.SYSTEM.lookup(...)` ⇒ bm 前 `DOH_URL=0` ⇒ `url=null` ⇒ **链路上零开销**。

## 八、播放中途 404 · 完整现象链与修法约束（2026-09-22 第九次精简时移出）

**现象链**（pid 21389《怒之杀》，净化本地 HLS，源 `111.170.9.52:9090`）：`起播 403ms` → 距起播 **3.96s** 报 `ExoPlaybackException: Source error` ＋ `InvalidResponseCodeException: Response code: 404`（`errorCode=2004`＝BAD_HTTP_STATUS）→ 自动恢复又播起 → **距恢复起播 10.6s 再 404**（**用户说的"第 10 秒"**）→ `兜底 回退原始直连`（**同一条死链**）→ `errorCode=3002` → `兜底 降级到 IJK` → `播放失败：出链 reason=自动兜底试尽`。**从首次 404 到报错白等 11.3s。**

**根因**：`PlayFragment.errReplay()`（620~644）＝①有别的已解析地址才 `errorWithRetry` ②`fallbackToRawUrl` ③`retryVariantUrl`（**IP:9090 非标准端口 ⇒ 直接跳过，恒空转**）④`compatFallback` ⑤`errorFinal`。而**「重新取链」`autoRetry()`（2157）全工程唯一调用点＝`errorWithRetry()`（1179）**，本例 `loadFoundVideoUrls` 为空 ⇒ **一次重取都没有**。**用户手动点重试＝重新取链 → 立刻正常播放（起播 403ms）** ⇒ **片子可播，是兜底链选错动作。**

**修法＝按错误签名分档**（**不可无条件加回**，否则最坏等待 64s→96s，`errorFinal` 1158~1167 注释已写明）：仅当「**播放已开始之后**」且「签名＝**404/410 / `2004`**」时**先试一次 `autoRetry()`**，接管则 return。三约束：①起播前的 404 不加（那时链接刚取）②只认"地址没了"类签名（超时/解码/容器失败不加）③**预算基准要回溯到本次 404 时刻**，不能用 `mEpisodeStartAt`（否则播了 10 分钟就判"预算用尽"跳过重取）。
