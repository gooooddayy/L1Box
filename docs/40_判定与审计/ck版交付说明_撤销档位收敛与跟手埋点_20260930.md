## 二、本版做了什么

### T0 —— 撤销 cj 的档位收敛（用户口径「低档还是去掉吧，保持 8 线程」）

| 文件 | 改动 |
|---|---|
| `util/DeviceProfile.java` | **净删** 7 个方法（−1854 字符）：`imageThreads` / `imageMaxRequests` / `imageMaxRequestsPerHost` / `imageConnectionPool` / `imageCacheBytes` / `itemViewCacheSize` / `siteTabBatch` |
| `util/OkGoHelper.java` | 5 处接线恢复**写死值**：并发 **12** / 单图床 **6** / 连接池 **8** / 磁盘缓存 **64MB** / `l1box-img` 线程 **8** |
| `ui/activity/FastSearchActivity.kt` | ① `SITE_TAB_BATCH` 由 `val … get()` **改回 `private const val … = 8`**；② `setItemViewCacheSize(6)` |

**撤销的附带收益（这才是真正的动机）**：
`App.java` 的 `onTrimMemory` / `onLowMemory` 会调 `markMemoryPressure()`，而它是 `tier = TIER_LOW` **只降不升**。
于是**任何机器**（不只是低配机）一旦内存紧张，`siteTabBatch` 就从 8 掉到 4 —— chip 建得更慢。
"低配机兜底"实际变成了"可能影响所有设备"的隐藏路径。撤销后此路径自然消失。

**精确保留**（不误伤）：`searchConcurrency` / `detailConcurrency` / `timeoutRunnerMax` / `spiderShards` /
`bufferTier` 系列**全部原样保留** —— 它们是改造前就有的，与本次撤销无关。

### T1 —— 临时埋点（本版专用，验证完整体撤除）

统一开关 `private const val L1_TRACE = true`，**全部事件驱动**（只在真发生/真插入/真停稳时各打一条），
绝不逐帧打印 —— 因为 `println` 是同步写 logcat，逐帧打会自己制造卡顿而污染结论。

| 埋点 | 输出 | 要回答的问题 |
|---|---|---|
| 左栏插入 | `[l1] 左栏插入：批量=N 标签=… 距末滚动=Xms 前Y=… 后Y=… 滚动段=Xms/N次 队列=… 待建=… 可滚=… 上限=… chip=…` | ① 插入时列表**真的静止**吗？② 插入有没有**改掉滚动位置**？ |
| 右栏停稳 | `[l1] 停稳收尾：取消=Xms 审计投递=Yms 预取=Zms 合计=… 待落=… 累计取消调用=…` | IDLE 三件活里**哪一件**最贵？ |
| 最差帧 | `帧耗时[本轮]：… 最差=…ms@时刻(阶段) ｜最差帧当时[右栏=… 左栏Y=… 左栏可滚=… 待建=…]` | 卡的那一下，用户**是否正在滑**？ |

## 四、🔬 本轮测试要做什么（关键）

**目标**：让埋点抓到"卡的那一下是谁造成的"。三件事，按顺序做一遍即可。

### 步骤

1. 打开 App，**发起一次搜索**（用你平时会卡的词，能出多个站点的那种）。
2. **搜索还在进行时**（左侧站点 chip 还在陆续冒出来的时候）：
   - 先**慢速**上下滑左栏几次 → 记住手感
   - 再**快速**上下滑左栏几次（就是平时会"卡住不跟手"的那种快法）
3. 切到右侧结果列表：
   - **快速**滑动，然后**松手让它惯性停下来** → 重点感受"停下瞬间的顿挫"
   - 重复 3~5 次
4. **等这一轮搜索完全收尾**（右侧不再插入新结果、日志打出帧耗时汇总）再停。

### 事后我会从日志里读这三行

| 埋点 | 判据 |
|---|---|
| `左栏插入` 的 `距末滚动` | 若**明显小于 400ms** 却仍插入了 ⇒ 守卫判错（L1 成立）。<br>若 `前Y ≠ 后Y` ⇒ **插入真的改掉了滚动位置**，直接锁定"卡住/被拽回" |
| `左栏插入` 的 `可滚=false` | 若大量出现 ⇒ 印证 L4：**chip 不够多时左栏根本不接管手势**（拖不动） |
| `滚动段=Xms/N次` | 若某段时长**远超 400ms** 且期间没有触摸 ⇒ 就是"手已松开、惯性仍在跑"的窗口 |
| `停稳收尾` 的 `取消/审计/预取` | 三者中谁的 ms 数最大，谁就是右栏顿挫的头号嫌疑 |
| `最差帧当时` | `右栏=滑动中` ⇒ 卡在滑动里；`待建>0` ⇒ 与 chip 创建有关 |

### 操作提示

- **不要**只滑一次就停 —— 一次滑动只产生一行埋点，样本太少。
- **不要**在搜索完全结束、右栏不再插数据之后才滑左栏 —— 那样 `待建=0`，测不到"插入与滑动打架"。
- 若想复现"拖不动"，**搜索刚发起的前几秒**就去滑左栏（那时 chip 还少）。
