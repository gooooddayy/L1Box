## 一、为什么改这一版

后续澄清：

> 我说的**快速搜索/快速滑动**，就是**上一次滑动的惯性还没结束后就开始下一次滑动**。

### cm 取证给出的量化证据（`_cm2.log` 的 14:43 段）

只统计**落在左栏内**（x<350）且纵向位移 >150px 的手势，共 **56 次**：

|---|---|---|
| 正常跟手 | **46** | 滚动 / 手指位移 = **0.97 ~ 1.00**（完美 1:1） |
| **完全零响应** | **20** | 手指滑 **350~684px，滚动 = 0** |

## 二、根因

`DslTabLayout` 里「能否滚动」**完全押在 GestureDetector 的返回值上**：

```kotlin
// 改动前
if (needScroll) {
    if (isEnabled) {
        intercept = super.onInterceptTouchEvent(ev) || _gestureDetector.onTouchEvent(ev)
    }
} else {
    if (isEnabled) {
        intercept = super.onInterceptTouchEvent(ev)   // ← needScroll=false 时【不喂 detector】
    }
}
```

两个结构性问题：

1. **漏喂 DOWN 即断链。** `needScroll=false`（chip 不足 ~18 个）期间，DOWN 事件**不被喂给 detector**。
   detector 是有内部状态机的（`mCurrentDownEvent` / `mDownFocusX,Y` 基准点）。
   基准点缺失后，它在后续 MOVE 上算出的增量与判定条件不再成立 ⇒ **`onScroll` 永不触发**
   ⇒ `onScrollChange` 不被调用 ⇒ `intercept` 恒 `false` ⇒ 事件被让给底下的 chip
   ⇒ **滚动彻底不发生**。
2. **`||` 短路隐患。** `super.onInterceptTouchEvent(ev)` 返回 `true` 时，detector **根本不会被调用**
   （Kotlin `||` 短路）。

## 三、改法（两项，均**只在 detector 未处理时生效**）

### ① 无条件喂 detector（顺带消除短路）

```kotlin
val detectorHandled = if (isEnabled) _gestureDetector.onTouchEvent(ev) else false
...
if (needScroll) {
    if (ev.actionMasked == MotionEvent.ACTION_DOWN) {
        _overScroller.abortAnimation()
        _scrollAnimator.cancel()
        l1ArmFallback(ev)
    }
    if (isEnabled) {
        intercept = super.onInterceptTouchEvent(ev) || detectorHandled
        ...
```

- detector 调用**提前并无条件执行** ⇒ 不再有「漏喂 DOWN」的窗口。
- 顺带消除 `||` 短路（detector 一定被调用）。
- **安全性**：`needScroll=false` 时 `onScrollChange` 自身 `return false`，不会滚动
  —— 行为与「不喂」等价。

### ② 原始位移兜底（不再依赖 detector 的状态机）

- **拦截阶段**：detector 未接管、且 MOVE 相对按下点已超过 `scaledTouchSlop`
  ⇒ 直接 `intercept = true` 接管。
- **处理阶段**：`onTouchEvent` 里 detector 返回 `false`（未处理本帧）且是 `ACTION_MOVE`
  ⇒ 用**原始位移**自己 `scrollBy`。

关键实现细节：

| 细节 | 原因 |
|---|---|
| 兜底判定用 `ViewConfiguration.scaledTouchSlop`，不写死 | 与系统触摸判定一致，避免误吃点击 |
| 兜底自滚**只在 `ACTION_MOVE`** | UP/CANCEL 帧 detector 本就不产生 `onScroll`，在此兜底会把「抬起点与最后 MOVE 的差值」多滚一次，破坏正常路径 |
| 位移方向 = `上一帧 - 当前帧` | 与 `GestureDetector.onScroll` 的 `distance` 同向，保证不反手 |
| 兜底日志每段手势最多 1 条 | 逐帧 `println` 会自造卡顿、污染结论 |

### 正向：`onFling` 加 `needScroll` 守卫

无条件喂 detector 之后，原本靠「`needScroll=false` 就不喂」间接避免的 fling 需要显式守卫：

```kotlin
if (!needScroll) return true
```

### **零回归性质**

两处兜底都**只在 detector 返回 `false` 时执行**：

- 拦截阶段：`if (!intercept && ...)`
- 处理阶段：`if (!handled && ...)`

⇒ **detector 正常工作时，走的还是原来那条路，行为逐字不变。**

## 四、本版**保留全部埋点**（ck 3 条 + cm 5 条 + cn 2 条）

原计划验完就撤，但本版的意义正是**证明"是不是 detector 路径失效"**，必须靠埋点分辨。

### cn 新增两条（**只在 detector 漏网时才打印**）

| 埋点 | 含义 |
|---|---|
| `[tp] ★★兜底接管（detector 未接管）左栏Y=…` | detector 未接管 ⇒ 兜底接管 |
| `[tp] ★★兜底滚动生效（detector 未处理）位移=…` | detector 未处理 ⇒ 兜底自滚 |

**判读方式：**

| 现象 | 结论 |
|---|---|
| 这两条**频繁出现** | detector 路径**确实在失效**，兜底把它救回来了（且是否还有残留零响应手势？） |
| 这两条**从未出现**，但断触好了 | 是「**无条件喂 detector**（补上 DOWN 基准）」起的作用 |
| 这两条从未出现，断触也没好 | 推断被推翻，需要重新取证（父级拦截已被 `★CANCEL=0` 排除） |

## 六、测试指引

### 复现场景（照用户自己的定义）

**「上一次滑动的惯性还没结束，就接下一次滑动」** —— 在**左栏内**连续快速滑动，
**不需要**滑到顶/底（cm 已验证中间位置同样会断）。

### 步骤

1. 发起搜索（用结果多的词）
2. 在**左侧站点还在陆续冒出来**、以及**站点出齐之后**，各做一轮连续快速滑动
   - 动作要点：手指快速上/下滑，**趁着的惯性还在跑就立刻再滑下一次**，反复 10 次以上
3. 感到"手动了但内容没动"就继续滑 —— 这种被吞的手势是**偶发**的，要攒样本
4. 切换右侧，快速滑 + 松手，重复 3~5 次
5. 说一声，我 dump 分析

### 判据（数据到手即可定论）

| 看什么 | 说明 |
|---|---|
| `★★兜底接管` / `★★兜底滚动生效` 出现次数 | 直证 detector 路径是否在失效 |
| 零响应手势（滚动=0 且惯性=0）还剩几次 | 对比 cm 的 **20/56**，看改善幅度 |
| `★CANCEL` | 仍应为 0（父级未拦截） |
| `帧耗时` 平均/最差 | 确认兜底没自造卡顿（cm 为 平均 6~7ms / 最差 33ms） |
| `右栏滑行` 突变与尾帧 | 右栏本版**未改**，作为对照基线 |

## 七、本版**没做**的事（明确边界）

| 项 | 状态 | 理由 |
|---|---|---|
| 右栏任何改动 | **未做** | cm 已证「惯性本身正常」，尾帧不收敛来自**用户主动按下中断**（＝Android 标准行为，`abortAnimation`）。用户目标"松手按惯性自然停下"本就是标准语义 |
| `tv_selectedItemIsCentered` | 已于 cl 关闭 | 字节码查明只走焦点滚动路径，保留 `mGridViewFilter` 作对照 |
| 撤除埋点 | **未做** | 本版要靠埋点判读，验完下一版一并撤 |
| 自动换线路 / 自动换源 | 不做 | 用户纪律 |
| 判死秒数（20+12s / 70s / 15s / 8s / 重取 2 次） | 一字未动 | 用户纪律 |
