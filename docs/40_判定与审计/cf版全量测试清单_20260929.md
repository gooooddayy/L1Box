## 一、ce 轮实测的结论（为什么要有 cf）

**ce 四项改动里三项生效**：① 自转发真的跑起来了（35 条）② 按 `do` 路由功能正常 ③ 净化真归因拿到 `Http503`（不再是 `Http0`）。

**但暴露了一个更精确的 bug —— 手绑 jar 的世代账本在冷启动「必然」失效**：

```
12:54:13.272  手绑成功 14942a7863        ⇒ 记 (main, gen1)
12:54:13.571  71b4332a 接管代理          ⇒ PROXY_GEN: 1 → 2
12:54:14.268  8ad2ef8d 接管代理          ⇒ PROXY_GEN: 2 → 3
12:56:21.269  /proxy do=WexAiYueYue key=14942a7863
              判定=拒:非代理持有者(手绑未登记或世代已变)   ← 我们自己 503
```

`proxyCapable()` 里的 `hb.gen != PROXY_GEN.get()`（1 ≠ 3）把它判死。而家族 jar 本进程有 **4 个**，总有一个先手绑、其余陆续接管 ⇒ **先手绑的那个必然出局**。

**对照组（证明判定逻辑本身可行）**：`0b9565d6a6`（海绵的 jar）恰好排在两次接管**之后**才手绑 —— 没被顶掉，**顺利放行，`do=ck` 还能 `返回=200`**。

## 二、cf 做了什么（2 项）

| 项 | 内容 | 为什么 |
|---|---|---|
| **① 手绑放行判据「去快照化」**（主修） | 放行条件从「绑定时 holder **且世代**都没变」改成「**绑定时那一任持有者 == 当前持有者**」。绑定时若还没有持有者（`getLoader` 连上的是进程最早那任），则只要求当前有持有者即认。**世代号降级为诊断留痕，不再参与放行** | 初版错在**语义**不在参数：它把「手绑」当成了冻结快照，而 `bindDexLoader()` 的事实是 `DexNative.getLoader()` **每次调用时现场去连当前在跑的代理** ⇒「手绑成功」本就是一个**持续成立的关系**。冻结后任何无关接管都会误杀 |
| **② 路由埋点判据修正** | `route` 从 `key.equals(recentJarKey) ? "recent" : "do"` 改成**由 `mapped` 是否命中直接决定**；日志新增 `手绑账本=` 字段；拒绝措辞拆成「从未手绑」/「手绑后已换届」两种 | 原判据**用错变量**：取链前刚 `getSpider()` 过该站点 ⇒ `key` 与 `recentJarKey` **天然相等** ⇒ 恒打 `recent`。ce 轮 56 条日志 `do` 出现 0 次，一度被误读成"路由没生效" |

### 安全边界（为什么敢放宽 ①）

`JarLoader.proxyInvoke` 在 key 门禁**之后**还有一道「ClassLoader 终审 + 运行时探测」（`probeFamily` / `isHolderClassLoader`）。一层放宽只影响"是否走到第二层"，**不会直接放到 native** —— 真正会 abort 的是打错 holder 的原生对象，那条路径由第二层按 loader 身份封死。
