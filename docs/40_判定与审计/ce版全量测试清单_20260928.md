## 二、ce 做了什么（4 项）

| 项 | 内容 | 为什么 |
|---|---|---|
| **① `/proxy` 自转发兜底**（A 类主修） | jar 返回 `null` 时，按那条 URL 里**已经写着**的信息自己把流取回来：`url` 解 base64 = 上游地址、`ck` 解 base64 = `k=…&Time=…&uid=…`（凭据）；复用**现有转发链**（Range 透传、m3u8 分片重写都会照做）。**只在 jar 不接单时启用**，jar 正常时一行不碰 | A 类之前 **100% 失败**，这条把它变成"有机会成功"，且不依赖 jar 内部行为 |
| **② 自转发的门禁** | 与 `/l1play` **完全一致**：只允许本机（或持有有效投屏码的局域网设备） | 否则就成了局域网里人人可用的开放代理 |
| **③ `/proxy` 按 `do` 路由** | 记下「站点 key → 它的 jar」，路由优先用请求里的 `do`，找不到才回退 `最近使用的 jar` | 排除"请求被送进另一个 jar 的 Proxy ⇒ 返回 null"这类结构性隐患 |
| **④ 净化失败的真归因** | 从 OkGo 的**原始响应**取真实状态码（dd 轮暴露：OkGo 3.0.4 抛 `HttpException` 时 `rawResponse` 已置空 ⇒ `code()` 读回 0，日志里只剩 `Http0`，等于白打）＋把异常原文一起打进日志 | **B 类定刀的唯一依据**：403 补头、404 是地址失效、5xx 是源站问题，三者修法毫无共通之处 |
| **⑤ 分段计时修正** | "结果落地"的耗时**结算在插入之后的下一帧**（原来只在插入那几行前后计时 ⇒ 阈值 25ms 一条都没触发，而帧埋点抓到 240ms，说明代价在布局/绘制里） | 让"卡在哪一步"变成可读的数字，而不是猜 |
