# 性能 / 内存 / 功耗 / 稳定性 四项评估与落地（2026-10-12 · dn 轮）

口径：**先量数据 → 先核对历史上是否已优化过 → 只做"必要"的 → 不硬拉指标、稳定优先**。
用户指示：「面向大部分手机，我的手机性能本身比较好 ⇒ 做到最好就行，非必要就不优化」。
所有实测都在真机 OPPO（1264×2780 @560dpi，8 核，堆 256MB，MemTotal 11179MB）上完成。

---

## 0. 一句话结论

| 项 | 结论 |
|---|---|
| 冷启动减负 | **已优化到位**（启动到首页出内容 ≈640ms），不建议再动 |
| 页面流畅度 | 主线程与绘制**都不超帧预算**（0/120），掉帧来自显示侧排队 ⇒ **app 侧无有效杠杆，不硬拉指标** |

## 1. 冷启动减负：已到位，不做

### 实测（冷启动 3 次，取 logcat 时间戳）

| 观测点 | 实测 |
|---|---|
| Splash 首帧 | **191 / 194 / 192 ms** |
| MainActivity 首帧 | **+126 / +126 / +139 ms** |
| 首页缓存命中 + 渲染 20 条 | 比 Splash 首帧晚 **40~75ms** |
| **从启动到首页出内容** | **≈640 ms**（含 adb 启动开销） |
| jar 下载 | 启动后 **~4s** 才发起（后台，不挡首屏） |

### 历史上已经做过的（**不要再重复劳动**）

| 机制 | 位置 | 说明 |
|---|---|---|
| 去掉 Splash 固定停留 | `SplashActivity.kt` | 原固定 500ms 品牌停留已删，改为 `post(goMain)` 下一帧直接跳 |
| Exo 播放缓存清理 | `ExoCacheConfig.purgeStaleOnProcessStart` | **只做 1 次改名**（与目录大小无关）+ 后台线程延迟分片删除 |
| 播放器缓存清理 | `App.onCreate` | 后台线程 + 延迟 5s（避免递归删目录卡主线程） |
| EPG 解析 | `EpgUtil.init` | 挪到 `epg-load` 后台线程，主线程只在真正查询时用 |
| 崩溃循环自恢复 | `StartupGuard.begin()` | 放在**一切业务初始化之前**，它要记录的正是"这次启动有没有走完" |
| 设备能力分级 | `DeviceProfile.init` | 并发/缓冲按档取值，先于业务初始化 |

### 剩余可选但**不做**：把主线程 init 后移

`App.onCreate` 目前仍在主线程串行做：`OkGoHelper.init` / `NetworkMonitor.start` / `ControlManager.init`（本地服务）/ `AppDataManager.init`（DB）/ `LoadSir` / `AutoSize` / `PlayerHelper.init` / `QuickJSLoader.init`（`System.loadLibrary`）/ `initCrashConfig` / `initExitGuard` / `ToastSweeper.start` / `Utils.initTheme` / `initBackgroundGuard`。

- 本机 Splash 首帧 190ms 里，Application.onCreate 占比不大（进程 fork + dex 映射是大头）
- 每一个都有明确的使用前置：OkGo 必须在首次网络请求前、ControlManager 必须在 `/proxy` 被访问前、PlayerHelper 必须在首播前、QuickJS 必须在首个 JS 站点前
- **后移＝人为制造竞态**：收益（低端机几十~一百毫秒）远小于风险（首播/首搜/代理偶发失败，且极难复现）
⇒ 按"非必要不优化"不动。

## 2. 页面流畅度：app 侧无有效杠杆，不硬拉指标

### 实测：`dumpsys gfxinfo`（首页网格上下滑动 16 次）

```
总帧数 1234
Janky frames        57 (4.62%)     ← 标准口径
Janky frames(legacy) 32 (2.59%)    ← legacy 口径
p50 / p90 / p95 / p99 = 11 / 17 / 19 / 29 ms
Missed Vsync 0 ; Slow UI thread 17 ; Slow bitmap uploads 2
**Slow issue draw commands 56**    ← 占 janky 的 98%
Frame deadline missed 57 ; (legacy) 1
```

### 逐帧阶段拆解（framestats 最后 120 帧）

| 阶段 | p50 | p90 | max | 超过 16.67ms |
|---|---|---|---|---|
| UI 线程（measure / layout / draw） | 1.11 ms | 7.74 ms | 9.13 ms | **0 / 120** |
| sync（上传位图 / 资源） | 0.21 ms | 0.57 ms | 1.86 ms | **0 / 120** |
| issueDrawCommands（栅格化） | 1.84 ms | 3.56 ms | 5.78 ms | **0 / 120** |
| **swapBuffers（提交 / 等 buffer）** | 3.07 ms | **15.30 ms** | 16.45 ms | 0 / 120 |
| 帧总耗时（含等 VSYNC） | 10.94 ms | 36.07 ms | 36.62 ms | — |

其中 `QueueBufferDuration` p90 **7.24 ms**。

### 结论

- **主线程逻辑与绘制都不超帧预算**（三段各 0/120）；帧总时长 p50 10.94ms 已贴近 120Hz 的 8.33ms 边界
- 被计入"掉帧"的部分主要来自**显示侧排队（swapBuffers / QueueBuffer）**，属于 SurfaceFlinger + 面板刷新节奏，**app 代码没有对应杠杆**
- 已做过的渲染侧优化：首页 item **仅 6 层视图 + 1 个渐变背景**；`setHasFixedSize(true)`；Picasso `.fit().centerCrop()`（按控件尺寸解码，不整图入内存）；`ToastSweeper` 的全树扫描已从"每帧"节流到 **~11Hz**（窗口级仍每帧，那是防弹窗闪现的必要代价，历史上降频曾导致横幅闪现回归）

⇒ **不硬拉指标**。若强行压到 ≤2%，唯一有效手段是把刷新率降到 60Hz 或砍掉列表动效 —— 那是牺牲体验换数字。

## 3. 内存与功耗

### 3.1 泄漏：受控实测**无**

```
基线（冷启首页）  Views 245  Activities 2  AppContexts 5   PSS 140 MB
5 轮进出后        Views 479  Activities 4  AppContexts 12  PSS 325 MB
第 15 轮（累计）  Views 479  Activities 4  AppContexts 12  PSS 325 MB   ← 与第 2 轮完全持平
send-trim 之后    Views 357  Activities 3  PSS 266~268 MB（图片缓存被放掉）
```

- **从第 2 轮起完全持平，13 次追加操作零增长** ⇒ 无线性泄漏
- 未捕获异常处理器、`ExitGuard`、`ToastSweeper`、`MemoryGuard` 的静态引用均指向 **Application 级**（`ControlManager.mContext = App` 已核对），无 Activity 被静态持有

⚠️ **如实标注**：冷启动基线就带 `Activities: 2` / `ViewRootImpl: 3`，我没能定位这 2 个额外实例是谁（release 包无 profiler，`run-as` 不可用）。影响面 = 个位数 MB 且不增长 ⇒ 按"非必要不优化"不动。

### 3.2 峰值 / OOM：历史 0 次 OOM

| 点 | 现状 |
|---|---|
| 图片 | 全部 `.fit().centerCrop()`，**有界解码**（不整图入内存） |
| `/proxy`（图片/资源本地代理） | `InputStream` **流式回写**，不整包缓冲 |
| 首页缓存 | 序列化后落 **DB**（`CacheManager`），**不常驻内存** |
| jar 下载 | **有意**整读进内存（1.86MB）—— 必须先校验魔数再动磁盘旧文件（dg 的 403 教训：缓存被写坏比下载失败隐蔽得多）。改流式会重新引入该风险 ⇒ **不动** |
| 字幕 | 小文件，`response.body().bytes()` 量级为 KB |
| 低端机机制 | `DeviceProfile` 三档（堆上限 / `isLowRamDevice` / MemTotal）+ `L1LoadControl` 缓冲水位 + `MemoryGuard`（前后台 + `onTrimMemory` + `onLowMemory` 释放图片缓存） |
| 历史实证 | `_d*_dump_1012*.txt`（**共 40 万行**）里 `OutOfMemoryError` = **0** |

### 3.3 功耗：本轮**唯一需要改的一处**

**全仓扫描结果（无 WakeLock / Alarm / Job / WorkManager / 定位）**

```
grep WakeLock|newWakeLock|AlarmManager|setRepeating|JobScheduler|WorkManager  → 0 命中
grep ACCESS_FINE_LOCATION|LocationManager|requestLocationUpdates            → 0 命中（未申请定位）
<service> / startForeground                                                  → 0（无前台服务）
后台播放                                                                      → 功能已下线（默认走画中画）
```

**所有"自续期 / 周期"调度逐条核对**：

| 调度点 | 停止条件 | 判定 |
|---|---|---|
| `VodController` 1s 缓冲补刷 | `stopBufferTicker()`，`onDetachedFromWindow` / 退后台均停 | ✅ 已受控 |
| `BaseVideoController` 进度刷新 | `startProgress / stopProgress` | ✅ 已受控 |
| `ToastSweeper` 帧循环（Choreographer） | `resumedCount > 0` 才续期 | ✅ 已受控 |
| **`ToastSweeper` 250ms 兜底轮询** | **无 —— 无条件、永不停止** | ❌ **本轮修掉** |
| Exo 缓存清理 / `cache-clean` / EPG | 一次性任务 | ✅ |

**为什么它是纯空转**：退到后台后 `sweepDecor()` 一看 `topActivity == null` 就立即 return，帧循环也早按 `resumedCount` 停摆 ⇒ 这一拍只做两次方法调用＋几个 `continue`。而它原本设想的职责「在后台重新拉起帧循环」，`onActivityResumed` 早已覆盖（回前台那一刻就 `scheduleFrame()`），且**生命周期事件比定时器更可靠**（不受 App Freezer 冻结/延迟影响）。

**修法**（`ToastSweeper`）：

1. 轮询（`FALLBACK_POLL`）只在 `resumedCount > 0` 时自续期
2. 最后一个前台页面 `onActivityPaused` / `onActivityStopped` ⇒ 立即 `cancelFallbackPoll()`（撤销待执行任务）
3. 回前台由 `onActivityResumed` / `onActivityStarted` **事件驱动**重拉
4. **首拍仍是启动后 2 秒**：`scheduleFallbackPoll` 里「已有待执行的一拍就直接返回」，避免"回前台重排"把首拍从 2s 提前到 250ms（那会改动冷启动期行为）
5. 前台其余行为**逐拍一致**：之后每 250ms 一次、窗口级"防弹窗闪现"扫描仍每帧执行

**量化：测不出干净数字（这台 ROM 会冻结后台应用）**

初版 A/B（启动 → 背景 60s）曾得出 dm 409 次 / dn 200・119 次。**20:45 复核后此解读作废**：该 60 秒窗口里应用早已被系统冻结
（`I/OplusHansManager: freeze ... scene: LcdOn`、`OplusBinderProxy ... calling: OFreezer`），量到的差异混入了启动收尾工作与冻结时机抖动。

严格重做（启动 → 空闲 25s → HOME → 逐 5 秒窗）：

| 版本 | 前台空闲 5s | 后台窗1 | 后台窗2 | 窗3~6 |
|---|---|---|---|---|
| dm（旧） | 454 | **133** | 47 | 0 / 0 / 0 / 0 |
| dn（新） | 425 | **79** | `/proc` 读空 | 0 / 0 / 0 / 0 |

⇒ 方向一致，但**窗口只有 ~10 秒（之后被冻结）且为单样本 ⇒ 不作为有效量化**。

⭐ **准确表述**：本项删掉的是"应用在没有前台页面期间、每秒 4 次的主线程空转唤醒"。
- **这台 ROM 上收益被冻结掩盖**（约 10 秒后一切都停），每个后台会话最多省 ~40 次唤醒 ⇒ 体感与电表都测不出。
- **在没有激进冻结的设备/ROM**（老 Android、电视盒子 —— 本项目主要受众，且盒子通常长期通电）上，旧代码会**一直**每 250ms 转下去，新代码**一次都不转**。
- 真机埋点确认取消/重拉成对有效：`前台页面已消失：兜底轮询停摆` / `回到前台：兜底轮询重新拉起`（13 对完美交替，末态在转）。

⚠️ **不夸大**：省下的绝对 CPU 是微秒级。本项价值是**结构性**的 —— 改完后 App 在后台没有任何周期性调度。风险为零、前台逐拍不变。

## 4. 稳定性兜底：已做过，本轮复核通过

| 层 | 机制 | 位置 |
|---|---|---|
| 后台线程异常 | 安全网：非主线程异常只记日志不杀进程；主线程仍走崩溃页 | `App.java` |
| 已知噪声分流 | 非主线程 + `NoSuchMethodError` + 指向 `android/os/Process` ⇒ 不写 `files/crashes/` | `App.java`（dm 落地） |
| 崩溃日志 | `CrashLog`（全 try/catch，不在处理器内二次抛错） | `util/CrashLog.java` |
| 启动崩溃循环 | `StartupGuard`：连续多次没走完 ⇒ 清首页缓存放行 | `util/StartupGuard.java` |
| jar 自杀（killProcess） | `JarKillNeutralizer` dex 层改方法名 ⇒ 抛可捕获异常 | `catvod/crawler/` |
| jar 自杀（exit） | `ExitGuard`：SecurityManager 只覆写 `checkExit`，按调用栈判定来源 | `App.java` |
| jar 弹窗 / 横幅 | `ToastSweeper` 两级清扫（帧钩子 + 250ms 兜底） | `util/ToastSweeper.java` |
| 网络与数据降级 | 弱网重连 / 切网感知 / DNS 兜底 / 各态看门狗 / 订阅四态提示 | 见上一轮评估文档 |
| 资源异常 | 图片 LRU + `MemoryGuard`；jar 内容校验（魔数）；缓存 DB 序列化 | 多处 |

**本轮日志实证**（含冷启动 + 前后台切换 + 首页加载）：
`ANR in` **0** ／ `OutOfMemoryError` **0** ／ `SIGABRT` / `Fatal signal` **0** ／ 唯一 `FATAL EXCEPTION` 是已知 `Init$3` 噪声，并被 `D/App: 已知噪声（jar 自杀调用已中和）⇒ 不记崩溃日志：Thread-9` 正确接住。

⚠️ **一处观察，明确不改**：`StartupGuard.success()` 只在启动后 10 秒的 `postDelayed` 里判定。我实测用 `force-stop` 连打 3 次就触发了「检测到启动崩溃循环，已清理首页缓存后放行」。这是该机制**设计内**的逃生门行为；放宽它等于削弱"启动崩溃循环自恢复"能力 ⇒ 维持不动。

## 6. 明确"不做"的清单（防止以后重复劳动）

| 候选 | 判定 | 理由 |
|---|---|---|
| 把 `Application.onCreate` 里的 init 后移/异步 | ❌ | 每个都有明确使用前置，后移＝引入竞态；本机收益小 |

## 7. 这次没测到的

- **弱网 / 断网 / 切网 / VPN / 系统代理**：本轮未复现（上一轮已核机制，`NetworkMonitor` 四项都在）。此前明确记录过：**VPN/系统代理零感知，必须复现才能下结论**。
- **低端机 / 电视盒子真机**：本机是旗舰（8 核 + 11GB RAM）。低端机的结论全部来自**机制**（`DeviceProfile` 分档 + 只能靠静态验证的分支），符合"不做单机适配、做兼容性预案"的口径，但**不等于已在低端机上验证过**。
- **播放页长时间播放的功耗**：本轮只测了前后台切换，没测连续播放。
