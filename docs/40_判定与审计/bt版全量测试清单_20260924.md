# 三、判定与根因（bt 三项修复）

> 测试阶段**不用看这一节**；每轮测完我在这里补判定。

## ① A2 无限转圈 · 根因链

**症状**：0 结果搜索**永远转圈**，从不给「暂无数据」（bs 实测 68 轮 / 201 秒 / 0 命中）。

**根因（一行代码）**：`JarLoader.loadJarInternal` 的 `finally` **无条件** `LOAD_SEQ.incrementAndGet()`。

- `getSpider` 只在**成功**时把 spider 存进 `spiders` 表；被跳过的站点（加固不可用 / 装载失败 / 主 jar 未挂载）**不进表**。
- 于是**下一轮搜索会把这个 jar 重新查询一遍** → `loadSeq` 每轮 +1。
- 而 `poolSignature()` 含 `loadSeq` ⇒ 池签名**每轮都变** ⇒ 复检判据③「池未变」永远为假 ⇒ 回 S3 等池变化 ⇒ S3 又看到签名变了 ⇒ 重搜 …… **无限循环**。

**修法**：`loadSeq` 只记**首次**装载结论（`SEQ_COUNTED` 按 jar key 去重），`load()` 里随 `classLoaders.clear()` 一起重置账本。
**语义依据**：装载序号要回答的是"本轮搜索有没有和**某次装载**重叠"，**重复查询不是装载事件**。

**代价**：0 结果场景最多多绕一轮（≈1 秒）才给空态。**这是有意为之** —— 宁可多等一秒，也不给假空。

## ② A3 8ms 假空 · 根因链

**症状**：冷启动首搜**8ms** 就摆出「暂无数据」（3 个独立进程全复现）。

**根因**：主 jar 还没挂载时，`classLoaders.get("main") == null` ⇒ `getSpider` **立刻**返回 `SpiderNull` ⇒ 站点被静默记成 0 条 ⇒ 复检时四条判据**全部成立**（池确实定论了、确实问全了、期间啥都没变、结果确实是 0）⇒ 诚实空态 —— 但那不是真空。

**修法**（判据从「完整性」升到「+ 前提有效性」）：
1. `JarLoader` 暴露 `mainSettled()`（主 jar 装载是否已有结论，`finally` 保证归零）；
2. 复检加**第五条判据**：主 jar 装载未出结论 ⇒ **一律不判空**；
3. `poolSignature()` 纳入该状态 ⇒ 主 jar 装完那一刻签名变 ⇒ S3 带着就绪的 jar **重搜一次**；
4. S3 末尾补一条「等主 jar 结论」的出口；
5. 新增 `spiderNullSeq()` 统计"被跳过的站点数"，收尾摘要打 `跳过=N` —— 真机从此能区分**「问了没结果」**和**「根本没问」**。

**为什么是机制性修复**：主 jar **装载失败**也是"有结论" ⇒ 不会无限等；**装载成功** ⇒ 签名变 ⇒ 自动重搜出结果。两个方向都收敛。

## ③ D1 外部播放器 403 · 根因链（两条）

**症状**：MX 起来后约 **10~12 秒**结束；上游 `HTTP error 403 Forbidden`；日志里 `改喂本机转发端点` **一次都没有**。

**根因①（主因）**：`wrapForExternalPlayer` 的第一条判据是
`if (headers == null || headers.isEmpty()) return url;` —— **站点不下发请求头时静默退回**，MX 拿到的是**裸地址**，上游防盗链直接 403。
bs 实证：4 次 MX intent 的 data **全是裸地址且无 `|` 后缀**，包装埋点 0 次。

**根因②（次因）**：即使包装生效，转发端点当时用的是 `getDefaultClient()`，**readTimeout = 10 秒**
—— 视频流只要 10 秒没有新数据（暂停 / 拖动 / 上游缓冲）就被 OkHttp 掐断。这就是日志里"另一个 10 秒"。

**修法**：
- 缺请求头时按播放地址补**同源 Referer** 后再包装（`fillMissingHeaders` 从 PlayFragment 搬到 `PlayerHelper`，净化预取与转发两条链路共用一份，口径不漂移）；
- 转发端点改用新增的 `OkGoHelper.getForwardClient()`（**连接 10 秒、读/写不设限**）。

**边界（沿用既有口径，没变）**：兜底 Referer **只喂转发链路**，绝不写进播放器默认请求头 —— 否则跨域 CDN 上的分片会集体 403（这是 bs 之前就踩过的坑）。

## ④ 投屏 · 与 D1 同源，但多一个约束

**为什么不能照搬**：投屏走 DLNA，**电视是另一台机器**，它自己去上游取流 ——
给 `127.0.0.1` 它解析出来是**它自己**，必然拉不动；而且 DLNA 的 `SetAVTransportURI` **只接受一个 URI**，天生没法带请求头。

**修法**：投屏地址换成 **`http://<本机局域网IP>:<端口>/l1play?t=<一次性随机码>`**。

**安全红线（这次唯一放开门禁的地方，逐条说清）**：
1. 只有**带有效投屏码**的 `/l1play` 请求才允许非本机访问；**没有码的请求依旧只允许本机** —— 门禁那一行只把 `/l1play` 移出，`/localfile/` 与 `/dns-query` 一个字没动；
2. 码＝**32 位十六进制 SecureRandom**，不可猜；
3. 码**只能取"本次投屏登记的那一条地址"** —— 拿去拼接别的 URL 不生效；
4. 电视拿到的 URL 里**不含上游地址、也不含站点请求头**（用码代替），所以抓包也拿不到；
5. 最多同时在册 8 条、12 小时过期、重新投屏即换码；
6. 取不到局域网 IP 时**原样退回**（宁可投屏缺头，也不给电视一个必然连不上的地址）。

**已知边界（如实记录）**：转发端点透传的是**主地址**那一条流。若上游是 m3u8 且**分片**另有防盗链，分片仍由设备直连（与改动前一样），这种情况本次修不了 —— 遇到就记下来。
