# 二、cg 版对三项的处理

## ① 手绑世代账本 → **静态推理收口，判定为已修复**

cf 轮无法造出「先手绑的 jar 之后又被别的 jar 接管」这个时序（配置里没有 `WexAiYueYue`，整轮只有 1 次手绑、0 次接管）。用户决定：**静态推理收口，不再要求实测**。

**收口论证（已固化进 `ProtectedInitJar.java` 注释）**：

1. **判据与原 bug 一一对应** —— 原 bug 成因是 `hb.gen != PROXY_GEN.get()`；唯一能把它判死的输入是"世代号变了"。现在这个比较**在代码里已不存在**（`HandBound` 没有 `gen` 字段）⇒ **原 bug 的触发条件本身被移除**。
2. **新判据只有两种走向，可穷举** —— 设 `H0`=绑定时的持有者 key、`Hc`=当前持有者 key：
   - `H0 == Hc` ⇒ 中间没有任何 `occupyProxy` 把别人扶上位（换届必换 key）⇒ 代理仍是绑定时那一任 ⇒ 放行合理；
   - `H0 != Hc` ⇒ 确实换过届 ⇒ 拒绝，与原语义一致。
   两种走向都与"这个 jar 还能不能碰当前代理"这个真实问题一致，没有第三种情况。
3. **`getLoader` 语义决定"手绑＝持续关系"** —— `DexNative.getLoader(context)` 是**调用现场**去连当时正在跑的代理并当场返回新 loader，拿到的东西天然是"当前"的。ce 轮的对照组已反证：`0b9565d6a6` 排在两次接管**之后**手绑，就能正常放行并 `返回=200`。
4. **万一推理有误，代价被封在第二层** —— `JarLoader.proxyInvoke` 的「ClassLoader 终审 + 运行时探测」仍按 loader 身份拦住。本层放宽的**最坏后果是"多走到第二层再被拒"**，不会变成 SIGABRT。

> 这是**删除式修复**（触发条件被移除），不是参数调优式修复 —— 前者不需要实测覆盖。
> 若将来配置里出现多 jar 站点交叉调用的场景，用日志核对一次即可（判据：`判定=放行` 出现，且不出现 `拒:手绑后已换届`）。

## ② `do` 路由 → **找到真根因：两张表是不同命名空间**

**真根因（cf 轮数据 + 代码追踪确认）**：

- `/proxy` 的 `do` 是 **jar 内部自造的短标识**（实测全部样本只有 `hmys`、`ck`）；
- 而 `siteJarKeys` 存的是 **`sourceBean.getKey()`**（配置里的站点 key，如 `海绵`/`WexAiReBo`）；
- **两者是不同命名空间 ⇒ 查表必然 miss** ⇒ 每次都回退 `recentJarKey` 碰运气。

**cg 的改法**：新增 `doJarKeys`（`do → jarKey`），**从成功请求里学**：

| 环节 | 做法 |
|---|---|
| 路由优先级 | ① `doJarKeys`（学到的，最可靠）→ ② `siteJarKeys`（站点 key，兼容 do==key 的配置）→ ③ `recentJarKey`（回退） |
| 登记条件 | **只有"放行且返回非 null"才记**（返回 null ＝这个 jar 不认这个 do，不得固化错路由） |
| 日志 | 新增 `路由=do(学到)` / `do(站点key)` / `recent(回退)` 三态 + **`表规模=do表N/站点表M`**（一眼看出路由表到底有没有被填起来） |

## ③ 分段耗时 → **找到真根因：结算时机赶不上**

**真根因（读代码确认，非阈值问题）**：

`flushSearchResults()` 设置 `pendingSegTag` 后，**紧接着同步**打帧快照 —— 收尾路径是
`flushSearchResults() → printRoundSummary() → snapshotFrameStats()`，**中间没有任何帧机会**。
而结算却挂在"下一帧的 `doFrame`"里 ⇒ **快照总是先出、结算永远赶不上**；且 `snapshotFrameStats` 还会把 `frameWorstMs` 等计数**清零**，等于证据被抹掉。

**cg 的改法**：抽出 `settlePendingSeg()`（幂等：先取 tag 再置空），**两处都调用**：

- **收尾时主动结算**（正常收尾 + 超时收尾各一次）—— 保证一定出数；
- **`doFrame` 里保留**（正常路径下更准）。
