# 三、判定依据（bu 三条修法的由来 —— 分析放后面）

bt 复测第 1 轮的现场日志（`adb logcat -d`，bt 五条判据版）里挖出的三件事：

## 洞 1：判空判据里没有"本轮有站点被跳过"

- **实证**：每轮日志都有 `跳过=1`（`18:15:18.639 搜索耗时：收尾 站点=40 命中=0 … 跳过=1`）。
- **机制**：`跳过` ＝ `JarLoader.getSpider` 的三处 `skipNull`（主 jar 没挂上 / 加固 jar 不可用 / 构造抛异常）。汇总的站点**压根没被问到**，却被记成"0 条"。
- **叠加 A2 的连带代价**：`loadSeq` 去重后签名在 jar 首次结论处冻结 ⇒「首次装载失败 ⇒ 后来装上」**再也不会改签名** ⇒ S3 永不重搜 ⇒ 直接判空。
- **对得上用户的观测**：`18:15:08.787 搜索首条结果：71ms 站点=剧圈99 关键词=军鸡`、`18:17:24.099 首条 1705ms 站点=剧圈99 关键词=军鸡` —— 同一个冷门词两次都命中，随后都给出了空态。
- **修法**：判据⑥ ＝「本轮没有**新面孔**站点被跳过」。只认新面孔（`JarLoader.skippedKeys()` 账本差集）—— 老面孔是本机跑不了的站点，拿它拦判空会退回无限转圈；新面孔可能是瞬时的，给它**一次**重搜。

## 洞 2：池签名只看站点数量，不看内容来源

- **实证**：`18:17:32.852 复检 池就绪=false(定论=true 缓存池=true) … 池未变=true(41|true|4|true->41|true|4|true)` → 1 秒后 `18:17:33.855 判定为真空，给出空态`。
- **机制**：签名四段（站点数｜定论｜loadSeq｜主 jar 定论）在"缓存池 41 站 → 网络池 41 站"时**逐字相同**（缓存本来就是上一次网络配置的存档，站点数常常一样）⇒ 换了内容的池被当成"没变"⇒ 判空。**敢不敢判空取决于一个布尔位的时序，而不是"池真的没变"。**
- **修法**：签名追加第五段 `isPoolFromCache()`。缓存池→网络池那一刻签名必变 ⇒ S3 自动重搜。

## 洞 3：幽灵收尾（`allRunCount` 初值 0 ＋ `count <= 0`）

- **实证**：日志里 **14 次** `搜索复检：0 结果 … 问全=false(0/0) 池未变=false(->41|true|7|true) jar装载=0->7` —— `roundPoolSig` / `roundLoadSeq` / `roundSiteCount` 全是**初值**（`roundPoolSig` 全文件仅一处赋值）⇒ 这一轮 `searchResult` **从未执行**就被收尾了。
- **机制**：`allRunCount` 初值 0，而新一轮开始时先 `set(0)` 再逐个 `increment`。落在那个窗口里的**孤立回调**（上一波迟到的结果）把计数打成 **-1**，`count <= 0` 就触发了一次"本轮没开始"的伪收尾。
- **为何没出事**：那一刻 `roundAsked=0` ⇒ 判据②（问全）恰好挡住。**纯属运气** —— 早几十微秒落进窗口就是假空。
- **修法**：`count <= 0` ⇒ `count == 0`。

## 顺带确认的事（不必修）

- `SEARCH_TIMEOUT_MS = 30000`（`FastSearchActivity.kt:74`）⇒"转几秒"**必然不是看门狗收尾**，是全部站点回调完的正常收尾。**慢站点没有被提前掐断。**
- 日志内 `Guard jar 内部 loader 未就绪` **0 条** ⇒ 那个被跳过的站点不是加固型，来自 `classLoader == null`（jar 下载/加载失败）或构造抛异常。

⇒ **`loadSeq` 每轮都在 +4，判据③（池未变）永不成立，S3 立刻又发一轮**，30 秒一轮地转下去。这与 bt 修的 A2 是**同一个机制**（"池签名变没变"用 `loadSeq` 做判据），说明 bt 的"同一 jar 只计一次"在真机上**没挡住它**：
- 18:58:23 → 18:58:53 这 30 秒里，该进程**没有任何一条 jar 装载成功的日志**（`自定义爬虫代码加载成功!` 只在 18:57:59 出现），序号却从 4 涨到 8。

## 洞 5：判据②（★问全☆）是**伪判据**，恒真

```

FastSearchActivity.kt:698    val askedAll = roundAsked >= roundSiteCount && roundSiteCount > 0
```

## 洞 6：站点"没回调"有一条**确定性**的漏计通道（`searchResult` 这个 LiveData 无人订阅）

|---|---|---|---|
| **529** | `ApiConfig.get().getSource(sourceKey) == null`（该 key 不在当前池里） | `searchResult.postValue(null)` | **无回调** |
| **610** | 站点类型不在 `{0,1,3,4}`（`else` 兜底） | `searchResult.postValue(null)` | **无回调** |

而搜索结果的**实际**派发走的是 EventBus：`SourceViewModel.java:982/996` 里 `if (searchResult == result) EventBus.post(RefreshEvent(TYPE_SEARCH_RESULT, …))`；`FastSearchActivity` 也只订阅 EventBus（`:411 refresh`）。
**全工程检索 `searchResult` ＋ `observe/Observer`，唯一的观察者是 `SearchSubtitleDialog` 里的 `subtitleViewModel.searchResult`（另一个类的另一个对象）** ⇒ 上面两处 `postValue` 投进了**没人订阅的 LiveData** ⇒ 这次回调永远不来 ⇒ 计数漏一格 ⇒ 本轮只能等 30 秒看门狗。冷启时池正从缓存池切网络池，`getSource(key)` 取不到 key 的概率恰好最高 —— 与"只有冷启立刻搜才这样"的观察一致。

## 结论

A2 **未通过**，且不是"慢一点"的问题，是**结构性不收敛**：判据③ 依赖的 `loadSeq` 每轮都动，判据② 又是恒真的伪判据，两者叠加后 S3 会一轮一轮地重搜，每轮还都要 30 秒（因为有站点不回调），再加上 bu 判据⑥ 的重搜，用户永远等不到"暂无数据"。

## 三、根因链（闭合）

1. 分片地址是**相对路径** ⇒ 播放器必须用"清单的 URL"当**基准（base）**去补全；
2. bt 之后，MX 拿到的清单 URL 是 **`http://127.0.0.1:9978/l1play?u=…&h=…`** ⇒ 基准变成"本机 9978 的根目录"；
3. 补全结果 = **`http://127.0.0.1:9978/<分片名>`**（实验 D 第一行）；
4. 本机服务没有这个路径 ⇒ 回 **HTML 首页**；
5. FFmpeg 在 **open 阶段**就要读第一个分片探编码 ⇒ 读到 HTML ⇒ **`AVERROR_INVALIDDATA`** ⇒ MX 弹出「**无法播放**」。

**⇒ 改前 8~12 秒、改后 1 秒内死** —— 因为改前 MX 拿到的是**上游原始地址**（base 正确、分片能取到），只是续传丢头才断流；改后 base 被换成本机，**第一秒就死在分片探测**。这就是"这次连 10 秒都没有"。

## 四、两个旁支（不是主因，但要说清）

- **为什么 #2/#6/#7 能打开**：这三次 MX 真的 `prepared` 出正常时长 ⇒ 那几集的清单里分片**应是绝对地址**（同站 `getQyM3u8` 与 `getM3u8` 是两个接口，返回格式不必一致）。⇒ **"能不能播"取决于该次清单用相对还是绝对分片**，这解释了同日同站时好时坏。
- **#3 属另一类失败**：240ms 就挂，与"分片"无关 —— 更像**上游当时自己返回了错误页**。旁证：本机用 PC 复现 #1 那条（地址已过签名期）拿到的是 **3397 字节 `text/plain` 的 ASCII-art 提示页**，根本不是 m3u8；CA 同理可发生在个别 CDN 节点上。

## 五、顺带查出的第二个问题（藏在同一段代码里）

**转发端点无条件回 `Accept-Ranges: bytes`，而上游并不支持 Range。**

实测（PC 与手机双重复现）：对上游发 `Range: bytes=0-1023` ⇒ 上游**返回 `200` + 完整 197865 字节**，**没有 `Content-Range`、也没有 `Accept-Ranges`**（＝忽略 Range）。
而 `servePlayForward` 里：`probe.addHeader("Accept-Ranges", (ar == null || ar.isEmpty()) ? "bytes" : ar)` —— `ar` 为空时**硬写 `bytes`** ⇒ **对 MX 谎报"这个地址支持拖动"**。

## 六、投屏预判（还没测，但机理同源）

D1-投屏 走的是**同一个 `servePlayForward`**，只是把端点换成局域网 IP＋一次性码。**电视同样会拿"局域网转发端点 URL"当 base 去拼相对分片** ⇒ 大概率**同源失败**。真机上测的时候按同一套判据看即可。

**用户原话**：「E3-复测这个字体颜色改成白色」。属**用户亲自下令的外观改动**（唯一允许在测试期动代码的口子），改动范围只限续播浮层的字色。

## 改了什么

| 项 | 改前 | 改后 | 位置 |
|---|---|---|---|
| 文字颜色 | `#FF1B5E20`（深绿） | `@color/white`（白，与同文件 `player_next_tip` 按钮同口径） | `player_vod_control_view.xml` `resume_jump_text` |
| 文字投影 | 无 | `shadowColor=#B3000000` / `Dx=0` / `Dy=1` / `radius=3` | 同上 |
| 注释 | 记「半透明淡绿底 ＋ 深绿字」 | 改记「半透明淡绿底 ＋ 白字」＋ 改白理由 | 同上 `:732` 附近 |

**为什么顺带加投影**：底是 `#73A5D6A7`（**只有 45% 不透明度的淡绿**），背后是**视频画面**。白字落在亮画面上会糊（一轮做设计时正因为这一点才把白字换成深绿字）。投影只加深轮廓、**不改变"白字"这个事实**，任何画面上都能读清。不想要投影的话去掉那 4 行 `shadow*` 即可，一行不用改 Java。

## 没动的东西（特意说明）

- **背景 `shape_player_resume_jump_bg`（`#73A5D6A7`）没动** —— 用户只说字色。
- **字号 / 内边距 / 停留 5 秒 / 点击才跳 / 无底部 Toast 全没动** —— E3 其余判据照旧测。
- **Java 一行没动**（`VodController` 里没有 `setTextColor`，颜色纯靠布局，安全）。

## 对测试的影响（要紧）

⚠️ **bu 包里仍是深绿字**（改动是在 bu 出包之后落的）⇒ **E3 只能等下一个包测**，拿 bu 包测等于测旧外观。

## 校验方案（等出包时执行）

- **不改闸门**：`check_l1box_regressions.sh:1146/1149` 锚的是 `resume_jump_layer` 与 `shape_player_resume_jump_bg` 两个**资源名**，**没有任何断言锚颜色值** ⇒ 不受影响。
- **不改 dex 清单**：`_br_dexsym.py:#5` 锚 `showResumeJumpTip` / `resume_jump_layer` / `resume_jump_text` / `shape_player_resume_jump_bg`，全是标识符与资源名，同样不涉颜色。
- **构建后**：`aapt2 dump resources` 或直接解包 `resources.arsc` 复核 `resume_jump_text` 的字色引用即可（资源名不变，正常情况下不必额外验）。
