# 播放缓存与风控：方案定稿

日期：2026-09-18　状态：**待拍板**（本文只定方案，不动代码）

---

## 一、一句话结论

1. **你担心的风控，风险不在"要不要缓存"，而在"用什么形态缓存"。** 方向 A（落盘）在任何风控维度上都是**零增量、甚至更少请求**；真正高危的是"多线程尽速预取"那种形态。
2. **你想要的"10 秒后加深"机制早就在跑，但基本上没生效** —— 本次 15 次真机会话里，够条件升档的 6 次只成功了 4 次，而且**失败时一行日志都没有**。修好它，是零风控、零流量就能拿到"往前 5 分钟"的正路。
3. **"去广告命中率"不是视频里的广告**，是 **m3u8 清单里的广告分片/跳转层**（播放列表层面）。本次 11 次净化里 **0 次命中、36% 白等 2 秒以上** —— 数据支持把它收紧。

## 二、先回答你问的四件事

### ❶ 去广告命中率 = 什么？

**不是**视频内容里的广告，**不碰视频画面**。它指的是 **m3u8 清单层面的广告**，两种形态：

| 形态 | 长什么样 | 净化怎么做 |
|---|---|---|
| **跳转层** | 清单第一行不是 `#EXTM3U`，而是**另一个 m3u8 地址**（先把你带到广告页再给真清单） | 再取一层，拿到真清单 |
| **少数派分片** | 真清单里**夹着几个域名/路径明显不同的分片**（就是插进来的广告片） | `removeMinorityUrl()` 把它们从清单里剔除 |

**"命中"** = 成功识别并剔除了；**"命中率下降"** = 原本能剔除的源，因为净化超时提前放弃，**直接连原地址 → 那几段广告会照播**。

代码位置：`PlayFragment:1301` `//remove ads in m3u8`、`startPurified()` → `removeMinorityUrl()`。

> 净化还有第二个作用（常被忽略）：命中后清单改由**本地 HLS 端点**（带 `.m3u8` 后缀）提供，等于明确告诉播放器"这是 HLS"，**消掉"第一下播不出、切一下就好"的容器误判**。所以净化不完全等于去广告。

### ❷ 「起播后立刻重缓冲」是什么影响？

`L1LoadControl.START_PLAYBACK_MS = 1500` 的含义是：**缓冲到 1500ms 才允许出画面**。

- 门槛**降** = 画面出得早，但出来时**兜里只有那么点余量**。若紧接着的分片来慢了，缓冲被吃穿 → **触发重缓冲（转圈）**。
- 用户感受：**"刚出来就卡住"** —— 这比"多等 0.5 秒再顺畅播"体感更差，而且会被记成"播放失败"。
- 两档门槛的分工：`bufferForPlaybackMs=1500`（首次起播）、`bufferForPlaybackAfterRebufferMs=5000`（重缓冲后恢复）。后者刻意保持 Exo 默认不动。

### ❸ 起播门槛降过吗？

**降过一次：2500ms → 1500ms**（`L1LoadControl:53`，Exo 默认 2500）。
**本次结论：不再降。** 收益 <0.5 秒，换来的是"起播即卡"的风险上升 —— 属于拿确定性换不确定性。

### ❹ 不预取下一集

**接受，方向 D 划掉。** 你的判断对：下一集预热要**提前调用一次取链**，会碰解析层（与既有的"不预热 spider jar"纪律边界最近），收益却只在"连看"时体现。不做。

## 三、本次真机日志的新发现（15 次会话 / be 版本）

### 发现 1：净化占了 1/3 会话的 2 秒以上，且 0 命中

| 指标 | 数值 |
|---|---|
| 净化耗时 中位 | **138 ms** |
| 净化耗时 P90 | **2655 ms** |
| 净化耗时 最大 | 2906 ms |
| **>1200ms 占比** | **36%**（4/11） |
| **>2000ms 占比** | **36%**（4/11） |
| 净化结果 | 无需处理 10、无净化 4、失败/超时 1、**命中 0** |

样本原话（`_be_test1.log`）：

```
13:27:27.720 净化 开始 url=https://vip.ffzy-play10.com/.../index.m3u8
13:27:30.030 净化 无需处理，直连 ms=2310      ← 白等 2.31 秒
13:27:30.030 起播 url=https://vip.ffzy-play10.com/.../2000k/hls/mixed.m3u8
```

⇒ **这批源上净化收益为 0，却给 36% 的起播加了 2+ 秒**。这是"秒播长尾"最直接的一块。

### 发现 2：深水位升档基本没生效（这是本轮最重要的发现）

```
I L1Buffer: 缓冲升档 @ 10s：水位 300s / 96MB
I L1Buffer: 缓冲升档 @ 15s：水位 300s / 96MB
I L1Buffer: 缓冲升档 @ 625s：水位 300s / 96MB
I L1Buffer: 缓冲升档 @ 76s：水位 300s / 96MB
```
**总共就 4 条。** 而同期：

| 指标 | 数值 |
|---|---|
| 起播次数 | 15 |
| 在播 ≥10 秒（具备升档条件） | **6** |
| 实际升档 | **4** |
| 升档失败时的日志 | **没有**（完全无观测） |

**根因（代码可证，结构性偏严）**：

`L1LoadControl.create()` 里：
```java
int bytes = min(DEEP_BYTES[tier], max(MIN_DEEP_BYTES, avail / 3));   // ← 用「创建时」的可用堆
```
升档守门时：
```java
if (availBytes() >= (long) deepBytes * AVAIL_FACTOR) { escalated = true; }  // ← 用「运行时」的可用堆比
```
`deepBytes` 取自**播放器构造那一刻**的可用堆 ÷3，而守门发生在**播了 10 秒之后** —— 这时候播放器已经吃了一大块内存，**运行时可用堆必然低于创建时**，于是 `avail >= deepBytes×3` **结构上就很难成立**。设备当时 `heap=256MB`（`DeviceProfile: buffer=aggressive`），堆越紧越明显。

⇒ 你要的"10 秒后加深"，机制在，**但门槛定得自相矛盾**。修它不需要任何额外流量、不碰风控 —— **这才是最该先做的一步**。

> 证据强度说明：15 次会话样本小，"6 次够条件只成功 4 次"是**指示性**的；但"守门公式结构偏严"是**代码可证**的。所以下一步不是拍脑袋改数值，而是**先把失败原因打进日志**，用数据定新门槛。

## 四、风控：把"会不会被限速"拆成能判断的五维

源站/CDN 判定"异常客户端"，实际能用的抓手就这几条。**逐条对照三种形态**：

| 风控维度 | 正常播放 | **A：落盘缓存** | **E：多线程尽速预取** | **E′：单线程跟随预取** |
|---|---|---|---|---|
| 并发连接数 | 1~2 | **不变** | 3~5 ⚠ | 2 |
| 分片请求速率 | ~0.17 次/秒（6s 一片） | **不变** | 2~5 次/秒（×10 以上）⚠⚠ | ~0.35 次/秒 |
| 请求顺序特征 | 严格顺序 | **不变** | 并行乱序，与播放器行为明显不同 ⚠ | 严格顺序 |
| 单位时间流量 | ≈1× 码率 | **不变** | 数倍码率 | ~1.5× 码率 |
| 命中缓存时 | — | **请求更少** ✅ | — | — |

**结论**：

- **A 在五个维度上全部不增加**。`CacheDataSource` 是"播放器本来就要发的那个请求，顺便把响应写一份到盘"，**请求次数、并发数、顺序、字节数一个都没变**；命中缓存时反而**少发请求**。所以 **A 不是"多线程加载"，它是"顺便留个副本"** —— 这是本轮唯一零风控的方案。
- **E 的多线程形态在四个维度上同时异常**，这才是你担心的那种"被限速、被拒播"的模样。**不要做。**
- 好消息：**你想要的"提前加载后面的时长"，不需要多线程**。HLS 的正确做法是**单线程、顺序、按播放速率小幅领先**地往下追 —— 效果一样（甚至更稳），而风控增量降到"并发 1→2、速率 ×1.5、顺序特征不变"。

> 补充一句物理事实，避免方案落空：**"拖到某处不卡"的前提是那个位置的数据已经在本地**。没看过的位置，A 和 E 都救不了第一次，只能当场下载。所以缓存类方案的真实价值是**"覆盖你已经到过的范围"**，而不是"全片随便拖"。

## 五、方案 A 定稿：启用 Exo 磁盘缓存

**做什么**：把 `ExoMediaPlayer:109` 的 `isCache` 由硬编码 `false` 改为可配置；接上现有 `SimpleCache`（`ExoMediaSourceHelper` 里代码齐备、且 helper 是**单例**、`mCache` 是实例字段 —— 基础设施天然可用）。

### ⚠ 先决条件（不满足会出严重 bug，必须先做）

**本机地址必须排除在缓存之外**（`127.0.0.1`：本地 HLS 端点 `/l1.m3u8`、去 BOM 端点、网盘 `/proxy`）。

原因不是省空间，是**会播错内容**：本地端点 URL 对每一集**都是同一个固定地址**。Exo 的缓存 key 默认取 URI，一旦开了缓存，**换集后播放器会直接命中上一集的残留清单**。历史上已经有"净化残留"的教训（`startPlayUrl` 里专门作废上一集的净化内容），这条路不能再踩一次。

实现：`getCacheDataSourceFactory()` 外层判一次 host —— 本机地址**不套** `CacheDataSource`，直接走上游。

### 开关与默认值

| 项 | 建议 | 理由 |
|---|---|---|
| **默认值** | **默认开** | 五维风控零增量；`FLAG_IGNORE_CACHE_ON_ERROR` 保证缓存出问题自动回退直连，**不影响播放成功率** |
| 目录大小 | **256MB**（可调，可设 0 = 关） | 512MB 对盒子偏大 |
| 设置页 | 新增"磁盘缓存"开关 + 容量档位 | 与你"能看见、能关掉"的习惯一致 |
| 埋点 | **必须**：缓存命中字节 / 忽略字节 / 上游字节 | 见下 |

### 收益要说实话

| 场景 | 收益 |
|---|---|
| 同一集内拖回已播位置 | **增量有限** —— 内存水位已经覆盖（见发现 2：修好后是 300 秒级） |
| 跨会话重看同一集 | **可能很好，也可能几乎为零** —— HLS 分片 URL 常带 token/时间戳，**跨会话 key 变了就命中不了** |
| 内存装不下的远距离回拖 | **真正的新增价值** |

⇒ 所以 **A 的开关不是重点，埋点才是**。命中率这件事只能真机测出来，不能靠推断。**先开+埋点，用一周数据决定去留。**

## 六、方案 E′ 定稿：跟随式预取（不是"多线程下载"）

**正名**：HLS 播放器拉片本身是"按需、顺序、同一连接"。传统"多线程下载"多见于直链 mp4。对 m3u8，正确说法是**分片预取**，正确的形态是**单线程顺序追播**。

**做什么**：

```
触发：播放位置 ≥10s（复用现有闸门）+ 开关开 + Wi-Fi
目标：让「已下载内容」始终领先播放点 W 秒（W 默认 300s，即 5 分钟）
方式：解析当前 m3u8 → 顺序取后续分片 → 经 Exo 官方 CacheWriter 写入同一个 SimpleCache
并发：1（绝不并发）
限速：「预取速率 ≤ 播放速率 × 1.5」，超前太多就 sleep 等待
闸门：播放器缓冲掉到 60s 以下 → 立刻暂停预取，回上来再继续
取消：换集 / 退出 / 出错 → 立即取消（代次作废）
```

**为什么单线程顺序**：并发只 1→2、速率只 ×1.5、**顺序特征与正常播放完全一致** ⇒ 行为识别类风控抓不到，风控增量最小。

**必须用 `CacheWriter`**：不能自己拼字节写进 `SimpleCache`，否则会出现"写了一半就可见"的**残片**，播放器读到坏数据。这是硬要求。

**技术风险（要盯的）**：预取侧与播放侧的**分片 URL 必须完全一致**，否则 `SimpleCache` 的 key 对不上，预取变白工。缓解：埋点同时打"预取写入字节"和"播放命中字节"，两者对不上立刻能发现。

### 熔断（你担心的风控，靠它兜）

| 监测项 | 触发条件 | 动作 |
|---|---|---|
| 播放段 HTTP 状态码 | 出现 403 / 429 / 451 | **立即停预取 + 本次会话不再开** |
| 分片下载耗时 | 比预取开启前劣化 >50% | 同上 |
| 重缓冲次数 | 本次会话 ≥2 次 | 同上 |

**意义**：把"会不会被限速"从**猜**变成**自愈**。就算我判断错了，它自己会退回去 —— 而不是一路恶化到不能播。这符合你"要机制性兜底、不要单机实测通过"的要求。

## 七、明确不做的

| 想法 | 为什么不做 |
|---|---|
| 多线程尽速预取 | 五维里四维异常，风控高危（第四节） |
