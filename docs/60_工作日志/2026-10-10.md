## 🎯 最终判定：HTTP 403 的响应体被写进 csp.jar（13:12 观测版复现）

### 决定性日志
```
13:12:15.513  JAR写入[A:ApiConfig] 开始 并发=1 原大小=1855517   ← 原文件是 1.85MB 合法 jar
13:12:16.913  JAR写入[A:ApiConfig] 开始 并发=2 原大小=0          ← ★ 并发（第一次已删文件）
13:12:16.914  JAR写入[A:ApiConfig] 结束 大小=9 头=Forbidde 判定=非法(未知头)
13:12:18.161  JAR写入[A:ApiConfig] 结束 大小=9 头=Forbidde 判定=非法(未知头)
（13:13:01 / 13:13:18 / 13:13:19 同样各写一次 9 字节 Forbidden）
```
**`大小=9 / 头=Forbidde` = HTTP 403 的响应文本 "Forbidden"。**
成功时是 `1859860 字节 / 头=PK\x03\x04 / 合法ZIP`。

### 因果链
换源 ⇒ jar 地址变 ⇒ `ApiConfig.downloadJar` 用 `User-Agent: okhttp/3.15`（`ApiConfig:145`）请求
⇒ 服务器 **403** ⇒ `convertResponse` **原来是无条件** `delete()+new FileOutputStream+write(body)`（不看状态码、不校验内容）
⇒ `csp.jar` 从 1,855,517 B 的可用 jar **变成 9 B 的 "Forbidden"**
⇒ 之后每次 `JarLoader.loadClassLoader` 都失败（`Expected valid zip or dex file`）
⇒ `loadJar` 失败出口 ②(`fMatched && !fLoaded`) → `callback.error("")`
⇒ `HomeFragment` 的 `mSilentReload` 分支 → Toast「线路切换失败,请重试」+ **return 不加载首页**。

### 两个并存缺陷（都实锤）
| # | 缺陷 | 证据 | 性质 |
|---|---|---|---|
| ① | `downloadJar` 不看状态码/不校验内容，**任意响应体都写进 jar 缓存** | `大小=9 头=Forbidde` | **主因**：一次 403 摧毁 1.8MB 可用 jar |
| ② | 同一 `csp.jar` 被**两次下载并发**写、无互斥 | `并发=2`（13:12:16.913） | 加剧（`loadedJarKeys` 只在装载成功后才写 ⇒ 二次也认为"需下载"） |

### 与「我前面改动」的关系（如实）
- **`downloadJar` 的逻辑我从未改过**（本次只在其中加 3 行观测）
- 并发下载也是**原有缺陷**
- ⭐ **为什么现在"频繁"**：db 之前换源失败**保留旧池** ⇒ 首页仍能用缓存/旧池渲染 ⇒ **jar 已被 403 摧毁但用户看不出来**；
  db 之后失败**清池 + 明确空态** ⇒ 同一个老 bug 的后果第一次被摆上台面。**与上一轮"成功率变低＝失败从隐形变可见"同理。**
- ⛔ 换源失败清池的口径**保持不变**（那是用户明确要的）；要修的是"403 摧毁可用 jar"本身。

### 修复方案（**待用户确认，本轮未动手**）
- **A（治本）**：`convertResponse` 改为"**先读进内存 → 校验头是否 zip/dex → 才删旧文件 → 才写**"；
  校验不过就 `throw IOException` ⇒ OkGo 走 `onError` ⇒ **现有兜底**（`cache.exists() && length>0` ⇒ 用旧 jar 加载 + 提示"网络不佳，已使用缓存数据源"）
  ⇒ **旧 jar 不再被摧毁，用户看到的是"已使用缓存数据源"而不是「线路切换失败」+ 首页不加载**。
- **B（加剧项）**：同一 jar 的下载串行化 + 双重检查（第二次进来会命中复用）。
- **C（可观测）**：记录 jar URL + HTTP 状态码（现在无法追"哪个源 403"）。
- ⛔ **不做**：改 User-Agent 去绕 403（属绕过访问控制）。

## 🛠️ dg 版修复出包（13:18~13:26）—— 403 不再摧毁可用 jar

### 改动（1 个文件 · `api/ApiConfig.java` · 批次 `dg`）
| 项 | 内容 |
|---|---|
| ① **内容校验** | `downloadJar` 的 `convertResponse` 改为**先把 body 读进内存 → 判头是否 zip(`PK`)/dex(`dex`) → 才删旧文件 → 才写**；非法则 `throw new IOException("jar 内容非法（HTTP …）")` |
| ② **同文件互斥** | 新增 `JAR_DOWNLOADING`（`ConcurrentHashMap.newKeySet()`）；入口 `if (!JAR_DOWNLOADING.add(fileName))` ⇒ 已有下载在途时**不发起第二个请求**，改为 `postDelayed(1500ms)` 延后重跑（届时先复检 `loadedJarKeys` 直接复用） |
| ③ **可观测** | 新增 `L1Sub: jar 下载 <url> → HTTP <code> 长度=<n> 判定=<合法/非法>`（终于能追是哪个源在 403） |
| ④ 标记清理 | 把最终回调包一层 `fin`：任何终态（成功/失败/无响应体）都先 `JAR_DOWNLOADING.remove(fileName)`，避免标记泄漏导致永久延后 |

**为什么抛异常是"修好"而不是"更糟"**：`downloadJar.onError` 本来就有兜底
（`cache.exists() && length>0` ⇒ `loadJarFileAsync(cache, ..., "网络不佳，已使用缓存数据源")`）
