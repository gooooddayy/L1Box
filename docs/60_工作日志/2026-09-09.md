# 2026-09-09 L1Box 闪退真因终局（m 版）

## 取证突破（crash_full3 全缓冲区日志）
- l 版三层拦截在该机全失效：fakeboot.dex 被拒（Attempt to load writable dex file，W^X）、SecurityManager 被禁（Android 14 setSecurityManager 抛异常）、JarToast 零命中。
- **"闪退后连杀两次"真凶是自己**：BaseActivity 检查 isNormalStart=false（只有 SplashActivity 置 true）时调 AppUtils.relaunchApp(true) = 拉起启动页+killProcess 自身。系统把崩溃应用直接重启到 MainActivity（跳过 Splash）→ 触发自杀重启。k 时代全部 "Sending signal SIG:9" 都是它，不是 jar 的 killProcess！
- 搜索中真正死亡进程无任何信号日志 = 静默 System.exit，来自加固 jar 加密内层 payload（外层 dex 用 python 验证零 exit 调用，静态补丁够不着）。
- 死亡前特征：SpiderLog 连接 127.0.0.1:9050~9054/9391/9392 全 ECONNREFUSED（加固"本地代理"从未起来）15 秒后自杀；wexguard so（libwexproxy/libdecjni）在 pool 线程执行。

## 残余闪退根因 = W^X（targetSdk）
- jun 变体 targetSdk=28 稳定，我们 targetSdk=30 → Android 10+ 对 >=29 禁止可写目录 dex 加载，加固 jar 内层解密 dex 偶发加载失败 → 自检失败自杀。官方/jun 均 28。
- 频次下降复盘：e 版后台线程安全网（第一次大降）、k 版官方签名（第二次大降）、残余=W^X 偶发。

## m 版修复（20260908m）
1. targetSdk 30→28（主修复，侧载分发无上架限制）
2. App.onCreate 设 isNormalStart=true（根除自杀重启链）
3. 新增 JarKillNeutralizer：重写 jar zip 内 dex 的 method_ids（System.exit/Runtime.exit/halt/Process.killProcess/sendSignal 的 name_idx 改指类描述符字符串→调用抛可捕获 NoSuchMethodError），重算 SHA-1/Adler32；JarLoader/JsLoader 统一入口调用 + jar setReadOnly（W^X 卫生）+ 下载前 cache.delete()
4. JarToastBlockLoader：fakeboot.dex setReadOnly + loadClass 自检日志
- dex 解析要点：string_ids_size@56/off@60, type_ids@64/68, method_ids@88/92；method_id_item 8B=class_idx u16+proto u16+name_idx u32；string_data uleb128 前缀。

## 弹窗双保险（20260908n，用户反馈 m 版闪退大幅降低=targetSdk 修复命中）
- 弹窗仍存根因：ProtectedInitJar/DexNative.getLoader/startGoProxy 直接传 App.getInstance()，加固 jar 用 context.getClassLoader() 建内层加载器 → 绕过外层拦截链。
- 修复①JarContextBridge(ContextWrapper)：getClassLoader 返回 JarToastBlockLoader 包装；JarLoader Init.init、ProtectedInitJar bindContext/bindDexLoader/invokeStartGoProxy 全部改传桥接 Context → 内层 payload 的 Toast/Process 也走拦截链。
- 修复②ToastSweeper 兜底：jar 可经原生 JNI 弹真 Toast 无法源头拦，在显示层扫 WindowManagerGlobal.mViews/mParams（主线程 80ms 轮询，反射失败自动停用），type==TYPE_TOAST 且文本不在宿主白名单（~60 条前缀）→ removeView(v,true)。宿主新加 Toast 须同步维护 HOST_TEXTS。
- m 版验证：用户实测闪退大幅降低。n 版已装机。

## n 版回归修复（20260908o，14:42 装机）
- 回归根因（日志铁证）：ClassCastException: JarContextBridge cannot be cast to android.app.Application —— spider jar 的 Init.init(Context) 内部把传入 Context 强转 Application，n 版的 ContextWrapper 桥接不是 Application → jar 加载失败 → 订阅解析不出来。

- 教训：给加固/任意 jar 传 Context 包装类，必须同时满足「类型兼容（含 Application 强转）」与「行为代理」，不是简单 ContextWrapper 就行。

## 弹窗真身终局钉死 + 方案A落地（20260909r）
- **真身 100% 确认**（非猜测，代码链路+日志双向印证）：那个顶部黑色横幅"正在初始化本地代理"+进度条，及下方"本接口免费分享！切勿上当！"，是第三方源 jar 的 `startGoProxy(Context)` 方法经 `WindowManager.addView` 塞进宿主界面的**内嵌 View，非系统 Toast**。证据：①logcat 全程零文案（17:33 才开记，17:30 弹窗已过）②uiautomator 树抓不到 ③只在"开软件首次加载源"出现（Go 代理二进制首次启动的一次性初始化）④ToastSweeper 只扫 WindowManagerGlobal 里 type==TYPE_TOAST 窗口，原理性扫不到这种 addView 内嵌 View。
- 关键链路：`ProtectedInitJar.invokeStartGoProxy` 反射调 jar `startGoProxy(Context)`，传的是 `JarContextBridge`（extends Application）。jar 内部把 ctx 当普通 Context 用 `ctx.getSystemService(WINDOW_SERVICE)` 拿 WindowManager 再 addView 横幅。而 `sp.init(App.getInstance(),ext)`（JarLoader 第193行）传真实 App 但横幅文案是"本地代理/Go代理"专属 startGoProxy，与 sp.init 无关。
- **方案A（用户选定）**：JarContextBridge 重写 getSystemService，对 WINDOW_SERVICE 返回空操作 WindowManager（addView/removeView/updateViewLayout 全 no-op）→ 横幅无处可挂不显示；Go 代理后台逻辑只依赖 filesDir/cacheDir/网络，全委托真实 Context，零影响。符合"不禁止只隐藏"。
- 编译坑：空操作 WindowManager 匿名类需 import android.view.ViewGroup（首次构建失败根因"程序包ViewGroup不存在"）。
- 产物 L1Box_v1.1.1_release_20260909r.apk（已构建成功、签名三方案 OK、dex 含 JarContextBridge 新代码确认进包），q 版归档。设备 USB 掉线未自动安装，待用户手动装或重连。
