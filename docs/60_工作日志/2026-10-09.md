### 根因（四环，全部有行号证据）
1. `SubscriptionActivity.kt:468-484 onPause()` 只 `saveApiUrl(新地址)` ⇒ **持久化身份换了，内存池没动**
   （`openEditDialog` 197-220 已把多仓 `lines/activeLineUrl` 作废 —— **多仓那一层修过，池这一层没修**）
2. `ApiConfig` **清池只写在一处**：空地址分支 `236-250`。该处注释自证：
   「之前只回调 error，内存里仍留着上一个源的数据，搜索/播放照常能用，重启才恢复空源」
   ⇒ **同一 bug 的另一种表现早就被修过，只修了"地址变空"，漏了"换成另一个源"**。
   两个失败出口（`384-413` 网络重试用尽 / `370-381` 内容不是配置）**都不清池**；
   且 `parseJson` 的 `toJson==null` 抛异常在 `clear()`（778 行）**之前** ⇒ 内容坏时池原样保留。
3. `HomeFragment.kt:796-803` 与 `527-543` 两个 error 分支**主动选择沿用旧池**，注释原文
   「切换失败也用**当前站点池**重拉一次」「仍用**已有站点池**/内置源渲染」。
   ⇒ **"失败不清池"本身是断网容错（好特性）**，问题在于**没区分「网络抖动」与「用户主动换源」**。
4. 后续全部按池走：首页候选 `451-459`、搜索 `FastSearchActivity.kt:2040`、播放解析 `getSource(key)`
   —— 而**缓存标签与搜索勾选按 Hawk 地址**（`HomeFragment.kt:292`、`SearchHelper.java:18-26`）

### 先回答用户提问：「几秒无池窗口」是什么情况
那是**方案 B（改地址即清池）**的产物，不是现有行为：
- 正常：0.3~2s（一次 HTTP 往返）
- 弱网：`ApiConfig.java:388-398` 重试间隔 **1.5s + 3s** ⇒ **4.5s+ 三次请求耗时** ⇒ 6~10s
- ⚠️ 要害：它**恰好把旧池清在最需要旧池的时刻**（新源拉不通时旧池已没了）⇒ **拆掉断网容错**
⇒ **结论：不采用 B**；`poolUrl` 判据取代它，且**零无池窗口**。

### 设计核心：三条不变量
> **`勾选的订阅` == `HawkConfig.API_URL` == `poolUrl`（池归属）**

新增 **1 个**概念 `poolUrl`（`parseJsonInternal` 成功即写；清池即置空）。它同时是 **真相标签**与**回退目标**
（回退到 `poolUrl` 是唯一"回退了一定有数据"的选择 ⇒ 比另存 `LAST_GOOD_URL` 更可靠、更精简；
也绕开了 `API_URL_BACKUP` 是"同值镜像"这个障碍）。

**4 态**：S0 一致 / S1 加载中 / **S2 换源失败但旧源可用（病灶，现在与 S0 无法区分）** / S3 无源可用。

**失败判定只需一条**：`本次地址 == poolUrl`？
- 相等（没换源，纯网络）⇒ **保持现状**（断网容错一行不改）
- 不等（用户换源/切线路失败）⇒ **回退**：三者一起回到 `poolUrl` + **常驻提示条**告知 + 「重试源 B」「就用源 A」

⭐ 为什么叫"完美一点"：**不逐条修下游 5 条混乱，而是让矛盾态不存在** ⇒ 缓存标签/搜索勾选/首页地址比对/收藏 key 全部自动正确，
以后新增"读地址"的功能也天然正确。

首次配置无回退对象（唯一必须断档）/ 旧源已被删则**清池不清退**（用已删的源更糟）/ 多仓切线路走同一条路（天然覆盖）/

### 根因（一条）
**SUB_FAIL 是"只由定时任务驱动"的状态，而排任务只写在「取消」这一个出口。**

| 路径 | 是否排节拍 |
|---|---|
| `enterSubFail()` 首次 → `reloadSubNow()` | ✗（靠回调） |
| `reloadSubNow().error()` → `showSubFailDialog()` | **✗** |
| 对话框「重试」(`left()`) → `reloadSubNow()` | **✗** |
| 对话框「取消」(`right()`) → `exitSubFailToEmpty()` | **★ 唯一**

⇒ 只要用户没点「取消」（点重试 / 直接返回 / 忽略对话框），节拍永不启动，
池恢复后搜索页无人接 ⇒ **永久加载中**。`onSubFailTick` 在"继续等"分支不打日志，所以线上完全看不出它有没有在跑。

**加重因素**：`subReloadTried` 在 **companion object（静态，L219）**，而 `subFailDialog` 是实例变量（L240）
⇒ 静态护栏跨实例保留 = "每**进程**最多自动重拉 1 次"（非"每启动"）
⇒ 用户"D2 失败 → 返回 → 再进搜索页"时，新实例**连自动重拉都不做**，直接弹框且不排节拍
⇒ 更容易落进死态（这正是 D3 的触发序列）。
