### 改动（ah 版）
- **A1** `ProtectedInitJar.init()` 全过程持 **进程级锁 `NATIVE_INIT_LOCK`**（含 `bindDexLoader`）。

- **A3** 启动失败 → 返回 false → 上层拒载该 jar 的站点。**旧版 `catch(Throwable ignored)` 吞异常 = 看着能用、一请求就 abort**（改名为 `startGoProxyOnce`，旧名加反向断言）。

### 铁律新增
- **native abort 是进程级死亡不是异常，`catch(Throwable)` 拿不到控制权 → 防线只能是「事前串行 + 事前门禁」，绝不能改成 try-catch 兜。**

### 二、首轮慢的真实机制（三层叠加）
`DexClassLoader` 创建数（`Configuring clns-N`）按分钟：
| 时间 | 场景 | clns 数 |
|---|---|---|
| 16:37~16:40 | 启动 + 首页（take 3） | 8（零星） |

三个叠加因子：
1. **`jarLoadPool` 单线程** -> N 个未加载 jar 串行排队，每个都要「解压 dex -> DexClassLoader -> 绑定原生 loader -> Go 代理 exec（~550ms）-> 健康检查」。
2. **`NATIVE_INIT_LOCK` 全局串行**（ah 加的防崩锁）-> 这个"税"是**买不崩的代价**，不能为提速去掉。
3. 后续轮**全命中缓存**：ClassLoader 缓存 + spider 实例 + `GO_PROXY_STARTED` 幂等 + HTTP 连接池 + DNS。
-> 首轮 = 把所有站点"开机"一遍；后续 = 直接发请求。**每进程只交一次**（除非进程重启）。

### 三、新发现真问题（P1）：JarKillNeutralizer 让被中和的 jar 彻底不可加载
日志原文（决定性）：
```
JarKillNeutralizer: 已中和 jar 自杀调用 d41d8cd98f00b204e9800998ecf8427e.jar   (16:42:07.093)
java.io.IOException: Failed to open dex files from .../d41d8cd98f00b204e9800998ecf8427e.jar
because: Failure to verify dex file: Invalid method name: 'Landroid/os/Process;'   (16:42:07.121 起 5 次)
```

- **机制**：`patchDex` 把 `killProcess/exit/halt/sendSignal` 的 **name_idx 改指到类描述符字符串** `Landroid/os/Process;`。
  注释称「该字符串不是合法方法名，调用时抛 NoSuchMethodError」——**但 ART 的 dex verifier 在「加载时」就校验方法名合法性**，
  直接判 `Invalid method name` -> **整个 dex 被拒** -> ClassNotFoundException -> **该 jar 的站点永久不可用**（不是"可用但被拦"）。
- **持久污染**：改坏的文件**就地写回磁盘**且第二次 patch 幂等（name 已变成 `Landroid/os/Process;` 不再匹配 `isKillName`）

- **代价**：涉事站点不可用；每次搜索重试（16:42:07 连续 5 次、间隔 200ms）。
- **好消息**：不崩（防自杀的原目标达成），属"防御过度"而非防御失效。
- **待定修法**（未执行，等用户拍板）：name_idx 改指**合法方法名**（如字符串表里已存在的 `toString`/`hashCode`）
  -> verifier 通过，运行时抛 NoSuchMethodError（或调用无害方法）。改动仅 `patchDex` 内一处 + 需在 string_ids 中定位替身名。
  另需处理**已被改坏的存量 jar**（删文件重新下载 or 按新逻辑重写）。
