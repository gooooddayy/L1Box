### 对象先分清（以前没明确）

### ① cj 不影响 ✅
7 个新方法全是 `tier == LOW ? 低档 : 原值` —— **中档和高档走同一分支，取的就是改造前的写死值**。
⚠️ **唯一例外**：`App.java` 两处 `markMemoryPressure()`（`onTrimMemory>=RUNNING_LOW`、`onLowMemory`）
会把 tier **只降不升**地永久打到低档 ⇒ `siteTabBatch` 8→4（每次读都取当前值，立刻生效）、
`itemViewCacheSize` 6→3（只在 initView 读一次，已建列表不受影响）。
⇒ 只会让**左栏 chip 建得慢**，不会让右栏变慢。查日志 `MemoryGuard`/`onLowMemory` 即可排除。

### ② 左栏"快滑卡住"＝ fling 撞界后守卫误判（代码链确证）
确证事实（`DslTabLayout.kt`）：
- **needScroll = maxScrollY>0**（L1586-98，`tabEnableSelectorMode` 默认 false，布局也没开）
  ⇒ **chip 总高没超栏高时，`onTouchEvent` 走 super、完全不吃手势** = 拖不动。
- **fling 边界与实际钳制差一个视高**：`onFlingChange` 竖向传 `startFling(-v, 0, maxHeight)`（内容总高，L1666），
  而 `scrollTo` 钳在 `maxScrollY = maxHeight - measuredHeight`（L1766）⇒ OverScroller 以为还能再滚一整屏。
- **越界中止只看 currX**（`computeScroll` L1777）⇒ 竖向 fling **永不提前 abort**，撞界后继续空转。
- **停手窗口计时源会冻结**：`siteTabsLastScrollMs` 靠 `setOnScrollChangeListener`（L266-268）更新，
  而该回调**只在 scrollX/Y 数值真变时触发** ⇒ 撞界后 `scrollTo` 被钳成同值 ⇒ 回调停 ⇒ 400ms 后
  `siteTabsBusy()` 变 false ⇒ **`addView` 落进"视觉静止但惯性仍在跑"的窗口**。
⇒ 慢滑无 fling，窗口判对；快滑造出"守卫以为已停手、实际未停"的重叠区。

### ③ 右栏"松手顿挫"＝ 收尾三件重活撞在 IDLE 同帧
- IDLE 分支（L291-299）同帧连做：`cancelOutOfWindowImages()` + `scheduleVisibleImageAudit()` + `prefetchAroundVisible()`
- `prefetchAroundVisible()`（L1304-1332）是**同步 for 循环**：每个 URL 一次 `Picasso…fetch()`（预算 200），
  末尾一次 **`System.out.println`（同步写 logcat）** ⇒ IDLE 帧尖峰
- `onScrolled` **空实现**（L302-307，"滑动中不取消任何下载"）⇒ fling 期间图片全速跑，
  **解码队列在 fling 结束时正好是积压峰值**，撞上上面的尖峰
- ⚠️ 待验证：布局给两个网格都开了 `tv_selectedItemIsCentered="true"`（L162/L173），
  该库源码不可读，**无法静态确认它在触摸路径是否生效**（若在滚动停止时做居中校正，就会额外一次 smoothScroll）

### 共同点
②③ 都发生在**"手势刚结束"那一刻**，本质是**"后台本该错开的工作撞上了用户停手"** ——
不是列表本身慢。

### 判错又自我纠正的两次（教训）
1. 先怀疑 `restoreScroll()` 在竖向每次 onLayout 归零 scrollY ⇒ **错**：

   且 `restoreScroll()` 只在 `onSizeChanged`(L1203) 与**横向** `layoutHorizontal`(L1296) 调用，

2. 又怀疑 `_childAllWidthSum` 在竖向用宽度累加是 bug ⇒ **错**：该变量名在竖向分支被复用为

## 🎯 目标对齐 + 断触原因分析（14:0x · **本轮不动代码**）

| cl 改了什么 | 解决的问题 | 是主诉吗 |

### 一、目标（待用户确认）
**共同本质：用户的手势与滚动，不应被 App 自己的逻辑打断或干扰。**
- **左栏**：任何速度都不**断触**（快滑/慢滑/连滑）；松手后惯性自然减速；只在顶/底停。
  **明确不是目标**：滑动中要加载站点。

### 二、左栏断触 —— 原因候选
**已排除**：~~插入 chip 触发 CANCEL~~ —— cl 版放开追加后**实测无改善** ⇒ 追加本身不会断触
（与 Android 语义一致：追加不移除不移动已有子 View）。
**⭐⭐ A. `needScroll` 的 false→true 一次性翻转**：翻转点在 **chip 17→18**（三轮复现）。
翻转前后 `onInterceptTouchEvent`/`onTouchEvent` **处理路径整体切换**（super ↔ gestureDetector），
拦截开始时会给子 View 发 **ACTION_CANCEL**，且接管后的滚动基准从翻转那刻起算。
**每次新搜索 chip 都从 0 涨到 40 ⇒ 必然翻一次** ⇒ 符合"快速滑动才断"（慢滑时 chip 早建完、翻转已过）。
**⭐⭐⭐ B. `removeAllViews()`（清空重建）**：**确定会 CANCEL**，但只在重搜时触发 ⇒ 待分辨。
**⭐ C. 其余**：`setCurrentItem(0,true,false)`（重建时）、`requestDisallowInterceptTouchEvent` 的手势空窗期。

### 三、右栏顿挫 —— **控件本身已查干净**
- `TvRecyclerView` **未重写** `fling`/`onTouchEvent`/`onInterceptTouchEvent`/`dispatchTouchEvent` ⇒ 标准 RecyclerView 惯性
- **全项目 0 处 SnapHelper / setOnFlingListener** ⇒ **不存在"按格停"的吸附**
- `TvSmoothScroller` 只服务 `smoothScrollToPosition`（程序化），触摸不经过
- `onScrollStateChanged` 里无额外滚动（仅触底加载更多）；`itemAnimator` 已 null
⇒ 惯性逻辑干净 ⇒ 顿挫只能来自**外部干预**：
**⭐⭐ D. 滑动中每 120ms 插入 12 条**（`notifyItemRangeInserted` 改锚点）—— **不体现在帧耗时上**，
正好解释"帧正常（5~7ms）但体感顿挫"。⚠️ 但 ck 第 2 轮所有 `待落=0` ⇒ 至少不是唯一原因。

**⭐ F. IDLE 时立刻 `scheduleFlush`**（惯性刚停就插数据）。

### 四、缺什么才能定论
**最大障碍：ACTION_CANCEL 在现有埋点里看不到**（现有埋点只测 chip 插入/停稳/最差帧，
而断触是**触摸事件流**的性质）。建议补一组"触摸/滚动取证"埋点（**只观测、不改行为**）：
① `dispatchTouchEvent` 记 DOWN/UP/**CANCEL** 时刻＋是否落在左栏矩形；
② 左栏 `needScroll` **翻转时刻**＋当时触摸状态＋chip 数；
③ 左栏 `onInterceptTouchEvent` 返回 true 的时刻（开始拦截＝发 CANCEL 那一刻）；
④ 右栏 `IDLE→DRAGGING→SETTLING→IDLE` 完整状态迁移时间线；
⑤ 右栏 fling 每帧 `dy` 采样（看滑行位移是否均匀）。⇒ 五条能把两侧都钉死。

## 🔬 cm 取证判定（14:4x）—— **"断触"的真相：不是触摸断了，是"撞界后毫无反馈"**

数据 → `_cm_trace.log`（23.3MB，2 轮搜索，**110 次按下**）
用户澄清关键前提：**「我说的快速滑动，就是上一次滑动的惯性还没结束后就开始下一次滑动」**

### ❌ 先排除三条（都有硬数据）
1. **不是 ACTION_CANCEL**：`★CANCEL = 0`，**DOWN=110 / UP=110 完美配平** ⇒ **系统从未取消任何手势**。
   （附带结论：`★左栏开始拦截` 出现 60 次但**无副作用** —— CANCEL 为 0 说明 **chip 不消费触摸**
   ⇒ `mFirstTouchTarget == null` ⇒ 拦截时无需发 CANCEL。**这60次"接管"不是断触来源。**）
2. **不是插入 chip 造成**（早被 cl 版证伪）。
3. **不是"位移被门槛吞"**：`_touchSlop` 的赋值行**被注释掉**（`//_touchSlop = vc.scaledTouchSlop`）
   ⇒ 阈值恒为 0 ⇒ 只要有位移就滚动。

### ⭐⭐⭐ 真正原因：**85% 的按下发生在"已经滑到边界"的状态**
```
DOWN 总数 110 ｜ 按下时已在【顶部 Y=0】= 34 ｜ 已在【底部 Y=上限】= 60 ｜ 合计 94/110 = 85%
maxScrollY 中位数 = 1937px ≈ 2 屏 ｜ 内容总高 ≈ 4000px ≈ 29 个站点
```
⇒ **左栏可滚范围只有约 2 屏**；快速滑动（实测单帧位移可达数百 px）**2~3 下就撞界**；
撞界之后无论怎么滑内容都不动 ⇒ 用户感受＝**「手在动、内容死住」＝ 断触**。
⇒ 且 `DslTabLayout` 是自定义 ViewGroup，**没有 EdgeEffect／回弹／发光等任何边界反馈**
（标准 RecyclerView 撞界会有边缘光效，用户一看就知道"到头了"）⇒ 只能理解成"触摸坏了"。
⇒ 与用户描述吻合："**快速**才断触"（快滑易撞界）、"慢滑好些"、"与加载无关"。

### 右栏：**惯性本身是好的，是被"按下"中断的**
19 趟 `右栏滑行` 的**尾6帧大多不收敛**（末尾仍有 80~160px/帧）⇒ 高速下被切断；
但**存在自然减速样本**（`尾6帧=[17,18,16,16,17,9]`）⇒ 惯性逻辑正常。
状态迁移显示**惯性阶段普遍只持续 60~250ms 就被"拖动"取代** ⇒ 正是用户的"惯性未结束就接下一次"。
⚠️ **按下即停惯性是 Android 标准行为**（RecyclerView 同样）⇒ "惯性被中断"本身**不是 bug**；
若用户要的是"连续滑动时惯性叠加"，那是**超标准语义**，需单独确认。
次要观察：`突变` 0~18 次/趟（相邻帧位移差>40px），`待落` 全程 0 ⇒ 与插入无关，疑为图片解码抢占，
**列次要项**。

### 🔍 根因（cm 取证量化后的结论）
`DslTabLayout` 里「能否滚动」**完全押在 detector 的返回值上**：
```kotlin
intercept = super.onInterceptTouchEvent(ev) || _gestureDetector.onTouchEvent(ev)
```
两个结构性缺陷：
1. **漏喂 DOWN 即断链** —— `needScroll=false`（chip<18）期间**不喂 detector** ⇒ detector 缺
   `mCurrentDownEvent`/`mDownFocusX,Y` 基准 ⇒ `onScroll` 永不触发 ⇒ `intercept` 恒 false
   ⇒ 事件让给 chip ⇒ **滚动彻底不发生**。
2. **`||` 短路** —— `super` 返回 true 时 detector **根本不被调用**。

### 🔧 改法（两项，均**只在 detector 未处理时生效** ⇒ 正常路径逐字不变）
- **① 无条件喂 detector**：调用提前到最前（`val detectorHandled = if (isEnabled) _gestureDetector.onTouchEvent(ev) else false`）
  ⇒ 消除漏喂窗口 + 消除短路。安全性：`needScroll=false` 时 `onScrollChange` 自身 return false。
- **② 原始位移兜底**：拦截阶段 `l1MovedEnough`（超 `scaledTouchSlop`）直接接管；
  处理阶段 `!handled && ACTION_MOVE` ⇒ `l1FallbackScroll` 自己 `scrollBy`。
- **配套**：`onFling` 加 `if (!needScroll) return true`（无条件喂后必须显式守卫）。
- **易错点（写进代码注释了）**：兜底自滚**必须限定 ACTION_MOVE** —— UP/CANCEL 帧 detector 本就不产生
  onScroll，若在此兜底会把「抬起点与最后 MOVE 的差值」多滚一次、破坏正常路径。

### 📡 埋点全保留（ck 3 + cm 5 + **cn 2**）
cn 两条**只在 detector 漏网时才打印**，是判读钥匙：
- `[tp] ★★兜底接管（detector 未接管）`
- `[tp] ★★兜底滚动生效（detector 未处理）位移=`
**判读**：这两条频繁出现 ⇒ detector 路径确在失效，兜底救回；从未出现但断触好了 ⇒
是「无条件喂 detector（补 DOWN 基准）」起的作用；从未出现且没好 ⇒ 推断被推翻，需重新取证。

和兜底条件那两条都判"未命中"。改为 `\(` `\)` 后全过。
⇒ **教训：闸门用 grep -E（ERE），断言正则里的 `(` `)` `[` `.` 必须转义；中文/`!`/`&&` 无需转义。**
