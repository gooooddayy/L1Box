# 气泡清理补漏 / 旋转按钮 / 本地播放页 —— 结论与处置（2026-09-18 · bg）

用户复测提出三件事：① 首页与「我的」的长按气泡仍在 ② 手机的旋转按钮 ③ 本地播放页。
逐条给结论，**其中只有第 ① 条是真问题并已修**。

---

## 一、气泡：首页 / 我的 仍在 —— 是真 bug，根因是「清错了层级」

### 根因

上一版（bd 批）清底部导航写的是：

```kotlin
mBinding.bottomNav.post {
    for (i in 0 until mBinding.bottomNav.childCount) {
        Utils.disableTooltip(mBinding.bottomNav.getChildAt(i))   // ← 清的是"菜单容器"
    }
}
```

**`BottomNavigationView` 的直接子 View 只有一个菜单容器**，真正承载「首页 / 我的」的
`NavigationBarItemView` 在它**里面**（孙子层）。所以这一段等于把容器本身的 tooltip 清了，
item 上的 tooltip 原封不动 ⇒ 气泡照旧弹。

### 修法（两件事，缺一不可）

**1）递归整棵子树**——新增 `Utils.disableTooltipDeep(View)`，逐层下探，命中真正带 tooltip 的那层。

**2）长按短路兜底**——在每个**可点击**的 View 上挂 `setOnLongClickListener(v -> true)`。

Android 的 `View.performLongClickInternal` 顺序是：

```
onLongClickListener → showContextMenu → startTooltip（弹气泡）
```

长按回调返回 `true` 就**直接短路**，根本走不到弹气泡那一步。所以这是**机制性兜底**：
无论 Material 之后在什么时机（切 tab、`setChecked`、菜单更新）又给它重设 tooltip，都弹不出来，
不依赖"我们清得够早、时机够准"。这也是为什么 `setTooltipText(null)` 单干不可靠——
它只解决"此刻的值"，解决不了"之后谁再设一次"。

### 为什么只给"可点击的 View"挂长按（重要，别改成无脑递归挂）

- `NavigationBarItemView` 本身 `clickable=true`，是长按回调真正的落点 ⇒ 挂它有效、无副作用
  （它本来就会消费触摸事件，长按也不承担任何业务）。
- 图标 / 文字这类默认 `clickable=false` 的子 View **绝不能挂**：一挂就变成 `longClickable=true`，
  DOWN 事件会被它们消费，父 item 收不到 click ⇒ **点文字切不了 tab**。

### 影响面

底部导航是全工程**唯一**由库自动设 tooltip 的控件：全工程 `setTooltipText` 只有我们自己的
`Utils` 一处（grep 已核），其余 7 处（控制条旋转/投屏、详情页投屏/下载/外部、订阅「更多操作」、
分享二维码）清的都是按钮**自己**，本来就是对的层，无需改动。

### 闸门教训（已顺手补上）

旧断言是 `must "$MA" 'Utils\.disableTooltip\('` —— **只验"调了清工具"，没验"清到了正确层级"**。
所以旧代码形式上是"合规"的，效果却是错的，闸门拦不住。

本轮改成断语义：

| 新断言 | 锁住的语义 |
|---|---|
| `must "$MA" 'Utils\.disableTooltipDeep\('` | 底部导航必须用递归版 |
| `mustnot "$MA" 'bottomNav\.childCount'` | 不许再只遍历直接子级 |
| `must "$UT" 'instanceof ViewGroup'` | 确实会下探子 View |
| `must "$UT" 'setOnLongClickListener'` | 长按短路兜底在 |

> 一句话：**闸门能防"形式回退"，防不了"语义不足"。** 断言写得越像"调用了某个方法"，
> 越容易放过"调了但用错"的写法。

## 二、旋转按钮：不是"没解决"，是 App 层面**没有可动的点**

### 证据（四条，互相独立）

| 证据 | 结果 |
|---|---|
| manifest 权限 | **无** `WRITE_SETTINGS` / `WRITE_SECURE_SETTINGS`（全部权限已逐条列出核对） |
| 全工程写系统设置的代码 | **零**（无 `Settings.System`、无 `accelerometer_rotation` 字符串） |
| 全工程方向调用 | 全部是**固定值**（`LANDSCAPE` / `PORTRAIT` / `REVERSE_*`），**没有一个 `SENSOR_*` 传给 `setRequestedOrientation`** |
| 设备当前实测 | `accelerometer_rotation = 0`（自动旋转**关**）、`user_rotation = 0` |

### 结论

App 对屏幕方向的全部行为 = **只改自己窗口的固定方向**，既不跟随传感器，也不碰系统开关
（没权限、也没代码）。所以"手机自动旋转被打开"**不是本 App 造成的**，App 也无法把它关掉
——那是系统级开关，改它需要 `WRITE_SETTINGS` 且用户显式授权，而我们连这个权限都没申请。

最常见的实际来源是**系统自己的引导**：App 强制横屏时，MIUI / HyperOS 会弹一次
"开启自动旋转"的提示，点了就开了；连接电脑用投屏工具（scrcpy / 妙享等）时也可能被改。

### 需要你知道的一点（唯一实质影响）

**不管系统自动旋转是开还是关，本 App 的表现完全一致**——因为播放页走的是固定方向，
不读系统开关。所以这条对 App 使用没有任何实际影响，不需要处置。
