# 播放解析兼容 —— 方案讨论（2026-09-17）

> 本文只讨论，不动代码。所有"现状"结论都取自当前源码（az = 15:11 出包那版）。

---

## 0. 一句话结论

**这件事有必要，但它不是"把成功率从 83.7% 拉到 95%"的那条路。**
真正卡成功率的是源侧（空返回 / 网盘代理 / 伪地址），那部分"提高解析能力"救不回来；
而"解析能力"能修的是**结构性潜在失败面**（白名单写死、协议补错、外部播放器拿不到请求头），
修完大概率不会变坏，但**很可能一条失败样本都不会少**。

所以我的建议是：**先加埋点测一轮，用数据决定改哪几条**，而不是凭感觉先改。

## 1. 我们现在的链路（事实，带出处）

### 1.1 播放器有哪些

| 编号 | 播放器 | 类型 | 内核 |
|---|---|---|---|
| 0 | 系统播放器 | 内置 | Android MediaPlayer（最弱） |
| 1 | IJK（硬解/软解两档） | 内置 | FFmpeg，格式最全，4K/HDR 弱 |
| 2 | Exo | 内置 | MediaCodec / 系统硬解，流媒体最强 |
| 10 | MX 播放器 | 外部 App | 需已安装 |
| 11 | Reex 播放器 | 外部 App | 需已安装 |
| 12 | Kodi | 外部 App | FFmpeg |
| 13 | 附近 TVBox | 外部设备 | 局域网投送 |
| 14 | VLC | 外部 App | libVLC（格式最全、缓冲好） |

- 短按「播放器」只在内置三档里循环：**Exo → IJK 硬解 → IJK 软解**（`PlayerHelper.getBuiltinItems()`）；
  外部播放器只在**长按菜单**里出现（避免误唤起）。
- 失败后的自动降级阶梯已经存在：`PlayerHelper.buildCompatFallbackPlan()` = **IJK 软解 → Exo**（与当前档相同则跳过），
  每集重置、不重复试同一配置。触发顺序见 `PlayFragment.errReplay()`：
  换地址 → 回退原始直连 → 同址换协议 → 换内核 → 终态提示。

> **这是我们已经比多数 fork 强的地方**：市面主流 TVBox 系只有"用户手动切内核"，
> 没做"失败后自动换内核"。我们做了。

### 1.2 一个地址是怎么被判定的

```
站点返回地址
   │
   ├─ SourceViewModel.getPlay():728
   │     if (isVideoFormat(url) && 站点没配 playerUrl)  → parse=0 直接播
   │     else                                          → parse=1 走解析
   │
   ├─ 直接播：PlayFragment.playUrl() → isPlayableUrl()（必须含 "://"）→ 播放内核
   │
   └─ 走解析：initParse() → doParse()
         · type 0 普通嗅探：WebView 打开页面嗅探，**最长等 20 秒**
         · type 1 json 解析：调第三方接口拿 url
         · parse 接口返回的 json：jsonParse() 拼 header
```

关键事实：

| 环节 | 实现 | 问题 |
|---|---|---|
| 直链判定 | `DefaultConfig.isVideoFormat()` | **写死正则白名单**：只认 `.m3u8/.mp4/.flv/.avi/.mkv/.rm/.wmv/.mpg/.m4a` 加少量平台特征。没命中的直链**一律被推去走解析**（最多白等 20 秒） |
| 协议相对地址 | `PlayFragment.jsonParse():2225` | `//host/x.m3u8` 被**硬补成 `http:`**；https-only 的 CDN 直接失败 |
| 非 http 结果 | `jsonParse():2228` | 非 `http` 开头直接 `return null`（magnet/ed2k 走迅雷通路，另有分支，不受影响） |
| 请求头携带 | `jsonParse():2234-2239` | UA / Referer 值前**多了一个空格**（上游遗留） |
| Exo 分流 | `ExoMediaSourceHelper` | 按 rtsp / rtmp / HLS / DASH / 渐进分流；`inferContentType` 只认 `.mpd/.m3u8`，其余走渐进+提取器（这层没问题，TS 提取参数已调优） |
| IJK 参数 | `IjkMediaPlayer` | 已补 `rw_timeout`（订阅没给时）、`probesize 512K`、`analyzeduration 2s`；**`protocol_whitelist` 里没有 `rtmp/rtmpt`** |
| 外部播放器带 header | MX / Kodi 走 `url\|Header=value&…` 拼接 | **VLC 的 Android Intent API 不支持自定义请求头** ⇒ 需要 Referer/UA 的源用 VLC **必然失败** |

## 2. 所谓"写死"，其实是三层，性质完全不同

### 第一层：App 判定层 —— 写死了，但**我们能改**

就是上面表里的 4 条：直链白名单、`//` 补 http、UA 前导空格、protocol_whitelist 缺 rtmp。
这一层是"我方逻辑"，改动零外部依赖。

### 第二层：内核能力层 —— 写死了，**只能换内核，不能改**

- Exo 靠系统 `MediaCodec` 硬解：老旧盒子/冷门编码会黑屏、闪退，这是驱动兼容问题，改参数救不了。
- IJK 基于 FFmpeg：格式最全、能软解兜住冷门编码，但 4K/HDR 弱、维护慢。
- 系统播放器：最弱，只做兜底。

**这一层的正确用法不是"改"，而是"换"——而我们已经有自动换的阶梯了。**

### 第三层：源侧层 —— 写死了，**谁都改不了**

防盗链（Referer/UA/Cookie 校验）、单 IP 限流、空返回、同一集地址轮换。
av 那一轮 43 次点播 7 次失败，**全部落在这一层**。

## 3. 逐条回答你的问题

### Q1：有必要吗？

**必要，但优先级是中低，且要预期管理。**

判断依据（av 全场景实测 43 次点播 / 10 站点，7 次失败）：

| 失败根因 | 次数 | 靠"提高解析能力"能救吗 |
|---|---|---|
| 源站空返回（Rebo ep1/ep3） | 2 | ✗ 源侧 |
| 网盘源本地代理失败（WexAiYueYue、大师兄 fangcloud） | 2 | △ 部分（见 B3） |
| 站点混入非 http 地址（`Ksvideo-<hex>`） | 3 | ✗ 源侧给了伪地址 |

**这 7 次里，0 次是"地址能播但播放器/解析不认"。**
所以：解析侧改动对当前成功率的**直接影响 ≈ 0**；它修的是"潜在失败面"，不是"已发生的失败"。

### Q2：是不是很多播放器已经写死了？

是，但要分清哪一层（见上面第二节）。**我们能改的只有第一层**，
而这一层恰好是你说的"对多种直链的解析"的落点。

### Q3：改动会不会触动风控？

**分两个口径，答案不同：**

**（a）源站风控** —— 有明确的红线和安全区：

| 动作 | 会不会触风控 |
|---|---|
| 换播放内核（Exo ↔ IJK）、调解码档 | **不会**。请求完全一样，源站看到的是同一个 UA、同一个 Referer、同一串地址 |
| 改地址字符串（补协议、去空格） | **不会**。地址本身不变 |
| **改 UA / Referer** | **会**。aw 轮就踩过：把源站 Referer 写进播放器默认请求头，导致跨域 CDN 的分片请求 **403**，已回滚 |
| 新增预探测请求（HEAD/Range） | **会多一点**。多一次请求就多一次被限流的机会，所以必须**限一次**，绝不放循环里 |
| 重试频率 / 并发 | **会**。这也是我们一直在收紧退避间隔的原因 |

> 你的担心是对的，而且已经有一条红线被验证过了（Referer 那次）。
> 所以原则定为：**只在不改请求的前提下做兼容；任何"多一次请求"的改动都要限次、且要单独拿给你确认。**

**（b）外部播放器（MX/VLC/Kodi）自己的行为** —— 另一个性质的问题：
它们**直连源站**，UA 变成它们自己的，且**不经过我们的代理**。
这等于把地址暴露给第三方 App，对源站呈现的是"另一个客户端"的访问特征。
这就是我一直把外部播放器放在长按菜单、不做默认、不进自动兜底的原因。做可以，但要你知情。

### Q4：有没有其他三方播放器能提高兼容性？

**我们已经有 5 个外部播放器了，不缺。** 市面还有的：

| 候选 | 兼容性定位 | 值不值得加 |
|---|---|---|
| **MPV**（libmpv） | 格式支持 ≈ VLC、缓冲最好（带宽不足时最稳） | **不建议内置**：每 ABI 增加数 MB～十几 MB 包体 + 需要 NDK 构建，且**救不了源侧失败**。真要用走外部 App 路线 |
| **AliPlayer**（阿里云播放器） | 只对阿里云盘场景有增益 | 没必要。我们不主攻网盘源 |
| **KSY**（金山云） | IJK 改造版，闭源 | 没必要，能力与 IJK 重叠 |
| 系统播放器（0 号） | 最弱 | 已内置，仅兜底 |

**结论：不加新内核。** 该做的是把现有 5 个外部播放器的通路修顺（见 B2）。

### Q5：市面大部分播放器配什么、怎么配？

- **主流 TVBox 系**（TVBox 原版 / FongMi / 影视仓 / OK影视 / CatVod 系）：
  内置 **Exo + IJK**（部分带系统播放器），用户在设置里手选；订阅通过 `playerContent` 返回的
  `parse / jx / playUrl` 决定该走解析还是直链；IJK 的解码档与 ffmpeg 参数（含 `rw_timeout`）由订阅的 `ijk` 字段下发。
- **更全的 fork**（如 takagen99/Box）：内置 System / IJK / Exo / **Aliyun** 四个 + 外部 MX / Reex / Kodi / 附近TVBox / VLC 五个
  —— **和我们几乎一模一样，我们只差一个 Ali**。
- **IPTV 类**：Exo 主用 + VLC / 外部播放器切换；社区共识是「格式支持 MPV = VLC > Exo = IJK，缓冲 MPV 最好」。
- **通行策略**（有一份源码拆解写得很直白）：默认用 Exo 播网络流，**播放异常时自动切 IJK**。
  多数 fork 只做到"手动切"，**我们做到了自动降级**。

**一句话：我们的播放器配置水平已经在市面主流之上，缺的不是"内核数量"，是几个判定细节。**

## 4. 候选改动清单

### A 类 · 零风险、纯收益（不改请求形态，建议做）

| 编号 | 改动 | 解决什么 | 风险 |
|---|---|---|---|
| A1 | **判定与试播解耦**：拿不准的地址**先直连试一次**（限时 ~8s），失败再自动进解析 | 白名单没命中的直链不再白等 20 秒嗅探 | 无。只是把"先解析"改成"先试播再解析"，不跳过任何原路径 |
| A2 | `//` 协议相对地址改为**继承来源协议 / https 优先** | 硬补 `http:` 导致 https-only CDN 失败 | 无 |
| A3 | IJK `protocol_whitelist` 补 `rtmp,rtmpt` | 现在 RTMP 直链会被 FFmpeg 拦下 | 无（Exo 侧已有 RtmpDataSource，只在 scheme == rtmp 时生效） |
| A4 | 去掉 `jsonParse` 里 UA / Referer 的**前导空格** | 严格 CDN 会把带空格的 UA 当异常 | 无。EXO 侧现在会 trim，IJK 侧不会 —— 统一对齐 |

### B 类 · 会多一次请求或改变请求形态（**需你点头**）

| 编号 | 改动 | 代价 | 风险 |
|---|---|---|---|
| B1 | 直链**预探测**（HEAD，失败退化为 `Range: bytes=0-0`，看 `Content-Type`） | 每个"拿不准"的地址多 1 次请求 | 多一次请求 = 多一次被限流的机会；必须**限一次**并加超时 |
| B2 | 外部播放器 **VLC 经本地代理注入 Referer/UA** | 走 `/proxy`（仅 127.0.0.1） | 现在 VLC 播鉴权源必挂；代理这层本身是失败点（av 里网盘源就栽在代理上），要评估 |
| B3 | 网盘源本地代理想路增强（UA / Referer / Range 组合） | 无额外请求 | av 里 2 次失败在这条路上，属于"本来就坏的层" |

### C 类 · 不建议

| 编号 | 做法 | 为什么不 |
|---|---|---|
| C1 | 内置 MPV / FFmpeg 全格式内核 | 包体与构建复杂度是另一个量级，且救不了源侧失败 |
| C2 | 自动换线路 / 换源 | 你已经明确否决，我也不推荐 |
| C3 | 对源站做多次可用性探测 | 直接触风控红线 |

## 5. 被锁住的天花板（必须先说清）

**"不碰线路" 这个定位，已经把单线路成功率的天花板锁住了。**
av 那 7 次失败全部是源侧问题，而我们能做的只是"更快、更清楚地失败"，不是"让它能播"。
真正能把成功率拉上去的动作只有两个：**换线路 / 换源** —— 你已否决，我尊重。

所以后面的所有改动，本质上都是**减少失败、缩短等待、避免误判**，不是增加成功。

## 6. 建议的下一步：先测后改

在动任何一行之前，建议先加**纯埋点、零行为改动**的一轮，用数据决定 A/B 做哪几条：

| 埋点字段 | 用来回答 |
|---|---|
| 判定结果（直连 / 走解析） | 有多少地址被白名单推去走了解析？ |
| 解析类型与耗时 | A1 能救多少"白等 20 秒"？ |
| 解析产出的地址是否可播 | 解析路径的成功率到底是多少？ |
| 实际使用的协议（http / https / rtmp / 伪地址） | A2、A3 有没有真实样本？ |
| 请求头里是否带 UA / Referer、是否带前导空格 | A4 有没有真实样本？ |

这样我们能得到一张"解析路径占比 / 解析成功率 / 各缺口命中次数"的表。
**如果解析路径占比很低（我预计会很低），那 A/B 就该缓做，把精力放回看门狗那条未观测的尾巴上。**
