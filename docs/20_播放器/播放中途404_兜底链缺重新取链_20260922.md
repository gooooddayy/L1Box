## 二、根因：**这一条路上没有「重新取链」**

`PlayFragment.errReplay()`（第 620~644 行）的兜底链，按顺序是：

```
1. 还有别的已解析地址？ → errorWithRetry("视频播放出错")   ← 只有这一支才会走到 autoRetry()
2. fallbackToRawUrl()   回退原始直连                      ← 同一条死链
3. retryVariantUrl()    同址 http↔https                  ← 端口 9090 非标准，日志显示「跳过」
4. compatFallback()     换内核（IJK ↔ Exo）               ← 同一条死链
5. errorFinal()         报错收工
```

而**「重新取链」= `autoRetry()`（第 2157 行）在全工程只有一个调用点：第 1179 行的 `errorWithRetry()`**。
`errReplay()` 里 `errorWithRetry()` **只在 `loadFoundVideoUrls`（别的解析地址）非空时才走**（第 627 行）；
本例 `loadFoundVideoUrls` 是空的 ⇒ **直接落到第 2~5 步，一次重新取链都没有**。

⇒ **对"链接已失效（404）"这个错误签名，兜底链选错了动作**：
死链上换协议、换内核、回退原始地址，**在物理上不可能成功**；
唯一有效的是**向站点重新要一条新直链**——而这正是**用户手动点「重试」**做的事（日志 15:08:57→15:08:58，
拿到新 IP `111.170.141.203 → 111.170.9.52` 后**立刻正常播放**，起播 403 ms）。

**所以这不是"源坏了"，是"兜底链在死链上打转"。** 用户手上那部片子**是可播的**。

---

## 三、为什么原作者故意没加（必须先承认的道理）

`errorFinal()` 的注释（第 1158~1167 行）写得很清楚，而且是**对的**：

> `autoRetry` 会排一次"重新取链"，而那意味着**又开一个 20+12 秒的看门狗窗口**，
> 会把"每一步都空转"时的最坏等待从预算内的 64 秒拖回 96 秒以上（实测就是这样绕过了旧预算）。

也就是说：**无条件把 `autoRetry()` 加回终态出口是错的**，会重新引入"最坏 96 秒"的老问题。
`errReplay` 里那句「再排一次重新取链只会又开一个 32 秒的观察窗口」也是同一个顾虑。

---

## 四、最小修法（**按错误签名分档**，不是无条件加回）

不要动终态出口的整体结构，只在**第 2 步之前**插一个**有签名门槛**的分支：

> 当「本次失败是**播放已开始之后**发生的」且「错误签名＝**链接失效类**（HTTP 404 / 410，
> 或 `errorCode=2004 BAD_HTTP_STATUS`）」时，**先走一次 `autoRetry()`（重新取链）**，
> 成功接管就 return；失败再按原顺序走 2→5。

三条约束（都必须有，否则会踩回老坑）：
1. **必须限定"播放已开始之后"**：`mPlayStartedAt > 0` 且已经 `prepared()` 过。
   起播前就 404 的（第 15:08:34 那次 `ms=221`）**不加**这一档——那时链接本来就是刚取的，重取无意义。
2. **必须限定错误签名是"链路失效"**：只有 404/410 这类"地址没了"才重取；
   超时、解码失败、容器不识别**都不走这条**（那些重取也没用）。
3. **必须受既有预算夹住**：`autoRetry()` 自己已有 `FETCH_RETRY_BUDGET_MS=8000` 与
   `AUTO_RETRY_DELAY_MS={1200,2500}` 两道闸，**直接把 `mEpisodeStartAt` 也用在"播放中途"这个场景需要重新定义基准**
   —— 建议用「**回溯到本次 404 发生的时刻**」当预算起点，而不是本集开播时刻，
   否则播了 10 分钟的片子会立刻判定"预算用尽"而跳过重取。

**预期收益**：本例那 11.3 秒的无用功变成「约 1.2 秒退避后重新取链」，
且**大概率一次就好**（用户手动重试 100% 成功）。

**风险**：如果站点对"频繁取链"有风控，重取会多一次请求。所以**每次 404 只重取一次**（`autoRetryCount` 已经天然限次）。

## 五、本批（bn）与该问题的关系

**无关。** bn 只改了三处，全部不在播放链路上：
`Spider.safeDns()` 返回值、`L1FallbackDns` 的计数与日志、`FastSearchActivity` 的耗时埋点。
本次故障的地址是 IP 字面量（`111.170.9.52:9090`），**连 DNS 查询都不会发**。
⇒ 这是**既有缺陷**，bn 只是第一次把它记进了日志。

## 六、附：同一窗口的第二类失败（也值得记一笔）

`15:08:34` 那次：从降级到报错**只用了 221 毫秒**（`播放失败：出链 … ms=221`）。
`retryVariantUrl()` 那句 `非标准端口，跳过 http↔https 重试` 意味着：
**对 `IP:9090` 这一大类源，协议重试这一档是恒空转的**，兜底链等于少了一档。
这不是 bug（非标准端口换 https 本来也没意义），但**在统计"兜底链有几档真正可用"时要扣掉它**。
