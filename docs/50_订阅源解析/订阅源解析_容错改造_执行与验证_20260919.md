## 二、本次修的确定缺陷

### 2.1 「切换源了还在用上一个源的线路数据」（用户实报，根因已定位）

数据类 `Subscription` 里：

```java
public String getEffectiveUrl() { return isMultiRepo ? getActiveLineUrl() : url; }
```

**多仓**订阅的生效地址不是 `url`，而是 `activeLineUrl`。而编辑订阅的代码只改了名字和地址：

```kotlin
item.name = newName
item.url = newUrl          // ← isMultiRepo / lines / activeLineUrl 三件套原封不动
```

⇒ 用户把地址换成新源，`getEffectiveUrl()` 依旧返回**旧仓的线路地址**，`onPause` 里
`ApiConfig.saveApiUrl(effective)` 写盘的也是旧地址。**界面上显示的、实际请求的，是两回事。**

修法：
1. 地址变更时把多仓身份三件套一起作废（`isMultiRepo=false / lines=[] / activeLineUrl=""`）；
2. 按新地址**重新识别形态**（`reloadSubscriptionLines` → `parseLines`），识别不出按单仓处理；
3. `getEffectiveUrl()` 加兜底：多仓但当前线路为空时回落第一条线路（否则写空串进 `API_URL` ＝ 切源后变空源）。

### 2.2 切源请求被"正在跑的刷新"静默吞掉（"有的时候"的另一半）

`HomeFragment.reloadSitePool()` 与 `onResume` 都有 `if (mReloading || mLoadInFlight) return`。
而这个"在跑的那次"是在**发起时刻**读的地址 —— 用户切源时它正拿着旧地址在跑，出去的那次直接被丢弃。
⇒ 切了源，界面停在上一个源的线路数据，且毫无提示。

修法：新增 `mPendingReload`。被跳过时置位，**在刷新收尾处补一次**（`schedulePendingReload`，延迟 800ms 让首页加载先落地，只补一次不循环）。

### 2.3 `http://` 拼空串（原方案 S1）

```java
} else if (!apiUrl.startsWith("http")) {
    configUrl = "http://" + configUrl;     // ← configUrl 此刻还是 ""
}
```
⇒ 漏写协议头的地址被拼成 `"http://"`，请求必败。**这是"某条线路怎么都拉不出来"的确定性原因。**

### 2.4 `split` 越界（原方案 S2）

`apiUrl.split(";pk;")` 后直接取 `a[1]`，而 Java 的 `split` 会丢掉尾部空串 —— 地址以 `;pk;` 结尾时数组只有 1 个元素。`loadConfig` 与调用方都没有 try ⇒ 可闪退。

### 2.5 裸 base64 必然解析失败（原方案 S3）

`FindResult` 只认 `[A-Za-z0-9]{8}**` 这个特定前缀（`*` 根本不在 base64 字母表里）。
裸 base64 的订阅一路走到 Gson ⇒ 抛异常 ⇒ 用户看到"解析配置失败"。

## 六、关于用户提供的那条源（已确诊，附完整证据链）

```
https://tv.<订阅源C>.top/m/111.php?ou=公众号欧歌app&mz=index&jar=index&123&b=tv
```

### 结论

**这条源本身没坏，但它在你的网络下被阻断了 —— 任何播放器都拉不到它。不是 App 的解析问题，也不是换源就能"修好"的 App 缺陷。**

### 证据链（三步定性）

**① DNS 被污染**

| 解析途径 | 返回 IP |
|---|---|
| 手机本地 DNS | `202.160.130.118`（ping 无响应） |
| 腾讯 DoH（doh.pub） | `104.21.63.117`、`172.67.145.116` |
| 阿里 DoH（223.5.5.5） | `188.114.97.3`、`188.114.96.3` |

两组 DoH 返回的**全是 Cloudflare 段**，而本地 DNS 给的是完全不同的 IP ⇒ 本地解析被改写。

**② 到真实 IP 的 TLS 握手被阻断**

```
* Connected to tv.<订阅源C>.top (104.21.63.117) port 443 (#0)   ← TCP 建连成功
* TLSv1.2 (OUT), TLS handshake, Client hello (1):          ← 发出 TLS 握手
* Recv failure: Connection reset by peer                    ← 立刻被 RST
curl: (35) Recv failure: Connection reset by peer
```

TCP 通、TLS 一发就断 ＝ 典型的 **SNI 阻断**（按握手里的域名重置连接）。

**③ 对照实验：你的网络是好的**

| 目标 | 结果 |
|---|---|
| `https://www.baidu.com/` | **200** |
| `https://1.1.1.1/`（Cloudflare） | 000 |
| `https://tv.<订阅源C>.top/` | 000 |

⇒ 是**到 Cloudflare 这条路被墙**，不是你的网络有问题。

### 能做什么、不能做什么

| | 说明 |
|---|---|
| ❌ App 层面无解 | DoH **也救不了**：DNS 能解对，TLS 握手照样被 RST。加 DoH 兜底对这类阻断无效 |
| ✅ 现成开关 | App 设置页已有「**安全DNS**」（腾讯/阿里/360），它挂在 OkGo 全局 DNS 上，订阅拉取一起走。<br>对"**只是 DNS 被污染、IP 本身可达**"的源，打开它就能救活 ⇒ **建议默认开着**。这类源在国内很多（尤其用 Cloudflare CDN 的） |
| ✅ 唯一出路 | 对这条 nxog 源：**换源**。任何播放器在你这条网络下都拉不到它 |

> 装机后用 bl 添加它，新增埋点会给出准确结论（预期是 `结论=空响应`）。
