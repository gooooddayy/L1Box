# 订阅源解析 · 现状测绘与优化方案（2026-09-19）

> 口径：**配置源 = 订阅**；线路 = 多仓里的子线路；影视站点 = 播放来源。
> 本文只谈"把用户给的订阅链接变成可用站点池"这条链路，**不碰播放、不碰换线路**。

---

## 一、先看清"解析"其实发生在两处（理解后面一切的前提）

```
用户粘贴订阅链接 / 扫码 / 导入文本
        │
        ▼
┌─ ① 添加阶段 ────────────────────────────────────────────┐
│  SubscriptionActivity.addSubscription()   (kt:289)     │
│  OkGo.get(url)  ← 无 UA、无 Accept、无超时设置、无重试  │
│  解析：urls[] → 多线路收拢成"多仓父"                   │
│        storeHouse[] → 多仓父（sourceName/sourceUrl）    │
│        其余 → 单仓                                      │
│  失败 → Toast「订阅失败,请检查地址或网络状态」          │
└─────────────────────────────────────────────────────────┘
        │ 启用（单选）→ HawkConfig.API_URL
        ▼
┌─ ② 启用阶段（每次开 App / 切线路都跑）────────────────┐
│  ApiConfig.loadConfig()                    (java:182)  │
│  ├ 拼 configUrl（clan:// 转换、;pk; 拆密钥）           │
│  ├ doLoadConfigRequest()  带 UA+Accept                │
│  │    失败重试 2 次（1.5s / 3s）→ 再失败用本地缓存     │
│  ├ convertResponse()                                  │
│  │    FindResult()      base64(`xxxxxxxx**` 前缀) / AES│
│  │    clanContentFix()  clan:// 替换                   │
│  │    fixContentPath()  `./` 相对路径修补              │
│  └ parseJsonInternal()  取 spider / sites / parses /   │
│                         lives / rules / ijk / ads      │
│  失败 → Toast「订阅更新失败，请检查线路配置」           │
└─────────────────────────────────────────────────────────┘
        │
        ▼  站点池 sourceBeanList（搜索/详情/播放都用它）
```

**关键含义**：同一条链接，①过得去不代表②过得去，反之亦然。用户看到的"解析失败"至少有两套完全不同的成因。

## 二、现在已经有的容错（别重复造轮子）

| 能力 | 位置 | 说明 |
|---|---|---|
| UA + Accept 请求头 | `ApiConfig:250-251` | `okhttp/3.15` + 浏览器式 Accept |
| 弱网重试 2 次 | `ApiConfig:282-293` | 间隔 1.5s / 3s，期间弹「正在重试」 |
| 拉取失败回退本地缓存 | `ApiConfig:294-306` | 缓存文件在 `filesDir/MD5(url)` |
| 订阅地址**双写备份** | `saveApiUrl:173` | 主键损坏自动恢复 + 提示 |
| base64 解码 | `FindResult:135` | ⚠️ **只认 `[A-Za-z0]{8}**` 前缀** |
| AES 解密 | `FindResult:141-148` | `2423` 自定义 CBC ＋ `;pk;` 指定密钥 |
| `clan://` 协议 | `clanToAddress:1202` | 含 `clan://local/` SAF 本地导入 |
| 相对路径修补 | `fixContentPath:1225` | `"./` → 订阅地址同目录 |
| 多仓收拢 | `SubscriptionActivity:304/335` | `urls[]` / `storeHouse[]` → 一条父源 |
| 并发防护 | `parseJson:648` | `synchronized(sourceBeanList)` 防站点池撕裂 |
| 字段级安全取值 | `DefaultConfig.safeJsonString/Int` | 类型不符不崩 |
| 空订阅即时清池 | `loadConfig:196-210` | 删除全部订阅后立即清空，不等重启 |
| Brotli / gzip | `OkGoHelper:179` | `BrotliInterceptor` + OkHttp 透明 gzip |
| SSL 兼容 + DoH 可选 | `OkGoHelper:221` | 自定义 `SSLCompat`；安全 DNS 可切换 |

**结论：网络层和"订阅格式"层的容错其实做得不差。缺口集中在「URL 规范化」「内容容错」「多仓判定」和「解析结果反馈」四处。**

## 三、发现的 8 个短板（按 命中概率 × 修复成本 排序）

### 🔴 S1. `loadConfig` 会拼出一个空地址 `http://`
**位置**：`ApiConfig.java:234-235`
```java
} else if (!apiUrl.startsWith("http")) {
    configUrl = "http://" + configUrl;   // ← configUrl 此时还是 ""
}
```
应当拼 `apiUrl`。触发路径：**多仓子线路的 `url` / `storeHouse.sourceUrl` 没带 `http` 前缀**（Stage① 只 trim、不校验、不补前缀）→ 该线路被选中后必然请求 `http://` → 100% 失败。
> 这一条单独就能解释"某个线路怎么都拉不出来"。
**成本**：1 行。

### 🔴 S2. `;pk;` 结尾时数组越界（潜在崩溃）
**位置**：`ApiConfig.java:221-224` — `String[] a = apiUrl.split(pk); TempKey = a[1];`
`split` 会丢掉尾部空串，所以 `"...json;pk;"` 得到长度 1 的数组 → `a[1]` 抛 `ArrayIndexOutOfBoundsException`，而 `loadConfig` 外层无 try → 直冲调用方（`HomeFragment.loadConfig` 也无 try）→ **FATAL**。
概率低，但代价是崩溃，且修复同样是 1 行。

### 🟠 S3. 纯 base64 的订阅内容不解码
**位置**：`FindResult:135`
```java
Pattern.compile("[A-Za-z0]{8}\\*\\*")   // 必须是 "8位字母数字 + **" 开头
```
`*` 不在 base64 字母表里 —— 也就是说**只有带那个特定分隔符的"加密订阅"才认**。一整段裸 base64（不少源站就是这么发的）会走到最后 `json = content`，然后 Gson 解析失败 → 「解析配置失败」。
**修法**：所有手段都失败后，最后再试一次"整段 base64 解码 → 若结果是 JSON 就采用"。

### 🟠 S4. 添加阶段的网络参数明显弱于启用阶段
**位置**：`SubscriptionActivity.kt:295`
```kotlin
OkGo.get<String>(url).tag("get_subscription").execute(...)   // 无 UA / 无 Accept / 无重试
```
后果是同一链接"添加时失败、启用后反而成功"，用户得到的是最没有信息量的一句「订阅失败,请检查地址或网络状态」。
**修法**：与 `doLoadConfigRequest` 对齐（同 UA/Accept、同 10s 超时、同 2 次退避重试）。

### 🟠 S5. 多仓判定过于苛刻，且失败后**静默降级**成"单仓"
**位置**：`SubscriptionActivity.kt:306-309` / `337-340`
```kotlin
// urls[]：必须 urlList[0] 是对象 **且同时**有 "url" 和 "name"
// storeHouse[]：必须 list[0] **同时**有 "sourceName" 和 "sourceUrl"
```
只检查**第 0 条**：第 0 条恰好缺字段（很常见——有的仓第一条是占位/公告），整份多仓就被判成"单仓"。
而"单仓"的 URL 指向的却是一份**多仓索引**，`parseJsonInternal` 里没有 `urls`/`storeHouse` 分支 → `sites` 为空 → **站点池 0 个，且不报任何错**。
**修法**：按字段别名**逐条**收集（`url`/`api`/`sourceUrl`、`name`/`sourceName`），不再"以一票否决"。

### 🟠 S6. JSON 解析零容错
**位置**：`parseJsonInternal:654` — `new Gson().fromJson(jsonStr, JsonObject.class)`
以下情况**全部**直接失败并弹「解析配置失败」：
- 文件头有 **BOM** / 零宽字符（用户用记事本另存过就会带）
- 前后有多余说明文字、或 JSON 被 HTML 包了一层（CDN/防火墙拦截页）
- **尾逗号**、`//` 注释（很多手写配置就这么写）
- 响应其实是个 JSON **数组**（`[{...}]`）而不是对象

**修法**：抽一个纯函数 `extract()`：去 BOM/零宽 → 取**第一个 `{` 到最后一个 `}`**（失败再试 `[`…`]`）→ Gson **lenient** 解析。

### 🟡 S7. "解析出 0 个站点"被当成成功，用户无从判断
`parseJsonInternal` 末尾只置 `sitePoolSettled = true` 就返回，**`sites` 为空也走 success**。用户看到的是：启用成功、首页空、没有任何解释。
**修法**：解析结束时明确区分三种结论并给出文案 ——
① 连不上（网络/域名不可达）② 内容不是订阅（返回的是网页/纯文本）③ 能解析但不是订阅（没有 `sites` 字段）。
顺带把结论写进 `L1Diag` 埋点。

### 🟡 S8. 两处小缺口的补充
- **非 UTF-8 响应**（GBK 站点）→ 中文站名乱码、严重时解析失败。可在字节层判定 UTF-8 非法时按 GBK 兜底。
- **对话框不补 scheme**：`SubsciptionDialog` 只校验"非空"，随后 `addSubscription` 对非 `http`/`clan` 开头直接弹「订阅格式不正确」把用户挡在门外，却不提示"是不是少了 http://"。

## 四、优化方案（三档，按你的"减少崩溃优先"原则排）

### P0 · 零风险，纯解析层（不做任何网络/播放改动）—— 建议全做
| # | 动作 | 落点 |
|---|---|---|
| 1 | 新增纯函数 `L1SubUrl.normalize()`：trim、去 BOM/零宽/换行、大写 scheme 归一、**无 scheme 自动补 `http://`** | `loadConfig` 开头（①）、`addSubscription`（②）、导入文本（③）、多仓子线路 `url`/`sourceUrl`（④）、`HomeFragment` 的 `pickedUrl`（⑤）**五处入口统一走它** |
| 2 | 修 S1：`"http://" + apiUrl` | `ApiConfig:234` |
| 3 | 修 S2：`a.length < 2` 时**不**当成 `;pk;` 形态 | `ApiConfig:221` |
| 4 | 新增纯函数 `L1JsonPick.extract()`：BOM/零宽清洗 + 首个 `{`…末个 `}` 截取 + lenient | `parseJsonInternal:654` 前 |
| 5 | base64 兜底：全部手段失败后整段解码试一次 | `FindResult` 末尾 |
| 6 | 0 站点/非订阅 的明确结论 + `L1Diag` 埋点 | `parseJsonInternal` 末尾 |

> 其中 1/4/5 都是**纯 Java、零 Android 依赖**的函数 —— 这一点很重要，见第五节。

### P1 · 低风险，行为对齐与判定放宽
7. **S4**：添加阶段拉取参数与启用阶段完全对齐（UA/Accept/超时/2 次退避重试）；失败时**不再静默降级**为"单仓"，改提示"地址能打开但内容无法识别，可能不是订阅源"。
8. **S5**：多仓识别放宽 + 字段别名 + 逐条收集（不再看第 0 条）。
9. **S8-a**：GBK 兜底解码（仅在 UTF-8 非法时触发）。

### P2 · 需要你拍板
10. **解析自检面板 / 诊断日志**：在设置页或订阅页显示"本次解析：站点 N / 解析 N / 直播 N，用时 Xms"。
    > 这条不是为了好看 —— **没有它，我们永远只能凭感觉说"成功率"。** 有了它，下次讨论"提升多少"才拿得出数字。

### 明确不做（守既有铁律）
- ❌ 不自动换线路、不做多源并发探测（早已否决）
- ❌ 不引第三方解析库、不新增 Service（加固 jar `killall` 环境，多一个入口多一个崩溃面）
- ❌ 不动播放侧净化、不动缓存线（那条线已定版收尾）

## 五、验证方案（**不靠"我手机上试了没问题"**）

这条链路的天然优势：**容错逻辑可以做成零 Android 依赖的纯 Java 类**，于是验证能完全脱离真机：

**① 宿主机 JVM 用例表（主力验证）**
用 `dl/jdk11` 的 `javac`/`java` 直接在电脑上跑一张固定的输入表，覆盖畸形输入：
```
URL: 前后空格 / 内嵌换行 / 缺 scheme / HTTPS 大写 / clan:// / ;pk; 结尾 / 空串
JSON: 带 BOM / 前后夹说明文字 / 尾逗号 / // 注释 / 被 HTML 包裹 / 顶层是数组 / 纯 base64
多仓: 第 0 条缺 name / 缺 url / 只有 sourceUrl / 字段用别名 / 空数组
```
每条给出**期望输出**，跑完打印通过率。这是"机制性兜底"的证明，而不是"我这台机器恰好没问题"。

**② 构建闸门断言（防回归）**
在 `check_l1box_regressions.sh` 增补断言，遵守既有判据纪律：
- 只锚**实际调用形态**（如 `L1SubUrl\.normalize\(`），不锚具体数值/写法
- **绝不锚局部变量名**（不进 dex ⇒ 构建会以 `dex 缺少修复代码` 失败、APK 不落盘）
- `mustnot` 写成调用形态，别写成自己注释里的旧写法

**③ 真机端到端（你做，我只给步骤）**
三件事：正常链接能出站点、**故意畸形**的链接给出正确文案（而不是"解析失败"三个字）、切线路不串源。
