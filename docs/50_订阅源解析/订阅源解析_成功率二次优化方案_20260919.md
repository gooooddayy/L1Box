# 订阅源解析：成功率二次优化方案（按风险 × 资源分档）

日期：2026-09-19　｜　前置：`订阅源解析_容错改造_执行与验证_20260919.md`（bl 批次已落地）
本文只谈**还没做**的事。已做完的六项（地址规范化 / `http://` 空串 / `;pk;` 越界 / 裸 base64 / BOM 与 HTML 外壳 / GBK）不再重复。

## 〇、口径声明（先说清，免得后面被误读）

| 问题 | 口径 |
|---|---|
| 能给"提升 N 个百分点"吗 | **不能。** 旧版零埋点、零基线；要数字必须两版同跑同一批源做 A/B，没做过。下文一律只写"**能救哪一类源**"，不写百分比。 |
| 这些方案一定有效吗 | 每项都标了**触发条件**。条件不出现＝没收益；收益大小取决于你手上的源有多"脏"。 |
| 风险怎么定义 | ① 会不会影响现在**正常**的源（回归风险）② 会不会引入**新的失败形态** |
| 资源怎么定义 | **开发**＝改动行数/文件数；**运行**＝内存 / 流量 / 电量 / 时延 |

## 一、现状盘点：现在的解析链走到哪一步了

| 环节 | 已具备 | 缺口 |
|---|---|---|
| **地址层** | `L1SubUrl.normalize()`：BOM/零宽/引号/漏协议头 | — |
| **网络层** | OkGo 全局：`retryOnConnectionFailure` / `followRedirects` / Brotli / 连接·读·写各 10s / DoH（**默认关闭**）<br>订阅请求：UA + Accept、重试 2 次（1.5s/3s）、失败落缓存 | ① 无独立超时 ② 重试不分错误类型 ③ **DoH 默认关** ④ DoH 不可达时不回退系统 DNS ⑤ 无网络恢复重拉 ⑥ 无协议回退 |
| **内容层** | `L1SubContent`：直接 JSON / 裸 base64（标准+URL-safe+缺 padding+双层）/ HTML 外壳 / 前后夹文字 / GBK | ⑦ 顶层是数组 ⑧ `//` 注释与尾逗号 ⑨ base64+gzip 组合 ⑩ 特征字段只有 5 个（`sites`/`urls`/`storeHouse`/`spider`/`parses`） |
| **语义层** | 多仓只认 `urls[]` / `storeHouse[]`；逐条宽松收集 | ⑪ 字段名变体（`api`/`list`/`lines` 等） |
| **结果层** | 0 站点会打 `L1Sub:` 日志 | ⑫ **sites=0 仍 `callback.success()`** ⇒ 界面显示"启用成功"却搜不出东西 ⑬ 失败文案笼统 |

## 二、A 档 —— 低风险 · 低资源（建议做）

改动都收敛在 `L1SubContent` / `ApiConfig` 两处，不动架构。

| # | 方案 | 触发条件（什么源会被救） | 类型 | 风险 | 资源 |
|---|---|---|---|---|---|
| **A1** | **解析失败回退上次缓存**。现在 `onSuccess → parseJson 抛异常 → 直接报错`，**明明有缓存也不用** | 源站把 JSON 改坏了 / 临时返回半截内容 | ✅ 真·成功率 | **低**：缓存文件名 = `MD5(地址)`，**换源天然不串**（新地址没有缓存） | 开发 ~20 行；运行 0 |
| **A2** | **顶层数组包装**：`[{...},{...}]` → 按形状判 `{"urls":[…]}` 或当单仓 | 源站直接返回线路数组 | ✅ 真·成功率 | **低**：仅当 `[` 开头才走，且元素必须含 name 类 + url 类字段 | 开发 ~40 行；运行 0 |
| **A3** | **`//` 与 `/* */` 注释、尾逗号清洗** | 手写/生成器导出的 JSON | ✅ 真·成功率 | **低**：洗的是字符串，仍要过"必须解出带特征字段的 JSON"守门 | 开发 ~40 行；运行 0 |
| **A4** | **base64 + gzip/deflate 组合解码** | 压缩后再 base64 的源 | ✅ 真·成功率 | **低**：解不出就返回 null，原逻辑照走 | 开发 ~30 行；运行 0 |
| **A5** | **请求头补齐**：`Referer`（源站自身）、`Accept-Language`、`Cache-Control: no-cache` | 开了防盗链的源站 | ✅ 真·成功率 | **低-中**：极少数源站会因多余头拒绝；可只加 Referer | 开发 ~5 行；运行 0 |
| **A6** | **失败时给出准确结论**（复用 `L1SubContent.diagnose()`）：把"返回的是网页(非订阅)"/"空响应"/"内容不是订阅"直接显示给用户 | 全部失败场景 | 可理解性 | **低** | 开发 ~20 行；运行 0 |
| **A7** | **0 站点不再当成功**：sites=0 时给明确提示，而不是弹"启用成功" | 站点池为空的源 | 可理解性 | **低** | 开发 ~15 行；运行 0 |

> A6/A7 **不提高成功率**，但能把"启用了却搜不出东西"这类最让人困惑的状况说清楚。用户已否决的是「自检面板」，这两项只是**结果提示**，不是面板。

## 三、B 档 —— 低风险 · 中资源（价值最高的一档，但要先设计）

| # | 方案 | 说明 | 风险点与规避 | 资源 |
|---|---|---|---|---|
| **B1** | **DoH 失败回退系统 DNS** | 现在：DoH 服务本身不可达 ⇒ 直接 `UnknownHostException`，**比不开还糟**。所以默认开 DoH 之前必须先做这一层 | 写一个包装 `Dns`：先试 DoH（带超时），失败/超时立刻走系统 DNS。最坏情况＝回到今天的行为 | 开发 ~60 行；运行 一次额外往返（仅首次解析） |
| **B2** | **「安全DNS」默认改为开启**（依赖 B1） | 现状 `App.java:244 putDefault(DOH_URL, 0)` ⇒ **绝大多数用户走系统 DNS**，DNS 被污染的源（很大一类）**一律失败** | 首屏多 ~50–150ms；靠 B1 兜底后无全盘失败风险 | 开发 1 行；运行 少量 |
| **B3** | **网络恢复后自动重拉**（**同一地址重试，不是换源**） | 进电梯/地铁/切 WiFi 时拉取失败 → 现在只能手动刷新或重启 | 必须三个条件同时成立才触发：**站点池为空** + **网络已恢复** + **非播放中**；且限流（如 30s 内最多 1 次） | 开发 ~80 行；运行 0 |
| **B4** | **http ↔ https 双向回退** | 源站强制跳转但老设备 CA 库认不了证书 | 只在**明确的连接/证书错误**上回退，且只试一次 | 开发 ~40 行 |
| **B5** | **多仓字段名宽松识别** | 现在只认 `urls[]`/`storeHouse[]`；源作者写别的 key 就识别不出多仓 | **误认风险最大的一项**：必须加形状判据（元素同时含 name 类 + url 类字段），且**只作用于"添加订阅"阶段**，不进单仓解析 | 开发 ~60 行 |
| **B6** | **UA 可切换重试** | 部分源站按 UA 做风控/防盗链 | 只在该源失败后换一个备选 UA 重试一次，**不全局改** | 开发 ~30 行 |

> **B2 是这一档里单项收益最大、改动最小的一项**，但它的前提是 B1——**没有 B1 就默认开 DoH，等于把"部分源失败"换成"可能全部源失败"**。

## 四、C 档 —— 中风险（先评估，暂不建议）

| # | 方案 | 为什么不建议现在做 |
|---|---|---|
| C1 | 更多 AES 变体（猜 key / 换模式） | 猜错会解出垃圾。虽有"过 JSON 校验才采信"守门，但存在"恰好解出形状正确的垃圾"的可能 ⇒ 静默错数据比明确失败更糟 |
| C2 | 单仓字段别名（`sites` 之外的名字） | TVBox 生态字段名约定俗成，变体罕见；误认风险实在而收益低 |
| C3 | 站点对象字段补全（缺 `api` 时从 `ext` 推断） | 会把**本来不显示的坏站点**放进站点池 ⇒ 搜索质量下降、失败集变大 |

## 五、D 档 —— 不做（已否决 / 越红线）

| 项 | 原因 |
|---|---|
| 自动换线路 / 自动换源 / 失败提示加"换线路"入口 | **用户红线**（换线路是用户手动的事） |
| 解析自检面板 | 用户已明确否决 |
| 多线程并发拉多个订阅源 | 已有否决记录（并发异常 ⇒ 风控） |
| 判不可播后跳过重取 / 网盘代理自动重试 | 已有否决记录 |

## 六、二维定位：风险 × 资源

```
资源（开发量）
  高 ┤                              C1  C3
     │                        B5
  中 ┤              B2*  B3  B4
     │              B1   B6                     C2
  低 ┤  A5  A6  A7        A2  A3
     │  A1  A4
     └──────┬────────┬────────┬────────┬────────→ 风险
           极低      低       中       高
```
（`B2*` 必须与 B1 同时做）

## 七、建议实施顺序

| 批次 | 内容 | 理由 |
|---|---|---|
| **第 1 批** | A1 → A7 全部 | 单项都小、都低风险，且**互不干扰**；能一次性把"内容层 + 结果层"补厚 |
| **第 2 批** | B1 + B2 一起 | 收益最大的组合，且必须配对上线 |
| **第 3 批** | B3 | 单独一批（要新增 `NetworkCallback` 生命周期管理，值得单独验证） |
| **第 4 批** | B4 / B5 / B6 | 按需挑，B5 要单独设计误认判据 |

---

## 八、一句话总结

现在这条链**地址层和内容层已经补得比较厚了**；**剩下的最大块空隙其实在网络层**——尤其
「**DoH 默认关闭**」和「**DoH 不可达时不回退**」这两件事合在一起，等于把一大类源（DNS 被污染）
默认判死。**B1+B2 是投入产出比最高的一组**，其次是把 A 档 7 项一次补齐。
