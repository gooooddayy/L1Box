`可用堆 ≥ 水位字节 + 32MB` 的判据在真机上稳定成立。

### 2. 🔴 起播放行时的缓冲量：**3240 / 4400 / 6000 / 6040 / 8040 ms，5/5 全部 ≥ 3000ms**

**这条直接推翻了批三的前提。** 门槛写的是 1500ms，但实际起播放行时缓冲量最小也是 3240ms —— 说明
HLS 的缓冲量是**按整片跃升**的（一片 6 秒，下完直接从 0 跳到 ~6000ms），所以：

- 门槛调 1000 / 1500 / 2200 **在这类源上完全不起作用**：同一瞬间三个值会一起满足，出画面时间不变。
- 推论：**"降门槛实现秒播"在 HLS 上是伪命题** —— 真正决定出画面时刻的是"第一片下完"。
- 反过来说，门槛**不是没用**：它只在"源很慢、第一片迟迟下不来"时才生效，而那正是需要它的场景
  （防止只攒了一点点就出画面、紧接着就重缓冲）。**所以结论是保留 1500ms 不动，而不是去调它。**

→ **批三取消。** 不调数值、不换判据。

## 二、批二做了什么

一句话：**把一套早就写好、但被硬编码关掉的磁盘缓存真正打开，并给它加上安全边界。**

改之前的状态是：`ExoMediaSourceHelper` 里 `SimpleCache` + 512MB LRU + 索引库一应俱全，
但唯一的调用点 `ExoMediaPlayer.java:109` 写的是 `getMediaSource(path, headers, false, errorCode)`
—— 那个 `false` 就是"不缓存"，**从未启用过**。

### 改动清单

| # | 文件 | 改了什么 |
|---|---|---|
| 1 | `player/.../exo/ExoCacheConfig.java`（**新建**） | 开关状态（默认开）＋缓存上限（256MB）＋**可缓存性判据** |
| 2 | `player/.../exo/ExoMediaPlayer.java` | `setDataSource` 里 `false` → `ExoCacheConfig.isEnabled() && isCacheableUrl(path)` |
| 3 | `player/.../exo/ExoMediaSourceHelper.java` | 上限 512MB → 取配置；目录兜底；建库失败退回直连；挂命中率监听 |
| 4 | `app/.../util/HawkConfig.java` | 新增 `EXO_DISK_CACHE`（默认 true） |
| 5 | `app/res/layout/activity_setting.xml` | 新增「磁盘缓存」开关项（照抄「IJK缓存」那一套） |
| 6 | `app/.../ui/activity/SettingActivity.kt` | 开关逻辑 ＋ 改完立刻推给 player 模块 |
| 7 | `app/.../util/PlayerHelper.java` | `init()` 里同步一次（覆盖"关掉缓存后重启"） |
| 8 | `check_l1box_regressions.sh` | +15 条断言（403 → **418**） |
| 9 | `build_l1box.sh` | dex 符号清单补 6 个（`ExoCacheConfig` / `isCacheableUrl` / `exo_disk_cache` / `exo-video-cache` / `onCachedBytesRead` / `L1Cache`） |

### 为什么开缓存是零风控

风控的实际形态是：**并发连接数↑、请求速率↑、请求顺序乱、单位时间流量↑**。
磁盘缓存这四个维度**一个都不增** —— 它是"播放器本来就要发的请求，顺便在本地留一份副本"，
在**命中时反而减少请求**（已下过的分片不再回源）。这与被否决的"多线程尽速预取"
（并发 3~5、速率 ×10、乱序、流量数倍）是**完全不同的两类东西**。

## 三、🔴 唯一的红线：本机端点必须排除（本批最高危项）

`http://127.0.0.1:9978/l1.m3u8`（净化命中后的本地 HLS 端点）与
`http://127.0.0.1:9978/proxy?...`（网盘源经加固 jar 暴露）这两种地址，
**每一集都是同一个固定地址** —— 集与集的区别只在服务端内存里，不在 URL 上。

而 Exo 的缓存 key 默认取 URI ⇒ 第 1 集播完，缓存里就有一份这个 URL 的清单与分片；
第 2 集请求**同一个 URL** ⇒ **直接命中第 1 集的残留** ⇒ 观感是"换集之后还在播上一集"。

**这不是概率问题，是必然发生的回归。** 所以 `ExoCacheConfig.isCacheableUrl()` 对
`127.0.0.1 / localhost / [::1] / 0.0.0.0` 一律返回 false，闸门里也留了断言防回退。

### 顺带排查过的三个"可能会删缓存"的既有机制（都已确认无冲突）

| 机制 | 位置 | 结论 |
|---|---|---|
| `cleanPlayerCache()` | `App.java` 启动 5 秒后调 | 只删 `ijkcaches/`、`thunder/`、`jpali/Downloads/` 三个子目录，**不碰 `exo-video-cache`** ✅ |
| `clearAllCache()` | `FileUtils.java:397` | 会删整个缓存目录，但**全工程没有任何调用点**（死代码）✅ |
| `StartupGuard` 崩溃循环恢复 | 连续 3 次启动没走完时 | 只删 `home_cache.json` 等首页缓存文件 ✅ |

→ 除"系统设置里手动清除缓存"（预期行为）外，**没有任何自动逻辑会删掉视频缓存。**

### 其它已处理的边界

- rtmp / rtsp：上游走独立 `MediaSource` 分支，根本不经过缓存工厂；判据里再兜一道。
- file / content / asset：本来就不走网络，缓存只会白写一份到盘 → 排除。
- 缓存库建不起来（目录拿不到 / 索引库打不开 / 目录被占用）：`newCache()` 返回 null，
  调用方**退回直连**，绝不因为缓存失败导致播不了。
- 本 fork **没有直播播放界面**（manifest 里无 Live 类 Activity），所以不存在
  "直播清单被缓存 → 播到旧分片"的场景。

### 真机（需要你配合，约 5 分钟）

**测试步骤**（关键在"重播同一集"，首次播放必然不命中）：

1. 随便找一集，**完整看到 20 秒以上**再退出（让分片落进缓存）。
2. **重新点进同一集**（同一个源、同一条线路）→ 这一步才会命中缓存。
3. 再**换 2~3 集**看看，重点确认：**换集后播的是新内容，不是上一集**（高危项）。
4. 去设置页把「磁盘缓存」**关掉**，再播一集，确认还能正常播（关掉不能影响播放）。

**抓取命令**（和批一一样，多加了 `L1Cache` tag）：

```bash
adb shell "nohup logcat -f /data/local/tmp/bj.log -v time L1Cache:I L1Play:I L1Buffer:I L1Diag:I AndroidRuntime:E *:S >/dev/null 2>&1 &"
# 按上面 4 步操作
adb shell "pkill logcat"
adb pull /data/local/tmp/bj.log
```

分析：

```bash
python _l1_batch2_stats.py bj.log
```

**另有一条更硬的证据**（直接看缓存有没有落盘）：

```bash
adb shell ls -la /sdcard/Android/data/com.github.tvbox.osc/cache/exo-video-cache/
```

有文件、有大小 ⇒ 缓存确实在工作。测试完记得把「磁盘缓存」开关拨回**开**（如果第 4 步关过）。

### 判定标准

| 项 | 通过条件 |
|---|---|
| 缓存库建立 | 日志出现一次「磁盘缓存已就绪 上限 256MB」 |
| 命中 | 第 2 步（重播同一集）后出现「命中读取」 |
| **本机端点不缓存**（高危） | 本机端点起播**不得**伴随命中 |
| 换集不串（高危） | 换集后播的是新内容 |
| 关闭有效 | 关掉开关后不再出现缓存日志，且播放正常 |
| 无回归 | 冷启动无崩溃、起播耗时与批一持平 |

### 构建环境：Kotlin 编译改为 in-process（一次性解决）

第一次构建失败在 `:app:compileReleaseKotlin`，报：

```
# There is insufficient memory for the Java Runtime Environment to continue.
# Native memory allocation (malloc) failed to allocate 1048576 bytes for AllocateHeap
Memory: 4k page, system-wide physical 16M... (4348M free)
```

**根因**：本机**页面文件被禁用**（16GB 物理内存，构建期只剩 ~4.3GB），另起一个 Kotlin 守护进程会在原生内存分配上崩溃。
脚本自带的 3 次自动重试**救不回来**（同一根因，不是瞬时故障）。

**处置**：`gradle.properties` 增加一行 ——

```properties
kotlin.compiler.execution.strategy=in-process
```

省掉一整个 JVM 的原生开销，全程只用一个堆。**注意这是"改执行策略"，不是"改堆大小"**：
`org.gradle.jvmargs=-Xmx1536m` 与 `kotlin.daemon.jvmargs=-Xmx1024m` **保持不变**（本机页面文件禁用，
堆不能往上加）。改后构建一次通过（BUILD SUCCESSFUL in 3m23s）。

**顺带确认**：第一次失败时 `:player:compileReleaseJavaWithJavac` 是**通过**的，
`dataBindingGenBaseClassesRelease` 也已生成 —— 说明 player 模块的 Java 改动与布局的 id 都没问题，
失败与代码无关。
