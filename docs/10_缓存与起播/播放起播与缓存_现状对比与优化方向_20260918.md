# 播放起播与缓存：现状对比与优化方向

日期：2026-09-18　状态：**待拍板**（本文只做对比与方案，不动代码）

---

## 一、一句话结论

- **「秒播」做过，且中位已经达标**：三份独立真机日志的点开到出画面中位数是 **1058 / 1061 / 1058 ms**，惊人一致 —— 中位就是 ~1.0 秒。**但长尾不行**：P90 落在 2.1~6.5 秒，最坏 ~8.5 秒。
- **「缓存」基本没做**：Exo 侧的 **512MB 磁盘缓存代码齐备、但从没被启用**（唯一调用点把参数硬编码成 `false`）；IJK 侧有开关但**默认关闭**且**明确排除 m3u8**；而实测的播放地址**绝大多数就是 m3u8** ⇒ **等于零缓存**。
- 所以现在的状态**不是「选了哪套缓存方案好不好」，而是「缓存能力一直没打开」**。

⚠ 同时要纠正一个可能的误解：现在**已经有一个「10 秒后加深」的机制**，而且它就在跑 —— `L1LoadControl`：播放位置 ≥10 秒后，把 Exo 的内存缓冲水位从 50 秒放到 150/240/300 秒（按设备档位）。它加深的是**内存**、不是磁盘，而且是**复用播放器自己的请求流**，所以**零额外流量、零抢带宽**。下文所有方案都要和它比增量。

## 二、起播链路：实测耗时构成（三份真机日志）

链路是**四段严格串行**，前一段不出结果，后一段不开始：

| 阶段 | 做什么 | 中位（3 份日志） | P90 | 最大 |
|---|---|---|---|---|
| ① 取链 | spider 解析出真实播放地址 | 107 / 112 / 82 ms | 388 / 311 / 552 ms | 616 ms |
| ② 净化 | **额外一次** HTTP GET，仅对 m3u8 与本机地址 | 136 / 121 / 149 ms | **2276 / 403 / 2655 ms** | **3551 ms** |
| ③ 播放器就绪 | 建连 + 拉清单 + 首片 + 缓冲到起播门槛 | 743 / 725 / 827 ms | 2367 / 1271 / 3614 ms | 6229 ms |
| ④ **点开→出画面** | ①+②+③ | **1058 / 1061 / 1058 ms** | 5699 / 2066 / 6537 ms | ~8.5 s |

样本量：① 73/54/19 次，② 42/29/13 次，③ 50/34/16 次，④ 50/34/16 次。

**从这张表能读出三件事：**

1. **取链不是瓶颈**（中位 ~100ms）。这轮之前花在取链上的优化已经到位。
2. **③ 是大头（约 70%）**，即"建连 + 拉清单 + 首片 + 等缓冲到门槛"。其中有一部分是我们自己设的**起播门槛 1500ms**（由 2500ms 降下来的）。
3. **② 净化占总时长 10% 左右，但贡献了最长的单段长尾** —— 它是一次**串行在起播之前**、对「能不能播」没有贡献的请求（它的价值是去广告/绕跳转层）。它自己有 2.5 秒超时兜底，所以最坏就是"白等 2.5 秒然后直连起播"。

> 说明：④ 的均值被一个 171 秒的跨会话误配样本污染，**本文一律用中位与分位数**，不用均值。

## 四、缓存现状：三个事实

### 事实 1：Exo 磁盘缓存「写好了，但没开」

`ExoMediaSourceHelper` 里**完整具备**：

- `SimpleCache` + `LeastRecentlyUsedCacheEvictor(512MB)` + `StandaloneDatabaseProvider`
- 目录 `getExternalCacheDir()/exo-video-cache`
- `CacheDataSource.Factory`（已设 `FLAG_IGNORE_CACHE_ON_ERROR`）
- 入口参数 `isCache`

而**全工程唯一的调用点**是：

```java
// player/src/main/java/xyz/doikki/videoplayer/exo/ExoMediaPlayer.java:109
mMediaSource = mMediaSourceHelper.getMediaSource(path, headers, false, errorCode);
//                                                             ^^^^^ 永远 false
```

⇒ **这套缓存从来没生效过**。这是上游 TVBox 的遗留（`git log` 显示该行为初始提交，非本项目改动）。

### 事实 2：IJK 缓存「开关默认关，且不覆盖 m3u8」

```java
// app/…/player/IjkMediaPlayer.java:79
if (Hawk.get(HawkConfig.IJK_CACHE_PLAY, false)) {   // ← 默认 false（设置页「IJK缓存」）
    ... 只对 .mp4 / .mkv / .avi 生效 ...
    // 明确排除 .m3u8：else if (!path.contains(".m3u8") && ...)
    mMediaPlayer.setOption(..., "cache_max_capacity", 60 * 1024 * 1024);  // 60MB
    path = "ijkio:cache:ffio:" + path;
}
```

- 默认**关**；
- 即使打开，**只覆盖直链 mp4/mkv/avi**，**m3u8 一律不缓存**（IJK 的 ffio 缓存是按字节流顺序缓存的，对分片式 HLS 不适用）。

### 事实 3：m3u8 是主流，所以"等于零缓存"

实测取链结果里绝大多数是 `…/index.m3u8`。⇒ **事实 1 未启用 + 事实 2 不覆盖 = 主流播放路径上没有任何缓存。**

### 附：现在**没有任何**多线程下载 / 分片预取 / 预加载代码

全工程搜索 `preload` / `prefetch` / 预加载：**0 命中**。

## 五、把你的目标拆成两半来谈

| 你的目标 | 现状 | 结论 |
|---|---|---|
| **点开秒播** | 中位 **~1.06 秒已达成**；长尾 P90 2~6.5 秒 | **做了一半**：中位达标，长尾要治 |
| **10 秒后开始正式多线程缓存** | **没有**。已有的"10 秒后"是内存水位加深（第 4 条） | **未做**，需要新建 |

**并且必须先讲清一个物理事实**（否则后面的取舍无法判断）：

> **缓存对"第一次点开"没有任何帮助** —— 盘上没有数据可读。缓存只在三种情况有价值：
> ① 同一集内**回退**到已看过的地方；② **再次打开同一集**（跨会话/跨线路）；③ 拖动到**已缓冲范围之外**。
>
> 所以「秒播」和「缓存」是**两个独立目标**。缓存唯一能反哺秒播的路径是：**提前把「下一集」的清单+首片抓下来** —— 见方向 D。

## 六、可优化方向（按风险从低到高）

### 方向 A｜启用已有 Exo 磁盘缓存（零额外流量）

**做什么**：把 `ExoMediaPlayer:109` 的 `isCache` 变成可配置（设置页开关），并挂上已有的 `SimpleCache`。

**为什么风险最低**：`CacheDataSource` 是**"播放器本来就要下的片，顺便写一份到盘"** —— 它**不发起任何额外请求、不占额外带宽**。这和"多线程预取"是本质不同的两件事。

**收益**：同一集内回退/拖动到已播范围 → 命中本地；重看同一集 → 清单+已缓存分片命中，起播显著加快；弱网下已缓存部分不受影响。
**代价**：占存储（512MB LRU，可下调）；首次创建会建一个 SQLite 索引（一次性）。
**不确定点**：HLS 分片 URL 常带 token/时间戳，**跨会话命中率可能不高**；需实测命中率才能说收益有多大。
**必做**：可开关 + 缓存目录大小可配 + 埋点统计命中率（`CacheDataSource` 的 `cacheIgnoredBytes`/`bytesRead`）。

---

### 方向 B｜治起播长尾：净化超时收紧

**做什么**：净化 client 的超时 2.5s → **1.2s**（净化的中位只要 136ms）。

**收益**：把"最坏起播"从 ~3.5 秒削到 ~1.5 秒。**直接命中长尾**。
**代价**：极慢源（>1.2s 才返回清单）的**去广告命中率下降**，那类源会直连、带广告播。
**风险**：低。净化本来就有"超时即直连"的退化路径，缩短只是让退化更早发生。
**可逆**：一个常量，改回一行。

> 这条是**性价比最高的"秒播"改动**：只影响最慢的那一小撮，不影响绝大多数。

---

### 方向 C｜治起播长尾：起播门槛再下调（按设备分档）

**做什么**：`L1LoadControl.START_PLAYBACK_MS` 1500 → 1000/800ms，**只对高配档生效**（低端机维持 1500）。

**收益**：直接提前"出画面时刻"。
**风险（明确）**：门槛降低 = 缓冲更少就播 ⇒ **起播后更容易立刻重缓冲**。而重缓冲门槛是 5000ms，用户会直接感到"卡住"。
**建议**：如果要动，**只在高配档动**，且必须实测"起播后 5 秒内是否出现重缓冲"。不能一刀切。

---

### 方向 D｜「下一集预热」—— 缓存唯一能反哺秒播的路径

**做什么**：当前集播放进入后半段后，**抓取下一集的清单 + 首片**写入缓存。点下一集时清单和首片已在盘上。
**收益**：**连看剧集时"下一集秒开"** —— 这是真正把缓存变成秒播收益的做法。
**代价/风险**：
- 用户不看下一集 ⇒ 白下（流量）。可设闸门："本集已看 >X%" 或 "本集剩余 <N 秒"才触发；
- 需要拿到下一集的取链结果 ⇒ **会触发一次取链**，这属于"提前跑解析"，**必须与"不预热 spider jar"的既有纪律区分开**（见下方"边界"）；
- 必须在 Wi-Fi / 用户开关下才做。
**结论**：**收益最高，但它是本轮唯一会额外消耗流量与请求的方案**，建议单独评估、单独开关。

---

### 方向 E｜你要的「10 秒后多线程缓存」（分片预取）

**先正名**：HLS 播放器拉片本身是"按需、顺序、同一连接"的。传统意义上的"多线程下载"多见于**直链 mp4 的分段下载**。对 m3u8，准确说法是**分片预取（prefetch）**：自己解析清单，用 2~3 个线程把后续分片提前下到本地缓存里。

**做什么**：
1. 起播后计时 10 秒（与现有 `L1LoadControl` 的门槛同源）；
2. 解析当前 m3u8 清单，取后续 N 个分片 URL；
3. 用线程池（**2~3 并发**）经 Exo 官方的 `CacheWriter` 写入**同一个 `SimpleCache`**（必须用 `CacheWriter`，不能自己拼 —— 否则会出现"写了一半就可见"的坏数据，播放器读到残片）；
4. 播放器已有的 `CacheDataSource` 自然命中。

**收益（必须诚实）**：它**与内存深水位高度重叠** —— 内存水位已经能装 150~300 秒内容。真正**新增**的价值只有：
- 越过内存水位（>300 秒）的远距离拖动；
- 跨会话重用（受 token 时效限制）。

**风险（这条最关键）**：**抢带宽**。预取与正在播放的流走同一条出口，在弱网/限速源上，**预取会让正在播的那一段变慢甚至卡住** —— 这与本项目"提高单线路播放成功率"的既有目标**直接冲突**。

**如果要做，必须同时满足这几条约束（缺一不可）**：
- 并发 **2~3**，绝不放任；
- **用"已缓冲时长"当闸门**：缓冲充足才预取，缓冲掉到阈值下**立即暂停预取**；
- 预取窗口有限（如 60~120 秒内容），不无限追；
- **仅 Wi-Fi + 用户开关**（流量）；
- 换集/退出立即取消；
- **必须有埋点**：预取耗时、抢带宽导致的起播/卡顿变化、缓存命中率。

**建议**：先做成"默认关、可开、带完整埋点"的窄版本，真机跑对照，**用数据决定是否保留**。不允许在无数据的情况下把它设成默认。

### 方向 F｜不建议做的

| 想法 | 为什么不做 |
|---|---|
| 把 IJK 缓存开关默认打开 | 它**不覆盖 m3u8**（实测主流地址），等于白开；且 ffio 只对直链 mp4 有效，收益面窄 |
| 净化与播放"并行"（先播原地址，净化回来再切） | 会造成"先播广告再跳走"的观感抖动，且切换要**重新起播**，反而更慢 |
| 提高预取并发数（4/8…） | 抢带宽风险线性上升，与"单线路成功率优先"冲突 |
| spider jar 预热 / 分源并发 / quick 参数 | **已在 ae/ai/al/am 四版被永久否掉**（兑现加固 jar 互杀崩溃），与本题无关，不要借"秒播"的名义复活 |

## 七、边界（必须守住的两条）

1. **"播放器层面的预热/预取" ≠ 已被否掉的"spider jar 预热"**。
   后者被否是因为它**抬高加固 jar 的初始化密度**，兑现了 killall 互杀崩溃链（`L1Box_知识总纲_20260914.md`）。
   方向 D/E 若只碰播放器与缓存（不提前初始化 jar），**不落在被否范围内**；但**方向 D 会触发取链**（= 调用 spider），所以它必须**单独评估**，不能默认开。
2. **不做自动换线路、不做换源引导**（用户既有口径）。

## 八、建议的推进顺序

| 顺序 | 做什么 | 风险 | 预期性质 |
|---|---|---|---|
| 1 | **方向 A**：打开 Exo 磁盘缓存 + 开关 + 命中率埋点 | 最低（零额外流量） | 先把"缓存"这件事从 0 变成 1 |
| 2 | **方向 B**：净化超时 2.5s→1.2s | 低（一行常量） | 直接削掉起播长尾 |
| 3 | **方向 C**：起播门槛按档位下调（仅高配） | 中（可能起播即重缓冲） | 需要真机对照 |
| 4 | **方向 D**：下一集预热（Wi-Fi + 开关） | 中高（额外流量+触发取链） | 收益最高，单独评估 |
| 5 | **方向 E**：10 秒后分片预取 | 高（抢带宽） | 做成可开关窄版本，用数据决定去留 |
