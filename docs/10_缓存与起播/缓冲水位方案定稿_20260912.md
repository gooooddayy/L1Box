# L1Box 缓冲水位方案 · 定稿（2026-09-12）

> 结论：方案可行，且**不需要反射、不需要动 Exo 源码**——Exo 2.18.7 的 `DefaultLoadControl`
> 本身留了足够的扩展点。4GB 手机**不会报错**，但要为它单独加一档，并把策略从"放开字节"
> 改成"**管紧字节、放长时间**"。

---

## 一、先纠正一个前提：现状水位不是 12.5MB，是 **50 秒**

上一轮讨论里我说的"默认 12.5MB"是错的。反编译 `exoplayer-core-2.18.7.aar` 后确认：

| 回调 | 触发点（字节码实证） | 对 `targetBufferBytes` 的影响 |
|---|---|---|
| `onPrepared()` | `ExoPlayerImplInternal.prepareInternal()`，紧跟 `resetInternal` | 无 overwrite 时 = **12.5MB**（`13107200`，`DEFAULT_MIN_BUFFER_SIZE`） |
| `onTracksSelected()` | `ExoPlayerImplInternal.handlePeriodPrepared()` → `updateLoadControlTrackSelection()` | = `calculateTargetBufferBytes()` = **视频 125MB + 音频 12.5MB = 137.5MB** |

而时间参数默认是 `minBufferMs = maxBufferMs = 50000`（50 秒）。`shouldContinueLoading`
的判停条件是：

```
targetBufferSizeReached = allocator.getTotalBytesAllocated() >= targetBufferBytes
buffered < minBufferUs(50s)  → 继续加载
buffered >= maxBufferUs(50s) 或 字节满 → 停止加载
```

**所以现状实际水位 = min(50 秒, 137.5MB ÷ 码率)。**
即：`720p/3Mbps ≈ 50 秒 / 19MB`、`1080p/8Mbps ≈ 50 秒 / 50MB`、`4K/30Mbps ≈ 36 秒 / 137.5MB`。

这件事很重要：**"水位"和"内存"是同一个物理量的两种写法（水位秒数 = 字节 ÷ 码率），
同码率下想让水位翻倍，内存就必须翻倍**——没有第四条路。方案能做的只有两件事：
① 把增量控制在堆预算内的安全比例；② 加运行期护栏，让它在任何设备上都退得回来。

## 二、你问的：对 4GB 手机影响到底多大

### 1) 坏消息：4GB 手机在现有分档里**不在低档**

`DeviceProfile.init()` 的判据是 `ActivityManager.getMemoryClass()`（Java 堆上限）：

```
mb <= 128 → 低档      192 ≤ mb < 256 → 中档      mb >= 256 → 高档
isLowRamDevice() → 强制低档
```

4GB 手机的 `getMemoryClass()` 通常是 **192MB 或 256MB**，`isLowRamDevice()` 返回 false
（那个标记只对 ≤1GB 的 Android Go 机/老盒子为真）。**结论：4GB 机会被当成中/高档，
吃到激进参数**——这正是你担心的那一类。方案必须为它单开一档，见第三节。

### 2) 好消息：`largeHeap` 已开，堆空间比想象的宽

`AndroidManifest.xml:59 android:largeHeap="true"`。这意味着 4GB 机上我们可用堆
（`Runtime.maxMemory()`）通常是 **~512MB**，而不是 `getMemoryClass()` 报的 192MB。
所以"几十 MB 的缓冲"占堆比例是个位数——**只要字节闸门设对，不会 OOM**。

### 3) 影响评估表（以 1080p / 5Mbps 的 4G 场景为例）

| 维度 | 现状 | 保守档（4GB 机）| 判断 |
|---|---|---|---|
| 缓冲内存 | ≈31MB | ≈48MB（闸门值）| **+17MB，占 512MB 堆的 3.3%** |
| 水位（抗卡顿余量）| 50 秒 | min(150 秒, 48MB÷码率) ≈ 77 秒 | 抗抖动能力约 +54% |
| 流量 | 每集约 31MB 起 | 每集约 48MB 起（多下 17MB）| **这是唯一真实代价** |
| CPU | — | 无差异（IO 线程多跑一会儿，解码不变）| 无 |
| 并发连接 | 1 条顺序 HTTP | 仍是 1 条（Exo progressive 单连接）| 无 |
| 崩溃风险 | 0 | 0（有 5 条参数断言 + OOM 护栏 + 压力回落）| 见第四节 |

> 流量这一项请你自己拍板：**4G 上网每集多耗 15~20MB**。如果介意，方案里预留了
> 一个一行的开关条件"仅在 WiFi 下进入阶段二"（自动判断网络类型，不是设置页开关）。

### 4) 一个反直觉但有利的点

对**高码率**源（4K/30Mbps），新的字节闸门 96MB 比 Exo 默认的 137.5MB **更紧**：
现状 36 秒 / 137.5MB → 改后 96MB ÷ 码率 ≈ 25 秒，但内存**下降 41MB**。
也就是说：**低码率源水位变长，高码率源内存变省**，不会两头都变差。

## 三、定稿方案

### 3.1 分档参数表（唯一权威表）

| 档位 | 触发条件（实际实现）| 起播门槛 | 阶段一（0~10 秒）| 阶段二（10 秒后）| 字节闸门 | 相对现状 |
|---|---|---|---|---|---|---|
| **关闭**（完全不接管）| `heap ≤ 128MB` 或 `isLowRamDevice()` | 默认 2500ms | 默认 50 秒 | **不升级** | 默认 137.5MB | **与现状完全一致，零风险** |
| **保守**（低端 / 4GB 机）| `MemTotal ≤ 4608MB` | **1500ms** | 50 秒（= 现状）| **150 秒** | **48MB** | 内存 +0~17MB |
| **标准** | 其余（`heap ≥ 192MB`）| **1500ms** | 50 秒 | **240 秒** | **72MB** | 内存 +0~22MB |
| **激进** | `heap ≥ 256MB` 且 `MemTotal ≥ 7168MB` | **1500ms** | 50 秒 | **300 秒** | **96MB** | 内存 +0（高码率反而 -41MB）|

> 阈值取 `MemTotal` 而非标称内存：4GB 标称机实测约 3.6~3.9GB、8GB 标称机约 7.2~7.8GB（系统保留）。
> 另有运行期两道闸门：开机时可用堆 < 96MB 直接不接管；升档时可用堆须 ≥ 字节水位 × 3，否则维持现状。
> **4G 上网也进阶段二**（已确认，按"抗卡顿最好"取舍，代价是每集约多耗 15~20MB 流量）。

* `totalMem` 取自 `ActivityManager.MemoryInfo.totalMem`（API 16+），阈值 4.5GB 是为了兼容
  4GB 标称机实际报 3.6~3.9GB 的情况。
* 新增的 `totalMem` 判定**只用于缓冲档位**，不改动现有 `tier()`（搜索/详情/线程池并发
  一律不变），避免连带风险。

### 3.2 为什么"前 10 秒"和"10 秒后"能是两个水位

Exo 的 `minBufferMs / maxBufferMs / targetBufferBytes` 都是**构造时定的 final 值**，
运行期换不了整体，换 LoadControl 实例又会让新旧分配器不一致（旧 `SampleQueue` 用旧
分配器，新 control 读新分配器计数 → 状态错乱）。

所以实现走"**同一个 LoadControl，只加一道自有字节闸门**"：

```java
class L1LoadControl extends DefaultLoadControl {       // 放在 player 模块
    private volatile boolean escalated;
    @Override public boolean shouldContinueLoading(long pos, long bufferedUs, float speed) {
        if (pos < ESCALATE_AT_US) {                    // 每集起播归零 → 自动复位
            escalated = false;
            if (bufferedUs >= STAGE1_US) return false; // 阶段一 = 现状 50 秒，一字不差
        } else if (!escalated && allowEscalate()) {
            escalated = true;                          // 放开 → 走基类（时间上限已放大）
            allocator.setTargetBufferSize(deepBytes);
        }
        return super.shouldContinueLoading(pos, bufferedUs, speed);
    }
}
```

要点：
* **阶段一就是现状本身**（50 秒），前 10 秒体验与今天 100% 相同，不存在"新引入的坏情况"。
* **升级触发点很干净**：`shouldContinueLoading` 每次都被传入 `playbackPositionUs`，
  不需要 Activity 生命周期、不需要定时器、不需要跨模块回调；切集后位置归零，
  新一集自动重新走"前 10 秒保守"。
* 时间上限放宽靠构造参数（`minBufferMs = maxBufferMs = 150/240/300 秒`），
  字节闸门靠自有字段——**两者都不碰 Exo 的 private 字段**。

### 3.3 三级兜底（"不报错"靠这三层，不靠机型运气）

**第一层 · 参数不变式（静态、构建期就能证）**
反编译出的 5 条断言（`Assertions` 会抛 `IllegalArgumentException`）：

```
bufferForPlaybackMs >= 0
bufferForPlaybackAfterRebufferMs >= 0
minBufferMs >= bufferForPlaybackMs
minBufferMs >= bufferForPlaybackAfterRebufferMs
maxBufferMs >= minBufferMs
```
我们的取值 `max = min = 150000/240000/300000`、`start = 1500`、`afterRebuffer = 5000`
**逐一满足**。并且会把这条不变式写成构建期闸门脚本断言（改参数改坏了直接构建失败），
所以"参数写错导致播放崩溃"这条路径被彻底堵死。

**第二层 · 升级前的可用堆守门（运行期）**

```java
long avail = Runtime.maxMemory() - (Runtime.totalMemory() - Runtime.freeMemory());
if (activityManager.MemoryInfo.lowMemory) → 不升级
deepBytes = clamp(档位值, 下限 32MB, 上限 avail / 3);   // 缓冲最多用掉 1/3 可用堆
if (avail < 档位值) → 夹小后再升，而不是硬上
```

**第三层 · 内存压力回落（60 秒冷却）**
`App.onTrimMemory(>= TRIM_MEMORY_RUNNING_LOW)` 与 `onLowMemory()` 已经存在
（`App.java:163-193`，现在只调 `DeviceProfile.markMemoryPressure()`），在同样两处追加
`L1LoadControl.onMemoryPressure()`：

* 立刻调 `DefaultAllocator.setTargetBufferSize(24MB)` → **把空闲块还给堆**
  （字节码：`if (new < old) trim()`，只释放未被引用的块，**正在播放的数据一块都不动**）；
* 进入 **60 秒冷却期**：这期间强制停在阶段一（50 秒）不再加深。
* **为什么是冷却而不是"本次进程永久关闭"**：`TRIM_MEMORY_RUNNING_LOW` 在列表里滚几张图就会触发，
  若设成永久关闭，最需要它的低端机反而永远用不上深水位。而 OOM 风险本来就由第二层的
  「可用堆 ≥ 水位 × 3」守门挡住 —— 内存还紧张时它根本升不上去，冷却只是让节奏更稳。
