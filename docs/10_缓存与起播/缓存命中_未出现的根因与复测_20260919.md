## 二、根因（源码级，已确认）

**这个 App 的"退出应用"会直接杀进程：**

`app/src/main/java/com/github/tvbox/osc/ui/activity/MainActivity.kt:95`

```kotlin
private fun confirmExit() {
    if (System.currentTimeMillis() - exitTime > 2000) {
        ToastUtils.showShort("再按一次退出程序")   // ← 首次按返回：只提示
        exitTime = System.currentTimeMillis()
    } else {
        ActivityUtils.finishAllActivities(true)
        Process.killProcess(Process.myPid())      // ← 2 秒内再按一次：直接杀进程
        exitProcess(0)
    }
}
```

⇒ **在首页连按两次返回（2 秒内）= 进程被杀**。下次打开就是**冷启动**，而冷启动按设计**必然清理缓存**。

**这正好解释了上一轮的 3 次进程重启**：为了"退回首页"多按了返回，越过了首页、退到桌面并杀掉了进程。

**要区分清楚（这是本轮唯一的关键）**：

| 操作 | 进程 | 缓存 |
|---|---|---|
| 播放页按返回 → 回到**详情页**（剧集列表） | 活着 | **保留 → 可命中** ✅ |
| 详情页按返回 → **首页** | 活着 | 保留 → 可命中 ✅ |
| 首页按返回 → 提示「再按一次退出程序」 | 活着 | 保留 ✅ |
| 首页**2 秒内再按一次** → 退到桌面 | **被杀** | **下次启动清掉** ❌ |
| 从后台划掉 App | **被杀** | **下次启动清掉** ❌ |

> `PlayFragment` 由 `DetailActivity` 托管（`DetailActivity.java:119/190`）⇒ 播放页按一次返回**只会回到详情页**，是安全的。

## 五、必须诚实说明的一点设计后果

「完全退出自动清理」是你明确要的（防止占用户存储），但它带来一个必然代价：

> **同一次 App 会话内**重看 / 拖回看过的部分 / 切集再切回 → **能命中，快**（批二实测快 8.5 倍）
> **退出到桌面（或划掉 App）之后再进来再看** → 缓存已被清，**要重新下载**

也就是说"上次看过、这次打开还能秒出"这个场景是**主动放弃的** —— 这正是你上一轮拍板接受的取舍（09-19「完全退出软件要自动清理」）。如果你哪天希望拿回跨会话的缓存，就是把清理判据改成"只在划掉 App 时清"或"超过 N 天清"，届时再说。

### 7.5 设计口径最终确认（用户 09-19 明确）

> **只要没完全退出软件 → 缓存生效**（同一次会话内：换集切回 / 拖回看过的段 / 从详情页重进同一集）
> **用户自己完全退出（划掉任务 / 强停） → 缓存清掉**（在**下一次打开软件**时归还存储）

最后一处差别只在**归还时机**：不是"划掉那一瞬间"，而是"下次打开那一瞬间"。原因：Android 对"划掉"不给应用任何回调（除非常驻前台服务），只有"进程启动"是可靠信号。残留最多 256MB，且位于 `Android/data/com.github.tvbox.osc/cache/`（系统缓存目录，空间紧张时系统也会回收）。

## 八、附：为什么清理不提前到「划掉那一刻」（用户 09-19 12:36 追问，技术论证）

**先纠正一个直觉**：难点**不在删除**。实测删除 252MB / 55 个文件耗时 **< 0.3 秒**（日志里那 10 秒是刻意延迟、错开起播 IO）。真正的难点是"**哪一刻知道用户划掉了**"。

### 8.1 三条路的对比

| 路径 | 能否感知"划掉" | 清理时机 | 可靠性 | 新增代价 |
|---|---|---|---|---|
| **现在这样**（`App.onCreate` 清理） | 不能 | 下次打开软件 | **100%** | 无 |
| 常驻后台服务 + `Service.onTaskRemoved()` | **能** | 划掉那一瞬间 | 中（服务会被系统停掉 ⇒ 退回现状） | notification 常驻 + manifest/权限/通知渠道 + 多一个崩溃面 |
| 靠最后一个 Activity 的 `onDestroy` | 看设备 | 不确定 | **低** | 无组件代价，但会**误清** |

### 8.2 三个硬事实

1. **Android 没有"应用被划掉"的广播**。进程消失的那一刻，已经没有运行代码的地方了。唯一官方回调是 `Service.onTaskRemoved()`，**前提是那一刻正好有 Service 在运行**。本 fork 是纯 Activity 架构（零 Service）⇒ 收不到，不是没写，是没人能接。
2. **"用户划掉"与"系统因内存压力杀后台"给应用的信号完全相同**（都是没有信号）。而后者恰恰是"用户还会点回来"的场景 ⇒ 一旦改成"进后台就清"，等于连"会话内命中"一起放弃。
3. **两条诉求在无服务前提下互斥**：要"切后台回来还能命中" ⇒ 后台期间不能删；要"划掉瞬间就删" ⇒ 必须有组件活到那一刻（那就是常驻/短命服务）。

### 8.3 唯一"代价较小"的候选（已评估，仍不推荐）

**短命服务**：退出后台时 `startService`，只待命几分钟、不挂通知栏；用户在这窗口内划掉就能收到 `onTaskRemoved`，同步改名 + 立即删（0.3s 内完成，来得及）。
- 仍不覆盖"待命窗口过后才划掉"的情况（退回现状）；
- 仍需新增 Service 组件 + manifest 改动 + 通知渠道（targetSdk 28 起前台服务须渠道）；
- 加固 jar 的 `killall` 互杀环境里，多一个进程组件 = 多一个崩溃入口 —— 与**「减少崩溃必须、加速锦上添花」**的项目大原则冲突。

**结论：收益仅为"把归还时机从下次打开提前到划掉后几分钟"，成本是一个常驻/半常驻组件与新的崩溃面 ⇒ 不做。** 维持"下次打开时归还"。
