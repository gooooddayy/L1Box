### 2.1 修了什么 bug

**原公式（自相矛盾）**：

```java
// 创建时：深水位字节 = 创建那一刻的可用堆 ÷ 3
int bytes = (int) Math.min(DEEP_BYTES[tier], Math.max(MIN_DEEP_BYTES, avail / AVAIL_FACTOR));

// 升档时（播满 10 秒后）：要求当前可用堆 ≥ 深水位字节 × 3
if (availBytes() >= (long) deepBytes * AVAIL_FACTOR) { escalated = true; }
```

两条合起来等价于要求 **「播了 10 秒之后的可用堆 ≥ 播放器刚创建时的可用堆」** —— 而播放器在这 10 秒里已经吃掉了一块内存，运行时可用堆**必然更低** ⇒ 条件结构上就难成立，而且失败时**一行日志都没有**。

**实测证据**（`_be_test1.log`，15 次会话）：

| 项 | 数值 |
|---|---|
| 升档日志 | **4 条** |
| 在播 ≥10 秒（够条件）的会话 | **6 次** |
| 失败时的日志 | **无** |

**现在（修正后）**：

```java
// 字节闸门按「堆上限」的比例定，而不是拿"创建那一刻的可用堆"去除
long budget = Runtime.getRuntime().maxMemory() / 4;
int bytes = (int) Math.min(DEEP_BYTES[tier], Math.max(MIN_DEEP_BYTES, budget));

// 守门判据 = 可用堆 ≥ 水位字节 + 余量(32MB)，且不低于 96MB 下限
long need = Math.max((long) deepBytes + RESERVE_BYTES, MIN_AVAIL_BYTES);
if (availBytes() >= need) { escalated = true; }
```

> **三重兜底一条没动**：可用堆不足 96MB 不接管、内存压力回落 + 冷却期、分配器目标尺寸下调触发 trim。只改了"守门基准"，没放宽安全边界。

## 三、为什么必须先做这一步（而不是直接调数值）

现有日志里 **起播中位 827ms（本批统计口径）/ 1058ms（上一版口径），都低于 1500ms 门槛** —— 这在逻辑上不该发生。

最可能的原因：**Exo 的 `bufferedDurationUs` 对 HLS 是分片粒度的** —— 一整片下载完才跃升，如果分片是 6 秒，那么缓冲从 0 直接跳到 6000ms，**1500ms、2500ms 门槛会在同一瞬间一起满足** ⇒ **门槛数值对起播时刻几乎无影响**。

如果是这样，批 3 的"自适应门槛"就**不能只改数值**，得换判据。所以批 3 之前必须先拿到「起播放行缓冲量」的真实分布 —— 这就是本批的意义。
