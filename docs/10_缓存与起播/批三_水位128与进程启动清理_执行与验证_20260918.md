## 一、本批做了什么（两件事，一起出包）

### 改动 1：Exo 深水位 96MB → 128MB

| 项 | 值 |
|---|---|
| 文件 | `player/src/main/java/xyz/doikki/videoplayer/exo/L1LoadControl.java` |
| 改动 | `DEEP_BYTES` 第三档（标准档）`96 << 20` → `128 << 20` |
| 时段水位 | 不变，仍 300 秒（只在播满 10 秒后放开） |
| 低端两档 | **刻意不动**（48MB / 72MB）—— 低物理内存机加深水位只会挤占播放器其他开销 |

**依据（这条决定了风险定级）**：Exo 自己的默认常量是 `DEFAULT_MUXED_BUFFER_SIZE = 137.6MB`、
`DEFAULT_VIDEO_BUFFER_SIZE = 125MB`。也就是说**改造前的 96MB 反而低于 Exo 官方默认 30%**，
128MB 仍在官方默认之下。所以这不是"少见的怪招"，而是常规量级 —— 风险点是**总流量上限 +33%**，
而顺序、并发、请求速率三个维度完全不变（水位加深只是让**同一条下载流**走得更远）。

**生效条件（重要）**：

```java
long budget = Runtime.getRuntime().maxMemory() / 4;
int bytes = (int) Math.min(DEEP_BYTES[tier], Math.max(MIN_DEEP_BYTES, budget));
```

本机实测 `堆上限=512MB` ⇒ `budget = 128MB` ⇒ 恰好落在 128MB；
**低堆设备会被自动夹小**（例：堆上限 384MB 的机器 → 96MB），不会硬顶。

**升档守门**：需 `可用堆 ≥ 128 + 32 = 160MB`。本机实测播放中可用堆 **384~484MB**，富余 220MB 以上。

### 改动 2：进程冷启动清理上一次会话的磁盘缓存

| 项 | 值 |
|---|---|
| 新增 | `ExoCacheConfig.purgeStaleOnProcessStart(Context)` |
| 调用点 | `App.onCreate()`（紧跟 `PlayerHelper.init()`，此刻尚无任何播放器实例） |
| 判据 | **进程结束**（Android 无"应用退出"回调，但"进程启动"是精确信号） |
| 手段 | **改名**（毫秒级，与目录大小无关）→ 后台**延迟 10 秒**递归删 |

**口径与用户操作的对应关系**：

| 用户操作 | 进程 | 缓存 |
|---|---|---|
| 退播放页 / 切集 / 切后台 / 回首页 | 还在，`onCreate` 不跑 | **保留 → 重看仍命中** ✅ |
| 划掉最近任务 / 强制停止 / 被系统回收后再进 | 重建，`onCreate` 跑 | **清掉 → 空间归还** ✅ |

**为什么用改名而不是直接递归删**：
- 删 200~300MB 要 0.5~2 秒。同步删会**拖慢启动**；与播放并发又会**争同一个目录**。
- 改名只动一个目录项 ⇒ **零等待**。改完播放器自动新建同名新目录 ⇒ **写的是新目录、删的是旧目录，零竞态**。
- **幂等**：删到一半被杀，下次启动会扫到残留的 `exo-video-cache-old-*` 继续删。

**目录名单一来源**：新增常量 `ExoCacheConfig.CACHE_DIR_NAME`，创建点
（`ExoMediaSourceHelper.newCache`）与清理点共用。两处各写一份字面串迟早漂移，
而漂移的后果是"清了但没清到"或"清了却还在写"，都极难排查 —— 闸门里留了 `mustnot` 防回退。

**IO 让位**：删除线程 `Thread.sleep(10_000)` 后才开始，且每个顶层分片目录之间 `sleep(200ms)`，
把一次长 IO 拆成若干短脉冲 —— 冷启动后用户很可能立刻点播，避免与起播抢磁盘。

## 三、风险清单

| # | 风险 | 影响 | 处置 |
|---|---|---|---|
| 1 | `renameTo` 失败（个别 ROM 对外置存储限制） | 这次没清干净 | 打 warn 并跳过，**绝不影响播放**；下次启动再试 |
| 2 | 外部存储与内置存储基准不一致（启动时外置未挂载 → 清内置、创建在外置） | 清理空跑一次 | 两处 fallback 顺序一致（外置优先）；极端场景概率极低，代价只是"这次没清"，不影响播放 |
| 3 | 删除线程与起播抢 IO | 起播变慢 | 延迟 10 秒 + 每个分片目录间隔 200ms；且改名保证删的是**旧目录**，与播放读写的目录不同 |
| 4 | 用户播放中 App 被系统回收 → 下次清理掉缓存 | 重看要重新下载 | **符合用户口径**（进程结束即视为完全退出），且不影响本次播放 |
| 5 | 128MB 在低堆设备上仍想加深 | 内存不足 | `maxMemory()/4` 已自动夹取；升档守门（需 160MB 可用堆）+ 内存压力回落 + 冷却期三重兜底不变 |
| 6 | 128MB 导致升档守门过不去 | 水位实际停在 50 秒 | 打「未升档 @ Xs：可用堆 … < 需要 …MB」，**日志直接给出是否需要退回 96MB** |
| 7 | 清理把正在用的目录也改掉 | 播放中断 | 改名发生在 `onCreate`，**此刻播放器尚未实例化**；单进程（manifest 无 `android:process`） |

**已确认无冲突的既有清理机制**（本批改动前已排查过）：启动 5 秒后的
`FileUtils.cleanPlayerCache()` 只删 `ijkcaches/thunder/jpali` 三个目录；`clearAllCache` 是全工程零调用
的死代码；崩溃恢复只删首页缓存文件。

## 四、明确不做的（本轮拍板）

| 项 | 结论 | 原因 |
|---|---|---|
| **按需预取** | **不做** | Exo 在拖动进度条后**本来就会**从新位置继续加载到水位上限 —— 日志里 `缓冲升档 @ 212s / @ 222s / @ 479s` 都不是从 0 开始的位置，正是拖动/续播后仍在往后加载。现有代码已在做，做了等于白做 |
| 独立并行预取器（L2） | 不做 | 会多一路并行下载 ⇒ 并发/速率/乱序三个维度同时异常，才是真正会被风控盯上的形态 |
| 无限预取（L3） | 不做 | 无上限、无边界 |
| 净化超时收紧 | 不做（早前拍板） | 牺牲广告命中率不值 |
| 起播门槛调整 | 不做（批一数据推翻） | HLS 缓冲量整片跃升，门槛数值几乎不起作用 |
