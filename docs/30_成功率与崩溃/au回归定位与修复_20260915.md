# au 回归定位与修复（2026-09-15）

> 命名说明：第二批原本被记作 **bt**，现按序列统一改称 **au**。本文取代原《bt 版真机测试记录》。

**一句话结论**：第二批新增的 **C1「补同源 Referer」把源站 Referer 写进了播放器的默认请求头**，而清单里的
分片实际托管在**第三方 CDN**（本次实测为小红书 `xhscdn.com`）。该 CDN **拒绝外站 Referer → 403**，
分片集体拉不到 ⇒ 起播失败。**根因已用真机对照闭环，并已修复。**

---

## 一、闭环对照实验（这是判定"是否回归"的唯一硬证据）

**为什么要重做对照**：上一轮做过一次"at 成功 / bt 失败"的对比，但事后核对发现**两次不是同一集**
（at 是 ep=2、bt 是 ep=0）——不同集的清单内容不同、净化结果也不同，**那次对照不成立**，不能作为结论。

**本次对照条件（三组严格一致）**：
- 同一台设备（测试机）、同一 WiFi
- 同一站点 `WexAiReBo`，同一线路 `线路二 (点击换线)`，同一集 `ep=0`
- 同一播放路径：取链 → **净化命中** → 起播 `http://127.0.0.1:9978/l1.m3u8`

| 组 | 版本 | 轮次 | 结果 | 起播耗时 | 实际命中节点 |
|---|---|---|---|---|---|
| 1 | **at** | 3 | ✅ 3/3 | 411 / 244 / 302 ms | `111.170.141.203` |
| 2 | **au** | 4 | ❌ **0/4** | 全部走完兜底链后提示 | `43.248.96.62`、`111.170.9.17` |
| 3 | **at** | 3 | ✅ 3/3 | 410 / 282 / 272 ms | **`43.248.96.62`、`111.170.9.17`** |

**第 3 组用的是第 2 组失败时的同两个节点 IP** ⇒ 下列解释全部被排除：

**结论：au 存在确定的、可复现的回归。at 6/6 成功，au 4/4 失败。**

## 二、根因：Referer 污染 → 跨域 CDN 403

### 2.1 关键观察：分片不在源站，在第三方 CDN

从设备内置代理读出**净化后的清单**（`adb forward` + 请求本地 `/l1.m3u8`）：

```
#EXTM3U
#EXTINF:6.000000,
https://sns-open-qc.xhscdn.com/professionalpc/104101uo31vschgdi5006hf7p9s000000340of6k0ep3ko
```

- 源站（取链地址）：`http://43.248.96.62:9090/nby/m3u8/getM3u8`
- **分片地址：`https://sns-open-qc.xhscdn.com/...`（小红书 CDN）—— 与源站完全不同域**

### 2.2 决定性实测：带外站 Referer 就被 403

直接请求该分片地址，只改 Referer 一个变量：

| 请求分片时带的 Referer | 结果 |
|---|---|
| **不带**（= at 的行为） | **200 OK**，正常返回数据 |
| `http://43.248.96.62:9090/`（= **au 的行为**） | **HTTP 403 Forbidden** |
| `https://www.xiaohongshu.com/` | 200 OK |

结论：该 CDN **对空 Referer 与自家 Referer 放行、对外站 Referer 拒绝**。

### 2.3 代码级定位：Referer 是怎么进到分片请求上的

```java
// PlayFragment.playUrl()
final HashMap<String, String> headers = fillMissingHeaders(url, rawHeaders);  // ← 补出 Referer
...
startPurified(url, url, content, headers, t0);   // ← 补过的头一路传给播放器
    → startPlayUrl(localHlsUrl(), headers)
        → mVideoView.setDataSource(url, headers)  // Exo: setDefaultRequestProperties(props)
```

`setDefaultRequestProperties` 是**默认请求头**，会对该播放器的**所有**请求生效 ——
包括本地清单请求，以及**清单里那些指向 CDN 的分片请求**。于是分片请求带上了
`Referer: http://43.248.96.62:9090/`，被 CDN 拒绝。

**失败症状完全吻合**：清单能取到（净化 173ms 命中），播放器却拉不到数据 →
约 6 秒后 Exo 报错 → 回退直连 → 变形 https → 降级 IJK → 试尽。

> 附：清单请求本身对 Referer 不敏感（带不带都返回 200 / 同样内容），
> 所以**只在清单层观察是发现不了这个问题的**——必须看到分片那一层。

## 三、修复

**原则**：补出来的 Referer 只给「净化预取」那一次请求用，**绝不进入播放器**。

| 位置 | 改动 |
|---|---|
| `playUrl` | 新增 `raw = rawHeaders`（站点原始头）；净化预取仍用补全后的 `headers` |
| `playUrl` 的 6 个播放出口 | 一律传 `raw`（`startPlayUrl(url, raw)` ×5、`startPlayUrl(finalforwardurl, raw)`） |
| `startPurified` 调用点 ×2 | 传 `raw` |
| `startPlayUrl` 汇聚点 | 删除 `fillMissingHeaders(...)`，改为直接沿用调用方给的头 |
| `fillMissingHeaders` | 保留（仍服务于净化预取），文档注释改为"仅供净化预取" |

**收益与代价**：
- ✅ 消除回归：播放侧请求头与 at **完全一致**，零新增风险
- ✅ 保留 C1 的主要收益：净化预取仍带 Referer（防"防盗链导致取不到清单"）
- ⚠️ 放弃 C1 在"直连播放"上的补 Referer（实测风险 > 收益：跨域 CDN 极普遍，
  而"严格防盗链 + 同域分片"较少；at 从来没有它，实际体验良好）

**闸门固化**（`check_l1box_regressions.sh` Y 节新增 4 条，防止再被塞回播放链路）：
```
must    startPlayUrl\(url, raw\);                        净化各出口必须用站点原始请求头
must    startPurified\([^)]*content, raw, t0\);          净化收尾必须用站点原始请求头
mustnot startPurified\([^)]*content, headers, t0\);      净化收尾不得把补全后的请求头交给播放器
must    final HashMap<String, String> headers = rawHeaders;  播放汇聚点不得再补 Referer
```

## 四、对上一轮结论的更正（重要）

上一轮记录里写着看门狗判据漏洞会让界面"**永久转圈、再无人接管**"。**这句话不准确，现更正**：

- **判据漏洞成立**：`mStartWatchdog` 的判据是「`speed > 0` 即算有进展」，
  而"一直在下数据、却始终不播"同样满足；20.0s 时判定"有进展"后 `return`，
  代码里**没有重新 arm**（已核对 `PlayFragment:233-236`）⇒ 对该次播放而言确实是终态。
- **但不等于永久死锁**：Exo 自身最终会在约 49s 报错，随后进入兜底链。
  **准确表述是：保护被延后约 19 秒（应为 30s 判死，实际拖到 ~49s），且中间界面无任何反馈。**

## 五、本轮顺带确认的其它问题（未修，待排期）

| # | 问题 | 证据 / 说明 |
|---|---|---|
| 1 | **降级阶梯带着坏地址重播** | 失败链里"变形 http↔https"把 `mPlayingUrl` 改成 `https://…:9090`（该端口不是 https，必不通），紧接着"降级到 IJK（第 1/1 档）"用的正是这个坏地址 ⇒ 白白浪费最后一次机会。修法：降级前把地址恢复成"回退直连"或原始地址 |
