# 目标对齐 + 断触原因分析（2026-09-30）

> 用户原话（本轮）：
> 「左边是我**快速滑动的时候会断触**，我滑动过程中不加载站点，滑动结束才加载，
> 我要的是**快速滑动不断触，无论快滑慢滑都不断触**，
> **加载不加载主要是有断触的感觉**；
> 右侧是我要的就是**用户一滑动就按照惯性停下就行，除非是到顶部和底部**，
> **惯性速度和滚动长度根据用户滑动速度来决定**。
> 我们先确定一下目标，和导致的原因是什么」

## 〇、⚠️ 先做一次自我纠正：cl 版**修错了方向**

| cl 版改了什么 | 它解决的问题 | 是不是用户的主诉？ |
|---|---|---|
| L-A/L-B：fling 上界 + 竖向中止 | "滑到中部突然跳到底部"（数据里的 517→1511） | ❌ **不是** —— 用户主诉是**断触**（手感），不是跳变 |
| L-C：放开滑动的追加 | "滑动中站点不出现" | ❌ **不是** —— 用户明确说「**加载不加载主要是有断触的感觉**」，即加载不是重点 |
| R-A：关掉选中项居中 | 可能的一次额外居中滚动 | ⚠️ 依据本就弱 |

**根因**：我上一轮把数据里**最显眼**的东西（517→1511 跳变、8.4 秒零更新）当成了主因，
但用户真正在意的是一件**数据里没有直接证据**的事 —— **手势被中断（断触）**。
⇒ 所以「还是一样卡」是合理的：**改的不是那个东西**。

**这一轮先不动代码**，按用户要求把**目标**和**原因**对齐清楚。

## 一、目标（按用户口径复述，请确认）

### 左栏

| # | 目标 | 明确**不是**目标 |
|---|---|---|
| **G-L1** | **任何速度下滑动都不断触** —— 快滑、慢滑、连滑，手指与内容始终连着 | ~~"滑动中要加载站点"~~（用户明确说不纠结） |

### 右栏

|---|---|

## 二、左栏断触：原因分析

### 2.1 先排除掉一个（cl 版已经证伪的）

| 候选 | 判定 |
|---|---|
| "搜索结果插入 chip 触发 ACTION_CANCEL" | ❌ **排除**。cl 版已把追加放开（滑动中不再阻塞），**用户实测无改善** ⇒ 断触不是插入造成的 |

> 这一条很重要：它说明 **`addView` 追加本身不会断触**（与 Android 语义一致 —— 追加不移除也不移动已有子 View）。

### 2.2 剩下的候选（按可能性排序）

#### ⭐⭐ A. `needScroll` 从 `false` → `true` 的**一次性翻转**

**代码依据**（`DslTabLayout.kt`）：

```kotlin
val needScroll: Boolean
    get() = if (tabEnableSelectorMode) true else { … else maxScrollY > 0 }   // 竖向：内容总高 > 视高

override fun onInterceptTouchEvent(ev: MotionEvent): Boolean {
    if (needScroll) {
        intercept = super.onInterceptTouchEvent(ev) || _gestureDetector.onTouchEvent(ev)
    } else {
        intercept = super.onInterceptTouchEvent(ev)     // ← 不接管
    }
}

override fun onTouchEvent(event: MotionEvent): Boolean {
    if (needScroll) {
        _gestureDetector.onTouchEvent(event); return true   // ← 自己处理
    } else {
        return (isEnabled && super.onTouchEvent(event))     // ← 完全不处理滚动
    }
}
```

**ck 实测**：这个翻转点就在 **chip 从 17 → 18 个**之间（第 2 轮：`chip=17 可滚=false 上限=0`
→ `chip=18 可滚=true 上限=91`）。

**后果**：手势进行中若发生翻转，`onInterceptTouchEvent` / `onTouchEvent` 的处理路径**整体切换** ——
ViewGroup 开始拦截时会向子 View 发 **ACTION_CANCEL**，且接管后的滚动基准点从"翻转那一刻"算起。

**为什么符合"快速滑动才断"**：慢速滑动时，chip 早就建完了（翻转早已过去）；
而**每次新搜索** chip 都从 0 涨到 40 ⇒ **每次都必然翻一次** ⇒ 若此时正在滑，就断一次。

**待验证**：需要看到"翻转时刻"与"CANCEL 时刻"是否重合。

#### ⭐⭐⭐ B. `removeAllViews()`（清空重建）

**确定会断触**（触摸目标集体消失）。触发条件是"重搜"（`queueSiteTabsReset`）。
若用户在**同一轮搜索内**滑动也断触，则 B 不是主因；若断触总伴随着"重新搜索"，则 B 是主因。

#### ⭐ C. 其余干扰点（依据不足，仅登记）

| 点 | 说明 |
|---|---|
| `setCurrentItem(0, true, false)`（重建时） | 会改选中项 → 触发库内滚动/布局 |
| `parent.requestDisallowInterceptTouchEvent(true)` | 只在 `onScrollChange` 里调 ⇒ **手势被判定为滚动之前是空窗期** |
| `dispatchTouchEvent` 的触摸记账 | 只读不拦截（不会造成 CANCEL） |

## 三、右栏顿挫：原因分析

### 3.1 先把"控件本身有问题"这条路查干净了

| 查了什么 | 结果 |
|---|---|
| `TvRecyclerView` 有没有重写 `fling` / `onTouchEvent` / `onInterceptTouchEvent` / `dispatchTouchEvent` | **全都没有** ⇒ 触摸惯性 = 标准 `RecyclerView` 行为 |
| 有没有 `SnapHelper` / `attachToRecyclerView` / `setOnFlingListener`（"按格停"的典型来源） | **全项目 0 处** ⇒ 不存在吸附 |
| `TvSmoothScroller` 会不会干扰触摸 | 它只被 `smoothScrollToPosition` 用（**程序化滚动**），触摸路径不经过 |
| `onScrollStateChanged` 里有没有额外滚动 | **没有**，只有"触底加载更多" |
| `itemAnimator` | 已置 `null` ✅ |

⇒ **右栏的惯性逻辑是干净的。** 那"顿挫"只能来自**外部对它的干预**。

### 3.2 可能的干预点（按可能性排序）

#### ⭐⭐ D. 滑动期间**持续插入数据**（每 120ms 12 条）

`flushSearchResults` 的节流：`SEARCH_FLUSH_MS=120`、`SCROLL_BATCH_MAX=12`
⇒ 滑动中每 120ms 一次 `addData` → `notifyItemRangeInserted` → RecyclerView 重新布局并更新锚点。
**注意**：这类干扰**不会体现在帧耗时上**（帧数据显示平均 5~7ms），但会改变滚动的连续性 ⇒
**"帧正常、体感顿挫"完全可能**。

⚠️ **但有一个反证**：ck 第 2 轮所有 `停稳收尾` 的 `待落` 都是 **0** ⇒ 用户那几次滑动时**没有**结果待插入。
⇒ 所以 D 至少**不是唯一原因**，需要用"搜索中滑 vs 搜索后滑"的对照来确认。

#### ⭐ E. 停稳瞬间的图片动作

IDLE 时 `prefetchAroundVisible()` 会**同步入队**一批 `Picasso.fetch()`。
埋点测出**方法本身**只要 0~1ms，但**后续下载/解码的 CPU 抢占发生在其后的若干帧** ——
埋点看不到，用户能感觉到。

#### ⭐ F. `flushSearchResults` 在 IDLE 时立刻触发

```kotlin
} else {   // IDLE
    if (pendingResults.isNotEmpty() && !flushScheduled) scheduleFlush()   // ← 停稳即插入
```
⇒ 惯性刚停就插数据 ⇒ 若此时用户在列表底部附近，内容增长会让"停在哪"发生变化。

## 四、要定论，还缺什么（取证方案）

**最大的障碍**：断触（ACTION_CANCEL）在现有埋点里**看不到**。现有埋点只记录"
chip 插入""停稳收尾""最差帧"，而断触是**触摸事件流**的性质。

### 建议补一组"触摸/滚动取证"埋点（**只加观测，不改行为**）

| 记录点 | 记什么 |
|---|---|
| `dispatchTouchEvent` | 每个 `ACTION_DOWN` / `ACTION_UP` / **`ACTION_CANCEL`** 的时刻，以及当时是否落在左栏矩形内 |
| 左栏 `needScroll` | **翻转时刻**（false↔true）+ 当时的触摸状态 + chip 数 |
| 左栏 `onInterceptTouchEvent` | 返回 true 的时刻（= 开始拦截 = 给子 View 发 CANCEL 的那一刻） |
| 右栏 `onScrollStateChanged` | `IDLE→DRAGGING→SETTLING→IDLE` 的**完整状态迁移时间线** |
| 右栏 fling | 每帧 `scrollY` 采样（`onScrolled` 的 `dy`），用来看**滑行位移是否均匀** |

**这五条能把两个问题都钉死**：
- 左侧："断触发生在第几毫秒、当时 `needScroll` 是什么、是不是正在翻转"
- 右侧："滑行位移是否均匀、顿挫发生在状态迁移的哪一步"
