## 一、动画缩放：有影响，但**不是主因**

用户配合做了「零成本实验」（0.5x 滑一组 → 改 1x 滑一组 → 改回）。两组对比：

| 动画缩放 | 样本 | **惯性时长中位** | **惯性帧中位** | 实测位移中位 |
|---|---|---|---|---|
| **0.5x** | 34 | **194 ms** | 25 | 3,139 px |
| **1.0x** | 26 | **233 ms** | 46 | 6,385 px |

**⇒ 改回 1.0x 只让惯性时长增加约 20%（194 → 233 ms）。**

⇒ **`animator_duration_scale = 0.5` 确实在起作用，但远不足以解释「很快就停」** ✔
（若它是主因，时长应当翻倍。）

⚠️ 但**建议你把它改回 1.0x** —— 它对所有滚动都有影响，且没有任何代价。

## 二、⚠️ 我的探针有 bug —— cq 的「理论距离」数据**无效**

看这组理论距离（独立 `OverScroller` 复算出来的）：

| vy | 理论距离 |
|---|---|
| 19738 | 13,706 |
| 22553 | 51,466 |
| 19605 | 99,707 |
| 28000 | 190,607 |
| 20394 | 271,839 |
| 17490 | 559,987 |
| 14332 | 979,031 |
| … | **2,546,629** |

**理论距离单调递增，与速度完全脱钩** —— 这是 `OverScroller` 的**飞轮（flywheel）**机制：

```java
// OverScroller.fling() 开头
if (mFlywheel && !isFinished()) {
    // 上一次的残余速度 **加到** 新速度上
    velocityX += oldVelocityX;  velocityY += oldVelocityY;
}
```

**我用了 `by lazy` 复用同一个探针实例，上一次没跑完就接着算 ⇒ 速度逐次累加 ⇒ 距离爆炸。**

⇒ **该轮「理论距离」不可用。** 已在 `cs` 版修掉（fling 前先 `abortAnimation()`）。
⇒ **这是我自己的埋点缺陷，不是设备行为** —— 记录在这里以免以后重复踩。

## 三、⭐ 但这一轮拿到了一个更关键的线索：**滚动几乎不减速**

用有效字段（`惯性位移`、`惯性时长`、`vy`）算「平均速度 ÷ 初速」：

| vy | 惯性位移 | 惯性时长 | **平均速度** | **平均/初速** |
|---|---|---|---|---|
| 19738 | 1,621 px | 70 ms | 23,157 px/s | **117%** |
| 28000 | 15,990 px | 716 ms | 22,332 px/s | **80%** |
| 24,591 | 12,126 px | 599 ms | 20,244 px/s | **82%** |
| 27,078 | 20,524 px | 1,257 ms | 16,327 px/s | **60%** |
| 16,718 | 3,668 px | 225 ms | 16,302 px/s | **98%** |

**自然惯性（`SplineOverScroller`）是指数/样条衰减** —— 平均速度应该**远低于**初速（典型 30~50%）。
**实测 60%~117%** ⇒ **滚动过程中速度几乎没有下降。**

再结合前几轮的独立观测（互相印证）：

- 短惯性样本普遍「**末帧 ≈ 首帧**」（例：169 → 161、202 → 188）
- 「平均速度 / 初速」接近甚至超过 100%

**⇒ 滚动是「匀速跑了一段，然后突然停」，不是「平滑减速停下」。**

## 四、🎯 这个特征指向一个具体的机制

| 特征 | `fling`（`SplineOverScroller`） | **`smoothScrollBy`（线性插值器）** |
|---|---|---|
| 速度曲线 | **衰减** | **恒定** |
| 停止方式 | 减速到 0 | **到点即停** |
| 与实测吻合 | ❌ | **✅ 完全吻合** |

**`smoothScrollBy` 在这套代码里唯一的入口是** ——

```java
// TvRecyclerView（javap 反编译定位）
public boolean requestChildRectangleOnScreen(View, Rect, boolean)
    ...
    148: invokevirtual  // Method smoothScrollBy:(II)V
```

⇒ **一旦 `requestChildRectangleOnScreen` 被调用，就会用 `smoothScrollBy` 替换掉正在跑的 fling
⇒ 表现就是「匀速一小段后突然停」。**

⚠️ 上一轮我以为这条路被排除了（`item_search.xml` 没有 `focusable`，子 View 不会请求滚动到可见）。
**但那个判断只覆盖了「子 View 主动请求」这一种触发方式** ——
`requestChildRectangleOnScreen` 还可能被**别的地方**调用（例如库内部、`scrollToPosition` 路径、
或 View 框架的其它入口）。**这正是 `cs` 版要确认的。**

## 五、cs 版（本版只加观测）

**新增：把惯性阶段的前 12 帧 dy 序列打出来。**

```
[tp] ★右栏惯性[停稳]：惯性帧=… 惯性位移=… 首帧=… 末帧=…
     ｜拖动帧=… 总帧=… 距UP=…ms 惯性尾5帧=[…] 惯性前12帧=[…]
```

**判据（一条就能定论）：**

| 前 12 帧形态 | 结论 |
|---|---|
| **基本恒定**（±10%，如 `[180,182,179,181,180,…]`） | ⇒ **匀速 ⇒ `smoothScrollBy` 类**（线性插值） |
| **单调递减**（如 `[240,220,200,185,170,…]`） | ⇒ 正常 fling 衰减 ⇒ 转查「为什么提前结束」 |

（只在停稳时一次性打印，不逐帧刷 —— 避免自造卡顿污染结论。）

**同时保留 `cr` 的探针修复**（`abortAnimation()`），所以本版也能拿到**有效**的理论距离。
