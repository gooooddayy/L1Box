## 三、E-1 详述：让"有结果"的搜索**早收尾**（本轮主修）

### 3.1 为什么两个出口都进不去

```
站点陆续回调（首条 75ms）… 最后一批回调结束
   ↓
39/40 停住 —— 那个站点不回了
   ↓
出口A：正常收尾 onFirstWaveDone()
       触发条件 = searchData() 里 allRunCount.decrementAndGet() == 0
       ⇒ 恒定 39/40 ⇒ 计数停在 1 ⇒ **永不触发**
   ↓
出口B：停滞检测 stallCheckTick()
       触发条件 = allRunCount > 0 && searchAdapter.data.size <= 0 && quiet >= 10s
                                  └────────── 有结果就不打扰 ──────────┘
       ⇒ 命中 144~331 条 ⇒ **判据直接为 false**
   ↓
只剩出口C：30 秒看门狗 ⇒ 超时收尾
```

### 3.2 修法

`stallCheckTick()` 拆成两支：

| 分支 | 判据 | 动作 | 为什么 |
|---|---|---|---|
| **有结果** | `在途 > 0` ∧ `静默 ≥ SETTLE_QUIET_MS(3000)` | `onFirstWaveDone(settled = true)` —— **正常收尾** | 结果已经在屏幕上，用户要的是"搜完了"这个信号。3 秒静默＝确实没人还在工作 |
| **无结果** | `在途 > 0` ∧ `静默 ≥ STALL_QUIET_MS(10000)` | `finishSearchByTimeout()` —— 超时收尾（**不变**） | 0 结果才需要走 S3 六条判据，阈值 10 秒维持 bv 口径 |

**为什么有结果时必须走"正常收尾"而不是"超时收尾"**：

| | 超时收尾 `finishSearchByTimeout()` | 正常收尾 `onFirstWaveDone()` |
|---|---|---|
| 线程池 | `searchExecutorService.shutdownNow()` **中断在途搜索** | 不碰 |
| 网络请求 | `cancel()` | `cancel()` |
| 结果 | 已入队结果照常落地 | 已入队结果照常落地 |
| **迟到结果** | 被 `shutdownNow` 掐死 ⇒ **丢** | `searchData()` 的 `else if (pendingResults.isNotEmpty())` 分支 ⇒ **正常落地并刷新列表** |
| 提示语 | 「部分站点响应超时，已展示当前搜索结果」 | 无（本就是正常完成） |

⇒ 有结果时走正常收尾，**结果条数一个字不少**，慢站点的迟到结果还能追加进来。

### 3.3 为什么阈值是 3000ms

- 实测站点回调集中在 **0~3 秒**（首条 55~317ms，冷启动最慢 2.5s）；
- 3 秒**完全静默**（任何回调——含空回调——都会刷新 `lastProgressMs`）意味着确实没人还在跑；
- **最坏代价可控**：若某站点恰好在收尾后才回来，它的结果会走迟到分支**正常追加到列表**，用户只会看到"结果变多了"，不会少。

### 3.4 埋点

新增一行（判"修法有没有生效"的直接证据）：

```
搜索稳定：N 秒无站点回调（在途=1 已回=39/40 命中=272），按「结果稳定」收尾
```

`printRoundSummary` 的标签新增第三态 `结果稳定收尾`（原只有 `收尾` / `补全收尾`）。

## 五、E-3 详述：DslTabLayout 手势回调的空指针

**崩溃现场**（唯一一次，21:32:29.192）：

```
java.lang.NullPointerException: Parameter specified as non-null is null:
    method kotlin.jvm.internal.Intrinsics.checkNotNullParameter, parameter e1
    at com.angcyo.tablayout.DslTabLayout$_gestureDetector$2$1.onScroll(Unknown Source)
    at android.view.GestureDetector.onTouchEvent(GestureDetector.java:724)
    at com.angcyo.tablayout.DslTabLayout.onInterceptTouchEvent(DslTabLayout.kt:1542)
```

**为什么会传 null**：Android 在 `ACTION_CANCEL` 后把 `mCurrentDownEvent` 置 null，随后**同一批**（日志里的 `nativeConsumeBatchedInputEvents` 是铁证）的 MOVE 事件仍会调 `onScroll(null, ev, …)`。

**修法**：`DslTabLayout.kt:1490`（`onFling`）与 `:1511`（`onScroll`）的参数 `e1/e2: MotionEvent` → `MotionEvent?`。

**零风险**：两个函数的体里**只用 `distanceX/distanceY/velocityX/velocityY`**，`e1`/`e2` 一次都没被读（已逐行确认）。改可空后 Kotlin 不再生成 `checkNotNullParameter`，框架传 null 也只是"参数没人用"。

**影响面**：同一个类 ⇒ 修一处覆盖**两个页面**（搜索页左侧竖排站点列表 + 首页分类栏）。

**代码来源已核实**：`git log` 显示该文件在本仓库只有上游最初那一次提交、工作区干净 ⇒ 是**上游原版**，不是我们改坏的（bu→bv 改动里也没有任何触摸相关内容）。

### 9.4 一个必须记的判据

> **改了语义就要同步改断言。** 本轮闸门 `:1328` 那条断言在 bv 时的语义是「**只准**对 0 结果生效」，而 bw 把"有结果也收尾"变成了正确行为 ⇒ 那条断言若不改，**源码越正确、闸门越红**。这与 bu 那次的教训正好是一对：**闸门红先分清是"源码错"还是"断言错"**。
