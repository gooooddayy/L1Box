# cm 第二轮取证判定（2026-09-30）—— "断触"被客观量化了

> 数据：`_cm2.log` 的 **14:43 段**（用户第二次测试：只在中间位置连续快速滑动）
> 该段共 196 条 `[tp]` 事件、71 次 DOWN/UP 配对

---

## 一、⭐ 结论先行：断触 = **手势被完全吞掉**

只统计**落在左栏内（x<350）且手指纵向位移 >150px** 的手势，共 **56 次**：

| 分类 | 次数 | 表现 |
|---|---|---|
| **正常跟手** | **46** | 滚动/手指 比值 **0.97 ~ 1.00**（完美 1:1 跟随） |
| **完全零响应** | **20** | 手指滑了 350~684px，**滚动 = 0** |

### 那 20 次零响应，进一步验证"抬起后有没有惯性"

```
手指=465 手势内滚动=0 抬起后惯性滚动=0   ← 真的完全没动
手指=457 手势内滚动=0 抬起后惯性滚动=0
手指=398 手势内滚动=0 抬起后惯性滚动=0
…（共 20 条，全部一样）
⇒ 20 次全部是「手势内不动 + 抬起后也不动」
```

**⇒ 不是"我测错了位置"（惯性没算进去），而是这 20 次手势被从头到尾吞掉了。**
**⇒ 这就是用户说的「断触」——手指在动，内容毫无反应。**

---

## 二、⭐⭐ 强相关线索：这些手势**没有被左栏接管**

在 DOWN→UP 区间内查找「`★左栏开始拦截`」（＝ `onInterceptTouchEvent` 返回 true，左栏开始接管）：

| 分类 | 有"接管"记录 |
|---|---|
| **正常跟手**的手势 | **34 / 36 = 94%** |
| **零响应**的手势 | **5 / 20 = 25%** |

⇒ **"没接管" ↔ "不滚动" 高度相关。**

### 代码上的因果路径（已确证的部分）

```kotlin
override fun onInterceptTouchEvent(ev: MotionEvent): Boolean {
    if (needScroll) {
        intercept = super.onInterceptTouchEvent(ev) || _gestureDetector.onTouchEvent(ev)
    }
    return if (itemEnableSelector) intercept else true    // itemEnableSelector 默认 true ⇒ 返回 intercept
}
```

⇒ 左栏要滚动，**必须** `onInterceptTouchEvent` 返回 true 来接管；
⇒ 而它是否返回 true，**完全取决于 `_gestureDetector.onTouchEvent(ev)` 的返回值**；
⇒ 而那个返回值又取决于 `GestureDetector` 内部的 `onScroll` 是否被触发。

**⇒ 链条上任何一环不成立，手势就会被"让给"底下的 chip，滚动彻底不发生。**

## 三、已排除的推测（避免重复走弯路）

| 推测 | 判定 | 依据 |
|---|---|---|
| 撞到边界后无反馈（上一轮的结论） | ❌ **被推翻** | 这 20 次里 **11 次在中间位置**（Y 既非 0 也非上限） |
| 手势太快、MOVE 不够 | ❌ 排除 | 零响应中位时长 **96ms**，正常 **105ms**，无差异 |
| 被识别成"双击" | ❌ 排除 | 两组"距上次抬起"间隔都集中在 <300ms（零响应 19/20、正常 31/35），无法区分 |
| 位移被门槛吞掉 | ❌ 排除 | `_touchSlop` 的赋值**被注释**，阈值恒为 0 |
| `needScroll=false` 导致不处理 | ❌ 排除 | 零响应手势 DOWN 时 `可滚=true`（chip=31，上限=1937） |

## 四、还差的最后一步（需要一次极轻的埋点）

现在能确定的是：**"没接管"→"不滚动"**。但还需定位**为什么 `onInterceptTouchEvent` 没返回 true**，
可能只剩两种：

| 可能 | 含义 | 修法方向 |
|---|---|---|
| **甲**：`_gestureDetector` 状态异常（没收到 DOWN 基准 / 内部 slop 未脱离） | `onScroll` 从未被调用 ⇒ `intercept` 恒 false | **绕开 `GestureDetector`**：自己在 `onTouchEvent` 里维护上次 Y、直接 `scrollBy`，并用 `VelocityTracker` 自己算 fling |
| **乙**：事件根本没到 DslTabLayout 的 `onTouchEvent`（被 chip 消费且未接管） | 左栏完全收不到 | 同样需要改成"主动接管" |

**两种可能的修法方向一致**：**不再依赖 `GestureDetector` 的返回值来决定是否滚动。**
所以可以直接做，风险是"改了但没解决"。

### 建议：加 3 条极轻埋点先定论（只加 5~8 行，不改行为）

| 埋点 | 回答 |
|---|---|
| `onTouchEvent` 被调用的次数（按 action 分类） | 事件到底有没有到左栏 |
| `onScrollChange` 被调用的次数 | 滚动逻辑有没有跑 |
| `_gestureDetector` 那条 `onScroll` 是否触发过 | `intercept` 为何是 false |

**⇒ 跑一轮，就能把"甲/乙"二选一定死，然后一次改对。**

## 六、附：本轮新增可长期引用的硬结论

1. **左栏 56 次手势里，46 次是完美的 1:1 跟手（0.97~1.00）** ⇒ **滚动机制本身没问题**
2. **20 次手势被完全吞掉（手势内 + 惯性后 全为 0）** ⇒ **"断触"是可量化、可复现的客观现象**
3. **"没接管"与"不滚动"强相关（25% vs 94%）** ⇒ 排查锁定在 `onInterceptTouchEvent` 的拦截判定上
4. **`_touchSlop` 恒为 0、chip 不消费触摸（CANCEL=0）** ⇒ 两条旧假设永久排除
