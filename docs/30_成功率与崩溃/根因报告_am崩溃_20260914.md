# am 版崩溃根因报告（ab → am 逐版对比）

日期：2026-09-14　日志：`logcat_am_20260914.log`（约 169MB，13:5x）

---

## 一、一句话结论

**不是"越改越差"改坏了代码，而是有一个从 ab 起就一直存在的判据盲区，从来没被堵住；al 引入的"预热"把这个原本低频的偶发事件，变成了"退出重进大概率复现"。**

盲区 = `ProtectedInitJar` 的家族判据要求 **`Init` 和 `DexNative` 出现在同一个 dex 里**。订阅里有一个**壳 + payload 多 dex 结构**的加固 jar，两者分处不同 dex → 判据恒为 false → 该 jar 被当成普通 jar，直接执行它自己的 `Init.init()` → native 崩溃（Java 层 catch 不到）。

## 三、判据为什么漏：代码级证据

`ProtectedInitJar.scan()` 遍历 jar 内**每一个 dex 独立判断**，任一命中才返回 true：

```java
while (entries.hasMoreElements()) {
    if (!entry.getName().endsWith(".dex")) continue;
    if (checkDex(readBytes(is), packageName)) return true;   // ← 每个 dex 单独判
}
```

而 `Dex.isProtected()` 的家族判据是**单 dex 内**的：

```java
if (!desc.startsWith("Lcom/github/catvod/spider/Init")) continue;   // ← 只处理 Init 类
hasInit = ...;
if (hasInit && !hasDexNative) hasDexNative = dexNativePresent();    // ← 只在"本 dex 有 Init"时才扫
if (hasInit && hasDexNative) return true;                          // ← 必须同一 dex 同时具备
```

于是壳 + payload 结构必然漏判：

| dex | 含 Init | 含 DexNative | 单 dex 判定结果 |
|---|---|---|---|
| `classes.dex`（壳） | ✅ | ❌ | false |
| `classes2.dex`（payload） | ❌ | ✅ | false（循环连 Init 都看不到，直接跳过） |
| **整个 jar** | — | — | **false → 当普通 jar** ❌ |

**反证**：崩溃栈里 `DexNative.getLoader` 和 `Init.init` 同时出现，说明 jar 里两个类都在；如果它们同处一个 dex，判据必然命中。所以只能是**跨 dex**。

## 四、为什么"退出软件 → 重进 → 搜索"几乎必崩

这条路径有两个动作叠加：

1. **`JarLoader.load()` 每次重进都执行**：
   ```java
   classLoaders.clear();                       // 丢掉上一代所有类
   ...以后再 getSpider → 每个 jar 都 new DexClassLoader(...)   // 生成"新一代"类对象
   ```
2. **而 jar 解压出来的 native 库（.so）在进程内是常驻的**——`dlopen` 过的库不会因为 ClassLoader 被释放而卸载，库内/注册表里的类引用还指向上一代。

两者相撞 → 新一代 Java 类调用常驻 native 库 → `mid == null`（ART 检出的失效 jmethodID）→ **SIGABRT，Java 层无法捕获**。

**不是"退出"杀进程，"重进"复用进程重新 loadConfig**——这正是 am 版刚确认过的机制（上一轮日志里 pid 5655 在 23 秒内跑了 5 轮配置重载）。

## 五、关键反证：ak 版（你实测 0 崩溃）日志里，同一个 jar 也在走危险路径

在 `logcat_ak_20260913.log` 里，这个 jar 走了 **13843 次**"普通路径"，栈是：

```
at com.github.catvod.spider.ProxyOrigin.init(...)
at com.github.catvod.spider.InitOrigin.init(...)
at com.github.catvod.spider.DexNative.getLoader(Native Method)   ← 注意：成功进入了 native
at com.github.catvod.spider.Init.init(Unknown Source:13)
```

差别在于：**ak 时它能成功进入 native 并抛出可捕获的 Java 异常**（被 jar 内部吞掉，记到 SpiderLog）；am 时它在 JNI 入口就 `mid == null` 直接 abort。

**结论**：判据漏判从 ak（甚至更早）就存在，**ak 的"0 崩溃"是时序运气，不是机制正确**。al 的预热把跨代初始化次数抬上去，撞上了 native 失配窗口。

## 七、修复方案（an 版，待拍板）

| # | 改动 | 性质 | 说明 |
|---|---|---|---|
| **A** | **运行时判据**：在调 `Init.init` 之前用 `classLoader.loadClass("com.github.catvod.spider.DexNative")` 探测，命中即当家族 jar | **治本、零盲区** | 静态扫描靠解析 dex 结构，总有结构变体；`loadClass` 是 JVM 自己的解析结果，**跨 dex、混淆、壳结构全都覆盖**。命中后走受控路径（或干净拒载） |
| **B** | 静态判据同步改为 **jar 级汇总**（任一 dex 出现 DexNative 类型引用即家族） | 治本（兜底） | 与 A 互为正交验证 |
| **C** | **撤销 al 的 warmUp 预热 + 分源并发**，回 ak 口径（10 并发 / 两参 / 按需加载） | 退速 | 去掉"配置就绪即集中加载全部 jar"这个密度放大器 |
| **D** | **家族 jar 跨代保活**：`load()` 不清除家族 jar 的 `classLoaders` 项，key 命中即复用同一 ClassLoader | 治本（治 `mid==null`） | 从根上避免"新一代类 × 常驻 native 库"失配。代价：家族 jar 每进程只加载一次（服务端更新 jar 时需重启软件生效） |
| — | 串行锁 / 单飞 / 门禁 / 路由账本 / 中和器 | 保留不动 | 保险，不占速度 |

**优先级建议**：A + C 必做（A 堵入口，C 去放大器）；B 顺手做；D 是最彻底的一层，但它有"jar 更新需重启"的代价，可以放到 A+C 实测之后再决定。

**预期**：退出重进不再产生"新一代类 × 常驻 native 库"的失配 → 崩溃面消失；搜索速度回到 ak 体感（比 al 慢一点，那是 ab 基线，也是你已拍板接受的取舍）。
