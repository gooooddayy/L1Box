# aq 版落地：把「判据修好」的代价补上

> 2026-09-14。上一版 ap 的结论是「判据修对了，但代价算错了」。本版把代价补上。
> 全部结论来自真机 logcat 与系统 dropbox 的行号级证据，不是推演。

---

## 一、你看到的那次"崩溃"，到底是什么

你说的是：**重新进入软件 → 搜索 → 结果为空**。

这不是 native 崩溃，**正好就是上面说的那个代价**。证据分两侧：

| 检查项 | 结果 |
|---|---|
| `Fatal signal` / `JNI DETECTED ERROR` / `SIGABRT` | 各 **0** |
| 系统 dropbox 的 `data_app_native_crash` | 19 条，最后一条 **13:57:28（am 会话）**，17 点测试窗口内 **0 条** |
| Java 崩溃（`data_app_crash`）/ ANR | **都不存在** |
| 18 次启动的进程退出原因 | 全部 `USER REQUESTED / REMOVE TASK`（就是你划掉应用） |
| 崩溃处理页（清单里注册了 CustomActivityOnCrash） | **从未被拉起** |
| 应用自身日志 | `加固 jar 内部 loader 绑定失败，已拒载其站点` **458 次** |

**为什么结果会是空的**：搜索的来源绝大部分是 jar 站点，而这一版把所有加固 jar 都拒载了
（每会话 13~17 次拒载，只有 2~4 次加载成功）。站点被拒载 = 该站点在这一轮彻底不参与搜索。

顺带说明唯一的数据缺口：**16:54–17:12**（USB 掉线那段）日志缓冲已被清空，之后的测试全在 17:12 以后，
有完整记录。所以"当时看到什么"这件事不需要再确认——证据链已经闭合。

## 二、根因：判据修对了，但手写受控路径从来没被真 jar 检验过

### 决定性对比（真机日志，行号级）

`DexNative.getLoader` 的**入口帧**：

| 版本 | 入口 | 次数 | 结局 |
|---|---|---|---|
| ak（0 崩基准） | `com.github.catvod.spider.Init.init` ← `JarLoader.loadClassLoader:146`（**普通路径**） | 13843 | 站点正常可用 |
| am | `com.github.catvod.spider.Init.init` ← `JarLoader.loadClassLoader:181`（**普通路径**） | 14678 | 站点正常可用 |
| **ap** | `ProtectedInitJar.bindDexLoader:327`（**手绑路径**） | 7802 | **全部抛异常** |

### 因果链（每一步都有证据）

1. **这批「壳 + payload 多 dex」加固 jar，在 ab→am 全线都是被漏判成普通 jar 的。**
   它们走的是 `Init.init(Context)` —— 而 jar 自己的入口里，次序是"先起 Go 代理、再取 loader"，天生自洽。
   ak + am 合计执行 **28521 次，0 崩溃**。

2. **ap 把判据修好了**（`FAMILY_TYPES` 跨 dex 汇总 + `probeFamily` 运行时探测），它们第一次进入我们手写的受控路径。

3. **手写受控路径跳过了"起代理"这一步。**
   异常的传播链是：
   `bindDexLoader:327` → `DexNative.getLoader` → `InitOrigin.init` → `ProxyOrigin.init` → okhttp
   → 依次去连 `127.0.0.1:8964, 8965, 8966 … 9031`（19+ 个候选端口）**全部 ECONNREFUSED**。
   这个异常块在 ap 里出现 **7738 次**，与 `ProxyOrigin.init` 帧数逐一对应。

4. **`getLoader` 拿不到 loader → `bindDexLoader` 返回 false → jar 被拒载。** 458 次。
   站点成片消失 → 搜索结果为空。

### 为什么会这样设计，以及为什么它是错的

原设计里有一句注释写着「白名单内 → 正常绑定；不在 → 干净失败，站点降级」。
这句话本身就是错的：**降级 = 站点直接消失，不是"少个网盘源"**。我在上一轮方案里也照抄了这个错误假设，
并据此判断了"多判家族"的代价。这个判断错误由我负责。

而更深一层的机制缺陷是：**手写路径从来没有被真 jar 检验过**——因为在此之前，所有真 jar
都被漏判走了普通路径，手写路径一直是空跑。判据修好的那一刻，缺陷就兑现了。

### 顺带修掉的第二个问题：进详情页会拆掉搜索

「反复进出详情页后补全停止」是独立的一个 bug：

点击搜索结果时对搜索池调了 `shutdownNow()`，并把返回值缓存起来、回页时重投。
但 `shutdownNow()` **只交出"还没开跑"的排队任务，已经在跑的被直接打断且永不回来**；
回页时队列通常已经空了 → 这一轮在飞的站点被永久丢弃，而且完成计数被重新基准化
（`allRunCount.set(pauseRunnable.size)`）→ 页面「正常收尾」却少一块结果。反复几次，剩余站点就都消失了。

## 三、本轮改了什么（一次出包，7 项）

### 1. 受控路径改成两条腿（`ProtectedInitJar.init`）

```
本进程已有代理在跑？ ──有──→ 先试手绑 getLoader（承接已有代理，省一次 killall+重启 = 提速）
        │
        └─没有 / 手绑失败 ──→ 交还 jar 自身的 Init.init（唯一能把代理起起来的入口）
                                   │
                                   └─ 成功 = jar 内部重启了共享代理 = 它成为新持有者（换届）
```

- 手绑路径保留：它是**提速**项（避免多余的一次 killall + 代理重启）。
- 回退路径是**可用性**项：不再有"拒载站点"这个结局，两条路都失败才降级。
- 回退为什么安全：jar 的自杀调用（`Process.killProcess`）已被 `JarKillNeutralizer` 在 dex 层改成
  合法方法名（运行时抛可捕获的 `NoSuchMethodError`），拿不到控制权的进程级自杀已不存在；
  且全程在 `NATIVE_INIT_LOCK` 内串行。实证支撑 = 那 28521 次 0 崩溃。

### 2. 换届规则推广：谁真正启动了代理，谁就是持有者（`occupyProxy`）

原来"受控接力"的判据是"旧持有者本代已无人请求"（`HOLDER_USED` 那套），只在切线路时才换届。
现在改成**只要一次初始化真正重启了共享代理就换届**——因为那一刻旧持有者的代理已经被 killall 死了，
必须同步降级它的路由。这套 per-generation 的接力判据连同 `mainLoader`、`resetProxyFlight`、
`takeOverIfStale`、`forgetStale` **整条撤除**（净删代码）。

### 3. `/proxy` 入站门禁进程级化（关键新增）

原门禁是按 key 的（`isNativeWindow(key)` + `recentJarKey`）。加固 jar 初始化时会 killall 共享代理，
而此刻进来的 `/proxy` 可能属于**另一个** jar —— 按 key 的判断对它完全无效，它会打到正被 killall 的
原生对象上 → `obj==null` → SIGABRT。

新增 `NATIVE_INIT_IN_PROGRESS`：**全进程任一 jar 在初始化 → 所有 `/proxy` 一律 503**。
这一条补上之后，`/proxy` 侧的 `obj==null` 那条崩溃路径才真正闭合。

### 4. 撤掉启发式家族信号（误伤源）

`nativeRef && processRef`（"既要载原生库又要拉子进程"）**整条删除**：
它把大量普通 jar 误判进受控路径（ap 的 458 次误拒载里，很大一部分就是这类误伤），
而它想兜住的"未知变体"本就由 `probeFamily` 零盲区覆盖。判据只留确定性特征 + 运行时权威探测。

### 5. 进详情页不再拆搜索（`FastSearchActivity`）

删掉两处点击回调里的 `shutdownNow()` 与 `cancelSearchWatchdog()`，并删掉随之失效的
`pauseRunnable` 字段与 `onResume` 重投逻辑。搜索是有界任务（看门狗 30 秒封顶），
后台跑完，返回时就是完整列表。

### 6. 拒载日志带 jar key 与失败点

`加固 jar 初始化失败（手绑与 jar 自身入口都不可用），已降级其站点：<key>`。
两条成功路径也各有独立日志（`手绑成功（承接已有的本地代理，未重启）` /
`交还自身入口初始化成功，本地代理已由它接管`），下次抓日志可以直接看清每个 jar 走了哪条路。

### 7. 闸门与 dex 符号表同步

- `check_l1box_regressions.sh`：P/N/R/S/T 节按新机制重写，新增 U 节（搜索池不得在进详情页时拆除，
  含 `shutdownNow` 只允许留在 4 处的计数断言），共 5 条反向断言。
- `build_l1box.sh`：dex 符号表换新（删 `startGoProxyOnce`/`isProxyHolder`/`resetProxyFlight`/
  `takeoverWanted`/`takeOverIfStale`/`HOLDER_USED`/`mainLoader`/`nativeRef`/`processRef`/
  `pauseRunnable` 等，加 `invokeSelfInit`/`occupyProxy`/`nativeInitInProgress`/
  `NATIVE_INIT_IN_PROGRESS`）。

## 四、结果预期

| 维度 | ap | **aq** |
|---|---|---|
| 加固 jar 站点可用 | **几乎全丢**（每会话 13~17 拒载） | **回到 ab 水平**（手绑或回退，两条路都失败才降级） |
| 搜索并发口径 | 全员 10（ab 口径） | 不变 |
| 首次搜索速度 | 慢（大量失败重试 + 端口扫描风暴） | 快于 ap（不再走 7802 次必败的端口扫描） |
| 代理重启次数 | — | 有代理可承接时不重启（手绑）；否则每 jar 一次 |
| 反复进出详情页 | 补全停止 | 结果完整 |
| `obj==null` 崩因 | 已堵（身份终审） | **再加一层**（进程级入站门禁） |
| `mid==null` 崩因 | 已堵（装载复用） | 不变 |

**没有提速承诺**：并发口径仍是 ab。本版唯一的提速来源是"手绑成功时省掉一次代理重启"，
以及"不再执行 7802 次必然失败的端口扫描"。真正的提速（进程内装载复用的收益）要等
"退出不杀进程"的场景才兑现——见下。

## 六、诚实边界

1. **手绑在"有代理可承接"时是否真能成功，本轮没有实证。** 7802 次手绑失败全部发生在
   "本进程还没有代理"的条件下，所以"有代理时手绑可行"是推断。若不成立，会全部走回退路径——
   可用性不受影响，只是每次多一次代理重启（慢一点）。日志会直接告诉我们是哪种。

2. **残留竞态窗口**：`/proxy` 正在 native 内执行时，另一个 jar 恰好开始初始化并 killall。
   本轮的进程级门禁能挡住"初始化期间**新进来**的请求"，挡不住"已经开始执行的那一次"。
   窗口 = 一次 holder `/proxy` 的执行时长 ∩ 一次 init 的开始时刻。**手绑成功时不重启代理，
   这个窗口基本不存在**——这也是保留手绑路径的理由之一。

3. **网盘源只有持有者可用**：非持有者家族 jar 的 `/proxy` 一律 503（降级不崩）。
   这是刻意的取舍：放行它们就是 `obj==null` 崩溃。实际影响 = 网盘类站点只在"最近一次初始化的
   那个 jar"上可用。

4. **"退出重进不再崩"的机制已就位（装载复用），但本轮测不出来**：
   你安装的版本"退出"= 划掉应用 = 进程被杀，每次都是新进程，进程内复用表用不上。
   所以复用这条只在"同进程内切线路/重载配置"时兑现。要验证它，需要一次"回桌面不划掉 → 重进"的测试。

5. **SpiderLog 的降噪没做**：那是 jar 内部的日志输出（7000+ 行一次），宿主控制不了。
   一加系统的 `LOGS OVER PROC QUOTA(420) DROPPED` 限流也是系统行为，我们无法关闭。
