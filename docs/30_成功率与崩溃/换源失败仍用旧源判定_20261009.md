# 换源失败后仍沿用上一个源的站点池 —— 判定书

- **判定日期**：2026-10-09
- **报告人**：用户（真机操作发现）
- **版本**：`L1Box_v1.0.0_release_20261008da`（对外 1.0.0，内部 1.1.1/vc31）
- **本轮性质**：**只做原因判定，未改动任何代码**

---

## 一、现象（用户原话）

> 「第一个源加载成功后，编辑订阅源为另一个源的时候，如果这个新源加载失败，会继续使用前面源的线路搜索以及使用。」

复现路径：

1. 配好源 A → 首页正常出内容、搜索可用
2. 进入订阅页 → 编辑启用中的那条订阅 → 把地址改成源 B（B 是一个**拉不通**的地址）
3. 留在 App 内 → 搜索、首页、播放**照常可用**
4. 用出来的全是**源 A** 的站点与线路；而订阅页/列表显示的是**源 B**（勾选、名称、地址）

---

## 二、根因：四环相接，每一环都是"故意"写的，合起来成了"欺骗"

### 环 1 ｜ 改地址的那一刻：只换了"身份"，没有动"事实"

`ui/activity/SubscriptionActivity.kt:468-484` `onPause()`：

```kotlin
val effective = checked?.effectiveUrl ?: ""
ApiConfig.saveApiUrl(effective)          // ← 新地址写进 Hawk（= 持久化身份已换）
Hawk.put(HawkConfig.SUBSCRIPTIONS, mSubscriptions)
...
if (isFinishing && before != after) EventBus...post(RefreshEvent(TYPE_HOME_REFRESH))
```

编辑对话框那边（`SubscriptionActivity.kt:197-220`）也做得很干净 —— 地址变了就把 `isMultiRepo / lines / activeLineUrl` **一起作废**，注释里明确写着"这正是『切换源了还在用上一个源的线路数据』"。

**所以：多仓识别这一层被修好了，但站点池这一层没有被碰。** 新地址只写进了 Hawk，**内存里的 `sourceBeanList` 仍然是源 A 的站点**。

### 环 2 ｜ 加载失败时：`ApiConfig` 只报错，不清池

`api/ApiConfig.java` 里**清池只写在一处** —— 空地址分支（`236-250`）：

```java
if (apiUrl.isEmpty()) {
    // 关闭/删除全部订阅后：立即清空内存里的站点池与相关配置。
    // 之前只回调 error，内存里仍留着上一个源的数据，搜索/播放照常能用，重启才恢复空源。
    synchronized (sourceBeanList) { sourceBeanList.clear(); ... }
    ...
    callback.error("-1");
    return;
}
```

⚠️ **这段注释本身就是铁证**：开发者早就发现过**同一个 bug 的另一种表现**（"删光订阅后旧源还能用"），于是修了 —— **但只修了"地址变空"这一支，漏了"地址换成另一个源"这一支**。两类情形在代码里走的是不同的分支，而只有前者清了池。

再看两个失败出口，**都不清池**：

| 出口 | 位置 | 行为 |
|---|---|---|
| 网络层失败（重试 2 次后） | `ApiConfig.java:384-413` | `sitePoolSettled = true` → `callback.error("订阅拉取失败，请检查网络")` —— **池原样不动** |
| 拿到响应但内容不是配置 | `ApiConfig.java:370-381` | 先试缓存回退，没有则 `callback.error("订阅内容异常：…")` —— **池原样不动** |

还有一个更隐蔽的细节 —— `parseJson`（`ApiConfig.java:750-767`）：

```java
String fixed = L1SubContent.toJson(jsonStr);
if (fixed == null) throw new IllegalStateException("订阅内容不是配置");   // ← 在 clear 之前抛
...
synchronized (sourceBeanList) { parseJsonInternal(apiUrl, jsonStr); }   // clear() 在 778 行，更靠后
```

也就是说，**"内容不是配置"时 `clear()` 根本没执行** ⇒ 池保持源 A 不变。这是"内容坏 → 池留旧"的直接代码依据。

> 追加结论：**同样是"新源加载失败"，池的结局有两种**（见第四节），取决于失败发生在哪一层。

### 环 3 ｜ 首页拿到失败回调后，**主动选择**沿用旧池

`ui/fragment/HomeFragment.kt:796-803`（`reloadSitePool` 的 error 分支）：

```kotlin
override fun error(msg: String) {
    mReloading = false; dataInitOk = true; jarInitOk = true
    // 切换失败也用当前站点池重拉一次，避免停留在旧线路内容或加载态
    startHomeLoad()
    schedulePendingReload()
}
```

`ui/fragment/HomeFragment.kt:527-543`（`loadConfig` 的 error 分支）：

```kotlin
override fun error(msg: String) {
    // 订阅拉取失败（离线/不可达等）不阻塞首页，仍用已有站点池/内置源渲染
    ...
}
```

**这两处注释把设计意图写得非常清楚**：失败时"不阻塞首页、沿用已有池"。

**这个设计本身是对的** —— 它保护的是**断网/源站临时抽风**场景：用户手上还有能用的源，不该因为一次网络抖动就把可用状态清成空。问题在于它**没有区分"网络抖动"和"用户主动换源"**，把后者也当成前者处理了。这才是本 bug 的真正要害。

### 环 4 ｜ 于是：后续一律按池走，全程用源 A

| 用途 | 代码位置 | 取的是池还是地址 |
|---|---|---|
| 首页分类 tab 与内容 | `HomeFragment.kt:451-459` `buildHomeSiteCandidates()` → `ApiConfig.get().getSourceBeanList()` | **池**（= 源 A） |
| 搜索站点集合 | `FastSearchActivity.kt:2040` `searchRequestList.addAll(ApiConfig.get().getSourceBeanList())` | **池**（= 源 A） |
| 播放与解析 | `ApiConfig.getSource(key)` / `getHomeSourceBean()` | **池**（= 源 A） |
| 首页缓存标签 | `HomeFragment.kt:292-296` `HomeCache.saveSkeleton(Hawk.get(API_URL), …)` | **地址**（= 源 B） |
| 搜索"已勾选站点" | `SearchHelper.java:18-26` → `Hawk.get(API_URL)` 当 map 的键 | **地址**（= 源 B） |

**同一份状态里"池"和"地址"分属两个源** —— 这就是混乱的根源。

### 为什么整轮都恢复不过来（不是"等一会就好"）

`HomeFragment.kt:735-736` `onResume` 的早退条件：

```kotlin
if (dataInitOk && jarInitOk && mSortDataList.isNotEmpty() && curUrl == mLastApiUrl) return
```

换源失败后：`dataInitOk/jarInitOk` 都被 error 分支置了 true，`mSortDataList` 是**源 A 的分类**（非空），而 `mLastApiUrl` 会在下一次 `onPause`（`713` 行）被刷成**当前 Hawk 地址 = 源 B** ⇒ 四个条件**全部满足** ⇒ **直接 return，不再重拉**。

- 留在首页不动：`mLastApiUrl` 仍是旧值 → 下次 resume 还能触发一次重载
- 只要**离开首页再回来一次**（去设置页、去搜索页都算）→ 早退条件成立 → **本轮会话内永远不会再试源 B**

⇒ 用户感觉"这个源改了等于没改"，而且重启前都这样。

## 三、一句话根因

> **"站点池属于哪个源"这件事没有被记录。** 代码只能用"当前地址"去猜，而换源失败时"地址（新）"与"池（旧）"必然背离；两个错误分支又都按"地址没变"的假设去救场（沿用旧池），于是错误状态被固化。

---

## 四、失败形态分类（同一个操作，两种不同症状）

| 形态 | 触发条件 | 池的结局 | 用户看到 |
|---|---|---|---|
| **A 型：静默沿用旧源**（本次报告） | 网络不可达 / 超时 / 内容完全不是配置（`toJson` 返回 null） | **保持源 A** | 一切"正常"，但实际全是源 A；界面显示源 B ⚠️ 最难发现 |
| **B 型：清成空池** | 拿到**合法 JSON 但没有 `sites`**（如 `{}`、只有 `{"urls":[...]}` 的多仓壳） | `clear()` 执行 ⇒ **空池**，`sitePoolSettled=true`、`lastSiteCount=0` | 首页"添加订阅"引导，搜索空结果；同时弹"订阅里没有可用站点，请检查源地址"（`warnIfNoSite`） |

**B 型反而是"诚实"的一类** —— 它没有骗人，只是用户会奇怪"我明明有源"。诊断时先看这两种，能直接区分是"网络问题"还是"源内容形态问题"。

---

## 五、是否会导致业务逻辑混乱 —— **会，且不止一条**

| # | 混乱点 | 证据 | 后果 |
|---|---|---|---|
| 1 | **持久化身份 ≠ 运行时事实** | `HawkConfig.API_URL` = 源 B；`sourceBeanList` = 源 A | 任何"读地址判断"的代码都得到错误结论 |
| 2 | **首页缓存被跨源污染** | `saveSkeleton` 用 `Hawk.get(API_URL)`（源 B）做标签，却拿源 A 的分类与影片 | 缓存文件 =「**源 B 的地址 + 源 A 的内容**」。下次冷启动 `tryRestoreCache` 地址一比**命中**，秒显源 A 内容并置 `mSkipHomeLoadOnce` ⇒ **连冷启动都跳过重拉**。cz 新加的"至少一个分类有影片"判据**拦不住**，因为源 A 的数据是完整的 |
| 3 | **搜索勾选状态失配** | `SearchHelper` 用**地址**当键存/取"已勾选站点"，`FastSearchActivity` 用**池**的 key 匹配 | 在源 B 下勾选的站点 ≠ 源 A 的 key ⇒ 勾选不生效/被当成"全选" |
| 4 | **收藏/历史记录会莫名消失** | `RoomDataManger.java:109-114`：记录按 `(sourceKey, vodId)` 存，`getSource(sourceKey)` 取不到且池已定论 ⇒ `info = null` ⇒ **从列表剔除** | 失败期间产生的记录带的是**源 A 的 key**。等哪天源 B 真的加载成功，这些记录一律被判"不在当前订阅里"而**静默消失** —— 用户会觉得"我的收藏自己没了" |
| 5 | **播放/解析走了另一套配置** | `parseFlags` / `parses` / `spider(jar)` 全在 `parseJsonInternal` 里随池一起换 | 界面（设置页）显示源 B 的解析开关与站点标记，实际生效的是源 A 的 ⇒ **开关看起来没反应** |

## 六、修复方案（**未执行，等拍板**）

### ⚠️ 先说清楚设计上的两难

"失败时沿用旧池"**不是纯粹的 bug，它是断网容错**（注释里写得很明确）。所以**不能**改成"失败就清池" —— 那会把"地铁里没信号"也变成"手上的源全没了"。

**正解必须能区分两件事**：
- **地址没变** → 拉取失败 = 网络抖动 ⇒ **保留旧池**（维持现状，是好特性）
- **地址变了** → 拉取失败 = 用户主动换源没成功 ⇒ **旧池已不代表他的选择**，不能继续冒充新源

### 核心做法：给站点池记一个"归属地址"

在 `ApiConfig` 里增加一个字段，例如 `poolApiUrl`：

| 时机 | 动作 |
|---|---|
| `parseJsonInternal` 成功填池后 | `poolApiUrl = apiUrl` |
| 空地址清池后 | `poolApiUrl = ""` |

然后以它作为**唯一的判据**，替代"猜"。

### 方案 A（推荐 · 判据修正，改动最小）

在**各个失败出口**（`ApiConfig` 的 `callback.error` 之前）加一条判定：

```
if (本次地址 != poolApiUrl)  →  清池 + poolApiUrl="" + 明确提示
else                         →  保持现状（沿用旧池，离线容错不变）
```

配套：
- `HomeFragment` 两个 error 分支：当"池已因换源失败被清空"时，走**空态 + 明确文案**（如「新源加载失败，已停用上一个源；可在订阅页切回」），而不是 `startHomeLoad()` 拿旧池重拉
- **顺手修掉混乱点 #2**：`HomeCache.saveSkeleton` 的标签改用 `poolApiUrl`（或在"池归属 ≠ 当前地址"时**禁止写缓存**）—— 否则换源失败一次，就会留下一份"新地址 + 旧内容"的缓存，比 bug 本身更持久

**优点**：一改就消灭"旧源被继续用"；不动"断网仍可用"的好特性；改动集中在 `ApiConfig` + `HomeFragment` 两处。
**代价**：换源失败后用户会**真的没有源**（这正是"诚实"的代价），所以文案必须写清楚怎么回退。

### 方案 B（可选 · 改地址即失效，比 A 更早一步）

在 `SubscriptionActivity.onPause()` 写入新地址的**同时**就清池（因为用户一旦改了地址，旧池就不代表他的选择）。
- 比 A 更彻底：连"失败的旧池还在"这个窗口都不存在
- 代价：改地址 → 新源加载完之间有一个**无池窗口**（通常几百毫秒~几秒），期间搜索会短暂显示空态
- **与 A 不冲突，可叠加**：A 管"失败之后"，B 管"改完到失败之间"

### 方案 C（⛔ 不建议 · 与既有口径冲突）

"失败自动切回上一个可用源"。
- **冲突点**：违反既定口径「⛔ 换线路是用户手动的事 —— 不许提自动换线路/自动换源」
- **额外障碍**：`ApiConfig.saveApiUrl`（`205-217`）把 `API_URL_BACKUP` 写成**与主键同值**，它是"防损坏镜像"，**不是"上一个可用源"** ⇒ 要实现 C 得另建存储
- 结论：除非你改口径，否则不做

### 方案 E（兜底 · 不改行为，只去掉"欺骗感"）

只在失败时把提示说清楚：「新源加载失败，当前仍在使用上一个源」。
- 成本最低，但**没有解决任何实质问题**，只是让用户知道自己在用旧源
- 建议作为 A 的补充文案，不建议单独采用

### 推荐组合

**A（核心）+ D（缓存污染，A 的配套）+ E 的文案**；是否叠加 **B** 由你定。

## 七、需要你拍板的三件事

1. **换源失败后，你希望是"真的没有源"还是"继续用旧源但明确告知"？**
   - 前者 = 方案 A（诚实，但有断档）
   - 后者 = 保留现有行为，只做方案 E + 修缓存污染（D）
2. **要不要叠加方案 B**（改完地址立刻停用旧源，代价是有个短暂无池窗口）？
3. **收藏/历史（混乱点 #4）要不要一起处理？** 它是既有设计（记录绑定 sourceKey，换源即视为"不在当前订阅"），不是本次 bug 引入的，但确实会被这个 bug 放大。
