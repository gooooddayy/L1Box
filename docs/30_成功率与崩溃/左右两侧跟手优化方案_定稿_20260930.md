## 一、目标

| # | 目标 | 可观测判据 |
|---|---|---|
| **G1** | 左栏在搜索进行中、**任意滑动速度**下都跟手，不再"拖着拖着断掉" | 快速滑动全程无 ACTION_CANCEL 导致的断触；帧埋点最差帧不再命中 `建站点栏` |

## 二、根因清单（两轮合并）

### 2.1 左栏（`DslTabLayout`，源码在 `TabLayout/` 内）

| 编号 | 根因 | 证据强度 |
|---|---|---|
| **L1** | **fling 撞界后守卫误判**：`siteTabsLastScrollMs` 靠 `setOnScrollChangeListener` 更新，而该回调**只在 scrollX/Y 数值真变时触发**；撞界后 `scrollTo` 被钳成同值 ⇒ 回调冻结 ⇒ 400ms 后 `siteTabsBusy()` 变 false ⇒ `addView` 落进"视觉静止但惯性仍在跑"的窗口 | ✅ 代码链确证 |
| **L2** | **fling 边界与实际钳制差一个视高**：`onFlingChange` 竖向传 `startFling(-v, 0, maxHeight)`（内容总高），实际钳在 `maxScrollY = maxHeight − 视高`（L1666 vs L1766） | ✅ 确证 |
| **L3** | **竖向 fling 永不提前中止**：`computeScroll` 的越界 abort **只检查 currX**（L1777），竖向 currX 恒 0 ⇒ 条件永不成立 | ✅ 确证 |
| **L4** | **`needScroll` 门槛**：`needScroll = maxScrollY > 0`（L1586-98）。chip 总高未超栏高时 `onTouchEvent` 走 super、**完全不接管手势** ⇒ 拖不动。<br>按 chip≈100px、栏高≈2145px 估算，**约需 21 个 chip 才开始能滚** | ✅ 确证（阈值待实测） |
| **L5** | **chip 创建固定成本偏高**：`getSiteTextView` 每个 chip 都重新 `setBackgroundResource`（解析 selector drawable）+ `getColorStateList`（解析 ColorStateList）+ `new TextView` + `new LayoutParams`。40 个 chip ⇒ 40 次 drawable/CSL 解析 | ✅ 确证 |
| **L6** | **`existsSiteTab` 是 O(n²) 且每次分配 String**：遍历所有子 View 并 `item.text.toString()`。`drainSiteTabQueue` 的 while 内逐个调用 + `queueSiteTab` 也调 ⇒ 40 个 chip 累计约 780 次遍历与字符串分配 | ✅ 确证 |
| **L7** | **锁门判定坐标系存疑**：`dispatchTouchEvent` 用 `getGlobalVisibleRect`（屏幕坐标）与 `ev.x/ev.y`（相对 Activity）比较（L1437-1438）。全屏 Activity 下两者一致，但存在系统栏/刘海/分屏偏移时判错 ⇒ `siteTabsTouchDown` 不置位 ⇒ **手指刚落下就被 addView 打断** | ⚠️ 待验证 |

### 2.2 右栏（`mGridView` : `TvRecyclerView`）

| 编号 | 根因 | 证据强度 |
|---|---|---|
| **R1** | **IDLE 同帧三件重活**：`cancelOutOfWindowImages()` + `scheduleVisibleImageAudit()` + `prefetchAroundVisible()`（L291-299）挤在同一帧 | ✅ 确证 |
| **R2** | **`prefetchAroundVisible` 是同步 for 循环**：每个 URL 一次 `Picasso…fetch()`（预算 200），末尾一次 `System.out.println`（**同步写 logcat**）（L1304-1332） | ✅ 确证 |
| **R3** | **fling 期间图片全速不下闸**：`onScrolled` 是空实现（L302-307，设计如此）⇒ 解码队列在 fling 结束时正好是**积压峰值**，撞上 R1 | ✅ 确证 |
| **R4** | **搜索期间 `cancelOutOfWindowImages` 被高频触发**：`flushSearchResults` 末尾 `scheduleImageWindow(0L)`（L1582）⇒ **每 120ms 一次**，持续十几秒 | ✅ 确证 |
| **R5** | **滑动中每 120ms 插 12 条**：`SCROLL_BATCH_MAX=12` + `SEARCH_FLUSH_MS=120` ⇒ `addData` 触发 `notifyItemRangeInserted` + 布局重算 | ✅ 确证（必要性待评估） |
| **R6** | `tv_selectedItemIsCentered="true"`（焦点项居中）在触摸路径是否生效——若在滚动停止时做居中校正，会额外一次 `smoothScroll` | ⚠️ 外部依赖，无法静态确认 |

### 2.3 共同点

> **②③ 都发生在"手势刚结束那一刻"，本质是"后台本该错开的工作撞上了用户停手"。**
> 不是列表本身慢 —— 两侧的绘制与滚动能力都没有问题。

## 三、任务清单

> 排序原则：**先撤销（T0）→ 先补埋点（T1）→ 再做确定性高的修复（T2-T5）→ 最后做需对照实验的（T6）**。
> 其中 T1 的依据：L1/L5/L6/R1 都能解释"卡"，但**静态分析无法判定哪一个是主因**；
> 盲改最可能的后果是"改了三处、只有一处有效，另两处引入新问题"。所以先量化，再动手。

### T0 — 撤销低档收敛（P0 · 用户已确认）

**改什么**（净删代码，回到改造前）：

| 文件 | 改动 |
|---|---|
| `util/DeviceProfile.java` | 删除 7 个方法：`imageThreads` / `imageMaxRequests` / `imageMaxRequestsPerHost` / `imageConnectionPool` / `imageCacheBytes` / `itemViewCacheSize` / `siteTabBatch` |
| `util/OkGoHelper.java` | `initPicasso` 内 5 处接线改回写死值：并行 **8** / Dispatcher **12·6** / 连接池 **8** / 磁盘缓存 **64MB** / `l1box-img` 线程池 **8** |
| `ui/activity/FastSearchActivity.kt` | ① `SITE_TAB_BATCH` 从 `val … get()` **改回 `private const val SITE_TAB_BATCH = 8`**；② `setItemViewCacheSize(DeviceProfile.itemViewCacheSize())` **改回 `6`** |
| `check_l1box_regressions.sh` | 撤销 cj 段 26 条断言，改为"**这 7 个方法名必须不存在**"的反向断言 |
| `_br_dexsym.py` | 移除 7 个 cj 方法名锚点，恢复默认 APK 指向新版本 |

**为什么连 `markMemoryPressure` 的入口一起评估**：低档收敛本身是中性的，但 `App.java` 两处
`markMemoryPressure()`（`onLowMemory` / `onTrimMemory≥RUNNING_LOW`）会把档位**只降不升地永久**打到低档 ⇒
**任何机器**一旦触发内存压力，`siteTabBatch` 就从 8 掉到 4（chip 建得更慢）。
这使"低配机兜底"变成了"可能影响所有设备"的隐藏路径。撤销后此路径自然消失。

**风险**：低配机（2G 内存老盒子）失去图片链路的收敛保护，一次搜索 250~500 张海报时堆压力回到改造前水平。
**预防**：这是用户明确选择（"低档还是去掉吧"）；若日后低配机复现 OOM，回归 `cj` 的做法即可（改动是净删，易回滚）。

### T1 — 补埋点：先量化"卡的那一下是谁造成的"（P0）

**为什么必须先做**：L1/L5/L6/R1/R4 五条都能解释"卡"，但**证据强度相同、无法排序**。

**埋什么**（全部只在调试期开，验证完即撤）：

| 位置 | 记录内容 |
|---|---|
| 左栏 `flushSiteTabsNow` / `drainSiteTabQueue` | 每次**真正 addView** 时：`距最后滚动=__ms`、`addView前scrollY=`、`addView后scrollY=`、本批条数 |
| 左栏 | 每次 `siteTabsBusy()` 返回 **false 且随即发生 addView** 时打一条（这是 L1 的靶心场景） |
| 左栏 | 一次滑动的"滚动起止"：首个 scrollY 变化 → 最后一个 scrollY 变化的时间差（用来区分 fling 何时真正结束） |
| 右栏 | IDLE 三件活各自耗时：`取消=__ms 审计=__ms 预取=__ms 条数=__` |
| 右栏 | `帧耗时` 最差帧**同时打出该帧的 scrollState**（IDLE/DRAGGING/SETTLING） |

**判据（能回答三个问题就算成功）**
1. 卡的那一帧，标签是 `建站点栏` 还是 `图片预取`/`结果落地`？
2. addView 发生时，左栏**是否还在滚**（前/后 scrollY 是否变化）？
3. IDLE 三件活里哪一件最贵？

**风险**：埋点本身影响被测对象（`println` 是同步 IO，打太多会自己制造卡顿）。
**预防**：① 一条埋点只在"真发生"时打，不做逐帧打印；② 全部走一个 `L1_TRACE` 常量开关，
默认 **关**，验证时开；③ 打完一轮立刻撤（沿用 ch 轮撤 `分段耗时` 的先例）。

**产出一版仅供测试的包**（`ck`），验完带着结论再出正式修复版。

### T2 — 左栏：把"停手判定"从「计时」改成「状态」（P0 · 修 L1）

**现状**：`siteTabsBusy()` = `touchDown || 距最后滚动 < 400ms`，而"最后滚动"靠滚动回调 —— **撞界后回调冻结，守卫提前失效**（L1）。

**改法（不改 `TabLayout/` 库，纯在 Activity 层）**：
新增一个**自停的帧探针**，只在"有排队 chip"时运行：

```
判定"真的停了" ⟺  400ms 窗口已过  AND  tabLayout.scrollY 连续 K 帧（K=3）未变化
```

- 探针每 16ms 读一次 `tabLayout.scrollY`（**代价极小**，一个 int 读 + 比较）
- 连续 3 帧不变 ⇒ 认定停手 ⇒ 允许 `flush`/`drain` ⇒ **探针立即自行停止**
- 队列清空或用户再次触摸 ⇒ 也立即停止
- 与现有 400ms 窗口取 **AND**（两者都满足才动手），既修 L1 又不误伤

**为什么不用"把 400ms 调大"**：调大到 800~1000ms 虽然能覆盖大部分 fling，但**用户真停手后也要干等**，
chip 迟迟不出现，观感直接变差；且 fling 时长不可控，调多大都可能不够。**帧探针是精准解**。

**风险**
- 探针自旋（忘记停止）→ 持续掉电/掉帧。
  **预防**：探针内部先判"无待建 chip 则 return 且不 re-post"；`onPause`/`onDestroy` 里显式移除回调；闸门加断言。
- 判定过严（K 太大）→ chip 出现明显延迟。
  **预防**：K=3（约 48ms）是"感知不到"的量级；实测若仍偏慢，降到 K=2。
- 撞界后 fling 空转期间，探针会认为"没停"而不 addView ⇒ **chip 暂时不出现**。
  **预防**：这是**正确**行为（用户还在滑动）；且空转由 L3 决定，T3 会缩短它。

### T3 — 修 fling 边界与中止判定（P1 · 修 L2、L3，**需改库**）

**改什么**（`TabLayout/src/main/java/com/angcyo/tablayout/DslTabLayout.kt`）：

| 位置 | 现状 | 改为 |
|---|---|---|
| `onFlingChange` L1666 | `startFling(-velocity, 0, maxHeight)` | `startFling(-velocity, 0, maxScrollY + measuredHeight)` 或直接传 `maxScrollY`，**使 fling 范围与实际钳制一致** |
| `computeScroll` L1777 | `if (currX < minScrollX \|\| currX > maxScrollX) abort` | 竖向时改判 **currY**：`if (isHorizontal()) 判 X else 判 Y` |

**收益**：惯性在视觉到底时**立即结束**（不再空转一个视高），
从根上缩短 L1 所说的"视觉静止但惯性仍在跑"的窗口。

**风险（本方案最高风险项）**：`TabLayout/` 是第三方库代码（angcyo.tablayout），
改它等于**维护一份 fork**，日后上游更新不可直接合并；且这两个改动会影响**所有**用到
`DslTabLayout` 的地方（虽然本项目只有搜索页用）。

**预防**
- 在改动处**逐字注明** `// L1Box fork: 原因 + 日期`，避免日后被当成上游代码误覆盖
- 改动**最小化**（两行），不做任何顺手重构
- 改前后各跑一次 `check_l1box_regressions.sh`（该脚本已含 TabLayout 相关断言）
- **灰度顺序**：T2 先上（不动库）→ 若 T2 已解决观感，T3 可以不做
  ⇒ **T3 设计为"可选"**，由 T1 的埋点数据决定是否必要

### T4 — 左栏：削掉 chip 创建的固定成本（P1 · 修 L5、L6）

| 编号 | 现状 | 改法 |
|---|---|---|
| L5 | `getSiteTextView` 每个 chip 重新 `setBackgroundResource` + `getColorStateList` | 在 Activity 里**缓存一次** `Drawable` 与 `ColorStateList`（成员变量懒加载），每个 chip 复用；`setBackground` 用缓存的 drawable（必要时 `getConstantState().newDrawable()` 避免共享状态串味） |
| L6 | `existsSiteTab` 遍历子 View + `toString()`，O(n²) | 增加 `HashSet<String> siteTabNames` 记账：`drainSiteTabQueue` 加之前先查 Set，加完写入 Set；`removeAllViews` 时清空 Set ⇒ **O(1)**，不再 `toString()` |

**收益**：单帧创建 8 个 chip 的成本下降；累计字符串分配大幅减少（降低 GC 压力）。
**风险**：缓存 Drawable 若被复用且带状态，可能出现"选中态染色串味"。
**预防**：先用 `getConstantState().newDrawable()` 复制；闸门加断言"chip 仍带 `bg_site_chip`"；
真机目视确认选中/未选中两态颜色正确。
**`HashSet` 一致性风险**：`removeAllViews()` 若漏清 Set，会导致"chip 明明被清空、却认定已存在"⇒ 该站点永久不出现。
**预防**：把"清空视图"与"清空 Set"封装进**同一个方法**，杜绝两处分别调用；闸门加断言。

### T5 — 右栏：把收尾三件活拆帧（P1 · 修 R1、R2、R4）

| 编号 | 改法 |
|---|---|
| R1+R2 | `prefetchAroundVisible()` 改**分帧**：每帧最多 4 个 URL，用自停 runnable 续跑；**去掉末尾 `System.out.println`**（或收进调试开关） |
| R2 | 预取过程中若用户**再次开始滑动**（scrollState != IDLE）⇒ **立即中止**本轮预取，剩余额度留给下次停稳 |
| R4 | `flushSearchResults` 末尾的 `scheduleImageWindow(0L)` 改为**带节流**（复用已有 `IMG_WINDOW_REFRESH_MS` 节流逻辑），避免搜索期间每 120ms 取消一次 |

**收益**：IDLE 帧的负载尖峰被摊平到后续若干帧，用户感知不到。
**风险**：预取变慢 ⇒ "滑到新位置后图片出现稍晚"。
**预防**：预取只是"提前取字节"的加分项，不参与可见性判定；分帧后仍会在几百 ms 内完成；
若实测观感变差，把"每帧 4 个"提到 6~8 即可（可调常量）。
**R5 暂不动**：by2 已实测"滑动中暂停落地"会导致**右侧断触 + 图片大面积变慢**并被否决，
**不可重蹈**。是否调整只由 T1 的埋点结果决定，且优先考虑"保持落地的同时降低单次插入成本"，
而不是再次暂停落地。

### T6 — 验证 `tv_selectedItemIsCentered`（P2 · 修 R6）

**做法**：A/B 对照实验 —— 临时去掉两个网格的 `tv_selectedItemIsCentered="true"`，对比"松手后停位手感"。
**为什么最后做**：需改布局 + 出包 + 真机对照，成本最高；且若 T5 已解决顿挫，此项可能不需要。
**风险**：该属性若同时被遥控器焦点导航依赖，去掉可能影响 D-pad 选中项居中。
**预防**：手机竖屏 fork 以触摸为主；改前先确认无 D-pad 相关逻辑依赖；只改 `mGridView`，
保留 `mGridViewFilter` 作对照。

## 四、风险与预防汇总（用户关注项）

| # | 风险 | 影响 | 预防措施 |
|---|---|---|---|
| 1 | **盲改**：五条根因都能解释现象，主因未定 | 改了三处只有一处有效，另两处引入新 bug | **T1 先补埋点**，用真机数据定主因再改；埋点在验证完即撤 |
| 2 | **改库**（T3 动 `TabLayout/`） | 第三方库变 fork，上游不可合并；影响面扩大 | T3 设计为**可选**；必需时改两行 + 逐字注明 fork 原因；用闸门与回归断言兜底 |
| 3 | **探针自旋**（T2） | 持续掉帧/耗电 | 探针"无待建 chip 即 return 且不 re-post"；`onPause/onDestroy` 移除；闸门断言 |
| 4 | **Drawable 缓存串味**（T4-L5） | 选中态颜色错误 | 用 `getConstantState().newDrawable()`；真机目视两态 |
| 5 | **HashSet 与视图不同步**（T4-L6） | 某站点永久不出现 | 清空视图与清空 Set 封装进同一方法；闸门断言 |
| 6 | **重蹈 by2 覆辙**（R5） | 右侧断触 + 图片大面积变慢 | **明确不做"滑动中暂停落地"**；只在埋点证明必要时才考虑，且优先降单次成本而非暂停 |
| 7 | **埋点自己制造卡顿** | 验证结论失真 | 单条埋点只在真发生时打；统一 `L1_TRACE` 开关默认关；用 `frameStage` 标签归因而非逐帧打印 |
| 8 | **撤销低档后低配机 OOM** | 老盒子崩溃 | 用户已明确选择；改动是净删、易回滚；保留 `cj` 作为可回退基线 |
| 9 | **chip 出现延迟**（T2 判定过严） | 左栏站点"半天不冒出来" | K=3 约 48ms（感知不到）；实测偏慢则降到 K=2 |
