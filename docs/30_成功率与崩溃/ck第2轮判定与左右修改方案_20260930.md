## 一、⭐ 本轮最大突破：第一次捕获"滚动位置被改掉"的现场

三轮数据（`round0` / `round1` / `round2`）里，**唯一一条 `前Y ≠ 后Y`**：

```
13:37:00.914  [l1] 左栏插入：批量=7 标签=追加 距末滚动=406ms
              前Y=517 后Y=1511 滚动段=4668ms/80次 队列=0 待建=0 可滚=true 上限=1511 chip=28
```

**三个数字放在一起看**：

| 量 | 值 | 含义 |
|---|---|---|
| `前Y` | 517 | 插入前，用户滑到中部 |
| `后Y` | **1511** | 插入后，**跳到了底部** |
| `上限` | **1511** | **后Y 恰好等于新的 maxScrollY** |

⇒ **插入之后，滚动位置被"吸"到了新内容的底部。** 这就是用户说的「卡住不跟手」——
**滑着滑着，列表突然跳到底部**。

### 为什么会跳？—— 与方案里预言的 L2/L3 完全吻合

`DslTabLayout` 的 fling 有两个已静态确证的缺陷：
1. **fling 边界用 `maxHeight`（内容总高），而 `scrollTo` 钳制用 `maxScrollY`（内容高 − 视高）** ⇒ 相差一整个视高
2. **`computeScroll` 的越界中止只检查 `currX`** ⇒ **竖向 fling 永不提前结束**，撞界后继续空转

### 完整因果链（本次现场）

```
用户滑动 → fling 开始（边界 [0, 旧 maxHeight]）
   ↓
插入新 chip（addView）→ 内容变高 → maxScrollY 变大（~1227 → 1511）
   ↓
fling 仍在空转（竖向不 abort）→ 每帧 scrollTo(0, currY)
   ↓
scrollTo 被钳到**当时**的 maxScrollY = 1511（新的底部）
   ↓
scrollY 从 517 一路"吸"到 1511 ⇒ 用户看到"跳到底/卡住"
```

**旁证**：`滚动段=4668ms/80次` —— **4.6 秒的滚动段**，远超正常 fling（通常 1~2 秒）⇒ **印证 fling 在长时间空转**。

> 注：前三轮只有这一条 `前Y≠后Y`，是因为另外几次 `前Y` 都是 `0`（用户没停在中部）。
> **要触发它，需要"滑到中部 + fling 还在跑 + 此时插入"三个条件同时成立** —— 这也解释了为什么这个卡顿"偶发但烦人"。

## 二、⚠️ 两条"看起来是，其实不是"

### 2.1 `右栏=滑动中` 的 107ms 尖峰 —— 又是 jar 装载

帧埋点：`最差=107ms@13:36:15(站点在跑) ｜最差帧当时[右栏=滑动中 …]`

毫秒级现场：
```
13:36:14.962  l1box-search-4 线程 exec dex
13:36:15.017  自定义爬虫代码加载成功！
13:36:15.028  ⭐ WebViewFactory: Loading
13:36:15.126  Quality: Skipped: true 12 cost 104.62409   ← 系统级帧耗时 104.6ms
```
⇒ 与帧埋点的 107ms 吻合。**真凶仍是「jar 装载 → WebView 初始化」**，不是右栏本身。
⇒ `右栏=滑动中` 只是说明"当时用户恰好在滑"，是**巧合**，不是因果。

### 2.2 ⭐ WebView 初始化**不是"每进程一次"**，而是**每个新 jar 一次**

第 0 轮 323ms、第 2 轮 107ms —— 两次都伴随 `WebViewFactory: Loading`。
原因：**加固 jar 走独立 `DexClassLoader`，每个 classloader 有独立类空间** ⇒ 每个新 jar 首次用到
WebView 时都要**重新初始化一遍**（`nativeloader: Configuring clns-10/11 … WebViewGoogle64CN` 可证）。

⇒ **这是"搜索时滑动卡顿"真正的、可重复的来源**（不是偶发）。

## 四、🔧 修改方案（左右一起改）

### 左栏 —— 3 项（全部有数据支撑）

#### L-A. 修 fling 边界：`maxHeight` → `maxScrollY`

**文件**：`TabLayout/src/main/java/com/angcyo/tablayout/DslTabLayout.kt`
```kotlin
// onFlingChange（竖向分支）
startFling(-velocity.toInt(), 0, maxHeight)      // 旧：内容总高（比真实可滚范围多一个视高）
startFling(-velocity.toInt(), 0, maxScrollY)     // 新：与实际钳制范围一致
```
**收益**：fling 不再"多算一整个视高的行程"，撞界即停。

#### L-B. 修越界中止：竖向要判 `currY`

**同文件 `computeScroll`**：
```kotlin
if (_overScroller.currX < minScrollX || _overScroller.currX > maxScrollX) {
    _overScroller.abortAnimation()      // 旧：只查 X ⇒ 竖向 fling 永不中止
}
// 新：
if (isHorizontal()) { 判 currX } else { 判 currY 是否越界 }
```
**收益**：**这一条直接掐掉"滚动被吸到底部"的根**（空转没了，就不会用新的 maxScrollY 去钳制）。

#### L-C. 放开"追加"的守卫，只保留"清空重建"的守卫

**文件**：`FastSearchActivity.kt`
```kotlin
// 现状：siteTabsBusy() 时 drainSiteTabQueue / flushSiteTabsNow 一律 return ⇒ 滑动中零更新
// 改法：
//   · 追加（siteTabsPending → addView）      → 滑动中**也允许**
//   · 清空重建（siteTabsNeedReset → removeAllViews）→ 滑动中**继续禁止**
```
**依据**：`addView` 是**追加到末尾**，不移除也不移动已有子 View；且实测中"追加"本身从未直接改变滚动位置
（唯一那次 517→1511 是 **fling 空转**造成，不是 addView 本身）⇒ 先修 L-A/L-B，追加就是安全的。
**收益**：滑动时能看到站点陆续出现 ⇒ 直接消除「一滑动就停止出结果」。

> **退路**：若真机上追加仍引发 ACTION_CANCEL，退化为「滑动中追加也限流」（如每 200ms ≤2 个），
> 而不是像现在一刀切全禁。

### 右栏 —— 1 项（依据较弱，属"顺手排雷"）

#### R-A. 关掉 `tv_selectedItemIsCentered`

**文件**：`app/src/main/res/layout/activity_fast_search.xml`（`mGridView`，L162）
```xml
app:tv_selectedItemIsCentered="true"   →   "false"    （或整行删除）
```
**依据**：字节码证明该开关会走 `requestChildRectangleOnScreen`（选中项居中），
**触摸滑动不经过**，但**触摸后 item 获得焦点时可能触发**额外居中滚动 ⇒ 正是"停下时又顿一下"的形状。
**保留 `mGridViewFilter` 不动**，作为对照。
**风险**：若该属性被遥控器焦点导航依赖，可能影响 D-pad 居中 —— 本 fork 以触摸为主，风险低。

### 明确**不改**的（有数据反面支撑）

| 项 | 为什么不动 |
|---|---|
| R1/R2/R4（停稳三件活、高频取消） | 三次实测合计 **0~3ms**，不是问题 |
| L5/L6（chip 创建成本） | 批量多为 1~4；`getSiteTextView` 不是可见卡顿来源 |
| WebView 初始化（323ms / 107ms） | **架构性**：每个独立 classloader 都要重来一遍。本轮**不动**，另立方案（预热/减少装载） |
| L4（chip<18 拖不动） | 内容确实不足以滚动，属合理行为；可后续考虑加 overscroll 反馈 |
| 站点爬虫 NPE | 属站点自身缺陷，非本项目 |

| 判据 | 期望 |
