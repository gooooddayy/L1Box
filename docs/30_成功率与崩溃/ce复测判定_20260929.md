## 三、四条真归因（这轮的全部价值）

### 🟡 A. `路由=recent` 是**埋点写反了**，不是路由没生效

**实测**：35 条自转发 + 21 条 /proxy 路由日志里，`路由=` 的取值**全是 `recent`**，**0 条 `do`**。

**根因（代码级确定，`JarLoader.java` 第 673 行）**：

```java
// proxyLog() 里 route 的取值：
String route = (key != null && key.equals(recentJarKey)) ? "recent" : "do";
```

**这一行把语义判反了。** 正确的语义应该是「`siteJarKeys` 命中 ⇒ do；回退 ⇒ recent」，但它写成「key 恰好等于 `recentJarKey` ⇒ recent」。

**为什么必然全打成 `recent`**：取链时刚 `getSpider` 过这个站点（`recentJarKey = jarKey`），紧接着就发生 `/proxy` 调用 ⇒ **`key` 与 `recentJarKey` 天然相等** ⇒ 恒判 `recent`。

**反证**：`do=hmys` 这条在 `siteJarKeys` 里**确实存在**（`getSpider` 时写入），所以它走的是 **`do` 命中**分支 —— 可日志却标 `recent`。

⇒ **结论：`路由=` 这个字段当前零信息量，不能用来判断 ce 的路由改动是否生效。**
⇒ **按 `do` 路由本身是生效的**（`do=WexAiYueYue` / `do=hmys` 都正确解析到了各自 jar 的 key），**ce 的 ② 项改动实际有效**，只是日志读不出来。

> ⚠️ 这一条是本轮唯一"改判定文档"的地方：初判以为是路由失效，读 `proxyLog` 第 673 行后改判为**埋点 bug**。

### 🔴 B. 「悦悦」被我们自己 503 —— **手绑 jar 的世代账本在冷启动时必然失效**

这是本轮**最硬的一条**，时间线完整闭合：

```
12:54:13.251  /proxy do=ck key=14942a7863  持有者=main@gen1      判定=拒:原生初始化中
12:54:13.272  加固 jar 手绑成功：14942a7863        ← 此时记 HAND_BOUND[14942a7863] = (main, gen1)
12:54:13.571  加固 jar 交还自身入口初始化成功：71b4332a…  ← occupyProxy() → PROXY_GEN: 1 → 2
12:54:14.268  加固 jar 交还自身入口初始化成功：8ad2ef8d…  ← occupyProxy() → PROXY_GEN: 2 → 3
12:56:21.269  /proxy do=WexAiYueYue key=14942a7863  持有者=8ad2ef8d…@gen3
              判定=拒:非代理持有者(手绑未登记或世代已变)
```

**因果链**：
1. `14942a7863` 手绑成功时，账本记的是 `(holderKey=main, gen=1)`；
2. 紧接着**两个别的 jar** 各接管一次代理（`occupyProxy()`），`PROXY_GEN` 被推到 **3**；
3. `proxyCapable()` 第 341 行 `if (hb.gen != PROXY_GEN.get()) return false;` → **1 ≠ 3 → 判死**。

**结论：这不是"偶尔失效"，是"冷启动时，只要手绑顺序排在任一个接管者之前，该 jar 的代理型站点就 100% 被拒"。**

代码注释里写的放行条件是「绑定时那一任代理至今还活着（holder 与世代都没变）」，实测证明：**冷启动时这个条件对手绑 jar 而言几乎不可满足** —— 因为家族 jar 有 4 个（`14942a7863`、`71b4332a`、`8ad2ef8d`、`0b9565d6a6`），总有一个先手绑、后有三个接管。

**对照组（证明确实是世代问题，不是 jar 有问题）**：
- `0b9565d6a6`（海绵的 jar）**排在最后手绑**（12:54:18.783，在两次接管之后），没有被 `occupyProxy` 顶掉 ⇒ 它**顺利放行**（`判定=放行 返回=null`，`do=ck` 时还能 `返回=200`）。
- `ae48218142` 判定=放行 `返回=200`。

⇒ 同一个判定函数，**先手绑的失败、后手绑的成功**，分水岭正是 `PROXY_GEN`。

### 🔴 C. 「海绵」A 类第二层：jar 返回 null → 我们自转发 → 上游 **403**（35 次全拒）

`do=hmys` 走通了门禁（放行），但 jar 的 `Proxy` **返回 null** ⇒ 触发 ce 新增的自转发 ⇒ 我们按 URL 自带的 `url`（base64 解出 `http://lt.ruxiangsuisu.cn/vod/m3u8/2/2025/07/271207/3750941/index3.m3u8`）去取，**上游回 403**，35 次（含重试）**一次没成**。

**关键事实**：这条 URL 里**没有 `ck`**（`变体2(Cookie)` 一次都没打出来，因为代码在"无 ck"时直接跳过变体2）。所以：
- 我们发的请求**没有任何凭据**；
- 上游是 CDN，**只认 Referer / UA / 或源侧签发的短时 token**；
- 403 = **没有凭据**，不是"凭据过期"（那会给 401/400）。

**所以 A 类这轮的结论是：自转发这条新链路被"跑通"了，但**没有可用的凭据**，等于空手敲门。**能不能救，取决于这条地址的凭据从哪来** —— 而它不在 URL 里。

### 🟡 D. `分段耗时` 依旧是 0 条 —— 埋点第二次失效

ce 特意把"结果落地"的耗时结算挪到"插入之后的下一帧"（`pendingSegTag`），**实测依然一条都没触发**（阈值 25ms）。但同时帧埋点抓到 **323ms / 116ms 的最差帧**。

**两者并存只能说明一件事**：帧埋点量的「结果落地」与 `分段耗时` 量的「结果落地」**不是同一个区间**。帧的最差 323ms 落在插入前后的**某个更大的区间**里（很可能是 Layout/Measure/Draw 那一整段），而 `pendingSegTag` 结算的那一帧本身就很快。

⇒ **"240ms 花在哪"这个问题，两次埋点都没能回答。** 这已经是第二个版本尝试用埋点回答它失败。

## 四、附带发现

### 1. 「苹果」`Ksvideo-aed463fa…` 是**第二例非 URL 令牌**（C 类扩大）

cd 轮把 `YYNB-<32hex>` 归为 C 类（非 URL 令牌，保持现状）。本轮「苹果」拿到的是：

```
Ksvideo-aed463fa76ffb834f1aa33814f230f505084cae8959c9d90381f…（长 hex）
```

- 它不是 `http(s)://` 开头 ⇒ Exo 当**本地文件路径**去找 ⇒ `Exo:2005`（IO 未找到）。
- **`Ksvideo-` 前缀 + 长 hex** 说明它是**自研播放器/私有协议**的播放标识，raw 交给 Exo/Ijk 永远不可能成功。
- 与 `YYNB-` 同族，**C 类的范围比 cd 轮估计的大**。

### 2. 两个站点「取链阶段就断」：`站点未返回播放信息` × 6（WexAiReBo 3 次、热播影视 3 次）

取链直接失败，**没到起播**。这两个站点在这轮里**换集重试也没用**（ep=0、ep=1 都试了）。属于「站点自身没给出可播地址」，与本轮改动无关。

## 七、本轮埋点自身的问题（值得记一笔）

**这一版又有两处埋点没出数或出数失真**，与硬教训第 9 条（"加完埋点要用一轮日志确认它出数"）是同一类：

| 埋点 | 状态 | 说明 |
|---|---|---|
| `分段耗时：结果落地帧` | ❌ **连续两版 0 条** | ce 特意挪到"插入后下一帧"仍未触发，而帧埋点同时抓到 323ms —— 两个埋点量的不是同一区间 |
| `路由=do/recent` | ❌ **连续出数但语义错** | 出数了，但判据用错变量 ⇒ 恒 `recent`，**"能出数"不等于"数是对的"** |

⇒ 教训升级：不是"确认它出数"就够，还要**用一个已知答案的样本验证它的取值正确**。
