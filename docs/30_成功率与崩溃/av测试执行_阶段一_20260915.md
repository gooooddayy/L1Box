`ExoPlayerImpl: Release` 正常出现 → 失败后播放器被干净释放，无泄漏。

### 3.2 ❌ 发现缺陷：取链失败后，加载浮层永不消失

**现象**（真机截图 `av失败后浮层残留_20260915.png`）：断网从详情页点选集 → 取链失败 → 界面**永久**停在「正在获取播放信息」+ 转圈。实测 **65 秒后浮层仍在**，只有一条 2 秒的 Toast 一闪而过。

**根因**（`PlayFragment.java`）：

```java
void errorWithRetry(String err, boolean finish) {
    if (!autoRetry() && isAdded()) {
        if (finish) Toast.makeText(mContext, err, Toast.LENGTH_SHORT).show();  // ← 取链失败走这
        else        setTip(err, false, true);
    }
}
```

取链失败的出口是 `errorWithRetry("获取播放信息错误", true)` —— `finish=true`，**只弹 Toast，不清理 tip 浮层**。而每次开始取链时 `play()` 会 `setTip("正在获取播放信息", true, false)`（带 loading 的浮层），失败时没人把它关掉。

**性质**：**上游既有缺陷**，不是本批引入（`errorWithRetry` 的这段逻辑是原有代码，被注释掉的旧 Toast 也印证）。但它**任何源取链失败都会触发**，影响观感严重（用户以为还在加载）。

**建议修法**（成本低，一行量级）：取链失败出口改为先关浮层再给提示，即把 `finish` 传 `false`，或在该出口显式 `setTip("获取播放信息错误", false, true)`（错误态、不转圈、可重试）。

### 3.3 一个测量口径的更正

`播放失败：取链 reason=站点未返回播放信息 ms=-1` 里的 `ms=-1` **是源码写死的**（回调内失败没有可测耗时），不是埋点缺陷。

## 四、场景 C：限速构造 —— 本机三条路都走不通（如实说明）

原计划用「系统级 HTTP 代理 + PC 端限速」造出「有数据在流、但出不来画面」。**已搭好并验证了隧道**（`adb reverse` + 限速代理，设备 `curl -x 127.0.0.1:8899` 实测 200/0.3s 通过），但**无法让 App 走这个代理**：

| 途径 | 结果 |
|---|---|
| `settings put global http_proxy` | ❌ `SecurityException`：shell(uid 2000) 无 `WRITE_SECURE_SETTINGS` |
| `content insert --uri content://settings/global` | ❌ 同样被 SettingsProvider 拒绝 |
| `cmd wifi` 子命令 | ❌ 全量帮助里**没有**任何代理相关子命令 |
| Wi-Fi 详情页 GUI | ❌ ColorOS 阉割，只有"断开/取消保存/分享"，无「代理」入口 |
| `am start .../proxy.ProxySettings`、`.../wifi.WifiProxySettings` | ❌ Activity 不存在 |

（设备未 root、且 PC `192.168.x.x` 与设备 `192.168.x.x/23` **不同网段**，直连方案也不成立。）

**后果**：本批 7 项改动里，有 4 项**依赖"空转"场景才能真机验证**（看门狗判据收紧 / 重新武装 / 90 秒预算 / 变形重试后用原地址）。这 4 项目前在 av 上**只有机制论证，没有真机空转证据**——它们同时也是本批最大的风险面（判死误杀）。

**替代覆盖**：
1. **反向已覆盖**：场景 D 的 11 次正常起播 + 场景 B，**看门狗触发 0 次** ⇒ 「不误杀」这一面有真机数据。
2. **正向未覆盖**：'空转能否在 32 秒内被终裁' 无真机样本 —— **如实标注为未验证**。
3. 机制侧有闸门断言固化（Z 节），且逻辑上：判据已排除「有网速」这一项，只认「离开 PREPARING」或「位置推进」。

> 若你愿意，可以把手机临时连到一个**能限速的路由器/软 AP**上，或在有 root 的设备上复测 —— 那是唯一能补上这块证据的途径。
