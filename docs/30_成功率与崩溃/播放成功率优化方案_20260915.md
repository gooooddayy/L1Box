# 播放成功率优化方案（2026-09-15 · 定稿 v4）

> **用户拍板（全部确认完毕，可直接开工）**
> 1. **不做**自动换线路 / 自动换站点；失败提示里**不出现「去换源」引导**（我们本来就是多源）。
> 2. **去广告取舍**：净化预取 **2.5 秒**超时，超时即直连起播（**起播优先**，个别源不再过滤片头广告）。
> 3. **分两批**出包验证。
> 4. **起播看门狗 20 秒**（"完全没有数据到达"才判失败）。
> 范围＝**在同一个地址上，把能试的都试完；试不动时，快速、明确地告诉用户结果。**
> 全部结论来自当前源码（as 版）逐行核对，附行号。

## 一、失败三分类

| 类别 | 现象 | 真实原因 | 能治吗 |
|---|---|---|---|
| **甲类 取链失败** | 一直停在「正在获取播放信息」/ 弹「获取播放信息错误」 | 站点 jar 卡死（**无超时**）、抛异常被吞、返回的 header 解析失败 | 部分能：**保证 12 秒内一定有结论** |
| **乙类 拿到链但播不出** | 立刻「视频播放出错」；**或黑屏转圈一直不报错** | 防盗链头不对/缺、地址已失效、**容器没被正确识别**、分片被净化误删、连接挂死、硬解不支持 | **大部分能** |
| **丙类 能播但慢** | 起播十几秒、缓冲多 | **为去广告先完整下载一遍 m3u8**（有跳转再下一遍，**实测最长白等 20s**：OkGo 全局超时 `10s`×2，`OkGoHelper:39`）；软解首帧慢 | 能 |

## 三、播放器兼容性：三个问题的事实回答

### 3.1 「播放器兼容性是所有人都一样吗？」

**起点一样，终点不一样；而且和机型无关。**

| 决定项 | 出处 | 说明 |
|---|---|---|
| **出厂默认 = Exo，全局统一** | `App.java:235` `putDefault(PLAY_TYPE, 2)` | 硬编码。**没有任何"低配机自动换 IJK"的逻辑** |
| **站点可覆盖** | `ApiConfig.java:604` → `SourceBean:17`；`PF:1229` 优先用站点的 | 这是"同一台机器不同站点行为不同"的头号来源 |
| **用户可改默认** | `SettingActivity.kt:183-201` | 写 Hawk，全局生效 |
| **外部播放器** | `PlayerHelper.getPlayersExistInfo():190` | 只有装了才进候选 |

设备差异**不在"用哪个播放器"**，而在"同一个 Exo 的缓冲档位不同"：`EXOmPlayer:42` → `L1LoadControl.create(DeviceProfile.bufferTier())`（150s/48MB、240s/72MB、300s/96MB）。低配机缓冲小 → 同一个地址更容易卡/超时。

> **原则**：**不按机型猜播放器**（会让问题变成"某些机器永远只能用 IJK"、换台机器复现不了）。
> 正确做法＝**同一起点 + 按结果降级**（B1）。

### 3.2 「自动切播放器 / 提醒切播放器，有吗？」

**都有，两套重叠 + 一个真 bug。先澄清：自动路径本来就已经只走内置播放器**（`VC:908` 注释写明：原先走 `mPlayerBtn.performClick()` 会唤起 MX/VLC，已改为 `switchToNextInternalPlayer()`）。**"自动唤起外部播放器"不存在**；真正会误唤的是**手动短按**那条路。

| 机制 | 位置 | 行为 | 问题 |
|---|---|---|---|
| **自动切（A 套）** | `PF:784-788` | Toast「播放出错,正在尝试切换播放器」+ `switchToNextInternalPlayer()`（`VC:914`，IJK ⇄ Exo 对切） | **`retriedSwitchPlayer`（PF:163）只置一次、永不复位**（`changeParse` PF:312 也不复位）→ **第二集起彻底失去这层保护** |
| **提醒切（A 套·第二次起）** | `PF:790-796` | 橙色可点击「切换播放器」文字链 → `mPlayerBtn.performClick()`（`VC:504`） | 该短按＝"跳到候选下一档"，顺序来自 `getExistPlayerTypes()` 的 **HashMap 迭代序（不确定）且含 10~14 号外部播放器** → **可能一下唤起 MX/VLC** |
| **自动降级链（B 套）** | `errReplay()` PF:335 → `compatFallback()` PF:1389 | 按 `buildCompatFallbackPlan`（`PlayerHelper:271`，**IJK 软解 → Exo**）逐档重播**同一地址**，每集 2 档；`fbKey = playFlag#playIndex` **换集自动复位（这套做对了）** | 与 A 套重叠 |
| **同址重播（C 套）** | `errorWithRetry` PF:807 → `autoRetry()` PF:1409 | 先试 `loadFoundVideoUrls` 里其他地址，再 `play(false)` 重播一次 | 排在上面之后＝第三次机会 |

**真实路径**＝同一错误依次触发三套，且 A 套切完会把 `pl` 经 `updatePlayerCfg()`（PF:323）写回该集配置 → 换集后口径可能与用户默认不一致。**方案：合成一条有顺序、有总额度、按集复位的链（B1）。**

### 3.3「换源不用提醒」→ 已采纳

删掉「返回换源」入口；失败只给**明确原因 + 可点击「重试」**，全案不出现"换源"字样。

## 四、内核与兼容性：要不要换"更强的播放器"？

### 4.1 你现在这套内核的实际配置（逐项核过）

| 项 | 现状 | 出处 |
|---|---|---|
| **主播放器** | **ExoPlayer 2.18.7**（Exo2，非 Media3） | `player/build.gradle:32` |
| **Exo 数据源** | **OkHttpDataSource**（不是 Exo 默认的 `DefaultHttpDataSource`，更可控） | `ExoMediaSourceHelper:179` |
| **Exo 音频软解** | **已开**：`EXTENSION_RENDERER_MODE_PREFER` + 工程自带 `ext.ffmpeg.FfmpegAudioRenderer` + `libffmpeg_jni.so` | `ExoMediaPlayer:59` |
| **Exo 视频软解** | **没有**（`ext/ffmpeg` 只有 4 个 *Audio* 文件） | `player/src/.../ext/ffmpeg/` |
| **Exo 硬解失败回退** | **未开启**（全工程无 `setEnableDecoderFallback` 调用） | grep 空 |
| **Exo HLS/TS 调优** | 已有 `FLAG_ENABLE_HDMV_DTS_AUDIO_STREAMS` + 时间戳搜索窗口 ×3 | `ExoMediaSourceHelper:131` |
| **Exo 容器识别** | **只按扩展名**判 `.m3u8`/`.mpd`；失败一次后才强制 m3u8（104-108） | `ExoMediaSourceHelper:135-144` |
| **Exo 隧道模式** | **开启**（`setTunnelingEnabled(true)`，上游原样） | `ExoMediaPlayer:66` |
| **Exo UA 处理** | 反射改**单例** Factory 的 `userAgent` + `headers.remove("User-Agent")` 改调用方 Map | `ExoMediaSourceHelper:186-208` |
| **Exo 跨协议重定向** | `setAllowCrossProtocolRedirects` **被注释掉** | `ExoMediaSourceHelper:181` |
| **全局 OkHttp 超时** | connect/read/write 各 **10s** | `OkGoHelper:39,145-147` |
| **兜底播放器** | **IJK 全功能 so**：`libijkffmpeg.so` **12.5MB** + ijkffmpeg/ijksdl/avcodec/avutil/swresample | `player/src/main/jniLibs/` |
| **IJK 软/硬解** | 两套预设（"软解码" `mediacodec=0` / "硬解码" `mediacodec=1`），默认**硬解码** | `ApiConfig:886/1146`；`App:236` |
| **IJK 其他调优** | `framedrop=5`、`protocol_whitelist` 很全、DNS 缓存、RTSP 参数、可缓存播放 | `IjkMediaPlayer:52-63,98` |
| 包内另有 | `libxl_thunder_sdk.so`(5.6MB)+`libp2p.so`(5.3MB)+`thunder.jar`（迅雷 P2P 引擎） | `jniLibs` |

### 4.2 「都用 Exo，是不是都差不多？别人会不会更强？」

**判断：真正决定成功率的是宿主这三层——而这三层我们还有确定性缺口。**

| 层 | 谁决定 | 换内核能解决吗 |
|---|---|---|
| **① 地址与请求头**（Referer / UA / 防盗链 / 重定向） | 宿主代码 | ❌ |
| **② 容器识别**（这地址到底是不是 HLS） | 宿主代码 | ❌ |
| **③ 网络层**（超时、重试、挂死） | 宿主代码 | ❌ |
| **④ 解码能力**（硬解不支持的编码） | 内核 | ✅ 只有这层 |

- Exo 是 Google 开源库，**代码同一份、版本不同**（我们 2.18.7＝2022 年底，主流已到 Media3 1.x）。版本差异真实存在，但升级要动整个 `player` 模块 + dkplayer 依赖，**风险与收益不成比例**。
- 极少数 App 内置 **mpv 内核**（兼容性上限最高），但体积、TV 遥控交互、功耗代价大，不适合做默认。
- **"别人播得出我播不出"，多数是 ①②③ 做得更细**，而不是内核更贵。

**结论：不换内核。** 现有搭配（Exo 主力 + IJK 全功能兜底 + Exo 音频软解 + OkHttp 数据源 + 外部播放器可选）已接近 TVBox 生态主流上限。

### 4.3 四个新增可优化点

| 编号 | 问题 | 改什么 | 风险 |
|---|---|---|---|
| **C4** | **容器识别结果没传给播放器**：净化阶段已 GET 到内容、也判过 `#EXTM3U`（`PF:921`），但**只用来决定"要不要去广告"，没告诉 Exo"这是 HLS"** → Exo 仍按扩展名猜，不含 `.m3u8` 字样的地址先走 Progressive → **先失败一次**才靠 `errorCode` 补救（观感＝"第一下播不出、切一下就好"） | 把已知判定**显式传给播放器**（媒体项直接标 HLS）；保留 Exo 原有 `errorCode` 补救 | 低 |
| **B7** | **硬解失败无回退**：机器硬解不支持该编码时直接报错，而 IJK 软解明明能放 | Exo 开 `setEnableDecoderFallback(true)`：**仅当解码器初始化失败**时换同编码软解解码器 | 低 |
| **B8** | **UA 残留**：`setHeaders` 反射改的是**单例** Factory 的 `userAgent` → **A 站设的 UA 残留到 B 站**；`headers.remove()` 还改调用方 Map | 改为**每个媒体源独立 Factory 副本**，不反射改单例 | 低（影响面广，需回归） |
| **B9** | **隧道模式**（`setTunnelingEnabled(true)`）在部分机型上会导致"有声音没画面" | **先埋点观察**，暂不改 | 先不动 |

## 六、明确不做

| 不做 | 理由 |
|---|---|
| 自动换同站线路 / 跨站换源 | 用户拍板：换源是用户的手动决定 |
| 失败提示里引导"去换源" | 用户拍板：我们本来就是多源，提醒多余 |

| 结果缓存、慢源分档超时 | 与"不把 0 结果当结论"的既有口径冲突 |
| 改搜索 / 详情页逻辑 | 本轮只碰播放链路，避免与刚归档的 as 混批 |

## 八、两批执行计划（用户定：分两批）

### 第一批｜速度 + 兜底正确性 + 埋点（8 项，零行为预期变更）

**A1、A2、B1、B2、B3、B4、C4、D2**

选这套的理由：全部落在"同一地址内的既定行为"上，**不新增任何用户可见入口**，且埋点就位后所有收益可量化。

**验证口径**
1. 冷启动 → 不同站点各点播若干部（含第 2 集及以后）。
2. 靶心①：**起播耗时中位数下降**（`stage=起播 ms`）。
3. 靶心②：`stage=兜底` **不得只在 ep=1 出现**（B1 生效的直接证据）。
4. 靶心③：`stage=起播 fail reason=no_frame` 可观测（B3 生效）；**不得出现"本该能播却被判死"**。
5. 重点回归：**B4 是否误杀软解源**（IJK 超时改变了失败时机）。
6. 崩溃线：`Fatal signal 6` / JNI / 拒载 **必须保持 0**。

### 第二批｜兼容增强 + 手动菜单 + 出口 UX（9 项）

**B5、B6、B7、B8、B9、C1、C2、C3、D1**

**验证口径**
1. **B6 手动菜单**：短按按 `Exo → IJK硬解 → IJK软解` 固定循环（不再可能跳到 MX/VLC）；长按列表含「IJK(硬解码)」「IJK(软解码)」两项，一次点选同时定播放器+解码。
2. **B8**：连续在两个不同站点播（A 站给 UA、B 站不给），确认 B 站不串用 A 站 UA。
3. **B7**：`stage=起播 reason=decoder_init` 后成功 的次数可观测。
4. **B9**：隧道观察数据（有声音没画面的次数）。
5. 崩溃线同样必须为 0。

### B6 手动菜单定稿

| 入口 | 定稿行为 |
|---|---|
| 自动 | 只在 IJK/Exo 之间切，且带解码档：`当前 → IJK软解 → Exo`（＝现有 `buildCompatFallbackPlan` 顺序），**不碰外部播放器** |
| 手动短按 | **写死顺序循环**：`Exo → IJK硬解 → IJK软解 → Exo`，**不含外部播放器**（不再依赖 HashMap 顺序） |
| 手动长按 | **完整列表**：`Exo播放器 / IJK(硬解码) / IJK(软解码) / MX / VLC / Kodi …` —— 一次点选同时决定"哪个播放器 + 哪种解码" |
| `play_ijk` 按钮 | 保留（`VC:593`，仅 `pl==1` 可见）作为解码快捷入口 |

## 九、验收指标

| 指标 | 口径 | 目标 |
|---|---|---|
| 起播成功率 | 出现画面次数 / 点击播放次数 | 相对 as 提升 |
| **"永久卡住"次数** | `stage=取链` 无结论的行数 | **0** |
| 起播耗时中位数 | `stage=起播` 的 ms 中位数 | 明显下降（A1） |
| **容器误判次数** | 走了 Progressive 又回退 HLS 的次数 | 归零（C4） |
| **硬解回退次数** | `stage=起播 reason=decoder_init` 后成功 | 可观测（B7） |
| 黑屏转圈判定 | `stage=起播 fail reason=no_frame` | 可观测（B3） |
| **第 2 集及以后的降级可用性** | `stage=兜底` 的集数分布 | **不得只在 ep=1 出现**（B1） |
| 崩溃线 | `Fatal signal 6` / JNI / 拒载 | **必须保持 0** |

## 十、诚实边界

- **整站失效 / 地址已死 / 鉴权头推不出来** —— 只能靠用户手动换源，程序侧无解（本方案也不再提示）。
- **站点自身取链慢** —— 宿主只能保证 12 秒给结论。
- **编码本身超出内置能力** —— Exo 无视频软解，IJK 软解是唯一内层兜底；两者都放不了只能靠外部播放器（用户手动）。
- **A1 的代价** —— 净化超 2.5s 的源**本轮不再过滤片头广告**（用户已确认接受）。
- **不升级内核的代价** —— Exo 2.18.7 在新设备/新 HLS 变体上的个别兼容问题**不会**被本方案修掉，这是刻意接受的风险（§4.2）。
- 本方案不碰 jar 装载节奏 → 崩溃面理论上为零；但 **B4（IJK 超时）会改变 IJK 的失败时机**、**B7 会新增一条软解回退路径**，验证时重点看这两处。
