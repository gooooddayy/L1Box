# cm 取证判定（2026-09-30）—— "断触"的真相

> 数据：`_cm_trace.log`（23.3 MB，2 轮搜索，110 次按下）
> 用户澄清关键前提：**「我说的快速滑动，就是上一次滑动的惯性还没结束后就开始下一次滑动」**

---

## 一、先排除三条（都有硬数据）

### ❌ 排除 1：不是 `ACTION_CANCEL`（手势从未被系统中断）

```
★CANCEL  出现次数 = 0
DOWN = 110 ，UP = 110   ← 完美配平
```
⇒ **系统从未取消过任何一次手势。** 用户感觉的"断触"**不是**系统级的触摸中断。

### ❌ 排除 2：不是"插入 chip 导致的"（早已被 cl 版证伪）

### ❌ 排除 3：不是"位移被门槛吞掉"

反编译 + 源码双查：`_touchSlop` 的赋值那行**被注释掉了**
```kotlin
var _touchSlop = 0
//_touchSlop = vc.scaledTouchSlop      ← 注释状态 ⇒ 阈值恒为 0
```
⇒ `absY > _touchSlop` 恒成立 ⇒ **只要有位移就滚动**，不存在"每帧位移不足被丢弃"。

> 补充：`★左栏开始拦截` 出现 60 次，但**不产生任何副作用** ——
> 因为 `★CANCEL` 为 0 说明**左栏的 chip 不消费触摸**（`mFirstTouchTarget == null`），
> 既没有触摸目标，ViewGroup 拦截时自然无需发 CANCEL。**所以这 60 次"接管"是无害的。**

## 二、⭐⭐⭐ 真正的原因：**85% 的按下，都发生在"已经滑到边界"的状态**

```
DOWN 总数 110
  按下时已在【顶部 Y=0】      : 34
  按下时已在【底部 Y=上限】    : 60
  ⇒ 边界处合计               : 94 / 110 = 85%
```

**左栏的可滚范围本身极小**：

| 量 | 值 |
|---|---|
| `maxScrollY`（可滚范围）中位数 | **1937 px ≈ 2 屏** |
| 内容总高 | ≈ 4000 px ≈ **29 个站点** |
| 其中 101/110 次按下时 `maxScrollY ≥ 1000` | 即"内容全长也就 2 屏左右" |

⇒ **快速滑动（实测单帧位移可达数百 px）只要 2~3 下就撞到边界**；
**撞界之后无论怎么滑，内容都不会动一下** ⇒ 用户感受就是**「手在动、内容死住」= 断触**。

### 与用户描述的吻合度

| 用户的话 | 数据的解释 |
|---|---|
| "**快速**滑动的时候会断触" | 快速滑动 → 单帧位移大 → **2~3 下就撞界** → 之后全是"无响应" |
| "无论快滑慢滑都不断触" | 慢滑不易撞界，所以慢滑时"断触"少；**恰好对应用户说慢滑感觉好些** |
| "加载不加载主要是有断触的感觉" | 与加载无关 ✔ 数据里 `待落` 基本为 0 |

### 为什么会"感觉像断触"而不是"知道到底了"

因为 **`DslTabLayout` 是自定义 ViewGroup，没有边界反馈**（无 `EdgeEffect`、无回弹、无发光）。
标准 `RecyclerView` 撞界时会有**边缘光效**，用户一看就知道"到头了"；
而这里**什么反馈都没有** ⇒ 只能理解成"触摸坏了"。

## 三、右栏：惯性本身是好的，但**几乎每次都被中断**

### 后半段数据：惯性"尾 6 帧"大多不收敛

| # | 尾 6 帧（最后 6 帧的位移） | 说明 |
|---|---|---|
| 2 | `[17,18,16,16,17,9]` | **✔ 正常减速**（收敛到 ~10px） |
| 4 | `[85,83,93,80,80,83]` | ✘ 末尾仍有 80px/帧 ⇒ 突然停 |
| 6 | `[126,109,108,120,106,97]` | ✘ 末尾仍有 100+px |
| 19 | `[-106,-91,-163,-144,-142,-58]` | ✘ 末尾仍有 140+px |

⇒ 19 趟滑行里，**只有个别是自然减速到停**，绝大多数是**高速状态下被切断**。

### 状态迁移解释了原因

```
14:34:30.340 拖动 offset=0
14:34:30.421 惯性 offset=824      ← 松手，惯性开始
14:34:30.671 拖动 offset=4090     ← 149ms 后用户又按下 ⇒ 惯性被 abort
14:34:30.776 惯性 offset=3188     ← 再松手
14:34:30.987 静止 offset=0
```
**惯性阶段普遍只有 60~250ms 就被"拖动"取代** ⇒ 正是用户描述的操作方式
（上一次惯性没结束就接下一次）⇒ **每次按下 `abortAnimation()`，惯性清零重来**。

> ⚠️ **这是 Android 标准行为**（`RecyclerView` 同样如此：按下即停惯性）。
> 所以"惯性被中断"本身**不是 bug** —— 但如果用户期望"连续滑动时惯性叠加"，
> 那是**超出标准语义**的需求，需要单独确认。

### 另一个次要点：`突变` 0~18 次/趟

`突变`＝相邻两帧位移差 > 40px。平滑惯性不该有；最高 18 次/148 帧（12%）。
⇒ 滑行中确有突兀位移，但**与数据插入无关**（`待落` 全程为 0），
更可能是图片解码回调抢占主线程所致 ⇒ **列为次要观察项，不是本次主因**。

## 四、🎯 结论

| 侧 | 结论 |
|---|---|
| **左栏** | **不是"触摸断了"，而是"很快就撞到边界、撞界后毫无反馈"**。可滚范围仅约 2 屏（29 个站点），快速滑 2~3 下即到底；之后的所有滑动都无响应，观感＝断触。**根因是"缺边界反馈"，不是触摸处理有问题。** |
| **右栏** | **惯性逻辑本身正常**（有自然减速样本）；"尾帧不收敛"是因为**用户按下的操作方式**中断了惯性（标准行为）。次要观察：滑行有 0~18 次突变，疑似图片解码抢占，待单独验证。 |

## 五、🔬 下一步：一个能直接判定的实验（不用改代码）

**实验**：请在下一次测试中，**只在"中间位置"做连续快速滑动**（不要滑到顶/底）。

- **操作**：发起搜索 → 等站点出齐 → 把列表停在**中间** → 在这个位置**反复快速连续滑动 10 次**（每次都在惯性未结束时接下一次）
- **判据**：
  - **如果不断触** ⇒ 完全印证"断触＝撞界无反馈"，**改法就是给左栏加边界反馈**
  - **如果照样断触** ⇒ 说明另有原因，我再从"按下到响应的延迟"这个方向查

这个实验能把结论从"85% 相关"推到"因果确认"，而且**不用改代码**。

## 六、附：本轮新增的三条硬结论（可长期引用）

1. **`★CANCEL = 0`**：左栏手势从未被系统取消 ⇒ 任何"插入导致 CANCEL"的旧假设**永久排除**
2. **`_touchSlop` 恒为 0**（赋值被注释）⇒ 库内不存在"位移门槛吞帧"
3. **chip 不消费触摸**（`mFirstTouchTarget` 为空）⇒ ViewGroup 拦截时不会发 CANCEL ⇒
   "开始拦截"这个动作在左栏是**无副作用**的，不是断触来源
