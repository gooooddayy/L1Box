## 二、结论一：**"改 DNS 导致搜索变慢"不成立**（证据级别：能站住）

### ① 首条结果完全不受 DNS 影响 —— 这是最硬的一条
| 条件 | 首条结果 |
|---|---|
| 冷启 · DoH **关** | 2574 ms |
| 冷启 · DoH **开** | 2201 ms |
| 冷启 · DoH **开** | 2850 ms |

如果 DNS 是元凶，**最先变慢的一定是首条结果**（用户"等一下才看到东西"的正是这一段）。
但三种情况的差异 **≤650 ms，全部落在冷启自身的抖动里**，而且 DoH 开的时候还更快一点。

### ② 总耗时同样不支持 DNS
同是"冷启 + DoH 开"，自己跟自己就已经差了 **10.98 s ↔ 15.35 s**（4.4 s 抖动）；
DoH 关那份只有一个样本 18.58 s，**落在同条件的抖动范围之外不多**，且方向与"DNS 拖慢"相反。
⇒ 拿"11 s vs 18.6 s"当 DNS 的锅，**样本量根本不够**。

### ③ DoH 在一轮里的实际暴露面很小
`熔断跳过=22 / 28` ＋ `失败=14 / 8` ⇒ 一轮里真正发出去 DoH 查询只有 **38 次左右**，
连续 3 次失败就熔断 5 分钟（`L1DnsPolicy` 按设计生效）。**38 次查询解释不了 10 秒级的差**。
失败的域名是 `fffgood.com` / `app2.dsx.ac` / `www.hkybqufgh.com` / `wangerniu.hzhnl.com` / `dns.alidns.com`
—— 都是站点探活的广告/镜像域，**回退系统 DNS 后结果数一模一样（都是 244）**，功能上零影响。

> ⚠️ 反过来说一句公道话：**第一次（B）DoH 是关着的**（`命中/失败/熔断` 全 0、`直连=2169`），
> 而它是四轮里**最慢的一轮（18.58 s）**。也就是说，**当前这批数据的方向是"关了更慢"**，
> 但我不打算凭 n=1 反过来给 DoH 邀功 —— 正确表述是：**开关 DoH 对搜索耗时的影响，落在测量噪声里**。

## 三、结论二：慢在哪 —— **冷启要等加固 jar 的本地代理就绪**

### 冷热对比（同关键词、同源、同 40 站点）
| | 首条结果 | 一轮总耗时 | 本轮装载增量 |
|---|---|---|---|
| **热态**（spider 已在内存） | **56 ms** | **7.10 s** | 1 |
| **冷启**（进程刚起） | 2201~2850 ms | 10.98~18.58 s | **40** |

⇒ **首条差 40 倍（56 ms → 2.6 s），总耗时差 1.5~2.6 倍**。这是"冷启特别慢、第二次快一点"的**全部来源**。

### 冷启里 40 个站点的钱花在哪（以 pid 19035 为例，秒钟＝相对进程启动）
```
+1.2s   替身层加载成功（Toast/Process 已挂拦截）
+2.9s   搜索轮次开始            ← 用户点了搜索
+5.5s   搜索首条结果（剧圈99）
+5.5s   SpiderLog: 开始下载JSON配置获取下载链接和MD5... / JSON解析错误，无法获取MD5或下载链接
+10.7s  加固 jar 手绑成功（承接已有的本地代理，未重启）：0b9565d6…
+21.5s  搜索耗时：收尾 总耗时=18583ms
```
同型证据（另外两个冷启进程）：
```
pid 20093：手绑 +8.0s   → 收尾 +12.4s
pid 21389：手绑 +16.4s  → 收尾 +22.8s
```

### 🔴 最直接的一条：**站点在等一个还没起来的本机端口**
```
D/SpiderLog(18863): Failed to connect to /127.0.0.1:8964
D/SpiderLog(18863): java.net.ConnectException: Failed to connect to /127.0.0.1:8964
D/SpiderLog(18863): Caused by: java.net.ConnectException: failed to connect to /127.0.0.1
                    (port 8964) from /127.0.0.1 (port 41932) after 15000ms: isConnected failed: ECONNREFUSED
```
`8964 / 8965 / 8966 …` 是**加固 jar 自己起的本地代理端口**。
进程刚起时这些端口**还没监听**，而站点一初始化就去连它 ⇒ **每个连接等满 15 秒超时**才放弃。
这解释了：为什么首条能很快（不依赖代理的站点先返回）、
为什么尾巴能拖 8~16 秒（依赖代理的站点只能干等）、
为什么体感是"**一段一段的**"（能返回的先返回，等代理那批最后一起到）。

### 为什么 `本轮装载增量=40` 每次冷启都是满的
40 个站点的 spider 全部在这一轮里**首次创建**（含加固 jar 装载）。
这事本身**按需触发**（不搜不装），所以"提前预热让它静默"在冷启首搜里**根本无处可等**——
也正因如此，**预热方案在 ae/ai/al/am 四版就已经永久否决**（会抬高加固 jar 初始化密度 → killall 互杀）。**这条不改**。
