## 〇、一句话结论

冷启动时先用本地缓存（该订阅地址上次成功拉取的原文）把站点池填上，**打开 App 就能搜、结果立刻出**；网络配置到达后**自动补全**，补出来的结果**追加在后面**、已有结果原地不动。

## 一、用户四个追问的逐条答复

### 问题 1：同一来源 / 不同来源，方案会不会冲突？

**结论：两种场景都不冲突。** 因为「能不能命中缓存」完全由**地址哈希**决定，代码里不存在「用 A 源的清单去搜 B 源」的通路。

| 场景 | 缓存文件 | 行为 |
|---|---|---|
| **同一来源**（没换过订阅地址） | `MD5(当前地址)` 存在 | 用**同一个源**的上次快照起步。差异只有：源后来新增的站点（缓存里没有）、源后来删掉的站点（缓存里还有）。**这是 A 的主场景** |
| **不同来源 · 该地址以前用过**（切回来） | `MD5(新地址)` 存在 | 用的是**这个源自己**的旧内容。地址不同 ⇒ 文件不同 ⇒ 不可能串到别的源 |
| **不同来源 · 该地址首次用** | `MD5(新地址)` 不存在 | 预热**静默跳过**，退化成今天的行为。零副作用 |

依据：`ApiConfig.java:232` — 缓存文件路径 = `filesDir + "/" + MD5.encode(apiUrl)`，`apiUrl` 是**完整订阅地址**。

**唯一的观感不一致点**（早前已记录在案）：同一地址内容更新、某站点被源删掉时，该站的缓存结果会留在列表里（点进去可能失败）。
**处理：不动它** —— 从列表里摘掉会造成列表跳动，与「结果追加在后、不闪」的要求冲突。

### 问题 3：订阅源加载后还会加载缓存清单吗？

**结论：不会。** 全工程「读缓存」只有三处入口：

| 读取点 | 条件 | 何时发生 |
|---|---|---|
| `ApiConfig.java:233-241` | `useCache == true` 且缓存文件存在 | **只在「设置页改过 DNS/DoH 后返回首页」** |
| `ApiConfig.java:326` | 网络通了但内容解析失败 | 内容异常兜底 |
| `ApiConfig.java:352` | 弱网自动重试 2 次全失败 | 网络失败兜底 |

第一处的 `useCache` 来源链条（已逐环核实）：

```
HomeFragment.kt:493   loadConfig(onlyConfigChanged, ...)
  └ HomeFragment.kt:304   onlyConfigChanged = mainActivity.useCacheConfig
      └ MainActivity.kt:28   useCacheConfig = intent.extras.getBoolean(CACHE_CONFIG_CHANGED, false)
          └ SettingActivity.kt:308   bundle.putBoolean(CACHE_CONFIG_CHANGED, true)   ← 全工程唯一发出处
```

而 `SettingActivity.kt:299-313`（`onBackPressed`）的条件是：**改过 DNS/DoH，且没改直播源**。

⇒ 三条结论：

1. **冷启动不读缓存**（`onlyConfigChanged = false`）—— 今天就是这样；
2. **改过 DNS 从设置页返回会读缓存，且 `:236-237` 读完直接 `return`、不发网络请求** —— 这是**早就写在代码里的故意行为**（改 DNS 不影响订阅内容，没必要重拉），**与 A 无关**；
3. **订阅加载成功后，没有任何路径会再读缓存** —— 「池已就绪」不构成读缓存的条件。

**A 之后再加一层硬护栏**：预热只在「本次进程启动后第一次 ∧ 池为空」时执行一次，执行完置标志，**此后本次启动内永不读缓存**（one-shot）。

## 二、方案必须补的护栏（原方案文档漏掉的一环）

`parseJsonInternal:738` 会**无条件**把 `sitePoolSettled` 置为 `true`。缓存走的是**同一条解析路径** ⇒ 缓存一读，搜索页就会以为「网络配置已经定论了」。

**后果**：若缓存清单这一轮搜不到东西，`reviewZeroResult` 的四条判据（池就绪 / 问全 / 池未变 / 结果 0）会**全部成立** ⇒ 直接甩「暂无数据」⇒ **把 #2 刚消灭的假空请回来**。

**护栏**：新增 `bootPoolFromCache` 标志（缓存读置位、网络 parse 成功即清除），复检判据① 改为：

```kotlin
val poolReady = ApiConfig.get().isSitePoolSettled() && !ApiConfig.get().isPoolFromCache()
```

效果：缓存池 0 结果 ⇒ 判据① 不成立 ⇒ 转 S3 等网络池 ⇒ **自动重搜**（复用 #2 现有机制，**零新增状态**）。

## 三、机制设计

### 3.1 预热（`ApiConfig.java`）

```
loadConfig(false, ...)   ← 冷启动
  ├─ [新增] 未预热过 ∧ sourceBeanList 为空 ∧ MD5(apiUrl) 缓存存在
  │     → parseJson(apiUrl, cache)   ← 填池，毫秒级
  │     → cacheBootDone = true       ← one-shot 护栏
  │     → bootPoolFromCache = true   ← 供搜索页查询
  │     → 【不通知 callback】        ← 否则首页会以为加载完、提前走 jar 流程
  └─ 照常 doLoadConfigRequest(...)   ← 网络请求照发，不 return
        └─ onSuccess → parseJson → bootPoolFromCache = false   ← 池换成真清单
```

约束：
- 缓存文件**坏掉就静默跳过**，**绝不删除**（沿用 `useCacheFallback:271-272` 的既有原则：不做不可逆动作）；
- 不碰权限、不碰加固链路、不碰净化链路；
- `parseJson` 全程受 `synchronized (sourceBeanList)` 保护（`:714`）⇒ 与网络 parse 并发**不会撕裂站点池**。

### 3.2 补轮（`FastSearchActivity.kt`）

**A. 0 结果时 —— 复用现有 S3，零新增代码**

缓存池 0 结果 ⇒ 判据① 不成立 ⇒ `beginWait()` 进 S3 ⇒ 现有 `onWaitTick` 按 `poolSignature()` 变化 + 连续两拍一致触发重搜。**#2 的机制原样承接。**

**B. 有结果时 —— 新增「补全守卫」**

```
首波完成 ∧ 有结果 ∧ 本轮用的是缓存池(bootPoolFromCache)
  → 进入补全守卫：继续按 READY_RETRY_DELAY_MS 探 poolSignature()
  → 签名变化（连续两拍一致，沿用现有去抖）
  → searchResult(appendOnly = true)
```

`poolSignature()`（已存在，`:528-535`）＝ `池大小 | 定论 | JarLoader.loadSeq()` ⇒ **天然覆盖 jar 装载变化**，不需要新增判据。

**C. `searchResult(appendOnly: Boolean = false)`**

`appendOnly = true` 时：
1. **跳过**三处清空（`:773-774` 适配器、`:781` tab、`:782-783` 站点表）；
2. 站点列表 = 真池可搜站点中 **`key` 不在上一轮已搜集合里**的那些（新增 `roundAskedKeys`）；
3. 结果由 `flushSearchResults` 的 `addData` **追加**；tab 由 `addWordAdapterIfNeed` **增量补**。

**请求成本**：差集为空（源没变化）⇒ **补轮一个请求都不发**，直接收尾；源新增 2 个站点 ⇒ 只发 2 个请求。**符合「搜索请求数与并发节拍一个字不改」的风控口径。**

**D. 天然安全的两个点（不需要额外写）**

- 补轮若 0 结果：判据④ `zero = searchAdapter.data.size <= 0` ⇒ 列表里已有缓存轮结果 ⇒ `zero = false` ⇒ **不会给空态**；
- 补轮与首波并发：`searchResult()` 入口 `shutdownNow()` 掉上一轮线程池并 `allRunCount.set(0)`，不会串轮。

### 3.3 jar 站在缓存轮能不能搜到？——能

`JarLoader.getSpider:389-429`：jar 未装载时会**自己 `loadJarInternal` 按需下载**，兜底返回 `SpiderNull`（**不崩**）。

⇒ 缓存轮里 jar 站**照样能搜**，只是首次要等 jar 按需下来。而这个下载**做不做 A 都要发生**（`HomeFragment.kt:544-546` 的主动加载 与 搜索时的按需加载 二选一，都会下），所以 **A 不新增 jar 下载总次数**。

## 八、补充：换源场景复核（09-24 13:00 用户追问后）

用户三问：①缓存清单每次搜索都会执行吗？②订阅源正常加载后会自动刷新成新的吗？③不然用户切换源，结果显示的是上一轮的线路 —— 是不是换源后等订阅源加载一次就会刷新缓存清单？

**逐条答复（全部有行号依据）**

| 问 | 答 | 依据 |
|---|---|---|
| **每次搜索都读缓存吗** | **不是。搜索动作完全不碰缓存文件** —— 它只读内存站点池。读缓存只发生在**配置装载**阶段，且只有冷启动首次那一次 | `searchResult():804` 取 `ApiConfig.get().getSourceBeanList()`（内存池，非文件） |
| **订阅加载后会刷新缓存吗** | **会，而且是立刻。** 拉取成功 + 解析成功 ⇒ 删旧文件 + 写新内容 | `ApiConfig.java:304-317` |
| **换源会串源吗** | **不会。** 物理上：文件名 = `MD5(完整地址)`，切源后指向**另一个文件**；写缓存 `:312-313` 的 `cache.delete()` 只删**当前地址那一个**，源 A 的文件**原样留存**（将来切回 A 还能命中） | `ApiConfig.java:232`、`:308-317` |
| **换源加载一次就刷新缓存吗** | **是。** 换到 B 后正常用一次 ⇒ 写 `MD5(B)` ⇒ 以后用 B 时缓存就是 B 自己的最新内容 | 同上 |

**关键时序护栏（A 不会让"切源"变差）**：切源是**运行中**操作，那一刻 `sourceBeanList` 里还是源 A 的站点（**非空**）⇒ 预热条件「池为空」**不成立** ⇒ **切源时压根不读缓存**，走的仍是「网络请求 → `parseJson` 覆盖池」的原路径。

**一个与 A 无关的现状行为（A 不会拉长它）**：切源后、到新源配置返回之前，内存池仍是旧源的站点 ⇒ 这个窗口内搜索得到旧源结果。窗口长度 = 新源配置拉取耗时，**今天就存在**，A 不参与。

### 由此产生的一处方案优化：补全守卫判据改为「池签名变化」

原设计把补全守卫限定在「本轮用的是缓存池」。现在改为更通用的判据：

> **首波完成后池签名发生变化（连续两拍一致）⇒ 补一轮**

好处：

- 缓存预热场景 ✅ 覆盖（原目标）；
- **切源场景 ✅ 一并覆盖** —— 新源配置到达即补一轮，旧源窗口的残留结果被追加刷新；
- jar 装载完成引起签名变化 ✅ 覆盖；
- 判据复用现有 `poolSignature()`，**不需要 `roundPoolFromCache` 参与补轮判断**（该标志仍保留给假空护栏用）。

**约束**：补全守卫**最多触发一次**（补完即收尾），避免 jar 陆续装载引发多轮补搜。这与 #2 的 S3（0 结果才重搜、无次数上限）是**两条独立路径**，互不干扰。

### 9.2 补强一：S3 必须增加「稳定出口」（方案未写，但不加就是死锁）

方案只写了"缓存池 0 结果 ⇒ 判据① 不成立 ⇒ 转 S3 等池变化 ⇒ 自动重搜"。**但池不一定还会变**：

> 预热成功 → 缓存轮 0 结果 → S3 等池变化 → 此时网络请求失败（或返回坏内容走 `useCacheFallback` 用**同一个缓存文件**重填）→ 池签名**一字不变** → S3 永远等不到变化 → **无限转圈**。

这是本方案最危险的一个洞。所以 S3 的判据从"等池变化"升级为**"还有没有东西在路上"**：

```
S3 每拍：
  ① 池未定论 ⇒ 等（有东西在路上）
  ② 签名还在动（本拍≠上拍）⇒ 记下、继续等（去抖，把一串集中落定的 jar 折叠成一次重搜）
  ③ 连续两拍一致（稳定了）：
       池变过        ⇒ 重搜（S2）
       没变过 ∧ 缓存池 ⇒ 等网络池
       没变过 ∧ 真池   ⇒ 承认空态（S4）
```

三个出口都齐了，任何情况下都不会无限转圈。代价是非缓存池场景多等 1 拍（0.5 秒）才判空 —— 无感。

### 9.3 补强二：护栏清除点必须是 3 处（少一处就出现死锁）

`bootPoolFromCache` 一旦置 true，必须保证"网络侧一有结论就撤掉"：

| 清除点 | 位置 | 为什么 |
|---|---|---|
| 预热失败 | 预热块 `catch` | 缓存坏掉时不能留着 true |
| 网络返回 | `onSuccess` **首行** | 无论接着走"解析成功"还是"内容异常回退到缓存"，池的归属都不再是预热那份 |
| 网络彻底失败 | `onError` 的 `attempt < 2` 判断**之后** | 重试途中池确实还会变，所以不能放在重试判断之前 |

闸门用 `count bootPoolFromCache = false; 3` 锁死，少一处即 FAIL。

### 9.4 守卫观测上限取 20 秒（40 拍）的依据

守卫**纯内存探池、零网络请求**，用户完全无感（不弹提示、不动界面）：
- 正常场景（池早已稳定）：第二拍即收工，成本≈读 3 个变量；
- 缓存预热/切源场景：需要等到网络配置到达换池。

上限照实测定 —— **订阅就绪实测 4.7~16.5 秒**，取 20 秒刚好覆盖；超过仍未回来则守卫收工，用户手动再搜一次即是全量新池（这与今天的行为一致，不是退步）。

### 9.5 补轮为什么天然满足「追加在后、不闪不重排」

| 机制 | 依据 |
|---|---|
| 结果追加 | `flushSearchResults` 在 `searchAdapter.data.size > 0` 时走 `addData(batch)`（追加表尾） |
| 跨轮去重 | `resultVods` 只在用户手动新一轮 `search()` 里清；补轮走 `searchResult()` 不清 ⇒ 同站点同影片不会出现两次 |
| tab 增量 | `addWordAdapterIfNeed` 先查同名再加；补轮不清 `spNames`/`keyToName`，映射仍在 |
| 选中项不动 | 补轮跳过 `setCurrentItem(0, …)`，不会把用户正看着的站点 tab 拉回"全部显示" |
