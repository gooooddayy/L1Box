## 一、可以做到 —— 而且比 v1 更简单

### 1.1 核心：判据只有一条，动作只有两个

```
加载得到结论（成功 或 失败）之后：

  成功 ⇒ 池在 parseJsonInternal 里已被新源覆盖（这一步等价于"清掉了前源"）
         poolUrl = 本次地址                                  ⇒ 回到 S0，全程无间隔

  失败 ⇒ ┌ 本次地址 != poolUrl   （用户换过源 / 切过线路）
         │    ⇒ 清池 + poolUrl = ""  ⇒ 空源 + 提示            ⇒ S3
         └ 本次地址 == poolUrl   （没换源，纯网络抖动）
              ⇒ 池原样保留 + 现有轻提示                        ⇒ 断网容错，一行不改
```

**就这么点东西。** v1 里那些"回退 / 提示条 / 双按钮"全部删掉了。

### 1.2 时序：为什么这样就"无间隔"

| 时刻 | 状态 | 池 | 用户能做什么 |
|---|---|---|---|
| T+0 | 你在订阅页把地址改成源 B，退出（`onPause` 只写地址） | **源 A（不动）** | — |
| T+0.05 | 回到首页 → `reloadSitePool()` 发起加载 | **源 A 继续用** | **首页照常显示、搜索照常能搜** ✓ |
| T+0.5~2 | 加载中（弱网则最长约 4.5s+ 三次请求耗时） | **源 A 继续用** | **全程可用，零空窗** ✓ |
| 加载成功 | `parseJsonInternal` 覆盖池为新源 | 源 B | 无缝换成新源 ✓ |
| 加载失败 | **此刻才清池** | 空 | 空源 + 提示 |

**"无间隔切换"就是靠这个顺序实现的**：清池动作被**推迟到有结论之后**，于是加载期间旧池一直是活的。

### 1.3 与 v1 方案 B 的本质区别（都"清池"，但完全不同）

| | 方案 B（v1，已否） | **本方案（v2）** |
|---|---|---|
| 清池时机 | **改地址那一刻** | **加载有结论之后** |
| 加载期间 | **池是空的** ⇒ 0.3~2s（弱网 4.5s+）无池窗口 | **旧池全程可用** ⇒ **零空窗** |
| 断网容错 | **被破坏**（恰好把旧池清在最需要它的时刻） | **完好**（同源失败根本不清） |
| 结论 | ❌ 不采用 | ✅ **采用** |

> 一句话：**清池本身没问题，问题只在"什么时候清"。** 你说的"加载新源后再清"正是把时机挪对了。

## 二、状态模型（v2 只有 3 态，比 v1 少一个）

| 状态 | 判据 | 池 | 用户看到 |
|---|---|---|---|
| **S0 一致** | `地址 == poolUrl`，池非空 | 有效 | 什么都不说 |
| **S1 加载中** | `地址 != poolUrl`，加载在途 | **仍是旧源，继续可用** | 现有轻提示（"正在重新拉取线路站点"之类），可正常使用 |
| **S3 空源** | 池为空且已有定论 | 空 | 空态 + **一行原因**（见第三节） |

⭐ **v1 的 S2（换源失败但旧源可用）被彻底消灭了** —— 因为失败立即清池，系统**不可能停留在"池是旧源、地址是新源"的矛盾态上**。这就是你要的"源出问题就别显示成有效状态"，而且是**结构性**地做到，不是靠提示文案提醒。

### 唯一的残余窗口：S1

S1 期间"地址（新）≠ 池（旧）"仍然存在，但此时**它是必须的**（正是它撑住了无间隔）。

要求：**S1 期间不能产生任何副作用**。需要堵的只有一处（见 3.3）。

## 三、提示设计（简单版）

你说"简单一点"，所以**不做常驻提示条、不做按钮、不加新界面**。只做三件事：

### 3.1 失败时的即时提示 —— **沿用现有的，不新加**

`ApiConfig` 的两个失败出口现在已经在 `callback.error(...)` 里给出**具体结论**：

- `"订阅拉取失败，请检查网络"`
- `"订阅内容异常：返回的是网页，不是订阅配置"`（由 `L1SubContent.diagTip` 生成）

`HomeFragment` 会用 `ToastUtils.showLong` 显示它。**这块不动** —— 它已经够具体。

### 3.2 空态文案区分两种情形 —— 这是"简单提示"的落点

现在空态只有一种文案（"添加订阅源"引导），所以"配了源但加载失败"和"压根没配源"长得一模一样 —— **这就是你说的"显示成有效状态"的另一半**。

改为按情形给一行：

| 情形 | 判据 | 文案 |
|---|---|---|
| 真没配源 | 订阅列表为空 / `地址` 为空 | 现有「添加订阅源」引导（不动） |
| **配了源但加载失败** | 有订阅 ∧ 池空 ∧ 已定论 | 一行：**「订阅加载失败，上一个源已停用；请检查源地址」** |

**这一行同时承担了三件事**：说明现在是空的、解释为什么（上一个源被我停用了）、给出下一步（检查地址）。而且它**常驻可见**（空态本身就在屏幕上）—— 不需要额外的提示条，就达到了"不再是有效状态"的效果。

> 建议把这句话作为**唯一新增的用户可见文案**，别的地方都不加。

### 3.3 配套（1 行代码）：堵住 S1 的缓存污染

`HomeFragment.kt:292` 现在写的是：

```kotlin
HomeCache.saveSkeleton(Hawk.get(HawkConfig.API_URL, ""), ...)   // ← 用「地址」做标签
```

S1 期间地址已经是源 B，但分类数据来自源 A —— 万一此刻有个在途的分类回调到达，就会写出「**源 B 的地址 + 源 A 的内容**」这种缓存。下次冷启动地址一比就"命中"，秒显旧源内容。

**改为用 `poolUrl` 做标签**（稳定态下两者恒等，行为不变；只在 S1 那个窄窗口里起作用）。

## 四、失败后清池要清哪些东西（实现要点）

`ApiConfig` 里**已经有一段**"正确清池"的代码 —— 就是空地址分支（`236-250`）：

```java
synchronized (sourceBeanList) {
    sourceBeanList.clear();
    spider = "";
    parseBeanList.clear();
    parseFlags = new ArrayList<>();
}
mHomeSource = null;
sitePoolSettled = true;
```

⚠️ **不要只 `clear()` 站点池**，必须连 `spider / parseBeanList / parseFlags / mHomeSource` 一起清 —— 否则设置页的解析开关、站点标记还是**旧源的**，就变成另一种"显示 A 生效 B"。

**做法建议**：把这段抽成一个私有方法（如 `clearPoolInternal()`），**空地址分支与"换源失败"分支共用同一段**。
好处：① 两处行为必然一致，不会再出现"只修了其中一支"（这正是本 bug 的成因）；② 以后加清池项目只改一处。

另外 `poolUrl` 要在这段里一并置空。

## 六、v2 带来的两个副作用（如实说明，你知情即可）

### 6.1 换源时若恰好断网，也会按"失败"处理

判据只认"地址 != poolUrl"，**不区分失败原因**。所以：**断网时换源 ⇒ 旧源同样被停用 ⇒ 空源**。

- 你的口径是"不回退"，所以这是必然结果（宁可空源也不误用旧源）
- 恢复很轻：联网后任意一次加载成功即恢复；重试入口就是现有的下拉刷新 / 订阅页切换
- 🔸 可选的精细版（**我不建议做**）：仅当"拿到了响应但不是配置"才清池，纯网络不可达时保留旧池。代价是多一个分支、多一个状态，与你"提示简单一点"的方向相反。**建议保持简单。**

### 6.2 清池后，历史/收藏会临时从列表消失（**不会真删**）

记录按 `(sourceKey, vodId)` 存，池空且已定论时 `RoomDataManger.java:109-114` 会把取不到源的记录**从列表里过滤掉**。

- 所以清池后，**旧源的历史/收藏会暂时看不见**
- 但**数据库里的记录一条没少**，等切回旧源（池重新有数据）就会**重新出现**
- 这是既有设计（"记录不属于当前订阅即隐藏"），不是本次引入的；只是清池会把它触发出来。**知情即可，不需要改。**
