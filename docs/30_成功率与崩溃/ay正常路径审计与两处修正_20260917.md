## 二、用户 09-17 的三条反馈与处置

### 1）「重新获取播放地址这个是不是有点多余」→ 删
**判定：对，多余，且与本工程既有风格不一致。**
- 工程里原有的临时提示都是**不带计数**的：「正在获取播放信息」「正在尝试备用协议重连」「播放失败，已切为 X 重试」；
- 只有我上一批加的「正在重新获取播放地址（n/2）」把内部重试次数暴露给了用户；
- 更关键的是**用户的本意被误读了**：他要的是"别因为试得太快而把能播的源判成播不了"，
  不是"把等待拉长给我看"。计数文案属于对需求的过度实现。

**改动**：删掉 `autoRetry()` 里的 `setTip`，保留埋点。重取期间沿用屏幕上原有的 loading 状态
（取链失败时仍是「正在获取播放信息」+ 转圈；兜底失败时是「播放失败，已切为 X 重试」+ 转圈）
⇒ **界面不会出现"两次无声失败后突然停在错误上"的空档，也不会多出术语**。

### 2）「重试时长太短会误判可播放的源，不是说特地把时间拉长」→ 退避保留，但预算改成真上限
退避**必须保留**：改动前是零间隔重打（两次取链只隔 **2~8 毫秒**），源侧抖动窗口是秒级，
零间隔等于没试就报错（这正是用户最初说的"不要一下不试就报错"）。

但发现一处**真逻辑缺陷**：`FETCH_RETRY_BUDGET_MS`（8 秒）原来只检查"现在有没有超预算"，
**没把这次要等的退避算进去** ⇒ 它约束不了总时长。
实测证据（ax 轮唯一那次失败）：

```
14:12:07.056  用户点播
14:12:13.500  首次失败 → 排第 1 次重取（此刻已过 6.44s，仍在 8s 内 ⇒ 放行）
14:12:14.940  第 2 次失败 → 排第 2 次重取（已 7.88s，仍在 8s 内 ⇒ 放行）
14:12:17.740  第 3 次失败 → 才给结论
              ⇒ 从点播到结论 10.68 秒，超出承诺的 8 秒
```
**修法**：把预算改成真 deadline —— `now + delay > 起点 + 预算` 就**不再排这一次重取**，直接给结论。
改后同一场景：第 2 次重取（要等 2.5s，合计 10.38s > 8s）被拒 ⇒ **7.88 秒给结论**，与承诺一致。

### 3）「没找到卡住的，所以一直没测试你那个卡住的」→ 事实确认
本轮 **看门狗 0 次触发**（10 次成功起播最快 176ms、最慢 3010ms，全部远低于 20 秒首次窗口）。
**32 秒终裁至今从未被观测到**（前两轮分别在 18s / 28.8s 被切走）。这条仍是唯一未验项，不粉饰。

### 3.2 机制交叉检查（补了三处此前没验的接缝）

1. **取链看门狗在重取时会不会失效** → `armFetchWatchdog()` 在 `play()` 内部
   ⇒ 每次退避重取都会**重新布防**（`mFetchDone=false` + 重置起点 + 重排 15s）。
   不存在"重取之后没人管卡住"的洞。✅
2. **退避期间用户换集** → `keyAtSchedule` 比对，不一致就作废这次重取。✅
3. **预算/额度重置** → `mEpisodeStartAt` 在「换集」与「用户手动重试」两处重置；
   `autoRetryCount` 在额度用尽后归零。✅

### 3.3 查清的"疑似 bug"（不是 bug，但要说清真因）

**那个 6.2 秒空档到底在等什么？** 此前一直归因为"本机代理连不上"。日志原文证明不是：

```
14:12:07.279  W/System.err  HttpException: network error! http response code is 404 or 5xx!   ← 净化预取
14:12:07.281  I/ExoPlayerImpl  Init
14:12:10.354  E/ExoPlayerImplInternal  HttpDataSource$InvalidResponseCodeException: Response code: 503
14:12:13.462  E/ExoPlayerImplInternal  Playback error（第二次）
14:12:13.467  兜底 降级到 IJK播放器（第 1/1 档）
```
⇒ **本机代理对本应用返回了 503**，即"地址格式完全合法、但后端 spider 取不到内容"。
Exo 自己的 load-error 重试（两轮各约 3.1 秒）把它拖成了 6.2 秒。
**这类失败与播放器层无关，播放层治不了**；能做的只是别再加白等（本轮已把白试的两次去掉）。

### 3.4 已知边界（未改，如实记录）

| 项 | 现状 | 为什么不动 |
|---|---|---|
| 取链**完全静默挂住**时 | 由取链看门狗 **15 秒**兜底，超过 8 秒承诺 | 15s 是"宁可不作为也不误杀"的一侧；实测正常取链仅 185~651ms，收紧不会提升成功率、只会增加误判风险 |
| 嗅探出多个候选地址时 | `loadFoundVideoUrls` 逐个试，**不受次数/8 秒预算约束** | 上游既有行为；候选集有界，且每个候选都是不同的地址（属于"多地址"而非"重复重试"）|
| 看门狗 32 秒终裁 | **从未被观测** | 本轮没有卡住的片子（用户没遇到）|
