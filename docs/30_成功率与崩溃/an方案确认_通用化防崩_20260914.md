# an 方案确认：通用化防崩（不针对任何单一源）

> 目标：**任何类型的源都不因我们自己的代码路径杀掉进程**。判据与防线全部改为不依赖某个具体源的类名/结构。

---

## 一、先说结论：错在哪（三条铁律，都有日志实证）

| # | 事实 | 证据 |
|---|---|---|
| 1 | **崩溃 = 判据漏判，不是"越改越差"** | 崩溃栈帧 `com.github.catvod.crawler.JarLoader.loadClassLoader(JarLoader.java:181)`——当前源码第 181 行正是**普通路径**的 `method.invoke(null, bridge)`。受控路径（`ProtectedInitJar.init`）**从不调用 `Init.init`**。行号直接证明：那个 jar 被当成了普通 jar |
| 2 | **判据有结构性盲区（ab 起就在）** | `scan()` 逐 dex 独立判定，`isProtected()` 要求 `Init` 与 `DexNative` **同一 dex**。该 jar 是**壳 + payload 多 dex**（栈里出现 `com.github.catvod.spider.merge.*` + `r8-map-id-...` 混淆块）→ 每个 dex 各判 false → 整体判普通 |
| 3 | **"退出→重进"必崩的根是跨代失配** | 栈 `Init.init → DexNative.getLoader → mid == null`（`CallStaticVoidMethod`）。每次重进都 `classLoaders.clear()` + 新建 `DexClassLoader`（新一代类），而 native 副本常驻进程：本会话出现 **15+ 个不同的 `cache/.ftyfnw*/ .wexlib*/ .wexfnw*` 随机名** = 每代重新抽解一次 native。新一代 Java 类 + 旧 native 缓存 → jmethodID 失效 → abort |

**两个 abort 出口**（全部崩溃都落在这里，无第三处）：
- **出口 A（入站）**：我们的 `/proxy` 路由 → `Proxy.proxy → DexNative.proxyInvoke(obj==null)`。
- **出口 B（初始化）**：我们对家族 jar 调 `Init.init` → 内部 `DexNative.getLoader` → `mid == null`。

**一个关键反证（决定方案能不能放开功能）**：jar **自己内部**的出站调用是走 HTTP 的——
栈实证 `ProxyOrigin.a → okhttp → ConnectException: failed to connect to /127.0.0.1 (port 8964) ECONNREFUSED`。
即：某个 jar 失去本地代理时，它的出站请求只会拿到**连接失败（良性）**，不会 abort。
**所以只要封住 A、B 两个入口，代理在 jar 之间"交接"本身是安全的。**

## 二、方案：五层，通用性优先

### L1 判据通用化（治本，跨 SDK / 抗壳 / 抗混淆）

判据从"逐 dex 独立 + 要求同 dex"改为 **jar 级汇总 + 多信号 OR + 运行时权威探测**：

| 信号 | 内容 | 为什么通用 |
|---|---|---|
| ① 类名 | 任一 dex 的 typeIds/字符串池出现家族入口类（`DexNative`/`ProxyOrigin`/`InitOrigin`/`GoProxyManager`/`AiWex`） | 覆盖同族全部变体；字符串池扫描同时覆盖**反射调用**写法 |
| ② 语义-原生 | 任一 dex 引用 `System.load` / `System.loadLibrary` / `.so` 字符串 | 加固必载原生库——不依赖任何类名 |
| ③ 语义-子进程 | 任一 dex 引用 `Runtime.exec` / `ProcessBuilder.start` | Go 代理必须拉子进程 |
| ④ 运行时探测（**权威**） | 建好 `DexClassLoader` 后、调用任何东西之前，`Class.forName(name, false, loader)` 逐个探测家族入口类 | **ART 在全 dex 内解析 → 多 dex 盲区彻底消失**；`initialize=false` 不触发静态初始化，零风险 |
| ⑤ 学习式兜底 | 判为"普通"的 jar，在 `Init.init` 前后快照 `cache/`、`files/`、子进程；出现原生指纹（新增随机名点文件 / `AiWex/` 目录 / 新子进程）→ **当场降级为家族**并写入持久名单，后续一律受控 | 未知 SDK 也能被"第一次就学会" |

④ 命中即家族（覆盖本 SDK 全家族）；①~③ 命中 → 家族；⑤ 命中 → 永久家族。
**方向是 fail-safe：宁可多判家族（后续只是拿不到代理），绝不漏判。**

### L2 危险路径 fail-safe（不依赖判据正确）

- `/proxy` 路由规则改为：**只有"当前持有者"或"已证明无原生库"的 jar 才放行；其余一律事前 503**。
  （现状是"不在账本就放行"→ 漏判的 jar 会被打进 native，这就是出口 A。）
- 家族 jar 的 `Init.init` 永不调用（受控路径手动绑定），L1 判准是前提、L2 是兜底。

### L3 消灭"互杀 + 跨代失配"（两个根的根治）

- **进程内 jar 的 ClassLoader 按 key 复用**（static，主/home 两个 JarLoader 实例共享）：同一 jar 在**一个进程里只装载一次**。
  效果：① 不再产生跨代失配（出口 B 的成因消失）② 不再重复抽解 native ③ `load()` 重载不再触发重新初始化 → **killall 互杀从"每进程 1~4 次"降到 0~1 次** ④ 退出→重进的第二次加载几乎零成本（顺带提速）。
- **代理单飞不随配置重载重置**：只要现任持有者的 ClassLoader 还活着，就不允许第二个 jar 启动代理。
- **受控接力（切线路触发）**：当前线路的家族 jar 不是持有者时，先关闭全家族 `/proxy` 闸门 + 等家族在途调用归零，再让该 jar 在原 ClassLoader 上启动代理接管。
  依据见上文关键反证：交接期间旧 jar 的出站调用只会得到连接失败，**不会 abort**。

### L4 去掉密度放大器

- **预热只预热非家族 jar**（家族 jar 一律不提前初始化）。
- 本轮速度口径先回 **ab（全员并发 10 + 两参搜索）**，把变量收敛到最少，便于判读验证结果。跑稳后另起一轮再谈提速（普通源并发、非家族预热都已具备条件）。

### L5 保留全部既有防线（零改动）

`NATIVE_INIT_LOCK` 进程级串行（含 bindDexLoader）、`initializingJarKeys` + `proxyQuietUntil` 800ms 门禁、`protectedJarKeys`/`proxyHolderKey`/`FAMILY_LOADERS` 身份终审、`JarKillNeutralizer` 合法替身名——**一条不撤**，它们是兜底，不占速度。

## 三、覆盖矩阵（崩溃形态 → 被谁封堵）

| 崩溃形态 | 现有防线为何失效 | an 封堵层 |
|---|---|---|
| `obj==null` @ proxyInvoke（入站 /proxy 打到被杀代理） | 漏判 jar 不在任何账本 → 直接放行 | **L1 + L2** |
| `mid==null` @ DexNative.getLoader（Init.init 跨代） | 漏判 jar 走了普通路径调 `Init.init` | **L1（不再调）+ L3（不再产生跨代）** |
| `killall begin` 互杀链 | 单飞按 jar 记账/随重载重置 | **L3** |
| 端口竞态 / waitHealth 错乱 | ah 已修（全局串行） | **L5 保留** |
| 未知 SDK 的原生入口 | 无从静态识别 | **L1-⑤ 学习式降级 + L2 fail-safe** |

## 四、诚实清单：边界与代价

1. **黑盒 jar 无法证明 100% 覆盖**。L1 的四层信号（类名/原生引用/子进程引用/运行时探测）语义上覆盖"要载原生 或 要拉子进程"的所有形态，加上 ⑤ 学习式兜底——但**理论上仍存在"既不载原生也不拉子进程、却能 abort"的形态**（今天没见过，也说不通机制）。这一点我不美化。
2. **误判代价（多判家族）**：家族 jar 拿不到本地代理 → 其**网盘/网盘代理类源降级（503）**；普通 spider（搜索、详情、普通播放）不受影响，**并且绝不崩**。
3. **受控接力依赖一条假设**："jar 不会绕过我们的路由、直接用别的机制调自己的入站代理"。已知的入站路径只有 `Proxy.proxy()`，由我们路由；出站路径是 HTTP（良性）。若实测出现"接力瞬间仍崩"，则升级为**单持有者不交出**（绝不允许换持有者，代价：切线路后需重启软件才能让新线路的家族源拿到代理）。
4. **`mid==null` 的最终形态**：L3 在**同一进程内**根治。若某个 jar 在**不同进程**间仍失配（例如 jar 自身更新），属于该 SDK 的跨进程行为，我们只能靠"干净拒载 + 降级"挡住，不崩。

## 五、验证方式（不靠"我这台机器没崩"）

**① 离线判据回归（关键，可在 PC 上跑，不需要设备）**
判据代码是纯 Java（读 zip/dex 字节），抽成 harness 后：输入订阅里**全部 jar**，输出每个 jar 的判定 + 命中信号。验收标准：
- **所有含 `DexNative`/原生信号/子进程信号的 jar 必须 100% 命中家族**（零漏判）；
- 普通 jar 零误判。
这条是"换台机器也成立"的证据，而不是单机运气。

**② 真机判据（退出→重进→立刻搜索，多轮）**
- `Fatal signal 6` = 0、`JNI DETECTED ERROR` = 0
- `killall begin`：每进程 ≤1（首次启动），稳态 0
- `DexClassLoader` 创建数：每进程 ≤ jar 种类数（证明复用生效）
- `cache/.` 随机 native 文件数：每进程不再增长（证明不再重复抽解）

## 八、提速路径全景（哪些能用、哪些已被实验否掉）

**先纠正一个容易误读的点：甲方案本身不含提速。** 甲的目标是「**不崩 + 速度 = ab**」，即"回到 ab 的水平，但不带 ab 的病"。它不是提速方案。

那么真正能提速的路，逐条清算（全部基于本项目的实测，不是理论推演）：

| 提速手段 | 提速效果 | 对崩险 | 证据 |
|---|---|---|---|
| 并发数 10 → 16 | 中 | **抬（已崩）** | ae 崩、ai 崩 3 次 |
| `quick=true` 快速返回 | 中 | **抬（已崩）** | ae 引入、ag 砍补全轮时漏撤、ai 崩 |
| 全量预热 `warmUp` | 首搜大 | **抬（已崩）** | al 崩 5 次 |
| 预热延迟 4 秒 | 首搜中 | **仍抬（已崩）** | am 崩 3 次 |
| 分源并发（普通 16 / 家族 10） | 小~中 | **未知（未隔离验证）** | 与预热同批上线，崩了无法归因到谁 |
| 家族 jar 提前加载 | 大 | **不可行（与密度无关）** | 互杀机制：后启动的必然 `killall` 杀掉先启动的，提前量越大、死得越多。不是"挤在一起"才崩，是**单独做就是错的** |
| **ClassLoader 按 key 复用（L3）** | **大（第二搜起近零加载成本）** | **降（同时治 `mid==null`）** | 机制明确，未实测 |
| 结果缓存（同关键词二搜） | 小 | 无 | 未做，零风险 |
| 慢源分档超时（当前只有全局 30s） | 体感中 | 无 | 未做，零风险 |

**结论**：不抬高崩险的提速手段只有三个 —— **L3 复用、结果缓存、超时细化**。其中**唯一能解决"首轮 jar 加载成本"的是 L3**；另两个只优化第二搜与慢源拖尾。

所以答案是：**「保稳定 + 真提速」这个组合，目前只有 L3（ClassLoader 按 key 复用）这一条路还没被实验否掉**。而它恰好也是 an 方案里治 `mid==null` 的那一层 —— 治崩与提速在这一层合流了。

诚实补一句：**唯一性来自"排除法"，不是来自"证明最优"。** 还有一条未被单独验证的（分源并发），它单独上线是否能既提速又不崩，理论上有可能（家族 jar 的 init 仍有 `NATIVE_INIT_LOCK` 兜底），但家族 jar 的初始化才是真正的瓶颈，所以它的提速上限也不高。值不值得花一个构建周期去单独验证，取决于批次二的实测结果。

## 九、落地分三批（每批单独出包、单独验证，不混批）

| 批次 | 内容 | 目标 | 代价 |
|---|---|---|---|
| **第一批（治崩，必做）** | L1 判据（jar 级汇总 + 运行时 `Class.forName` 探测）+ L2 `/proxy` fail-safe + L4 撤 `warmUp` / 撤分源并发（回全员 10） | **不崩，速度 = ab** | 纯替换 + 纯删除，无新增风险 |
| **第二批（提速）** | L3 ClassLoader 按 key 复用（static，主/home 两实例共享） | 第二搜起近零加载成本；顺带消灭 `mid==null`；`killall` 降到 0~1 次/进程 | 家族 jar 每进程只加载一次 → **服务端换 jar 需重启软件才生效** |
| **第三批（功能完整）** | 切线路受控接力（`ensureHolder(key)`） | 切线路后新线路的家族网盘源可用 | 依赖"出站是良性 HTTP 失败"这条反证 |

**为什么必须分批**：上一轮的教训就是变量混批（分源并发 + 预热 + 判据改动同时上线），崩了之后无法归因，多耗了 al、am 两版。

**L1 与 L3 的分工（关键，必须说清）**

- **L1 是主**：它让漏判消失 → 漏判的 jar 不再走危险路径。**与"退出"是否真的杀掉进程无关**，无论如何都生效。
- **L3 是辅 + 提速**：它让"跨代"这件事本身不发生。前提是进程还活着（"退出"只是回桌面、"重进"复用进程重新 `loadConfig`，这是本项目的实测行为）。**若某些机型的"退出"真的会杀掉进程**，L3 在那一台上只贡献提速、不贡献治崩 —— 但 L1 依然兜住，不会崩。
