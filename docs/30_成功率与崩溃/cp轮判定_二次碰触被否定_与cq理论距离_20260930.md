## 一、你的假设：「快速滑时手指二次碰触导致停止」

**数据否定，而且理由很硬。** 把每个惯性结算与「本次 UP → 下一次 DOWN」的间隔配对：

| 惯性时长 | 抬手→下一次按下 |
|---|---|
| **13 ms** | 1023 ms |
| **13 ms** | 1010 ms |
| **17 ms** | 943 ms |
| **22 ms** | 899 ms |
| **32 ms** | 1105 ms |
| 41 ms | 958 ms |
| 58 ms | 1887 ms |
| 77 ms | 1232 ms |
| 215 ms | 1138 ms |
| 2247 ms | 2727 ms |

**47 条全部是「延续较久」——一次都没有出现「惯性结束时刻 ≈ 下一次触摸时刻」。**

**惯性在 13 毫秒就停了，而你的下一次触摸在 1 秒之后**，中间隔着整整一秒。

**两个旁证：**

| 项 | 数值 | 含义 |
|---|---|---|
| `DOWN` 总数 | **48** | |
| `UP` 总数 | **48** | 与 48 次右栏 UP **完全一致** |
| `★CANCEL` | **0** | 没有多余的手势、没有被打断的手势 |

⇒ **如果真有"抬手后又碰一下"，必然产生一组额外的 DOWN/UP。实际一组都没有。**
⇒ **「二次碰触」假设不成立** ✔（这是一个很有价值的排除，因为它本来很符合"速度与时长不相关"的现象）

## 二、cp 新埋点给出的决定性事实

`cp` 把「拖动帧」与「惯性帧」切开后，第一次看清了惯性阶段的真实形态：

| 项 | 结果 |
|---|---|
| **`惯性帧=0`（fling 一帧都没跑）** | **出现 0 次 / 47** |
| 惯性阶段确实有滚动 | **47/47 全部有** |

典型现场（16:05:09，惯性 13ms 那次）：

```
16:05:09.627  ★右栏UP 手速=-21139 手指位移=-683 接触=70ms 可下滚/可上滚=true
16:05:09.627  ★右栏fling请求 vy=21139
16:05:09.628  右栏状态→惯性 待落=2 offset=30153
16:05:09.639  右栏状态→静止 待落=2 offset=30483   ← 11ms 后，只滚了 330px
16:05:09.640  ★右栏惯性[停稳]：惯性帧=2 惯性位移=330 首帧=169 末帧=161
```

**关键三点：**

1. **惯性真的跑了 2 帧**（首帧 169px、末帧 161px）
2. **末帧速度仍有 161px/帧 ≈ 23000px/s** —— 完全没有衰减
3. **结束点卡在帧边界**（13ms ≈ 2 × 6.5ms）⇒ **不是被外部 `stopScroll` 掐在任意时刻**，
   而是 **`OverScroller` 自己在某一帧里报告「跑完了」**

⇒ 所以不是「一帧都没跑」，也不是「被外部打断」——
**是 `OverScroller` 认为它已经到达终点。**

## 三、⭐ 重大发现：设备 `animator_duration_scale = 0.5`

```
animator_duration_scale     : 0.5
window_animation_scale      : 0.5
transition_animation_scale  : 0.5
屏幕密度                     : 560 (density 3.5)
```

**安卓的 `OverScroller` 是动画时钟驱动的** ——
`SplineOverScroller.update()` 用 `AnimationUtils.currentAnimationTimeMillis()` 计算已过时间。

**`animator_duration_scale = 0.5` ⇒ 动画时间流逝速度翻倍 ⇒ `timePassed` 增长 2 倍 ⇒ fling 时长减半。**

**这能解释一部分「惯性变短」，但解释不了「距离只有 330px」** ——
距离由 `mSplineDistance` 决定（只与速度、摩擦、密度有关），**与动画时钟无关**。

⇒ 所以还需要 `cq` 的独立复算来定位剩下的部分。

## 四、cq 设计（本版只加观测）

**做法**：在 `onFling` 探针里，用**同样的 (velocityX, velocityY)** 跑一个**独立的 `OverScroller`**
（`l1ProbeScroller`，`by lazy`，不参与任何 View 的滚动），读它的 `finalY` 作为**理论滑行距离**。

同时把 `animator_duration_scale` 与 `density` **每次实时读出来记进日志**
⇒ 你切换系统缩放设置后，两组数据能在同一份日志里区分开。

**判据表：**

| 独立 scroller 算出的理论距离 | 实测惯性位移 | 结论 | 下一步 |
|---|---|---|---|
| **很长**（数千~数万 px） | 只有几百 px | **`OverScroller` 被替换/中止** | 继续锁定替换者（`smoothScrollBy` 系列） |
| **也是几百 px** | 几百 px | **`OverScroller` 本身就算出短距离** | 指向系统级因素（缩放/密度），修法是在 app 内补偿 |
| 理论距离随「动画缩放」改变而改变 | — | 缩放是直接变量 | 在 app 内不依赖动画时钟 |

## 五、⚠️ 需要你配合的一个「零成本实验」

**cq 埋点会实时记录当时的动画缩放值**，所以请你按这个顺序滑两组：

1. **先用现在的 0.5x** 快速滑 6~8 下（短接触快甩）→ 停一下
2. **到「开发者选项 → 动画程序时长缩放」临时改成 1x** → 再快速滑 6~8 下 → 停一下
3. **改回 0.5x**（恢复你原来的设置）

**⇒ 两组数据一对比，「动画缩放到底影响多大」立刻可量化**，而且不影响你的日常使用。

（如果你不想动系统设置，只测第 1 组也能定论「理论距离 vs 实测距离」那一条。）
