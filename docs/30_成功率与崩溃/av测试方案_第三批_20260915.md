## 一、这批改了什么（先说清，你才好判断）

全部是「**失败链走错路**」的通用缺陷，**跟具体哪个站点无关**。前三条是上一轮真机对照里抓到的，第四条是历史遗留。

| # | 改前的问题 | 改后的行为 | 影响面 |
|---|---|---|---|
| 1 | 看门狗拿「网速 > 0」当"有进展" | 真进展只看**离开准备中**或**位置推进**；「有数据但没画面」另给一次延长观察，到点照样交兜底 | **所有源**：以前会永久转圈，现在必有尽头 |
| 2 | 看门狗一旦解除/判死就**永久失效** | 每次起播（含降级重播）都重新武装 | **所有降级场景**：第二档以后才有人接管 |
| 3 | 变形重试（http↔https）把地址改坏后，**后续降级拿这个死地址去播** | 降级回到**变形前的原地址** | **所有源的兜底**：不再浪费仅剩的额度 |
| 4 | 同一次起播的失败被处理**两次**（换源/释放后迟到的 error 回调） | 同一次起播只处理一次 | **所有源**：降级额度不再被凭空吃一半 |
| 5 | 「兜底试尽」这个真失败出口**没记埋点**；取链超时耗时写死 `-1` | 都记真实值；净化失败补粗归因 | 只影响**证据质量**，不影响播放 |
| 6 | 净化内容 `m3u8Content` 跨线程无同步（历史遗留） | 加 `volatile` | 本地 HLS 端点读到空内容的概率 |
| 7 | 每一档降级都空转时，用户要盯着转圈**最坏约 160 秒**才看到提示 | 本集自动重播设 **90 秒总预算**，超了直接给提示 | **所有源的"最坏等待"被锁死**（换集或手动点重试才重新给满） |

**风险面**：全部改动都在宿主播放层，**不碰加固 jar 装载**、不新增线程、不新增用户可见入口。唯一行为变化是「以前永远转圈的地方，现在会有尽头」。

## 二、测试总原则（针对大多数场景，不针对单个站点）

1. **每个结论必须横跨 ≥3 个不同站点**。单站点失败/成功一律不进结论，只记观察。
2. **采样要覆盖三种源类型**：普通直链源、命中净化的源、网盘/代理源。
3. **判定只看埋点，不看感觉**。`L1Play` 一条行就是一次事实，避免"看起来还行"。
4. **只看机制性指标**，不看单次耗时抖动：成功率、误判次数、重试次数上界、崩溃数。

## 三、测试场景

### 场景 A：正常路径基线（验「不误杀」—— 这批最重要的风险点）

**目的**：看门狗现在会在 32 秒后终裁。要证明它**没有把正常源误杀**。

**怎么做**：5~10 部**不同站点**的片子，每部播 **≥30 秒**（关键：上次 10 秒看不到 20s 才动作的看门狗），其中一部**连播 3 集**。

**判定**：

| 指标 | 通过标准 |
|---|---|
| 起播成功率 | ≥ 95%（跨站点合计） |
| 起播耗时中位数 | ≤ 2s（与 au 的 560ms 同量级，允许波动） |
| **看门狗误判** | **`看门狗判定无画面` 计数 = 0** |
| 应用崩溃 | `Fatal signal` / `JNI DETECTED` / `ANR` **全为 0** |

> 只要出现 1 次「起播已经出画面了、又被判死重启」，就算**不通过**。

---

### 场景 B：失败链有界性（断网，不需要坏链接）

**目的**：证明 failsafe 链不会循环、不会卡死。

**怎么做**：双断网（WiFi + 移动数据都要关，这台机两个都开着）→ 切集 → 观察 60 秒 → 恢复网络 → 不重启应用直接再切集。

**判定**：

| 指标 | 通过标准 |
|---|---|
| 取链失败后的自动重试 | **恰好 1 次**（不能 0 次也不能循环） |
| 每次真失败 | 有一条 `播放失败：` 埋点（**这是这批新补的**，改前一条都没有） |
| 失败到提示的时间 | 单次失败 **≤ 40 秒**；本集最坏（每档都空转）**≤ 135 秒**（预算 90 秒 + 一个终裁周期） |
| 预算机制 | 日志里应出现 `本集自动尝试预算用尽，直接提示` —— 出现即说明"最坏等待"被锁住了 |
| 恢复网络后 | 免重启直接切集即可起播 |
| 崩溃 | 0 |

---

### 场景 C：看门狗真的会响（需要构造，我来搭）

**目的**：证明判据修正是**真的生效**，而不只是"没误杀"。

**怎么构造**：这台机不能 root，但可以用**系统级 HTTP 代理 + 我这边限速**造出「有数据在流、但慢到出不来画面」：
1. 我在 PC 上起一个限速代理；
2. 设备设全局代理指向它；
3. 播片 → 分片被限速 → 出现"有网速、无画面"；
4. 观察看门狗是否在 **32 秒内**接管并进入兜底链；
5. 测完清除代理设置。

**判定**：

| 指标 | 通过标准 |
|---|---|
| 空转样本 | `看门狗` 日志出现「起播无画面但有数据在流…再观察 12 秒」→ 之后出现**终裁** |
| 终裁后 | 进入兜底链（有 `兜底 降级到 …` 或明确提示），而不是停在转圈 |
| 降级后用降级重播 | 看门狗**再次生效**（日志里能看到第二轮看门狗） |
| 限速放宽到"慢但能播" | **不判死**（这条验的是不误杀的另一面） |

> 若代理对设备不生效（部分机型会忽略全局代理），我会如实说明，改用日志统计替代。

---

### 场景 D：净化路径稳定性（验 volatile + 上一批的修复没退化）

**目的**：上一批刚修好「Referer 污染导致分片 403」的回归，这批复核它 + 验证 `/l1.m3u8` 端点的稳定性。

**怎么做**：反复播**命中净化**的源 ≥8 轮（跨 ≥3 个站点）。

**判定**：

| 指标 | 通过标准 |
|---|---|
| `/l1.m3u8` 起播成功率 | ≥ 90% |
| 起播日志 | 有 `净化 命中，走本地 HLS` → `起播 url=http://127.0.0.1:9978/l1.m3u8` |
| 请求头 | 仍有 `补同源 Referer` 埋点（说明修复保留了收益、没退回原点） |
| 无内容空端点 | 日志里不出现"本地端点返回空"的迹象 |

---

### 场景 E：连播与状态不串（跨场景覆盖）

**目的**：证明换集后额度/看门狗状态真的重置，没有跨集污染。

**怎么做**：一个源连播 5 集（其中至少 1 集失败）。

**判定**：
- 第 5 集的起播耗时与第 1 集**同量级**（不能越播越慢）；
- 失败集之后的那一集仍能正常起播（额度确实重置了）；
- 崩溃 0。

## 四、分工

**需要你做的**（只有场景 A + E 的一小部分）：

1. 播 **5~10 部不同站点**的片子，每部**至少 30 秒**（这是硬要求 —— 看门狗 20s 才第一次动作、32s 才终裁，10 秒的观察窗口看不出任何东西）；
2. 其中一部**连播 3~5 集**；
3. 碰到转圈或报错时**别急着退出**，让它自己走完（现在它会自己往下走），你只需要记住"大概等了多久"。

## 六、我要提前说明的诚实边界

1. **场景 C 的构造可能受机型限制**（部分 Android 忽略全局代理）。若不生效，我会直接说明，不会拿"没触发"当"通过"。
2. **场景 A 的误判判定是决定性的**：只要出现一次"出画面了又被判死"，这批的看门狗就太激进，我会把延迟从 32 秒放宽再出一版，而不是把这条判定放宽。
3. **断网只能验"连不上"**，验不出"净化误删好分片"——那一支只能靠场景 D 的正常源对比间接覆盖。
4. **90 秒预算不是"起播超时"**：它只在「看门狗判死」这条路上检查，已经在播、或位置在推进的播放**不会**被它打断；它只回答"还要不要再重播一次"。所以慢源不会被它掐死，只会更早拿到提示。
5. 本方案**不测**单站点特性问题（那是源的问题，不是 App 的问题）。
