# 搜索结果到「完全显示」变慢 —— 跨版本归因（2026-09-22）

> 用户口述：**「搜索结果到结果完全显示变慢了，比前面几个版本」**；并补充「不一定是 dns，只是我自己猜的」。
> 本文只回答两件事：**这些版本各自改了什么、哪些改动可能在搜索路径上**，以及**哪些嫌疑已经能用数字排除**。
> 结论分「已定论」与「待真机数据」两档，不混淆。

---

## 一、版本改动清单：谁碰了搜索路径

搜索一轮的耗时 = **站点池规模** ×（每站：DNS → 建连 → jar 侧请求 → 解析）+ **jar 装载/下载**。
所以只有动到「网络层 / jar 装载 / 站点池 / 搜索 UI」的版本才可能影响它。

| 版本 | 改动文件（源码 mtime 实录） | 在搜索路径上？ |
|---|---|---|
| bi 09-18 18:11 | `PlayFragment`(17:58) | ❌ 播放页 |
| bj 09-18 19:11 | `player/.../ExoMediaPlayer`(18:54)、`PlayerHelper`(18:57) | ❌ 播放器/缓存 |
| bk 09-18 21:48 | `player/.../L1LoadControl`、`ExoCacheConfig`、`ExoMediaSourceHelper`(21:38~21:39) | ❌ 播放缓存 |
| bl 09-19 17:03 | `L1SubUrl`(16:49)、`Subscription`(16:54) | ❌ 订阅解析 |
| **bm 09-19 19:21** | **`OkGoHelper`、`okhttp3/dnsoverhttps/DnsOverHttps`、`App`、`HawkConfig`、`ApiConfig`、`L1DnsPolicy`、`L1SubHeaders`** (18:57~19:07) | ✅ **是** |
| bn 09-22 14:21 | `catvod/crawler/Spider`、`L1FallbackDns`、`RemoteServer`、`FastSearchActivity`(14:11~14:13) | ✅ 是（收口＋观测） |

**⇒ 在 bl 与 bm 之间，唯一横跨到搜索路径的改动就是 bm 的网络层（DoH）。** 用户「改了 dns 后变慢」的直觉方向是对的，
但要说明白它**怎么**影响、影响多少——见下。

## 二、bm 把 DoH 从「等于没开」变成「真在工作」（代码级证据）

### 2.1 开关关着时，DoH 对象其实就是系统 DNS

`okhttp3/dnsoverhttps/DnsOverHttps.java:127-129`：

```java
public List<InetAddress> lookup(String hostname) throws UnknownHostException {
    if (this.url == null)
        return Dns.SYSTEM.lookup(hostname);      // ← url 为空直接走系统 DNS，零开销
```

bm 之前 `HawkConfig.DOH_URL` 出厂默认是 `0`，`OkGoHelper.getDohUrl(0)` 返回空串，于是
`new DnsOverHttps.Builder().url(dohUrl.isEmpty() ? null : ...)` ⇒ **`url == null`**。
也就是说：**改造前的 DoH 对象挂在链路上是完全无成本的**——它每次都在第一行就短路回系统 DNS。

bm 把 `DEFAULT_DOH` 改成 `1`（腾讯），`url` 变成 `https://doh.pub/dns-query` ⇒ 短路失效，
**每个未命中缓存的主机名都要先发一次 DoH 查询**（`includeIPv6` 默认 true ⇒ A + AAAA 两条并发 HTTPS）。

### 2.2 而且当时挂给 jar 的是裸对象，没有回退与熔断

bm 里 `Spider.safeDns()` 返回的是**裸** `OkGoHelper.dnsOverHttps`。而 bm 同时把
`DnsOverHttps.lookupHttps()` 末尾的「静默回退系统 DNS」改成了**如实抛出**
（`DnsOverHttps.java:175-181`，为的是让外层能感知失败），回退职责交给包装类 `L1FallbackDns`。

两者一叠加 ⇒ **走 `safeDns()` 这个入口的 jar，从「DoH 挂了会静默回退、慢一点但能通」变成「直接失败」**，
而且它拿不到包装类的 3 次失败熔断、也拿不到 2 秒短超时（熔断/短超时都只在包装类里）。**这是 bn 要收口的东西。**

### 2.3 注入点顺序已核实：OkGo 确实挂上了 DoH

`OkGoHelper.init()` 的执行顺序是关键——先建 DoH，再建客户端：

```
init() {
    initDnsOverHttps();              // ① 建 dnsOverHttps，并把 fallbackDns 重新赋值为"带 DoH 的包装"
    ... builder...dns(fallbackDns);  // ② OkGo 全局 client 抓到的是①之后的对象 ⇒ 真的带 DoH
    OkGo.getInstance().setOkHttpClient(okHttpClient);
    initExoOkHttpClient();           // ③ Exo 侧 client，同样 .dns(fallbackDns)
}
```

（字段初值 `fallbackDns = new L1FallbackDns(null)` 只是"未启用 DoH"的安全底，会被①覆盖；
客户端是在①之后构建的，所以捕获到的是覆盖后的实例。若顺序颠倒，客户端会永远握着那个 null 包装。）

**因此**：`JarLoader.doLoadJarInternal()` 里那句 `OkGo.<File>get(jar).execute()`（jar 下载）走 OkGo ⇒
**jar 下载的域名解析现在也过 DoH**。这条把「DNS 改动」和「搜索慢」真正连起来了。

两个规律：

1. **每一轮里都有一个 jar 固定晚 ~7~10 秒才装完**（+9.8 / +10.4 / +10.4 / +13.4），
   且**都是同一个 jar**（`加固 jar 手绑成功：0b9565d6a6b5ecd989a7de9e1d50677e`，跨进程同指纹）。
   ⇒ 一轮搜索的收尾时间基本由**它**决定，而不是由 DNS 决定。
2. 这一轮的 jar 装载是**搜索触发的**（不搜不装，`getSpider` 命中缓存就不装），所以「先预热」这条路早已被否。

**对照 bl（36 站点）**：`_bl_host.log` 一轮 17:40:54 → 17:40:57.933，**3.4 秒**，轮内**零 jar 装载事件**（全 main jar 站点）。

> ⚠️ **这两者不能直接当成 A/B**：站点池不同（36 vs 40，源也不同），且 bl 那一轮一个加固 jar 都没装。
> 真正的可比对象只能是「同一个包、同一个源、冷对冷」。

## 四、已排除的嫌疑（带数字，可以结案）

| 嫌疑 | 证据 | 结论 |
|---|---|---|
| **bk 引入的冷启缓存清理** | 日志里「转入待删」→「删除完成」恒为 **10.2s**（10.2/10.2/10.2，三次一样）；而代码里 `Thread.sleep(PURGE_DELAY_MS=10_000)` + 每目录 `PURGE_SLICE_GAP_MS=200` ⇒ **真删耗时 ≈ 0**（17 个文件/22MB 与 55 个文件/55MB 同为 10.2s） | **排除**。既不阻塞主线程，也不与搜索抢 IO |
| `App` 里延迟 5 秒的 `cleanPlayerCache()` | `FileUtils.cleanPlayerCache()` 只删 `ijkcaches/`、`thunder/`、`jpali/Downloads/` | **排除**。不碰 jar 缓存，不会导致重新下载 |
| 站点池变大 | 日志实录 36（bl）→ 40 → **88**（19:54:35 那一轮，用户刚加了源） | ⚠️ **不可比因素**，跨版本比较必须先对齐站点数 |

## 五、待真机数据才能定的部分

「同一个 jar 为什么每次冷启都要多花 ~7~10 秒」目前**只能二选一或叠加**，日志不足以判定：

- **(a) 它在重新下载**：`doLoadJarInternal` 的磁盘命中判据是
  `MD5.getFileMd5(cache).equalsIgnoreCase(订阅声明的 md5)`，而 `patch(cache)` 在**比对之前**就改写了文件
  （代码注释自己写了「订阅声明的 md5 与它天然对不上」）⇒ 只要这个 jar 被中和过一次，**每次冷启都对不上 ⇒ 重新下载**。
  另外还有一条更硬的：`getSpider` 里 `jarMd5 = urls.length > 1 ? urls[1].trim() : ""`，
  **订阅没写 `;md5;` 时 md5 为空串**，而空 md5 会把整个本地命中分支跳过、**直接落到下载**——
  即「没声明 md5 的 jar 每次冷启都必然重下一次」。
  下载走 OkGo（现在挂 DoH），OkGo 三超时 = `DEFAULT_MILLISECONDS = 10000`，**与观察到的 ~10.4s 高度吻合**。
- **(b) 加固 jar 自身的初始化要联网/解压**（`加固 jar 手绑成功` 之前的那段时间）。

bn 的埋点正好能切开这两者：
- `本轮装载增量` ↑ 而有 `加固 jar 手绑成功` ⇒ 走的是装载路径
- 若走下载 ⇒ `[OkHttp] sendRequest>>` 会在同一时间窗出现且耗时接近 10s
- `DNS(窗口内): DoH命中/失败/熔断/直连` ⇒ 直接回答「DoH 有没有参与、有没有失败」

### 现场要做的（设备连上后）

1. 装 `bn.apk`（`adb install -r FreeBox-src/bn.apk`）
2. 冷启（先划掉 App 再进）→ 搜一次 → 记「看到第一条结果的秒数」+「全部显示完的秒数」
3. 同会话再搜一次 → 记同样两个数
4. 把 `_bn_host.log` 给我；我读 `搜索首条结果` / `搜索耗时` / `DNS(窗口内)` 三行
