## 三、A 类：门禁放行之后，**露出第二层 —— jar 自己不接这一单**

日志原文：

```
21:38:09.942  本地代理：do=ck   key=0b9565d6a6 … 判定=放行 返回=200  耗时=0ms   ← jar 自己的 ck 代理：成功
21:38:09.950  取链 拿到直链 url=http://127.0.0.1:9978/proxy?do=<站点E>&type=m3u8&url=…&ck=…&sign=…
21:38:09.975  本地代理：do=<站点E> key=0b9565d6a6 … 判定=放行 返回=null 耗时=1ms   ← 同一个 jar，返回 null
21:38:09.976  本地代理：/proxy 无可用响应 do=<站点E> 结果=null                     ← 我们只能回 503
```

**判定**：
1. 门禁已放行（**不是我们挡的**），`proxyMethods` 里也有这个 jar 的 `Proxy`，**是我们调用后 jar 返回了 null**。
2. 同一个 jar 对 `do=ck` 能返回 200 ⇒ **jar 的 Proxy 整体是好的**；它只是**不认 `do=<站点E>`**。
3. `do` = 站点 key（`<站点E>` = <站点E>）。`siteKey→jarKey` 由 `getSpider` 决定，本轮 `recentJarKey` 与<站点E>所用 jar 一致 ⇒ **不是"路由到错 jar"**，而是 **jar 内部的派发表里没有这个 key**（这套"host 自己 newInstance 蜘蛛 + jar 的 Proxy 按 do 派发"的机制，注册链路在 jar 内部，我们看不到）。
4. **地址本身是自描述的**：`url` 解 base64 = `http://<源站地址>/vod/m3u8/2/2023/06/140931/1402551/index3.m3u8`；`ck` 解 base64 = `k=9d4dcd6507914d5b3dd4c7f22a60bece&Time=6ABA6DC2&uid=144380146`（`Time` = 播放时刻的 unix 时间戳）。**要取回它需要的信息，全在这条 URL 里。**

> 附：PC 侧对 `<源站地址>` 的探测一律 403（连根路径都 403），**无法替手机验证**，只能靠真机。

## 四、B 类：上游是 **token 门禁的 HLS 服务器**（本轮用实测问出来了）

直接对 `<源站地址>/` 做请求，服务器（nginx）逐条回执：

| 请求 | 回执 |
|---|---|
| `/hls/xxx.m3u8`（无 token） | **501** `缺少token参数` |
| `?token=abc`（格式错） | **401** `Token格式无效` |
| `?token=<全 0 的 96 位>` | **401** `Token格式无效` |
| `?token=<app 实测抓到的真 token>` | **400 Token已过期** |

**判定**：
- 这个上游是**时间戳签名 + token 门禁**的盗链防护 CDN，不是网络/DNS/解码问题（此前已逐条排除）。
- 我们的 `净化 预取失败(远端地址/**Http0**)` 里 **0 是 OkGo 丢掉状态码后的残值**（OkGo 3.0.4 抛 `HttpException` 时 `rawResponse` 已置空 ⇒ `code()` 读回 0）⇒ **这一版的"带状态码"没能真正带出来**，是我上一版埋点的缺陷。
- 配合 Exo 报的 **2004（= 非 2xx）**，可以确定：**服务器回了明确的拒绝码，只是我们没读到是几**。
- 值得注意的旁证：app 每次取链都拿到**新 token**（三次尝试三个不同 token），**仍然被拒** ⇒ 很可能是**源侧的 token 时效/签发与 CDN 不同步**（我们改不了）。**但必须先拿到确切状态码再定性，不许猜。**

## 七、方案（ce 批次）

### P1（建议全做，都是低风险）

| # | 项 | 做法 | 预期 |
|---|---|---|---|
| **P1-1** | **`/proxy` 在"jar 返回 null"时自转发兜底**（A 类主修） | 解析 `url`/`ck`/`type`，**复用现有转发链**（带 cookie/UA/Referer、2.5s 超时、**m3u8 分片重写**）把流取回并回给播放器；**只在 jar 返回 null 时启用**（jar 正常时一行不改）；门禁与 `/l1play` 完全一致（只允许本机，或带合法投屏码 —— 否则会变成局域网开放代理）；日志 `本地代理：自转发 url=… 结果=…` | A 类从"必失败"变成"有机会成功"，且**不依赖 jar 内部行为** |
| **P1-2** | **按 `do` 路由**（A 类辅助） | `getSpider` 记 `siteKey→jarKey`；`proxyInvoke` 优先用 `do` 对应的 jar，找不到才回退 `recentJarKey` | 排除"路由到错 jar"这一类；本轮不是主因，但属结构性隐患 |
| **P1-3** | **净化失败的真正归因** | `Http0` 说明 OkGo 3.0.4 的 `HttpException` 读不到码 ⇒ 改为**从 `HttpException.response` 取原始码 + 把 `getMessage()` 一起打进日志**；再不行就用我们自己的 OkHttp 复请求一次拿真实码（仅在失败分支、仅打日志） | **B 类定刀的唯一依据**（403/404/5xx/401 各是不同修法） |
| **P1-4** | **修掉无效的分段计时** | 结果落地的计时改成"插完数据后 `post{}` 里再结算"（把之后的布局/绘制一起算进去），并按 `addData`/`setNewData`/图片回填分子段 | 下一轮能直接说清 240 ms 花在哪，而不是猜 |
