## 二、流程梳理（这是你问的"流程是否清晰"）

整条链路只有**两个阶段**，两个阶段各有一个看门狗，互不干扰：

### 阶段一：取链（问站点要地址）

```
点播 / 换集
   └─ armFetchWatchdog(15s)          ← 兜住"卡住不返回"
      ├─ 拿到地址 ──────────────► 进入阶段二
      ├─ 站点返回了地址但形态有问题（非 URL，如 Ksvideo-xxx）
      │     └─ 起播前判掉 → errorWithRetry → 退避重取（1.2s / 2.5s，共 2 次，8 秒预算）
      └─ 失败 / 超时 ───────────► errorWithRetry → 同样退避重取
                                     └─ 次数或预算用尽 → 「站点已失效，请返回重试」/「获取播放信息错误」+ 可点「重试」
```

**你提的"不要一下不试就报错"——就是这一层**：原来是零间隔（实测两次请求只隔 2~8 毫秒）且只试 1 次，现在退避到秒级、试 2 次。

### 阶段二：起播（拿到地址之后，到出画面为止）

```
startPlayUrl(地址)
   ├─ 不是 URL → 判掉（不进播放器、不进兜底链）
   ├─ armStartWatchdog(20s)          ← 兜住"黑屏转圈不报错"
   ├─ 出画面 → 解除看门狗，结束
   └─ 没出画面
        ├─ 播放器自己报错 → errReplay（同一次起播只处理一次）
        └─ 20s 无进展 → 延长 12s → 32s 仍无进展 → 判死
             └─ 降级阶梯，每次只走一步：
                  1. 回退原始直连（只在净化命中过、且只有 1 次）
                  2. 同址换协议 http↔https（只在标准端口，私有端口跳过）
                  3. 内置播放器降级（IJK 软解 → Exo，最多 2 档）
                  4. 全试尽 → 「视频播放出错」+ 可点「重试」
```

**两个看门狗的分工是清晰的**：取链看门狗管"要不到地址"，起播看门狗管"要到了但播不出"。

## 三、发现的 3 个问题（已修）

### P0-1　本集预算形同虚设：填 65 秒和 90 秒实际效果完全一样

**现场**：看门狗判死点分别在 **32 / 64 / 96 秒**（每次降级重播都会重新布防，各给 20+12 秒）。
而预算判据写的是"**当前是否已经超过预算**"：

| 判死时刻 | `elapsed > 65000`？ | 动作 |
|---|---|---|
| 32s | 否 | 降级 |
| 64s | **否**（64 < 65） | **降级** ← 本应在这里停 |
| 96s | 是 | 提示 |

⇒ **一次降级都没拦住，最坏等待仍是 96 秒**。把预算从 90 秒改成 65 秒（ax 那批）**是个无效改动**，
但注释里写着"最坏要等 96 秒才出提示，太长"，与行为不符。

**修法**：判据改成"**再跑一个完整窗口会不会超预算**"

```java
elapsed + START_WATCHDOG_MS + START_WATCHDOG_STALL_MS > EPISODE_RETRY_BUDGET_MS
```

取值 70 秒 = 一次降级 + 一个完整窗口（32+32=64 秒），另留 6 秒给取链与起播开销。
效果：**允许一次降级，最坏 64 秒**（原 96 秒）。

### P0-2　预算用尽之后，还会再开一个 32 秒窗口

**现场**：预算用尽那一支走的是 `errorWithRetry()`，而它会调 `autoRetry()`——
**又排一次"重新取链"，那等于再布防一次 32 秒看门狗**。

这次没被咬到，只因 `autoRetry` 内部另有 8 秒取链预算、而此时 elapsed 早就超过 8 秒，
把它挡了回去（**是巧合，不是设计**）。一旦有人调整那个 8 秒值，最坏等待会立刻弹到 160 秒。

**修法**：新增终态出口 `errorFinal(String err)` —— 与 `errorWithRetry` 的**显示形态完全一致**
（同一个 `setTip(err, false, true)`），唯一区别是**不触发任何自动重取**。
用在两处：① 预算用尽 ② 起播兜底链全试尽。

> 这里没有恢复被废除的 `finish` 参数：那是"只弹 2 秒 Toast、不关 loading 浮层"的分支，
> 与"是否要重试"是两件事。`errorFinal` 只跳过重试，**不改显示**。

### P1-1　排队中的退避重取无法被取消

**现场**：`autoRetry` 用 `mHandler.postDelayed` 排一次 1.2~2.5 秒后的重取，Runnable 里只比对
**集标识**。用户在**同一集**上点「重试」（或点重播）时集标识并没有变 ⇒ 队列里那次照跑，
**与用户刚发起的那次撞成两个并发取链请求**。

（当前不是高频问题：正常流程下"显示提示"意味着重取已经全部用尽、队列是空的。
但这属于"靠巧合安全"。）

**修法**：加一个重取代次 `mRetryGen`，换集 / 手动「重试」/ 主动重播三处自增，
Runnable 里比对代次，不等就直接作废。

## 四、是否引入新问题：逐项核对

| 核对面 | 结论 |
|---|---|
| `errorFinal` 会不会造成"再也不重试" | 不会。它只用在起播阶段"已无手段可试"的两处；**取链阶段 7 个失败出口全部保留 `errorWithRetry`**（退避重取照旧） |
| 两个出口的显示会不会不一致 | 不会，都是 `setTip(err, false, true)`，同一个「重试」链接、同一套错误态 |
| 预算判据改成"含下一窗口"会不会砍掉降级机会 | 会砍掉**第二次以后**的降级。剩余余量：取链耗时 ≤ 6 秒时首次判死仍会降级。取链实测中位约 200ms、最慢约 3 秒 ⇒ 正常情况下降级机会保留 |
| `mRetryGen` 的线程安全 | 读方可能在 OkGo 回调线程、写方在主线程（非 volatile）。最坏情况是读到旧值 ⇒ **退回改动前的行为（重取照跑）**，不会更糟 |
| 是否有残留的死代码 / 未用变量 | 无。`speed` 仍在判死埋点里使用；`mWatchdogRound` 语义已收敛为"是否已延长过一次" |
| 注释与行为是否一致 | 已核。本轮修掉 1 处（预算注释声称的行为与代码不符）——它正是 P0-1 长期没被发现的原因 |

## 五、误判审查（你最关心的那条）：没有一处会误伤"能播"的源

10 个会动手干预的机制，逐个问"它会不会在源本来能播的情况下动手"：

| 机制 | 会不会误伤 | 理由 |
|---|---|---|
| 起播看门狗 20+12s | **不会** | 判据只有两条：**离开「准备中」** 或 **播放位置动过**。刻意**不看网速**（Exo 取不到时恒为 0，拿它当判据会误杀慢源）。实测正常源最慢 2774ms 就绪，32 秒余量极大 |
| 取链看门狗 15s | 不会 | 正常取链约 200ms |
| 回退原始直连 | 不会 | 只在净化命中过、且只在已失败之后 |
| 变形 http↔https | 不会误判 | 已限定标准端口；私有端口直接跳过 |
| 内置降级 | 不会 | 只在播放器已经报错之后 |
| 非 URL 地址早判 | 不会 | 判据是"不含 `://` 且不是 magnet/ed2k 等"，实测被拦的全是 `Ksvideo-<hex>` 这类 |
| 净化（去广告） | 不会 | 只在清单可解析时改写；解析不了就原样放行 |
| 退避重取 | 不会 | 只在已失败之后；且重取会重新走完整取链，不改动播放中的状态 |
| 预算 | 不会 | 只在"判死"这条路上检查；**正在缓冲且位置已推进的播放不会被它打断** |
| 失败去重 `mFailHandledAt` | 不会 | 只忽略"同一次起播"的重复 error 回调 |

**一句话**：所有会动手的机制，触发条件都是"**已经确证失败**"或"**确证没有任何进展**"，
没有一处拿"速度/耗时"这类会波动的东西当判据。
