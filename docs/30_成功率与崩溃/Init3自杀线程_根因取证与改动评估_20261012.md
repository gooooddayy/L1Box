# `Init$3` 自杀线程 · 根因取证与改动评估（2026-10-12）

> 对应长期待办 5。本文件**只做根因取证 + 改动评估**，⛔ **未改任何代码**。

---

## 一、一句话结论

`com.github.catvod.spider.Init$3` 是**加固 jar 自己起的"睡 5 秒后自杀"线程**，它**唯一的工作就是自杀**；
jar 先做三道"二次打包"自检，**我们的 App 名 `L1Box` 不在它的白名单里**（而**包名 `com.github.tvbox.osc` 在白名单里**，所以只报 App 名）
⇒ jar 走"自杀分支"（`goto` 跳过全部正常初始化）⇒ 自杀被 `JarKillNeutralizer` 中和成 `Process.equals(I)V` ⇒ NoSuchMethodError。

**⇒ 这个"崩溃"本身：功能损失 = 0**（线程除自杀外什么都不做，进程由 App.java 后台安全网兜住）。
**⚠️ 但同一个分支还跳过了 6 项正常初始化**（含 `startGoProxy` 与 4 个后台线程）——
而**我方 `invokeSelfInit` 只看"反射没抛异常"就判定"代理已被它接管"** ⇒ **账本讹记了一个不存在的代理持有者**。这才是真正值得改的地方。

## 三、⭐ 反汇编铁证

### 3.1 自杀线程全文（`Init$3` 一共只有 4 条指令）

```
com.github.catvod.spider.Init$3.run:()V          // insns size = 18 (16-bit units)
0000: const-wide/16 v0, #int 5000                // ← 就是它！睡 5000ms
0002: invoke-static {v0,v1}, Ljava/lang/Thread;.sleep:(J)V
0005: goto 000a
0006: move-exception v0                          // 只 catch InterruptedException
0007: invoke-virtual {v0}, Ljava/lang/InterruptedException;.printStackTrace:()V
000a: invoke-static {}, Landroid/os/Process;.myPid:()I
000d: move-result v0
000e: invoke-static {v0}, Landroid/os/Process;.killProcess:(I)V   // ← 自杀（已被中和）
0011: return-void
```

**⇒ 它对 5 秒后的世界只有一件事要做：杀掉自己。** 没有心跳、没有保活、没有回写、没有网络。
**⇒ 这条线程死掉，功能损失严格为 0。** 这也**精确解释了「装载成功后恰好 +5.00 秒」**（4 次实测 4.98~5.00s）。

### 3.2 三道自检 + 自杀分支（`Init.init(Context)`）

```
Init.init(ctx):
  if (!Init.a(ctx))  { log("包名不匹配，疑似二次打包");        goto 0x00a1 }   // a() = 包名白名单
  if (!Init.b(ctx))  { log("App名称不匹配，疑似二次打包");      goto 0x00a1 }   // b() = App名白名单
  if ( Init.c(ctx))  { log("签名DN命中黑名单，疑似二次打包");   goto 0x00a1 }   // c() = 签名黑名单
  ── 正常初始化块 ──────────────────────────────────────────────
  Init.get().c = (Application) ctx          // 注入 Application
  Init.saveConfig()                          // 保存配置
  Init.startFloatBall()                      // ★ 起它自己的悬浮球
  checkCallingOrSelfPermission("android.permission.INTERNET")
  Init.startGoProxy(ctx)                     // ★ 起本地 Go 代理
  new Thread(merge/A/aa ).start()            // ★ 后台任务 1
  new Thread(merge/A/ab ).start()            // ★ 后台任务 2
  new Thread(merge/A/acc).start()            // ★ 后台任务 3
  new Thread(merge/A/ad ).start()            // ★ 后台任务 4
  return

  0x00a1:                                    // ← 三道自检任一不过都落到这里
  Init.get().c = (Application) ctx
  SpiderDebug.log( AES("6ODi1b8xyfKfZpaErEEE9w==") )   // 解密后 = 「加载失败」
  new Thread(new Init$3()).start()           // ← 睡 5 秒 → 自杀
  return
```

## 五、影响面评估

### 5.1 `Init$3` 本身：零功能损失 ✅

| 项 | 结论 |
|---|---|
| 线程干什么 | 只自杀（§3.1 全文为证） |
| 进程会不会死 | **不会**（`App.java` 后台线程安全网兜住） |
| 崩了会丢什么 | **什么都不丢** |
| 实际代价 ① | 每进程 2 行 ERROR 日志（`AndroidRuntime` + `App`） |
| 实际代价 ② | **每次崩都往 `files/crashes/` 落一份崩溃文件**（`CrashLog.save()`，内有 `trimOld` 兜底，不会无限涨）⇒ 真崩溃会被这些噪声淹没 |

### 5.2 ⭐ 真正的问题：被判据挡掉的 6 项初始化 + 我方的"假成功"

`goto 0x00a1` 把整块正常初始化**全部跳过**（§3.2）：
`saveConfig` ／ `startFloatBall`（jar 自己的悬浮球）／ `INTERNET` 自检 ／ **`startGoProxy`（本地 Go 代理）** ／ **4 个后台网络线程**

其中 `Init.get().c = ctx` 这一项**我方已用 `bindContext()` 反射补上**（所以不构成问题），但**另外 6 项没有任何补偿**。

⚠️ 更关键的是我方记账链：

```java
// ProtectedInitJar.invokeSelfInit()
method.invoke(null, bridged);
return true;                       // ← 只看"反射没抛异常" ⇒ 恒为 true
```
```java
// ProtectedInitJar.init()
if (!bound) { bound = invokeSelfInit(clz); tookProxy = bound; }   // ← invokeSelfInit 恒 true
if (tookProxy) { occupyProxy(clz, key); ... }                    // ← 于是恒走这里
```

**⇒ 反射调用不会抛异常（异常抛在 jar 新起的线程里），所以我们 100% 认定"代理已被它接管"，
把 `GO_PROXY_STARTED=true`、`PROXY_HOLDER=该 jar` 记在账上 —— 而代理实际根本没起。**

⇒ 后果链：后续 jar 的 `bindDexLoader` 手绑会去连一个不存在的代理（**10-10 12:41:49 `Failed to connect to /127.0.0.1:8964`** 与此一致）；
`/proxy` 门禁也会放行一个死的代理 ⇒ **代理型站点必然失败**。

📌 这一条同时**修正了 10-12 上一份方案文档里的一个推测**：那里写的是"线程死掉 ⇒ 初始化不完整"；
实际是 **"初始化整块压根没执行"**，比原推测更确定。

## 六、要改什么（四个选项 + 推荐）

| # | 选项 | 内容 | 代价 / 风险 | 建议 |
|---|---|---|---|---|
| **A** | 让 App 名落进白名单 | 把 `app_name` 改成白名单里的名字（`NewBox`/`MBox`/`TVBox`…） | ❌ 代价三重：① 撞**构建闸门**（`check_l1box_compat.sh` 校验"应用名"）② 与 10-07 定的**对外口径**（L1Box）冲突、`TVBox` 还是禁用词 ③ 一旦判据通过，jar 会**真的启动它自己的悬浮球 + 本地代理**（新的可见行为，风险未知） | ⛔ **不做** |
| **B** | ⭐ **侦测"自检失败"并改记账**（**推荐**） | ① 在 `SpiderDebug.log(String)` 里识别已知文案（`疑似二次打包`／`包名不匹配`／`App名称不匹配`／`签名DN命中黑名单`）置一个标记；② `invokeSelfInit` 调用前清标记、返回后读标记 ⇒ 命中即判定"**jar 自己放弃了初始化**"；③ 新增第三态：**jar 仍可用（不拒载、站点不消失）**，但**不 `occupyProxy`、不置 `GO_PROXY_STARTED`、也不记 `rememberHandBound`**（不把它算作任何形式的代理持有者），并打一条明确日志 | 极小：只读一个标记、只改记账分支；不动 jar 字节、不碰判死秒数 | ✅ **推荐**（本轮不动，等你点头） |
| **C** | 什么都不改 | 保持现状 | 零风险，但账本继续讹记死代理（代理型站点继续失败） | 可接受，但不如 B |
| **D** | 只降噪 | 在 `App.java` 后台兜底里把"已知的 `Init$3` + `Process.equals`"识别为预期噪声：不落 `crashes/` 文件、不打堆栈 | 极小 | 可选，可与 B 合并一批 |

**为什么 B 不做成"拒载"**：`ap` 轮踩过 —— `init()` 返回 false 会**降级该 jar 的站点**，
实测 458 次拒载 ⇒ **站点成片消失（用户实测"搜索为空"）**。所以 B 的语义必须是
**"照样用，但不假装它有代理"**，绝不能拒载。

### 仍需确认的开放问题（决定 B 的边界）

1. **这些 jar 的站点到底依不依赖 `/proxy`？** 若依赖，B 只是把"打不通"变成"明确 503"，**功能不会变好**；
   真正让它们恢复得靠 A（让 `startGoProxy` 跑起来）——但 A 的代价如上。
2. **`startFloatBall` 一旦被放行 = jar 自己的悬浮球会弹出来**，我方 `ToastSweeper` 只处理 Toast、拦不住它 ⇒ 这是 A 的隐藏成本。
3. B 的标记要不要**排除**"我们自己的 `SpiderDebug.log` 输出里恰好含这些词"的误判（目前只有 jar 会这么打，风险很低）。
