# 首页「刷新中杀进程 ⇒ 暂无数据且不自动加载」判定书（2026-10-07）

**结论：根因已用真机日志实证；与 cv / cw / cx 三次改动无关（老问题）。**

## 一、症状

首页下拉刷新 → 刷新动画还在转时，从最近任务划掉软件 → 再次进入首页显示「暂无数据」，
**隔几秒也不自动加载**（用户 2026-10-07 报告，可稳定复现）。

## 四、判定：两个缺陷叠加

### 缺陷 1 —— 半截缓存的产生点：`HomeFragment.startHomeLoad()`（源码 410 行）

真拉首页**之前**先执行 `HomeCache.clearVideos()`：把缓存里所有 tab 的影片列表清空，并**异步落盘**（600ms 合并窗口）。

- **正常情况**：清空后请求很快回来，各 tab 用 `putVideos` 重新写满 ⇒ 完全看不出来
- **刷新中杀进程**：清空已落盘、新数据从未写入 ⇒ 磁盘留下「**骨架 7 个 tab 完整、影片列表全空**」

### 缺陷 2 —— 半截缓存被误认为可用：`HomeFragment.tryRestoreCache()`（源码 369 行）

```kotlin
val tabs = cache.tabs ?: return false
if (tabs.isEmpty()) return false      // ← 只验「骨架非空」，不验「影片非空」
...
mSkipHomeLoadOnce = true              // ← 于是后面跳过重拉
```

⇒ `有影片的=0` 也被判「命中」，把半截缓存当成好缓存。

### 交点 —— 空态且不重试：`GridFragment.initData()`（源码 311 行）

```java
if (ApiConfig.get().getHomeSourceBean().getApi()==null){
    showEmpty();                       // ← 显示「暂无数据」，且【不发起任何请求】
    return;
}
```

该分支的注释原文就是「系统杀死 app 恢复缓存的 fragment 后会直接 getList，此时首页 api 都未加载完」
—— 它**假设上游稍后会把数据补上**；而缺陷 2 让上游判定「缓存够用」**不补** ⇒ **两边互相指望，谁也不动**。
这就是「隔几秒也不自动加载」的机制性原因（不是超时太短，而是**根本没有重试方**）。

## 五、与本次改动无关的证据

- cv / cw / cx 三次改动只涉及 `FastSearchActivity` / 字幕源 / 网盘库 / 联想与评分链路
- `HomeFragment.kt` / `GridFragment.java` / `HomeCache.java` **从未出现在任何一份差异对照报告中**
  （`cu到cv`、`cv到cw`、`cw到cx` 三份报告的差异清单里都没有它们）
- 时间线涉及的关键函数（`tryRestoreCache` / `clearVideos` / `GridFragment` 空态分支）在改动前后**逐字节相同**

## 六、可选观察（本轮顺带发现）

- `HomeCache.clearVideos()` 用它自己的注释说是「防止换线路后旧数据混入新缓存」——
  但 `tryRestoreCache` 已有 `cache.apiUrl != curUrl` 校验，**换线路本来就会失效** ⇒ 这个「清空」的必要性可以重新评估。

## 七、复现步骤（已实证）

1. 打开 App，等首页出内容
2. **下拉刷新**
3. **趁转圈还在转**（约 1 秒以上，让「清空」那一步来得及落盘）从最近任务划掉 App
4. 重新打开 ⇒ 首页「暂无数据」，且不会自己恢复

## 八、修复方案（待确认后执行）

### 方案 A（精准 · 最小改动 · 建议必做）

`tryRestoreCache` 增加「至少一个分类真的有影片」的校验：

```kotlin
// 刷新中被杀会留下「骨架有、影片全空」的半截缓存：此时不得用缓存，
// 否则会渲染出空分类并跳过网络加载 ⇒ 必须走全量重新加载
if (tabs.none { it.videos != null && it.videos.isNotEmpty() }) return false
```

效果：半截缓存一律判不可用 ⇒ 走正常全量流程（loadConfig → jar → `startHomeLoad`）⇒ 真拉首页。

### 方案 B（治本 · 改变缓存语义 · 可选）

把 `clearVideos()` 改成**只清内存、不落盘**，让磁盘上永远保留「上一次完整缓存」。

| 维度 | 说明 |
|---|---|
| 好处 | 即使被杀，下次冷启动仍能秒显旧数据，体验更稳 |
| 安全性 | `tryRestoreCache` 有 `apiUrl` 校验，换线路自动失效 ⇒ 不会串数据 |
| 代价 | 需改动 `HomeCache` 的语义（「清空」不再立即反映到磁盘），要重新界定各调用点的预期 |
