## 二、这批改的 3 项（全部来自 av 全场景实测，与具体站点无关）

### 1. 失败出口统一：关转圈 + 错误态 + 「重试」

- **改前**：`errorWithRetry(String err, boolean finish)` 分两支 —— `finish=true` 只弹 2 秒 Toast，**不关** `setTip("正在获取播放信息", true, false)` 的 loading 浮层。取链空返回（站点偶发不给地址）走的正是这一支，实测界面继续转了 **65 秒**。
- **改后**：`errorWithRetry(String err)` 单出口 → `setTip(err, false, true)`；`setTip` 里"可点重试"的判据从"只认 `视频播放出错`"放宽到全部错误态（唯一例外：`站点已失效，请返回重试`，它的动作是"返回"，文案已写明）。
- **口径不变**：只给「重试」一个出口，不引导换源、不引导换播放器。
- **保留**：出口之前的静默自动重试一次（`autoRetry`）——弱网下这次提示根本不会出现，符合"用户无感"。

### 2. 本机代理地址不做 http↔https 变形

- **改前**：守卫是 `isLocalHlsUrl(url)`（`url.contains("/l1.m3u8")`）——**只挡净化端点**。
- **实测**：网盘源的 `http://127.0.0.1:9978/proxy?...` 漏过守卫，被变形出 `https://127.0.0.1:9978/proxy?...`（本机同一端口不存在另一套协议，TLS 握手必失败）。
- **改后**：新增 `isLoopbackUrl(url)`（`://127.0.0.1` / `://localhost` / `://[::1]`），变形前用它拦下。

### 3. 不是 URL 的地址早判，不进播放器与兜底链

- **实测**：站点对同一剧集同一集，2 分钟内一次给 https 直链（284ms 就绪）、一次给 `Ksvideo-<hex>`（全工程搜不到这个协议）。后者让界面空转 **6.1~6.3 秒**（起播→尝试→兜底降级 IJK→失败），还会被上游静默重试再走一遍。av 里这类共 3 次。
- **改后**：`startPlayUrl` 入口判 `isPlayableUrl(url)` —— 判据只有一条"必须含 `://`"，**但放行迅雷专用通路**（`Thunder.isSupportUrl`：`magnet:` / `thunder` / `.torrent` 都不含 `://`，它们由 `play()` 里更早的 `Thunder.play` 拦截处理）。命中即 `PlayTrace.fail("地址", …)` 留痕 + 走失败出口，**不试兜底链**。
- **静默重取保留**：出口仍走 `errorWithRetry` → `autoRetry`，所以源侧轮换出可用地址时能自动救回来（这正是"用户无感"要的）。
- **预期**：从 ~6.1 秒缩到 ~0.3 秒出结论（首次尝试即刻判掉 + 静默重取一次）。**属预期，未实测。**

## 三、为什么只改这 3 项（其余逐条否决，避免堆改动）

| 候选 | 结论 |
|---|---|
| 判不可播后**跳过**静默重取 | ❌ 否决：同站同集 2 分钟内一次给 https、一次给该地址 ⇒ 源侧会轮换，重取有概率直接拿到能播的地址，这是**提成功率**而不是省时间 |
| 取链空返回后**自动换线路** | ❌ 否决：那是换源，你的口径明确"不做自动换源、不引导换源"。只能静默重取同一个站点 |
| 网盘源 `127.0.0.1:9978/proxy` 失败后自动重试 | ❌ 否决：代理有没有起来属加固 jar / 代理持有者那一层（aq 域），播放层不碰，只统计占比 |
| 起播速度再优化 | ❌ 否决：本轮靶子是"别卡死 + 失败可见"，速度实测基本持平（且站点构成不同，比了也不算数） |
| 看门狗 32s 终裁 / 场景 C | ⏸ 挂起：本机不可制造"空转"，仍只能机制论证 |

## 四、闸门新增（`check_l1box_regressions.sh` AA 节，10 条）

- 失败出口只剩一个形态 / `finish` 参数必须已废除 / 不得只弹 Toast / 必须落到错误态 / 必须带可点「重试」
- 本机代理不得变形 / 变形守卫不得只挡 `/l1.m3u8`
- 非 URL 地址必须起播前判掉 / 必须留痕 / 判据必须放行迅雷专用通路
