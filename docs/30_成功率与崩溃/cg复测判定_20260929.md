## 二、判定（逐项）

### 【判定 1】① 手绑世代账本 —— **已静态推理收口，本轮不再验证**

cg 对这一项**行为零改动**，只把论证固化进 `ProtectedInitJar.java` 的注释块（四段：判据与 bug 一一对应 / 分支可穷举 / `getLoader` 语义 / 二层兜底）。

判定依据（静态，不依赖本轮实测）：

| 论证 | 内容 |
|---|---|
| ㈠ **判据与原 bug 一一对应** | 原 bug 是「绑定时的世代号 vs 当前世代号」比较。该比较**在代码里已不存在**（`HandBound` 里已无那个 `gen` 字段）⇒ **触发条件本身被移除**。这是**删除式修复**，不是参数调优 ⇒ **不需要实测覆盖**。 |
| ㈡ **新判据可穷举** | 只剩两种走向：`H0==Hc`（没换届）⇒ 放行；`H0!=Hc`（真换届）⇒ 拒绝。无中间态。 |
| ㈢ **`getLoader` 语义** | 手绑拿到的是「调用现场连到当前正在跑的代理」的 loader（ce 轮对照组已反证）。 |
| ㈣ **代价封在第二层** | ClassLoader 终审仍在，最坏是「多走到第二层再被拒」，**不会 SIGABRT**。 |

⇒ **判定：已修复（静态收口）。本轮无 `拒:` 记录，与"不该拦的确实没拦"一致，但不再作为验证项。**

### 【判定 2】② `do` 路由 —— **学习机制已生效，但本轮无第二次调用可体现收益**

**cf 轮的事实**：13 次 `/proxy` 调用，`do` 分别是 `hmys`(11) / `ck`(2)，**全部 `路由=recent(回退)`** ⇒ `siteJarKeys` **13 次全 miss**。

**cg 改法**：新增 `doJarKeys`（`do` → jarKey），路由优先级改为 **学到的 `doJarKeys` → `siteJarKeys` → `recentJarKey`**；只在「放行且返回非 null」时登记（防固化错路由）。

**本轮数据**：`表规模=do表1/站点表40` ⇒ **`doJarKeys` 确实从 0 涨到 1，学习机制生效** ✅

⚠️ **但这行日志标的是 `路由=recent(回退)`，这不是 bug**，需要说清两点：

**㈠ 本轮只有 1 次 `/proxy` 调用。** 就是「从 0 学到 1」那一次。既然调用时表里还没有这个 `do`，`routeDo=false`、标 `recent(回退)` **是正确的**。

**㈡ 日志有"自证效应"。** 代码里 `doJarKeys.put(...)`（第 680 行）**在 `proxyLog(...)`（第 681 行）之前**执行，所以打印这一行时**表里已经含本条**。⇒ `表规模=do表1` 是"含本条之后"的数，不是"调用当时"的数。**看这一行不能推出"路由用了 `do`"。**

⇒ **判定：机制已生效（表从 0→1），但"收益"需要有第二次同 `do` 的调用才能观测（本应标 `do(学到)` 并命中正确的 jar）—— 本轮无此样本。判"已生效但未观测到收益"。**

**顺带确认**：`key=ae48218142` 是**非加固 jar**（`ae48218142817cd9759e0bd80b97d7de.jar`，走 `JarKillNeutralizer`），`返回=200` ⇒ 非加固 jar 的代理调用**正常**。

### 【判定 3】③ 分段耗时 —— **真根因找到了：不是"结算点不可达"，是"成本根本没到 25ms 阈值"**

**先说证伪**：前三轮我怀疑了两件事，本轮都**证伪**了：

| 曾经的怀疑 | 本轮证据 | 结论 |
|---|---|---|
| 「结算被 `doFrame` 抢先清掉 `pendingSegTag`」 | 代码顺序正确（843 行 `settlePendingSeg()` 在 844 行 `snapshotFrameStats` **之前**）；且若 `doFrame` 先清，它自己也会 `segLog` 出数 | ❌ 证伪 |
| 「埋点根本没执行到」 | `帧耗时[本轮]` 出数 1 条，证明收尾路径走到了、`settlePendingSeg()` 也被调用了 | ❌ 证伪 |

**真根因**：`segLog()` 是**阈值打印**——

```kotlin
private fun segLog(name: String, startMs: Long) {
    val cost = SystemClock.elapsedRealtime() - startMs
    if (cost >= SEG_WARN_MS) System.out.println("分段耗时：$name=${cost}ms")   // SEG_WARN_MS = 25
}
```

而 `flushSearchResults()` 的落盘节奏是：**每 120ms 一拍**（`SEARCH_FLUSH_MS=120`），**每拍只落增量的一小批**（滑动态最多 12 条，`SCROLL_BATCH_MAX`）。本轮 `搜索首条结果` 埋点 0 条、`结果落地(...)` 埋点 0 条 ⇒ 说明**每一拍的 `addData` 插入成本都 < 25ms**（`searchAdapter.addData` 是有增量的通知，不是整表重刷）。

**⇒ 判定：「分段耗时 0 条」不是埋点坏了，而是——它在**如实报告"插入本身不慢"**。**

**这个结论恰好被另一条独立证据侧面印证**：`帧耗时 最差=314ms@16:06:06(结果落地)` —— 314ms 的成本**不在**我们的插入代码里，而在插入**之后**的布局/绘制。所以"插入 < 25ms"与"这一帧花了 314ms"**并不矛盾**，正因为如此，分段计时（只量插入）就永远不会超过 25ms。

⚠️ **但这一轮还多出一个新发现（314ms 的真凶）**：

```
16:06:06.630  469   469 I WebViewFactory: Loading com.google.android.webview version 117.0.5938.60
16:06:06.634  469   469 D nativeloader: Configuring clns-11 for other apk …/WebViewGoogle64CN.apk
16:06:06.641  469   820 I System.out: 加固 jar 手绑成功（承接已有的本地代理，未重启）：0b9565d6a6…
16:06:06.935  469   469 I Choreographer: Skipped 37 frames!
16:06:06.935  469   469 I Quality : Skipped: false 37 cost 313.51004 processName com.github.tvbox.osc
```

**314ms 与 WebView 首次初始化（`WebViewFactory: Loading … 117.0.5938.60`）落在同一时刻，数值精确吻合（313.51 ≈ 314）。**

⇒ **判定：`最差=314ms@结果落地` 里的 314ms，实质是「加固 jar 首次构造 WebView（取 Cookie/UA）」的初始化成本**——`stage("结果落地")` 只是当时**碰巧停留的阶段标签**（`frameStage` 是"最后一次 stage() 设的值"，不是"这一帧真的在做的事"），**不是我们的落地代码慢**。

> 📌 这也解释了为什么 cd / ce / cf 三轮的最差帧都标「结果落地」且数值相近（240~314ms）：**同一个"首次 WebView 初始化"成本，被同一个阶段标签盖住了**。**`frameStage` 这个标签存在语义坑**，需要在下一轮（若还要继续量）时改成"帧起点到帧终点的真实阶段推断"，或者至少在 WebView 初始化前后显式 `stage()` 一次。

## 四、待办（仅记录，等统一出方案）
