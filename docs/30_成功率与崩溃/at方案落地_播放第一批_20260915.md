## 三、静态复核：崩溃面审计（你要的"提前判定问题"）

**结论：本批改动不新增任何线程、不碰 jar 装载节奏、不引入新的进程级操作。**

| 审计项 | 结果 |
|---|---|
| 是否新增线程 / 线程池 | **否**。新增只有 `mHandler.postDelayed`（复用既有主线程 Handler） |
| 遗留定时任务 | `onDestroyView()` 同时 `cancelStartWatchdog()` + `finishFetchWatchdog()`，不会在视图销毁后对着已释放的播放器做兜底 |
| 失败出口是否会循环 | 不会。出口统一为 `errorWithRetry → autoRetry`，每集上限 1 次再重解析，之后收敛为明确提示 |
| 看门狗是否可能误杀慢源 | 三层保护：`STATE_PREPARING`+位置 0+网速 0 才判死 / 判死前再复核 10 秒 / 任一进展立即解除 |
| 取链请求是否会重复 | `mFetchDone` 一次性闸门；15 秒判超时后只自动重取 **1** 次 |
| 是否触碰加固 jar / 防崩线 | **完全没碰**（本批零 jar 相关改动） |

### 审计中新挖出的三条事实（都写进了闸门，防被改回去）

1. **⭐ B4 的守卫是"承重"的，不是冗余** —— 实测站点 IJK 选项在 `IjkPlayer.initPlayer()`（`:39`）落地，**早于** `setDataSource()`。也就是说我补的 `rw_timeout` **本来会覆盖站点设置**，全靠那句「订阅已指定就跳过」挡住。守卫的 key 匹配格式已核实为 `4|rw_timeout`（`IjkMediaPlayer:39-41` 用 `split("\\|")` 解析）。**谁删掉这一行，就等于悄悄改掉所有站点的解码设置。**
2. **Exo 的网速信号可用** —— `ExoMediaPlayer:275` 用 `TrafficStats` 实现了 `getTcpSpeed`，所以看门狗判据在 Exo 下有效。且它只会「假阴性＝不判死」，**绝不会误杀**。
3. **IJK 超时单位正确** —— `DEFAULT_RW_TIMEOUT_US = 20L*1000*1000`（**微秒**）。这个参数写错单位会把 20 秒变成 20 毫秒，属必查项。

## 四、诚实边界（做不到 / 已知缺陷 / 本批未做）

| 项 | 说明 |
|---|---|
| **"起播后可能重启一次"（极少数慢源）** | 取链超过 15 秒但**最终会成功**的源：看门狗先判超时并自动重取，旧结果迟到会起播，随后重取结果再起播一次。**有界**（每集最多 2 次取链，最终收敛到明确提示），不崩不循环。要彻底消除需给取链结果带请求代次（要动 `SourceViewModel` 5 处），按「宁可少动」本批未做 |
| **慢但能播的源会更早进入兜底** | 起播 30 秒（20+10）无任何进展即判死并降级。这是你拍板的取舍（20 秒） |
| **整站失效 / 地址本身已死 / 鉴权头推不出来** | 程序侧无解，只能你手动换源。本批不引导、不提醒 |
| **净化的去广告能力变弱** | 2.5 秒超时的代价：个别源不再过滤片头广告（你拍板的「起播优先」） |
| **订阅超 5 秒仍可能空态** | 搜索线遗留边界，文案准确 + 自动重搜，不静默 |
| **已识别但本批未纳入：`RemoteServer.m3u8Content` 的 volatile** | 主线程写 / NanoHTTPD 服务线程读，理论上有可见性缺口。我改了、闸门也加断言了，但**构建时宿主机内存不足无法出包** → 为保持「源码 ≡ 产物」**已回退**。实际收益接近零（服务线程每次请求读一次、ARM64 缓存一致；即便读到旧值也会被回退直连自愈）。**下一批出包时一并带上。** |

## 六、装机后怎么看（如果以后有机会测）

```bash
adb logcat -s L1Play            # 只看播放埋点
```
| 你要看的 | 在哪一行 | 判读 |
|---|---|---|
| 起播慢在哪一步 | `播放心跳：净化 … ms=` | 净化耗时若接近 2500，说明这个源在超时阈值上（可考虑调大） |
| **B1 是否真的生效** | `播放心跳：兜底 …` 出现在**第 2 集及以后** | 只要不是只在第 1 集出现，就说明"每集独立额度"生效了（改动前第 2 集起完全没有这层保护） |
| 黑屏转圈是否被判死 | `播放失败：起播 看门狗判定无进展` | 若同时伴随"本该能播"，说明判据太严，把 20 秒调大即可 |
| 是否有误杀 | `播放心跳：看门狗 起播有进展，解除 …` | 出现在判死前＝判据正常工作 |
| 崩溃线 | `Fatal signal 6` / `JNI DETECTED ERROR` / `拒载` | 本批目标是**保持 0** |

## 七、本轮构建踩到的环境问题（与代码无关，但要知道）

| 现象 | 真因 | 处理 |
|---|---|---|
| JVM 直接起不来：`insufficient memory` / `AvailPageFile size 0M` | **本机页面文件被禁用**，提交上限 ≈ 物理内存 16.3GB，且已被吃满（只剩 644MB） | 构建堆已从 `3072m` 永久下调到 **1536m**（Kotlin 2048m→1024m）。**这台机器上不要再改回 3072m** |
| `Could not receive a message from the daemon`（3 次重试全失败，无 hs_err 文件） | 守护进程在编译/合并 dex 途中被系统**杀掉**（无崩溃报告＝进程级内存终止）。此刻可提交仅 **1658MB**，而构建峰值约 **2.2GB** | 出包成功那次可提交有 1886MB。**根治＝启用系统页面文件**（系统属性 → 高级 → 性能设置 → 高级 → 虚拟内存 → 勾选自动管理）。勾上之后这类失败会彻底消失 |
| 闸门"全绿"但代码编译不过 | 第 5 道闸门是**文本静态断言**，抓不到语法/编译错误 | **教训：闸门绿 ≠ 能编译。大段改完后，第一道真验证是构建本身** |
