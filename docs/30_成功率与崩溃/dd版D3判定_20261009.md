# D3 用例判定：切回可用源后，搜索页一直显示加载中

> 批次：`dd`（`L1Box_v1.0.0_release_20261009dd.apk`）
> 用户报告：**D1、D2 已通过，D4 没问题，只有 D3 失败** —— 切换回正常源后搜索页一直显示加载中。
> 结论：**这是 dc 引入的 SUB_FAIL 出口设计不完整，不是 dd 判据的问题**（dd 的判据工作正常，D4 通过可佐证）。
> ⛔ 本文件只做原因判定，**未改任何代码**。

## 二、根因：SUB_FAIL 的"探池节拍"只在「取消」这一个出口被排

### 代码事实

```kotlin
// 1) 进入 SUB_FAIL —— 只有"首次"会去重拉，其余一律弹框，且【不排节拍】
private fun enterSubFail() {
    phase = Phase.SUB_FAIL
    showLoading()
    if (!subReloadTried) { subReloadTried = true; reloadSubNow(); return }
    showSubFailDialog()                      // ← 不排节拍
}

// 2) 同址重拉失败 —— 也是弹框，【不排节拍】
override fun error(msg: String) { …; showSubFailDialog() }      // reloadSubNow 内

// 3) 对话框「重试」—— 重新 loading + 重拉，【不排节拍】
override fun left() { subFailDialog?.hide(); showLoading(); reloadSubNow() }

// 4) 对话框「取消」—— ★ 唯一排节拍的地方
override fun right() { subFailDialog?.hide(); exitSubFailToEmpty() }

private fun exitSubFailToEmpty() {
    showEmpty(); ToastUtils.showLong("订阅加载失败，请检查源地址")
    searchWatchdogHandler.postDelayed(waitTickRunnable, READY_RETRY_DELAY_MS)   // ← 只有这里
}

// 5) 节拍本身：SUB_FAIL 状态唯一的"自动恢复"入口
private fun onSubFailTick() {
    if (ApiConfig.get().hasSubscription()) { …自动重搜… }   // 池恢复才会响
    if (hasSubUrl()) { postDelayed(waitTickRunnable, 500L) }  // 否则静默续排（不打日志）
}
```

⇒ **只要用户没有点「取消」**（点「重试」、或直接返回后再进、或对话框被忽略），**节拍永远不会启动**，
SUB_FAIL 就成了一个**没有任何自动驱动的死态** ⇒ 池恢复后搜索页不知道 ⇒ **永久加载中**。

### 第二个加重因素：护栏是静态的，跨实例保留

```kotlin
companion object {
    private var subReloadTried = false      // ← 静态：跨 FastSearchActivity 实例保留
}
private var subFailDialog: TipDialog? = null // ← 实例变量：每次新建
```

`subReloadTried` 在 companion object 里 ⇒ **"每启动最多自动重拉 1 次"实际是"每进程最多 1 次"**。
用户"D2 失败 → 返回 → 再进搜索页"时，新实例**不会再自动重拉**，直接弹框 + 不排节拍
⇒ 比第一次更容易落进"无节拍"状态。这与对话框字段（实例级）形成明显不对称。

### 为什么 D2 能过、D4 也没问题

- **D2 能过**：用户在 D2 里**确实点了「取消」** ⇒ 走 `exitSubFailToEmpty()` ⇒ 空态 ＋ 提示 ＋ 节拍被排上 ⇒ 观察到的行为符合预期。
- **D4 能过**：D4 验的是 `isCurrentLoad` 判据（迟到失败不得清当前可用源的池）。日志显示 19:42/19:43 的池归属变迁与 Hawk 完全一致（Hawk=9877 时清池、切回好源后池恢复）⇒ **dd 的判据本身工作正常** ✓

## 三、影响面（按严重度）

| # | 影响 | 说明 |
|---|---|---|
| ① | **D3 场景必然失败** | "订阅加载失败 → 换回可用源"这条最常见的自救路径失效；池恢复了界面还停在加载中 |
| ② | 用户唯一出路是点「取消」 | 而「取消」的语义是"放弃"，用户心理上会理解为"不修了"，不会预期它启用自动恢复 |
| ③ | 自动恢复能力形同虚设 | dc 宣称的"订阅恢复后自动重搜"只在一种操作序列下生效 |
| ④ | 静态护栏加剧 | 反复进出搜索页后，连一次自动重拉都不再有 |

## 四、修复方向（待确认后再动手）

**最小根治（3 处）**

1. **`enterSubFail()` 统一排节拍**（幂等）—— 进入 SUB_FAIL 就保证节拍在跑，
   不再依赖"用户必须点取消"。这一条即消灭 D3。
2. **恢复判据加严**：`hasSubscription() && ApiConfig.get().isSitePoolSettled()`
   —— 池非空 **且已定论**才算恢复，避免装载半途误判触发空搜。
3. **`subReloadTried` 改为实例级**（或"池从空变非空后允许再自动重拉 1 次"）
   —— 消除"每进程仅 1 次"的过强护栏，与对话框字段的实例语义对齐。

**可选（体验）**

4. 用户点「重试」时也顺手排上节拍（由第 1 条自然覆盖）。
5. SUB_FAIL 态在 `onResume` 兜底补排一次节拍 —— 用户"回订阅页改地址再返回搜索页"是最常见的操作路径。

**不建议**

- ❌ 不要"失败就自动切回上一个源" —— 与"零回退，只提示"的口径冲突。
- ❌ 不要把节拍周期缩短当作修复 —— 问题不是"等得不够久"，而是**根本没有重试方**。

---

## 五、判据（以后遇同类问题可直接套用）

> **凡是"某个 UI 状态只由定时任务驱动"，就必须确认：进入该状态的每一条路径都排了任务。**
> 只要有一条路径漏排，这个状态就会变成死态 —— 而且只在特定操作序列下复现（点取消就好、点重试就死）。
> 检查方法：`grep` 该状态名，看 `enterXxx()` 里有没有排任务；再看 `removeCallbacks(xxx)` 的所有位置。
