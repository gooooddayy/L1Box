## 一、⭐⭐ 核心确证："滑动期间左栏完全不更新"

### 铁证（一次滑动的前后对照）

| 时刻 | chip | 埋点 |
|---|---|---|
| 13:29:51.945 | **23** | `批量=1 可滚=true 上限=801` |
| ↓ | ↓ | **用户开始滑动…… 持续 8.4 秒** |
| **13:30:00.361** | **31** | `批量=8 距末滚动=401ms 滚动段=8348ms/168次 上限=1937` |

⇒ **这 8.4 秒里 chip 从 23 只涨到 31，而且那 8 个是最后一次性补建的**（`批量=8` 正好等于增量）
⇒ **滑动期间一个 chip 都没建** —— 这就是用户说的「一滑动，就停止出结果」

### 机制（代码层，完全对得上）

```kotlin
private fun siteTabsBusy(): Boolean =
        siteTabsTouchDown ||                            // 手指正按在左栏
        SystemClock.elapsedRealtime() - siteTabsLastScrollMs < SITE_TAB_SETTLE_MS   // 400ms 内滚过
```
```kotlin
private fun drainSiteTabQueue(tagName: String) {
    if (siteTabsBusy()) { scheduleSiteTabs(); return }   // ← 直接顺延，不建
    ...
}
```

⇒ 用户滑动左栏时，`touchDown=true` 或滚动事件持续刷新 `siteTabsLastScrollMs`
⇒ `siteTabsBusy()` **恒为 true** ⇒ `drainSiteTabQueue` 每次进来就直接 return
⇒ 站点结果全部堆在 `siteTabsPending`，**直到用户停手 400ms 后才一次性建出来**

### 所有"有滚动时插入"的 `距末滚动` 都是 400/401ms

| 数据 | 值 |
|---|---|
| 13:29:40.310 | `距末滚动=401ms` 批量=6 |
| 13:29:43.129 | `距末滚动=400ms` 批量=4 |
| 13:30:00.361 | `距末滚动=401ms` 批量=8 |

⇒ 每次都是**卡着 400ms 阈值**才动手 ⇒ 守卫精确工作，**用户不停手就永远不建**。

### ⭐ 这解释了为什么"批量"能到 8

第 0 轮所有插入都是 `批量=1~6` 且 `队列=0`（从不积压）。
本轮出现了 **`批量=8`** —— 正是 `SITE_TAB_BATCH` 的上限 ⇒ **队列真的积压了** ⇒ 积压的唯一来源就是"滑动被挡"。

### ⭐ 因此"依然卡"的性质要重新定义

⇒ 用户报的「卡」与「停止出结果」**极可能是同一件事**：**滑动期间左栏被冻结**。
之前归因的"性能/绘制/图片"方向，在本轮数据里**全部站不住**。

## 四、🔍 新发现：滚动事件"稀疏"，待细查

`滚动段` 的 `时长/事件数` 换算成平均间隔：

| 来源 | 事件间隔 |
|---|---|
| 第 0 轮 | 3164ms/35次 = **90ms/次** |
| 第 0 轮 | 2853ms/106次 = 27ms/次 |
| 第 1 轮 | 2648ms/103次 = 26ms/次 |
| **第 1 轮** | **8348ms/168次 = 50ms/次** |

⇒ 正常情况下滚动应**每帧一次（16ms）**，实测是 26~90ms ⇒ **明显不均匀，有些帧 scrollY 没有变化**。

**可能的机制**：`DslTabLayout.onScroll` 里有位移门槛
```kotlin
val absY = abs(distanceY)
if (absY > _touchSlop) { handle = onScrollChange(distanceY) }   // 每帧位移小于 slop ⇒ 被吞
```
⇒ 每帧位移不足 `touchSlop`（约 8dp）时**这一帧的位移被丢弃**，累积够了才跳一次 ⇒ 观感"一顿一顿"。

**但这与用户"慢速流畅、快速卡"的描述方向相反**（慢速时每帧位移更小、更容易被吞）。
⇒ **此条存疑**，需要补埋点（记录每次 `onScrollChange` 的 `deltaY`）才能定论。

## 五、🎯 结论与修复方向（**性质已改变**）

### 问题性质

| 原来的假设 | 本轮数据修正为 |
|---|---|
| 渲染/绘制性能问题 | ❌ **性能没问题**（平均 6~7ms） |
| 右栏收尾三件活 | ❌ **排除**（0~1ms） |
| chip 创建成本 | 🔻 **可能性很低**（批量 1~4） |
| **滑动期间左栏被守卫冻结** | ⭐ **确证为"卡 + 停止出结果"的直接原因** |

### 修复方向（有据可依）

**核心矛盾**：09-28 引入"停手窗口"是为了防止**插入打断手势**；但实测证明
**插入根本不会改变滚动位置** —— 本轮所有埋点都是 **`前Y == 后Y`**。

**而 `addView` 是"追加到末尾"，它不移除也不移动已有子 View**。
真正会打断手势的只有 `removeAllViews()`（清空重建，会瞬间清掉手指下的所有子 View）。

⇒ **精准修法**：
| 操作 | 现状 | 建议 |
|---|---|---|
| **追加新 chip**（`siteTabsPending` → `addView`） | 滑动中**禁止**（守卫挡住）| **滑动中允许** —— 追加不改已有项、实测不改滚动位置 |
| **清空重建**（`siteTabsNeedReset` → `removeAllViews`） | 滑动中禁止 | **保持禁止**（这个才真的会打断手势） |

⇒ 用户滑动时能看到站点陆续出现（"不停止出结果"），且不会打断手势。

**风险**：若实测仍有 ACTION_CANCEL，可退化为"追加也限流"（如每 200ms 最多 2 个），
而不是像现在这样**一刀切全禁**。
