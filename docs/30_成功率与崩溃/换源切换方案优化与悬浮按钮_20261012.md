# 一、问题 1：画中画里的播放/暂停按钮图标

## 1.1 原因（已定位到行）

**"悬浮播放器"＝系统画中画（PiP）**。它的三个按钮不是 App 布局里的控件，而是进 PiP 时交给系统的 **`RemoteAction`**：

`ui/activity/DetailActivity.java:1012-1018`
```java
List<RemoteAction> actions = new ArrayList<>();
actions.add(generateRemoteAction(android.R.drawable.ic_media_previous, BROADCAST_ACTION_PREV,  "Prev", "Play Previous"));
actions.add(generateRemoteAction(android.R.drawable.ic_media_play,     BROADCAST_ACTION_PLAYPAUSE, "Play", "Play/Pause"));
//                                    ↑ 中间这个图标【写死】为 ic_media_play
actions.add(generateRemoteAction(android.R.drawable.ic_media_next,     BROADCAST_ACTION_NEXT,  "Next", "Play Next"));

PictureInPictureParams params = new PictureInPictureParams.Builder()
        .setAspectRatio(ratio)
        .setActions(actions).build();
...
enterPictureInPictureMode(params);      // ← params 只在"进入 PiP 这一刻"构建一次
```

**两个缺陷**：

| # | 缺陷 | 后果 |
|---|---|---|
| ① | 中间按钮的图标**写死 `ic_media_play`**，从不随播放状态变化 | **播放中也显示 ▶，暂停中也显示 ▶** ⇒ 用户看到的"暂停时显示播放样式" |
| ② | `PictureInPictureParams` **只在进入 PiP 时构建一次**，之后播放状态变化**不会**刷新 | 即使图标逻辑修对了，PiP 里也不会更新（除非重新 `setPictureInPictureParams`） |

> 对照：**App 内**的按钮是**对的** —— `VodController.onPlayStateChanged`（1180+）里
> `STATE_PLAYING → setImageResource(ic_pause)`、`STATE_PAUSED → setImageResource(ic_play)` ✓
> ⇒ **只有 PiP 这一路漏了**，所以是"样式问题"而不是"状态问题"。

## 1.2 修法（下一版）

1. 把 PiP 参数抽成 `buildPipParams()`，中间按钮图标**按当前播放状态**取：
   `playing ? android.R.drawable.ic_media_pause : android.R.drawable.ic_media_play`
2. **播放状态变化时刷新 PiP 参数**（仅当处于 PiP 时）：
   - `VodController.onPlayStateChanged` 的 `STATE_PLAYING` / `STATE_PAUSED` 分支
   - `togglePlay()` 之后
   ⇒ 调 `DetailActivity` 侧的 `setPictureInPictureParams(buildPipParams())`
   ⚠️ `setPictureInPictureParams` 是 **API 26+**，项目 minSdk 24 ⇒ 用现成的 `Utils.supportsPiPMode()` 把住
3. 进 PiP 时用 `buildPipParams()`（替换现在这份写死的）

# 二、问题 2：换源时的"缓存归属"审计 —— 三个缓存里**只有一个缺归属**

用户的诉求拆开是三句：**① 切换要丝滑 ② 显示"本来的状态" ③ 缓存兜底不能错误拦截源的加载**。
先按这三句审计现有三处缓存：

| 缓存 | 存什么 | 归属判据 | 结论 |
|---|---|---|---|
| **订阅 JSON**（`useCacheFallback`） | 订阅配置文本 | **文件名 = MD5(apiUrl)** ⇒ 换源天然不命中 | ✅ **安全**（不会串源） |
| **首页内容**（`HomeCache`） | 分类骨架 + 影片列表 | `apiUrl` 字段（db 轮已改为写 `poolUrl` 并做完整性校验） | ✅ **安全** |
| **spider jar**（`csp.jar`） | dex 包 | **无** —— 只有一个文件名 `csp.jar`，任何源共用 | ❌ **问题所在** |

## 2.1 核心缺陷：jar 缓存的"兜底"会**永久钉死**一个源

`api/ApiConfig.java:589-598`（下载失败兜底）
```java
@Override
public void onError(Response<File> response) {
    super.onError(response);
    // 弱网兜底：下载失败但本地还有旧的 jar 缓存 → 先用旧的顶上，别让整个源瘫掉
    if (cache.exists() && cache.length() > 0) {
        loadJarFileAsync(cache, fileName, jarKey, loader, callback, "网络不佳，已使用缓存数据源");
        return;                 // ← 用【可能属于别的源】的旧 jar 顶上
    }
    callback.error("");
}
```

`api/ApiConfig.java:697-710`（装载回调）
```java
MAIN_HANDLER.post(() -> {
    if (success) {
        loadedJarKeys.put(fileName, jarKey);   // ★ 用【当前源的】jarKey 标记【这份旧文件】
        if (successToast != null) Toast(successToast);   // "网络不佳，已使用缓存数据源"
        callback.success();                    // ★ 向上层报"成功"
    } else {
        callback.error("");
    }
});
```

**而 `loadJar` 的复用判据是**（同一文件 503 行附近）：
```java
if (cache.exists() && jarKey.equals(loadedJarKeys.get(fileName))) { callback.success(); return; }
```

### ⇒ 三件事同时发生了（这正是用户说的"错误拦截源的加载"）

| # | 发生了什么 | 后果 |
|---|---|---|
| **①** | 用**旧 jar**（可能属于**上一个源**）顶上 | **串源**：新源的地址配着旧源的 jar |
| **②** | `callback.success()` | 上层（`HomeFragment`）以为"**新源装载成功**"，其实没有 |
| **③** | `loadedJarKeys.put(fileName, 新源的 jarKey)` | **把旧文件登记成"新源的 jar 已加载"** ⇒ 下次切到该源时**复用命中 ⇒ 直接 success，永不重新下载** |

**第 ③ 条最要命**：**一次弱网失败 ⇒ 这个源被永久钉在错的 jar 上**。
用户反复切源时看到的就是"有的源好好的、有的源怎么弄都不对"——**这是"混乱"的一个确定来源**，而且**不可自愈**（除非清 App 数据）。

> ⚠️ **与我上一版改动的确有关系**：dg 让"HTTP 403（jar 内容非法）"也走这条兜底路径（之前 403 会把 9 字节垃圾写进去 ⇒ 后续 load 失败 ⇒ `error`）。
> 也就是说：**这条兜底本身是原有代码，但 dg 让它更容易被触发** —— 用户这次提得很准。
> **另一面**：dg 也把"403 摧毁 jar"堵住了（见 3.1），两条要一起看。

## 2.2 顺带发现的两处"看不见"

| # | 问题 | 影响 |
|---|---|---|
| ① | jar 兜底这条路**只有 Toast、没有日志** | 线上完全看不出发生过"降级用缓存"⇒ 归因困难 |
| ② | `loadJarFileAsync` 的 `successToast` 在**真下载成功**（`successToast == null`）与**降级兜底**（有 toast）之间**共用同一条 success 路径** | 上层拿不到"这是降级"的信息，无法据此调整 UI 或状态 |

# 四、方案：把"缓存归属 + 不假成功 + 不阻塞加载"变成三条硬约束

## 4.1 三条不变量（建议写进闸门钉住）

> **① 不串源**：任何缓存，**只有归属当前源/线路时才允许使用**。
> **② 不假成功**：缓存兜底**不得**让上层以为"真源已就绪"。
> **③ 不阻塞真加载**：缓存只能**垫着显示**，**不得取消或跳过**对真源的加载。

对照现状：**①** 订阅 JSON ✅／首页 ✅／**jar ❌**；**②** jar ❌；**③** jar ❌。

## 4.2 具体改动点（分轻重）

### 【A】jar 兜底必须带归属判断（**必做**，直接解决"永久钉死"）

- 兜底前判断"**这份 `csp.jar` 是不是当前 jar 源的**"：
  新增一个记录 `jarFileOwners: fileName → 该文件内容对应的 jarKey`
  （由**真正下载并校验通过**的那次写入时登记，`loadJarFileAsync` 不再改它）
- 只有 `jarFileOwners[fileName] == jarKey` 时才允许用缓存顶上；
  否则 ⇒ **如实失败**（`callback.error("")`）—— 宁可失败，也不串源
- **`loadedJarKeys` 只在"内容确实属于该 jarKey"时写入**（堵住 ③）

### 【B】兜底要能被上层区分（**必做**，让"不假成功"落地）

- 给 `LoadConfigCallback` 的降级路径一个**明确标记**（不新增接口也行：把 `successToast != null` 作为"降级"信号透出）
- `HomeFragment` 收到"降级成功"时：
  - **照常推进**首页加载（丝滑，不空窗）✅
  - 但**不再把它当做"该源 jar 已就绪"**（`loadedJarKeys` 不写）⇒ 下次仍会尝试真下载
  - 提示保留（用户明确说这个提示本身没问题），但**不能拦后续加载**

### 【C】jar 兜底补日志（**必做**，现在完全不可观测）

`L1Sub: jar 降级用缓存 文件=csp.jar 归属匹配=<是/否> 结果=<采用/放弃>`

### 【D】让"切换更丝滑"（**建议**，对应用户第 1 句诉求）

现有能力其实已经具备：`HomeCache`（按 `poolUrl` 归属）+ 冷启动秒显（`tryRestoreCache`）。
需要补的是**切源时的过渡表达**：

| 时刻 | 应该显示 |
|---|---|
| 刚切到新源、新源尚无缓存 | 「正在加载…」占位（**不显示上一个源的内容** —— 那会串源） |
| 新源有自己的历史缓存 | **直接用它秒显**（这才是"显示本来的状态"） |
| 新源加载成功 | 覆盖为最新 |
| 新源加载失败 | **本线路的失败态**（空态 + 原因），而不是一片混乱或上一个源的内容 |

⇒ 关键就一句：**过渡期只能显示"本线路"的东西**（缓存或加载态），**绝不显示别的线路的内容**。

### 【E】"显示本来的状态"与"换源失败清池"的关系（**要点，需确认口径**）

- 10-09 定的是：**换源失败 ⇒ 清前源池**（不许把别的源显示成"有效状态"）；
- 10-12 用户说：**哪怕线路有问题，也要尽量显示本来的状态**。
- **二者不冲突**：清池清的是"**前一个源**的池"（别人的东西）；"本来的状态"指的是"**这条线路自己**应有什么"。合起来就是：
  > **只显示本线路自己的东西；本线路没有（或失败）就如实说，不拿别人的顶上。**

# 【v2 · 重新分析（2026-10-12 14:0x）】拿到现场日志后的修订

用户口径（本轮确认）：① 画中画保持语义（暂停显示 ▶ 表示"点它继续"）② jar 归属不匹配**直接如实失败** ③ 新源无缓存 ⇒ **加载中占位** ④ **一批改**。

## 一、取证障碍（先说清楚，避免结论跑偏）

`_dg_dump_1012b.txt`（10-12 13:45 抓，12,197 行）里 **App 应用日志（`System.out`）计数 = 0**：
设备 `main` ring buffer 原为 **256 KiB**，13:40~13:45 系统日志写入 4,600+ 行把 I 级应用日志挤掉。
⇒ 本轮**无法**从日志定性"弱网换源混乱"的现场形态。已在设备上把缓冲提到 **4 MiB**（`logcat -G 4M` 成功），下次不会再丢。

**但代码层证据是充分的** —— 下面三条都可由源码直接判定，不依赖现场。

## 二、⭐ 本批真正的头号原因：dg 的互斥 key 用错了（**我引入的真回归**）

```java
// ApiConfig.java
487:  loadJar(useCache, spider, callback, "csp.jar",      jarLoader);      // ← 所有源固定同一文件名
492:  loadJar(useCache, spider, callback, "csp_home.jar", homeJarLoader);

550:  private static final Set<String> JAR_DOWNLOADING = ConcurrentHashMap.newKeySet();
593:  if (!JAR_DOWNLOADING.add(fileName)) {                                  // ← key = fileName = "csp.jar"
594:      System.out.println("L1Sub: jar 已在下载中 ⇒ 延后重试 文件=" + fileName);
595:      MAIN_HANDLER.postDelayed(() -> downloadJar(...), JAR_RETRY_DELAY_MS);   // ← 延后无次数上限
596:      return;
597:  }
```

**缺陷**：`fileName` 对所有源都是同一个字符串 `csp.jar` ⇒ 这个互斥实际是**跨源全局互斥**，
而它想防的只是"同一份 jar 被两个流同时写"（观测到 `并发=2`）。

**后果（弱网放大）**：
1. 源 A 的 jar 下载在途（弱网下 OkHttp 可挂几十秒）
2. 用户切到源 B ⇒ B 也认为"需要重下" ⇒ `JAR_DOWNLOADING.add("csp.jar")` 失败
3. ⇒ **每 1.5 秒延后一次**，直到 A 结束。延后**没有次数上限**
4. ⇒ 用户看到 **B 源"不加载 / 很久才加载"**

⇒ 这正是用户上一轮的直觉：**"你前面改动导致改动了原来的逻辑"** —— 他判断对了。
⇒ 这也解释了用户反复强调的 **"提示/机制不要错误拦截源的加载"**。

**正确修法**：互斥 key 用 **`jarKey`（`jarUrl + "|" + md5`）**，而不是 `fileName`：
- 同一份 jar 的并发 ⇒ 仍然互斥（防交错写）✓
- 不同源 ⇒ 互不阻塞 ✓

## 三、原有缺陷（dg 的兜底把它从"偶发"变成"必现"）

```java
// downloadJar.onError（弱网/内容非法兜底）
if (cache.exists() && cache.length() > 0) {
    loadJarFileAsync(cache, fileName, jarKey, loader, fin, "网络不佳，已使用缓存数据源");
    return;
}
// loadJarFileAsync 成功路径（699）：
loadedJarKeys.put(fileName, jarKey);      // ← 登记的是【当前源的 jarKey】，但文件可能是【上一个源的 jar】
```

**三个后果**：
| # | 后果 | 说明 |
|---|---|---|
| ① | **串源** | `files/csp.jar` 是所有源共用同一个路径 ⇒ 兜底用上的"旧 jar"可能属于**别的源** |
| ② | **假成功** | 用了别人的 jar 却 `callback.success()` ⇒ 上层以为"新源已就绪" |
| ③ | **永久钉死（最严重）** | 把**当前源的 jarKey** 登记进 `loadedJarKeys` ⇒ 复用例 `if (cache.exists() && jarKey.equals(loadedJarKeys.get(fileName)))` **直接命中** ⇒ 该源**永远不再下载真 jar** |

⇒ 用户口径 **"提示网络不佳，已使用缓存，这个一定不要错误拦截源的加载"** 说的就是 ③ —— **它真的会拦截，而且是永久性的**。

**修法（按用户口径"归属不匹配直接如实失败"）**：
- 兜底前加**归属判据**：本地缓存必须**确实是当前源的那一份**（`loadedJarKeys[fileName] == jarKey`，或缓存的 md5 与当前源声明的 md5 一致）
- 归属不符 ⇒ **如实失败**（不登记、不 success）
- 归属相符（同一个源自己的旧 jar）⇒ 允许兜底，但**不写"已加载"标记**（下次仍会真下载）

## 四、附带发现（长期存在，本轮只记录 + 观测，不动手）

### `JarKillNeutralizer` 的中和逃到了线程外

```java
// JarKillNeutralizer：把 System.exit / Runtime.halt / Process.killProcess / sendSignal
// 的 name_idx 改指到合法方法名（优先 toString/hashCode/equals）
// 注释自陈：「抛 NoSuchMethodError（普通 Error，可被上层 catch(Throwable) 吞掉）」
```

真机崩溃（10-09 起长期存在，10-12 13:06~13:15 密集 12 次）：
```
java.lang.NoSuchMethodError: No static method equals(I)V in class Landroid/os/Process;
    at com.github.catvod.spider.Init$3.run(Unknown Source:14)     ← jar 自起线程
    at java.lang.Thread.run
```
`Process.equals(I)V` 与 `Process.killProcess(I)V` **签名完全一致** ⇒ 就是被改名的那一处。

**关键**：它抛在 **jar 自己起的 `Init$3` 线程**里 ⇒ **逃出了** `ProtectedInitJar.invokeSelfInit` 的
`try { method.invoke(...) } catch (Throwable)` ⇒ 落到 App 的全局 handler：
```java
// App.java:341（后台线程安全网）
Thread.setDefaultUncaughtExceptionHandler((thread, throwable) -> {
    CrashLog.save(thread, throwable);
    if (thread == mainThread && caocHandler != null) caocHandler.uncaughtException(...);
    else Log.e("App", "后台线程异常(已拦截,不闪退): " + thread.getName(), throwable);
});
```
⇒ **进程不会死**（这层网是有效的），**但那个线程的工作随之丢失**（自杀调用之后若无 catch，其后的初始化代码不再执行）。

**诱因**（jar 自己打的日志，铁证）：
```
SpiderLog: App名称不匹配，当前App名: L1Box
SpiderLog: App名称不匹配，疑似二次打包
```
`res/values/strings.xml` 的 `app_name` 现为 **`L1Box`**（合规改名）。
`JarContextBridge` **只覆写了 `getClassLoader()`**，没有伪装 App 名 ⇒ jar 读到真实值 ⇒ 判定"二次打包"⇒ 走自杀分支。

出现频率：10-10 de 版 12 次、df 版 8 次（10-12 因日志被冲无法统计）。
⇒ **与本轮"弱网换源"很可能相关**（线程工作丢失 ⇒ 本地代理/初始化不完整；10-10 12:41:49 有 `Failed to connect to /127.0.0.1:8964` 紧随其后）。

⛔ **本批不动它**（涉及加固行为，风险高且证据不足）：先加观测，确认 `Init$3` 崩溃与源加载失败的相关性后再定。

## 六、判据（可复用）

> **凡是"用文件名/路径做互斥或缓存键"的地方，先问一句：这个键在不同数据源之间是否唯一？**
> `csp.jar` 是**共用的物理文件名**，不是**源的标识**。用共用键做互斥 = 把本该并行的两件事串起来；
> 用共用键做复用判据 = 把 A 的东西认成 B 的。

> **"兜底降级"的返回值必须与"真成功"可区分。** 否则降级会被上层记成"就绪"，
> 而下游的复用判据（`jarKey.equals(loadedJarKeys.get(fileName))`）会把它**固化**成永久状态。
