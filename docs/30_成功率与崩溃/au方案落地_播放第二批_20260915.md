### B7 · Exo 硬解失败回退
- `ExoMediaPlayer.java:63`：`mRenderersFactory.setEnableDecoderFallback(true)`
- **现实收益在音频**：设备硬解不支持 AC3/DTS 这类编码时，落到工程自带的 ffmpeg 音频软解，而不是直接报错
- **视频侧无第二个渲染器**（Exo 官方扩展只有音频没有视频），所以不会改变视频播放行为
- **风险：低**。这是 Exo 官方机制，不改任何 API 调用顺序

### B8 · 每源独立数据源工厂（修 UA 跨站点残留）
- `ExoMediaSourceHelper.java:160` `getDataSourceFactory(headers)` + `:171` `createHttpDataSourceFactory(headers)`
- **改掉的**：原先反射改写**单例工厂**的 `userAgent` 字段 → **A 站点设的 UA 会永久残留到 B 站点**（"换了源就播不出"的来源之一）
- 顺带修正：不再从调用方的请求头表里摘除 User-Agent、不再原地改写调用方的表（播放器侧改为只读）
- **风险与预案**：每次起播新建一个 `Factory` 配置对象（轻量）；`OkHttpClient` 与连接池仍是共享的 → **连接数、并发度都不变**。缓存路径同样改为带上当次请求头（`getCacheDataSourceFactory(headers)`），`Cache` 仍单例。

### B9 · 隧道模式埋点（只观察，不改行为）
- `ExoMediaPlayer.java:335`：报错日志带上 `tunneling=on(工程固定) retryPath=…`
- `setTunnelingEnabled(true)` 是上游原样，**本轮不动**；先让日志能把"错误是否集中在隧道模式下"看出来，下一版再决定
- **风险：零**（一行日志）

### C1 · 请求头兜底补全 —— **只补 Referer**
- `PlayFragment.java:334` `fillMissingHeaders`，在两个汇聚点调用：
  - `playUrl`（`:1129`）：覆盖净化预取 + 直连起播
  - `startPlayUrl`（`:1334`）：覆盖兜底链重播
- 只补**缺失的同源 Referer**（取地址 `scheme://host/`），绝不覆盖站点已给的值；本地地址（127.0.0.1 / localhost）直接跳过
- **与方案的差异见 §3**：方案写的是"补 Referer/UA"，实施时收敛为只补 Referer
- **风险与预案**：补的是同源地址，对不需要 Referer 的源无影响；任何异常都原样返回入参

### C2 · 同址换协议重试
- `PlayFragment.java:1788` `retryVariantUrl()`；接在兜底链 `回退直连 → **变形** → 内置降级` 之间
- 只换 `http↔https`，地址其余部分一字不改；`rtmp/rtsp` 与本地地址不参与；**每集只试一次**（`mVariantTried`）
- 有可见提示「正在尝试备用协议重连」，避免用户以为卡住
- **预案**：失败自动走下一档（内置降级），`mVariantTried` 保证不会形成循环

### C3 · 去 BOM 改本地做（弃第三方）
- `PlayFragment.java:1289` `retryWithoutBom()` + `:359` `stripBom()`
- **改掉的**：把播放地址转发给第三方去 BOM 接口 —— 那本身就是个新的失败点（第三方异常＝凭空多一次失败），也会把整份清单发到外部
- 现在：本地拉一份 → 剥 BOM → 经内置代理 `/l1.m3u8` 播（不依赖任何外部服务）
- 触发条件：**同一地址已经失败过一次**（`autoRetryCount>0`）且未试过（`mBomRetried`）→ 不影响首次起播耗时
- BOM 两种形态都处理：`\uFEFF`，以及被按 latin1 读出的 `ï»¿`
- **预案**（三重退路）：本地代理不可用（`serverPort<=0`）／拉取失败／内容不是清单 → **一律退回按原地址播**。复用净化那枚 2.5 秒超时的 client，不新增长等待

### D1 · 失败出口收敛
- `PlayFragment.java:1004`：提示文案 = 「视频播放出错，**重试**」（橙字可点）
- `:1017` `retryFromScratch()`：点重试＝把本集所有"已试过"标记清干净（额度/看门狗/回退地址/去 BOM/变形/降级阶梯），从取链重新来一遍
- 不再提供「切换播放器」文字链：自动链已逐档试过；手动切换是操作栏「播放器」按钮的事（短按内置循环、长按完整列表）
- 全案**不出现"换源"字样**、不做任何换源引导（按你的口径：本来就是多源）

## 3. 与定稿方案的差异（三处，全部往更保守方向收）

| 项 | 方案原文 | 实际实施 | 原因 |
|---|---|---|---|
| **C1** | 补 Referer / UA | **只补 Referer** | 工程里没有"固定 UA"的公共出口（只有一组随机浏览器 UA 的工具 `UA.randomOne()`）。给同一个源每次请求随机 UA ＝ **把不确定性带进播放链路**，与"稳定优先"相悖。UA 缺失时播放器用自带默认值，**行为与改动前一致**；站点显式给了 UA 的照旧原样使用。已加反向断言防止随机 UA 被引入 |
| **B9** | 隧道模式埋点 | 埋点，收敛为**一行错误日志** | 无行为变更即可满足"先观察"的目的；不新增统计通道 |
| **B8** | 每源独立 Factory | 同方案 + 附带修正 | 连带把"改调用方请求头表"一起去掉，表所有权更干净 |

## 5. 崩溃面预案（逐条：为什么不会崩 / 万一有症状怎么办）

| 新增面 | 为什么不会崩 | 症状与对策 |
|---|---|---|
| `retryWithoutBom` 的异步回调 | 回调最终都汇入 `startPlayUrl`，后者开头有 `mActivity == null \|\| !isAdded()` 保护 | 页面已销毁后回调 → 直接 return，无异常 |
| `fillMissingHeaders` 每次起播调用 | 纯字符串切分 + `HashMap` 复制，全 `try-catch` | 异常 → 返回原请求头，等同于未改造 |
| `retryVariantUrl` | 纯字符串拼接 + 既有 `startPlayUrl` | — |
| 每源新建 `DataSource.Factory` | `OkHttpClient` 共享，连接池不变；对象本身极轻 | 若观察到连接数异常升高（理论不会），回退方式＝把 factory 缓存进 `OkHttpDataSource.Factory` 字段但按 UA 区分（一行改动） |
| `setEnableDecoderFallback(true)` | Exo 官方机制，不改变调用序列 | 若某机型出现"卡在解码器切换"，关掉这一行即可（一行） |
| 播放器菜单候选项计算 | 主线程调用、遍历几十项、全 `try-catch` | 若菜单开不出来，短按仍可用（两条路径独立） |
| D1 的 `retryFromScratch` | 全 `try-catch`，内部 `play(false)` 有 `mVodInfo == null` 保护 | — |

**共性**：本轮没有任何新增线程、没有新增进程级操作、没有任何与 jar 装载节奏相关的改动 → **不触碰防崩线**。

## 6. 诚实边界

1. **仍不做自动换线路 / 换站点**，失败提示也不引导换源（按你的口径）。
2. **整站失效、地址本身已死、鉴权头推不出来** —— 这三类程序侧无解，只能你在节目页手动换源。D1 的作用是让你**立刻知道该换源**，而不是对着黑屏猜。
3. **C2 变形重试对"两种协议都不通"的源无效**（一次尝试的固定成本，不会循环）。
4. **B9 只是埋点**：隧道模式是否真会导致"有声音没画面"，本轮**没有结论**，要等实测日志。
5. **效果未经真机验证**：本批所有收益（起播提速以外的成功率提升）都是**机制性推断**，靶心指标待实测。
6. 取链看门狗 15 秒在"慢但会成功"的源上仍可能造成**极少数慢源起播后重启一次**（第一批已记录的已知边界，有界、不崩、不循环）。

## 8. 真机对照：C1 造成回归，已修复（2026-09-15 晚）

第二批装机后做了严格 A/B 对照（同设备、同站点、同线路、同集、同路径），**发现 C1 引入确定回归**：

| 组 | 版本 | 轮次 | 结果 | 命中节点 |
|---|---|---|---|---|
| 1 | at | 3 | OK 3/3（411 / 244 / 302 ms） | 111.170.141.203 |
| 2 | **au（本批）** | 4 | **FAIL 0/4** | 43.248.96.62、111.170.9.17 |
| 3 | at | 3 | OK 3/3（410 / 282 / 272 ms） | **43.248.96.62、111.170.9.17** |

第 3 组命中的节点与第 2 组失败时**完全相同** ⇒ 节点差异、时间因素、内容差异全部排除。

**根因**：C1 补出来的 Referer 被写进了**播放器的默认请求头**（`setDefaultRequestProperties` 对它下面
所有请求生效），而清单里的**分片托管在第三方 CDN**（实测小红书 `xhscdn.com`）。该 CDN 对外站
Referer 返回 **403**（空 Referer 返回 200）⇒ 清单取到了、分片全 403 ⇒ 起播失败。

**修复**：补出来的 Referer **只给净化预取那一次请求用**，播放侧一律使用站点原始请求头；
`startPlayUrl` 汇聚点也不再补 Referer。C1 在「直连播放」上的补 Referer 一并撤除（实测风险 > 收益）。

**结果**：C1 的收益收窄为「净化预取」（防防盗链导致取不到清单），风险归零。

**闸门**：`check_l1box_regressions.sh` Y 节新增 4 条断言，固化「补的 Referer 不得进入播放器」。

**完整证据链**见 **`au回归定位与修复_20260915.md`**。
