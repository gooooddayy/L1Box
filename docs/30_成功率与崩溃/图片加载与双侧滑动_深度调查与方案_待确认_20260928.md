1. **成功率其实不低（69~83%），真问题是"吞吐"**：命中 254~270 条结果 ⇒ 该有 250+ 张图要下载，

## 二、图片为什么慢/不出：7 条根因（逐条带证据）

| # | 根因 | 证据（代码/常量） |
|---|---|---|
| R1 | **并发只有 4 路，而且是同步阻塞下载** | `L1Executors.fixed("l1box-img", 4)`（`OkGoHelper.initPicasso`）；`MyOkhttpDownLoader.load()` 里 `client.newCall(...).execute()` 同步阻塞 —— 4 个线程同时只扛 4 张图 |
| R2 | **下载不可取消** | 实现的是 Picasso 的 `Downloader`（只有 `load`/`shutdown`，无 cancel）⇒ 图片滚出屏幕后**下载照跑不误**，队列被"没人看的图"占满 |
| R3 | **超时 10 秒**（继承主 client） | `OkGoHelper.DEFAULT_MILLISECONDS = 10000`；一张卡住的图最多占住 1/4 并发 **10 秒** |
| R4 | **图片 client 与接口 client 共享 Dispatcher/连接池/超时** | `OkHttpClient imageClient = client.newBuilder()...` ⇒ 只加了 `cache(...)`，其余全部共用 |
| R5 | **无优先级，纯 FIFO** | Picasso 内部队列；一次搜索 250+ 张一次性入队，可见项排在中后段 |
| R6 | **数量级决定了排队** | 250 张 ÷ 4 并发 × 平均 300ms ≈ 19 秒（还没算超时占位）—— 这就是"整体显示慢"的数学下限 |
| R7 | **请求头对图床不友好（成功率侧）** | `MyOkhttpDownLoader` 默认 UA 写死 `Dalvik/2.1.0 (Linux; U; Android 13; M2102J2SC …)`，且**没有 Referer** ⇒ 豆瓣类图床 418；失败域名数据完全吻合 |
| 附 | 每张图还要跑圆角变换；Picasso 未显式设 `memoryCache` | `RoundTransformation` + 默认 15% heap |

> 一句话：**不是"图坏了"，是"250 张图挤在 4 条窄道上，还排着没人看的队"**。

## 三、两侧"不跟手"：不是渲染（0 掉帧），是这三件事 + 一个度量缺口

| # | 判断 | 依据 |
|---|---|---|
| S1 | **右侧**：插入批次 + 默认 item 动画 ⇒ 手指下的 item 位移/重排，视觉上"跳一下" | 全工程未设 `itemAnimator`（RecyclerView 默认 `DefaultItemAnimator` 生效）；结果每拍 12 条持续插入 15 秒 |
| S2 | **左侧**：站点 tab 增补时逐个 `addView` ⇒ 40 次 `requestLayout` | `flushSiteTabsNow()` 循环 `addView`；已加触摸记账，但落地瞬间仍会有一次布局 |
| S3 | **左侧**：tab 太少时"本来就没得滚" | 库只在 `maxScrollY>0` 时接管手势（**不动库**）；几个 chip 时拖不动不是 bug |
| S4 | **度量缺口**：系统只在掉帧 >30 帧才打日志 ⇒ 微卡（<500ms）看不见 | 本轮 L1Box 0 条掉帧正好说明"需要应用内自己量" |

## 四、方案

### P1（低风险，建议全做；改动集中在 4 个文件）

| # | 改动 | 预期收益 |
|---|---|---|
| 图1 | **图片 client 独立化**：独立的 Dispatcher/连接池 + 超时 **connect 4s / read 6s / write 6s**（卡住的请求快速让位）；并发 **4 → 8** | 吞吐翻倍 + 卡死不占道（直击 R1/R3/R4） |
| 图2 | **请求头按域名策略**：默认 UA 换常见浏览器 UA；对 `*.doubanio.com` 等补 `Referer`；**418/403 只换一次策略重试**（仅图片链、仅一次，404/504 不重试） | 成功率 68~83% → 目标 ≥85%（直击 R7） |
| 图3 | **可见优先**：绑定图片前判断 position 是否在"可见 + 预取窗口"内，不在就只显示灰图不发请求；停稳后只补刷可见区间 | 队列里只剩"用户真要看"的图 ⇒ "滑到哪立刻出"（直击 R2/R5/R6，**注意：这不是暂停**，可见项照常加载） |
| 图4 | **图片埋点升级**：`图片队列：请求=N 可见=R 非可见=S`、`可见首图：P50=…ms P90=…ms`；再加**应用内帧耗时**埋点 `帧耗时：P50/P90/max 掉帧=N`（把"丝滑"量化，补 S4） | 下一轮可验收，不再靠体感 |
| 图5 | 占位图改为共用 Drawable 实例（少一次资源查询/每次绑定） | 绑定更轻 |
| 滑1 | **关闭列表 item 动画**（`itemAnimator = null`） | 消除持续插入动画与位移跳动（直击 S1） |
| 滑2 | 滑动中插入改"**小批 3~5 条/拍**"，停稳一次落完（**不暂停**） | 单帧变化更小 ⇒ 更跟手 |
| 滑3 | 左栏批量落地用 `suppressLayout(true) → addView… → suppressLayout(false)` 包起来 | 一次布局而不是 40 次（直击 S2） |

### P2（中风险，P1 数据不达标再上）

| # | 改动 | 说明 |
|---|---|---|
| P2-1 | **自研图片加载器**（OkHttp `enqueue` 异步 + **可 cancel** + 双缓存 + 可见优先优先级） | 根治 R2/R5：滑出屏幕立即取消，并发可上 12~16。改动集中在搜索页图片绑定，保留接口便于回退 |
| P2-2 | **按域名 URL 缩略**（如豆瓣 `/l/`→`/s/`） | 流量与解码量大幅下降；必须按域名白名单 + 可回退，否则可能取不到图 |
| P2-3 | 磁盘缓存分区与容量策略（现 64MB 单一目录） | 命中率与空间平衡 |

### 明确不做
- 滑动中"暂停落地/暂停图片"（by 实测已证：右侧断触 + 图片大面积变慢）；
- 修改 `DslTabLayout` 库源码（`needScroll` gate、`_touchSlop=0`）——只做 app 侧规避；
- 任何判死秒数改动。

| 指标 | 现状 | 目标 |
|---|---|---|
| 图片网络请求数 ÷ 可见图片数 | 5~24 / 250+（严重不足） | ≥1.0（非可见请求 ≈ 0） |
| 可见图片首图耗时（新埋点） | 未测 | P50 < 800ms |

| 帧耗时 / 掉帧（新埋点） | 未测（系统只报 >30 帧，L1Box 0 条） | P90 < 16ms，掉帧事件保持 0 |
| 搜索早收尾 | 12~15s | 不变（不改判定） |
