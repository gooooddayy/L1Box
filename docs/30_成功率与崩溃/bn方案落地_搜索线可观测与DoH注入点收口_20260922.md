# bn 方案落地：搜索线可观测 + DoH 注入点收口（2026-09-22）

> 本批的定位是**观测与收口**，不是"再赌一个提速方案"。用户的原始诉求是
> 「先把导致搜索变慢的原因找出来」以及「这几轮改了 DNS 后速度变慢了」。
> 因此本次改动**一行都不改解析/搜索行为**，只做三件事：把裸注入点堵上、把失败留痕、把耗时量化。

---

## 一、先纠正我自己上一批的一个错误判断

我在 bm 批次里说过「bm 改动集 13 个文件，**无一在搜索链路上**」。**这句话不成立**。

它的推理方式是错的：我只检查了「`FastSearchActivity.kt` 有没有被改」，而 DoH 是**共享注入点**，
它会从网络层漏进搜索/取链路径。实际查到三处直接使用 DoH 的地方：

| # | 位置 | 形态 | 风险 |
|---|---|---|---|
| 1 | `catvod/crawler/Spider.java:68` `safeDns()` | **返回裸 `OkGoHelper.dnsOverHttps` 给 jar 用** | 裸 DoH 对私网地址/IP 字面量**直接抛** `UnknownHostException`（`isPrivateHost` + `resolvePrivateAddresses=false`）；且 bm 已把"查询无结果"从**静默回退系统 DNS** 改为**如实抛出** ⇒ 从这个入口拿 DNS 的 jar 会由「慢一点但能通」变成**直接失败** |
| 2 | `server/RemoteServer.java:243` `/dns-query` | `lookupHttpsForwardSync`（裸） | `catch` 里返回**空应答** ⇒ 对客户端等于"DNS 服务器不回话"。该端点是 IJK 用的（`ControlManager` 里 `setDotPort(DOH_URL > 0, port)`）——**bm 把 DoH 默认开到 1 之后，这条链路才第一次投入使用** |
| 3 | `ui/activity/SettingActivity.kt:113` `setUrl(...)` | 设置页实时切换 | 正常，需保持（包装层每次解析都读 `doh.url()`，所以实时切换不受影响） |

另外确认**没有**暴露的两条（避免误伤）：
- `catvod/net/OkHttp.java` 的共享客户端用的是 `dns()` → `get().dns != null ? get().dns : Dns.SYSTEM`，
  而 `setDoh()` **全工程无调用点** ⇒ 该客户端**始终走系统 DNS**，不受 DoH 开关影响。
- `OkGoHelper`（OkGo 全局 client）与 Exo 的 client 都已挂 `fallbackDns`（bm 已做，闸门守住）。

> 结论：**"改了 DNS 之后搜索变慢"这个怀疑方向是对的，只是机制不在 `FastSearchActivity`，
> 而在共享注入点。** 我在 bm 注释里写过前置条件「所有 `builder.dns(...)` 注入点都必须挂包装类」，
> 但闸门只查了 `builder.dns(dnsOverHttps)` 这种**写法**，查不到「方法返回 Dns 对象」这种形态 —— 这就是漏掉的那一类。

## 二、用现有日志能证明什么（同机、同操作对照）

### 2.1 搜索轮次耗时（bm 前后各一份宿主机 logcat）

| 版本 | 站点数 | 轮次耗时 | jar 装载增量 | 判定 |
|---|---|---|---|---|
| **bl**（DoH 默认关）17:40:54→17:40:57 | 36 | **3.4s** | **Δ = 0** | 判「真空」，**不重搜** |
| **bm**（DoH 默认开）19:56:23→19:56:37 | 40 | **14.2s** | Δ = 41 | 判「与初始化重叠」，自动重搜 |
| bm 热轮 19:56:38→19:56:43 | 40 | **4.6s** | Δ = 1 | 同上 |
| bm 热轮 19:56:44→19:56:49 | 40 | **4.8s** | Δ = 1 | 同上 |

**这两组不能直接当 A/B**，原因在 `JarLoader` 的代码事实：

- `getSpider()` 命中 `spiders[key]` 就直接返回，**不再走装载**；计数写在 `loadJarInternal()` 的 `finally` 里，
  即便 jar 早已装好、仅仅是"这个站点第一次被使用"，序号照样 +1；而 `jar == ""`（走 main jar）时**根本不计数**。
- ⇒ **`LOAD_SEQ` 增量 = 本轮里"首次创建 spider 的站点数"**。
  bl 那次 Δ = 0 ⇒ 那 36 个站点**全是 main jar 站点**（秒级就绪）；bm 的 Δ = 41 ⇒ 几乎每个站点都要装自己的
  加固 jar。**两者源不同，14.2s vs 3.4s 的差主要来自"有没有加固 jar 要装载"。**

### 2.2 App 侧请求耗时（净化/起播，历次日志汇总）

| 批次 | DoH 默认 | 净化 ms（样本） | 起播 ms（样本） |
|---|---|---|---|
| bi（09-19 18:4x） | 关 | 68 / 80 / 162 / 201 / 520 / 1467 | 293 / 295 / 508 / 824 / 1529 |
| bj（09-19 19:3x） | 关 | — | 168 / 256 / 906 / 1910 / 2129 / 2169 / 2481 / 4710 |
| bk2（09-19 11:5x） | 关 | 169 / 186 / 1115 / 1467 / 1601 / 1870 | 694 / 800 / 1619 / 1634 / 1646 |
| **bm**（09-19 19:5x） | **开** | 50 / 79 / 145 / 162 / 180 / 183 / 1925 | 284 / 323 / 533 / 549 / 590 / 608 / 896 |

**读法**：分布高度重叠，bm 的净化中位（≈162ms）与起播中位（≈570ms）**不高于**旧版
（旧版净化中位 201~1467ms、起播中位 508~1646ms）。⇒ **在"App 自己发请求"这条路径上，
没有可测的 DNS 拖慢**（这条路径正是走 OkGo/`fallbackDns`/DoH 的那条）。

### 2.3 于是"冷启特别慢"的分解

1. **≈10 秒**：40 个站点首次创建 spider，其中若干是加固 jar 的装载（日志里装载事件集中在
   发起后 0~10.5s）。**这是本批无法消除的部分**——"预热/提前加载"已被永久否决
   （抬升加固 jar 初始化密度 → killall 互杀）。
2. **1~2 整轮**：0 结果被判"假空"而整轮重搜（见下）。**这是纯浪费，但属于 bn 之后的活。**

### 2.4 `verdictEmpty` 的判据问题（记录在案，本批**不改**）

`unreliable = !roundPoolSettled || seqNow != roundLoadSeq`。由于 2.1 的语义，
**首轮（Δ ≈ 站点数）必然判定为"重叠"** ⇒ 只要这一轮 0 结果就必定重搜一整轮，
并弹「正在初始化播放源，自动重试…」。用户实测一次"搜不到"要走 **14.2 + 4.6 + 4.8 ≈ 24 秒**。
**改动它会改变行为（真空判定更激进），按"不引入新问题"的要求排到本批之后，先用本批的数据定论。**

## 三、bn 实际改了什么（三处，均为"只收口/只留痕"）

### ① `Spider.safeDns()` 改返包装层
`return OkGoHelper.dnsOverHttps` → `return OkGoHelper.fallbackDns`。
效果：jar 侧拿到的 DNS 变成「私网/字面量绕开 DoH + DoH 失败回退系统 DNS + 连续 3 次失败熔断 5 分钟 +
DoH 客户端 2s 超时」。**DoH 正常时行为与原来完全一致**；DoH 不可用时由"直接失败"回到"慢一点但能通"。

### ② 本机 `/dns-query` 端点补失败留痕
`RemoteServer` 里 `catches` 时打 `L1Dns`：`本机 /dns-query 上游 DoH 失败，返回空应答：name=... 原因=...`。
**空应答行为保持不变**（只加日志）—— 该端点只在安全DNS 开启时才被 IJK 用起来。

### ③ 搜索线耗时量化（`L1FallbackDns` 计数 + `FastSearchActivity` 埋点）
- `L1FallbackDns`：`lookup` 的每个分支计数（`DoH命中 / 失败 / 熔断跳过 / 直连`）；
  失败时 `Log.w("L1Dns", ...)` 记 host、原因、以及"是否刚触发熔断"。**失败日志量天然有界**
  （连续 3 次失败即熔断 5 分钟，熔断期内不再产生失败日志）。
  （原先这里 `catch (Throwable)` **静默吞掉**，等于把 `DnsOverHttps` 特意改 throw 求来的"失败可见"又吞回去。）
- `FastSearchActivity`：新增
  - `搜索首条结果：耗时=xxxms 站点=... 关键词=...`（**用户体感来自"多久看到第一条"**）
  - `搜索耗时：<收尾|超时收尾|无可搜站点> 站点=N 命中=M 首条=xxxms 总耗时=xxxms 本轮装载增量=K DNS(窗口内):DoH命中=.. 失败=.. 熔断跳过=.. 直连=..`

  有了这两行，下一轮真机日志可以直接把"慢在哪一段"读出来，不必再推理。

## 五、请真机做的两件事（都要记数字，不要记"感觉"）

**前置**：设置页 →「安全DNS」应显示**腾讯**。

### A/B 实验（不用等新包也能做，用来直接回答"是不是 DNS 拖的"）
> DoH 开关是**实时生效**的（设置里改完立刻作用于后续请求），所以同一会话内就能对比。

| 步骤 | 动作 | 记录 |
|---|---|---|
| A1 | 同一会话（热）搜同一个词，等结果出来 | 第一条出现约几秒、结果总数 |
| A2 | 设置 → 安全DNS → **关闭** → 回到搜索页搜同一个词 | 同上 |
| B1 | 保持关闭，**完全退出** App（不要连按两次返回）→ 重进 → 冷启搜一次 | 同上 |
| B2 | 设置 → 安全DNS → **腾讯** → 完全退出 → 重进 → 冷启搜一次 | 同上 |

判读：**冷启对冷启、热对热**比较（jar 冷热状态必须对齐，否则不可比）。
若 A1≈A2 且 B1≈B2 ⇒ 与 DNS 无关；若"关闭"明显快 ⇒ DoH 在你的网络上有问题，
我会把默认值改回关闭并保留手动开关。

## 六、本批**没做**的事（以及为什么）

| 项 | 决定 | 理由 |
|---|---|---|
| 改 `verdictEmpty` 判据（去掉"本轮自己造成的装载增量"这个假阳性） | **推迟** | 会改变行为：真空判定更激进，可能让 09-14 修好的"冷启首搜空源"回来。等本批数据出来再动 |
| 只补搜"真出异常"的站点 | **推迟** | 需要改 `SourceViewModel` 的失败通道，属行为变更 |
| 搜索进度可见化（"已返回 x/40 站点"） | **不做** | UI 变更，与"先找原因"无关 |
| 冷启清缓存挪到更晚（避开与 jar 装载抢磁盘） | **不做** | 推测性收益，且会让存储归还变慢；先看埋点数据 |
| spider/jar 预热 | **不做（永久否决）** | 抬升加固 jar 初始化密度 → killall 互杀 |
