## 0. 两侧分别是什么控件（先说清对象）

`activity_fast_search.xml` 的 `llSearchResult` 结构：

```
llSearchResult (RelativeLayout)
├── llWord (宽 120dp, match_parent 高)
│   └── tab_layout : com.angcyo.tablayout.DslTabLayout  ← 【左栏】站点 chip 纵向列表
└── llLayout (layout_toEndOf=llWord)
    ├── mGridView       : com.owen.tvrecyclerview.TvRecyclerView  ← 【右栏】搜索结果网格
    └── mGridViewFilter : com.owen.tvrecyclerview.TvRecyclerView  ← 过滤结果（与上互斥）
```

⇒ 用户说的"左侧"＝`DslTabLayout`（第三方库，**源码在本仓库 `TabLayout/` 内，可读**）；
"右侧"＝`mGridView`（`com.owen:tv-recyclerview:3.0.0`，**外部依赖，源码不在仓库**）。

## 1. 问题①：cj 的档位改动会不会拖慢两侧？—— **不会（有一个例外）**

### 结论：常规路径下完全不影响

`DeviceProfile` 的 7 个新增方法，**中/高档返回值与改造前的写死值逐字相同**：

| 方法 | 改造前（写死） | 中/高档（现在） | 低档 |
|---|---|---|---|
| `imageThreads` | 8 | **8** | 4 |
| `imageMaxRequests` | 12 | **12** | 6 |
| `imageMaxRequestsPerHost` | 6 | **6** | 3 |
| `imageConnectionPool` | 8 | **8** | 4 |
| `imageCacheBytes` | 64MB | **64MB** | 24MB |
| `itemViewCacheSize` | 6 | **6** | 3 |
| `siteTabBatch` | 8 | **8** | 4 |

全部是 `tier == TIER_LOW ? 低档值 : 原值` 的形式 —— **中档和高档走的是同一个分支**，
取值就是改造前那个常量。所以"中/高档会不会变慢"这个问题本身不成立：**两边取的是同一个数**。

### ⚠️ 唯一的例外：运行期内存压力会**永久**降档

`App.java` 有两处调用 `DeviceProfile.markMemoryPressure()`：

| 位置 | 触发条件 |
|---|---|
| `onTrimMemory` L176 | `level >= TRIM_MEMORY_RUNNING_LOW` |
| `onLowMemory` L197 | 系统内存紧张（覆盖面比 onTrimMemory 广） |

`markMemoryPressure()` 的实现是 `tier = TIER_LOW`，且注释明确「**只降不升**」。

**影响面（关键）**：只有**运行期读取**的档位会变，且只在降档之后：
- `siteTabBatch()` → 8 **降到** 4（每次 drain 都读 ⇒ 立刻生效）
- `itemViewCacheSize()` → 6 **降到** 3（**只在 `initView` 读一次** ⇒ 已建好的列表不受影响）

⇒ 对用户的机型（中/高档），这是**唯一**可能被 cj 影响的路径，且只会让**左栏 chip 建得更慢**
（每帧 4 个而非 8 个），**不会**让右栏变慢。

**是否已触发可查**：日志里搜 `MemoryGuard` / `系统内存紧张(onLowMemory)` / `DeviceProfile.describe()`。
若从没出现过，则本次报的两个现象与 cj **完全无关**。

### 结论：问题②③ 的根因**不在 cj**（详见下），是**改造前就存在的库层与交互层行为**。

## 2. 问题②：左栏"速度一快就卡住不跟手"

### 2.1 已确证的代码事实（不依赖推测）

**事实 A —— 内容不够高时，左栏根本不接管手势。**

`DslTabLayout.kt`：
```kotlin
val needScroll: Boolean
    get() = if (tabEnableSelectorMode) true else { ... else maxScrollY > 0 }   // L1586-1598
val maxScrollY: Int
    get() = max(maxHeight - measuredHeight + ..., 0)                            // L1611-1615
```
`tabEnableSelectorMode` 默认 `false`（L140），布局 xml 也没开 ⇒ `needScroll = (内容总高 > 视高)`。

`onTouchEvent`（L1566-1584）：
```kotlin
if (needScroll) { _gestureDetector.onTouchEvent(event); return true }
else { return (isEnabled && super.onTouchEvent(event)) }   // ← 完全不走滚动逻辑
```
⇒ **chip 总高还没超过栏高时，拖动无效**。这是"卡住不跟手"的一种形态（此时怎么拖都不动）。

**事实 B —— 竖向 fling 的边界与实际钳制范围不一致（差一个视高）。**

`onFlingChange`（L1665-1667）竖向传的是：
```kotlin
startFling(-velocity.toInt(), 0, maxHeight)      // max = 内容总高
```
而 `startFling` 内部（L1700-1711）把它当作 fling 的 Y 上界：
```kotlin
_overScroller.fling(scrollX, scrollY, 0, v, 0, 0, min, max, 0, measuredHeight)
```
但真正生效的钳制在 `scrollTo`（L1757-1770）：
```kotlin
y > maxScrollY -> super.scrollTo(0, maxScrollY)   // maxScrollY = max(maxHeight - measuredHeight, 0)
```
⇒ OverScroller 认为还能再滚 `measuredHeight`（**一整个视高**），但 `scrollTo` 早就钳死了。

**事实 C —— 越界中止只检查 currX，竖向 fling 永不提前终止。**

`computeScroll`（L1773-1781）：
```kotlin
if (_overScroller.computeScrollOffset()) {
    scrollTo(_overScroller.currX, _overScroller.currY)
    invalidate()
    if (_overScroller.currX < minScrollX || _overScroller.currX > maxScrollX) {
        _overScroller.abortAnimation()          // ← 只看 X
    }
}
```
竖向 fling 时 `currX` 恒为 0，而 `minScrollX = 0`（L1625，`tabEnableSelectorMode=false` 分支）、
`maxScrollX >= 0` ⇒ 条件**永不成立** ⇒ **竖向惯性不会被提前中止**，会在"视觉已到底"之后继续空转。

**事实 D —— "停手窗口"的计时源会在 fling 撞界后冻结。**

`FastSearchActivity.kt` 的守卫：
```kotlin
private fun siteTabsBusy(): Boolean =
        siteTabsTouchDown ||
                SystemClock.elapsedRealtime() - siteTabsLastScrollMs < SITE_TAB_SETTLE_MS   // 400ms
```
`siteTabsLastScrollMs` 的三个更新点是 L268（`setOnScrollChangeListener`）、L1440（ACTION_DOWN）、
L1446（ACTION_UP/CANCEL）。其中滚动那条：
```kotlin
mBinding.tabLayout.setOnScrollChangeListener { _, _, _, _, _ ->
    siteTabsLastScrollMs = SystemClock.elapsedRealtime()
}
```
`View` 的该回调**只在 scrollX/scrollY 数值真正变化时触发**。
结合事实 B/C：fling 撞到边界后 `scrollTo` 被钳成同一个值 ⇒ **回调停止触发** ⇒
`siteTabsLastScrollMs` 冻结 ⇒ 400ms 后 `siteTabsBusy()` 变 `false` ⇒
**`drainSiteTabQueue` 认为"用户已经停手"，开始 `addView`** —— 但此刻 `_overScroller` 还没结束。

⇒ **在"视觉静止但惯性仍在跑"的窗口里插入子 View**，触发 `requestLayout` / 布局重算，
表现就是拖动被掐断、跟手感丢失。

### 2.2 为什么"慢速流畅、快才卡"（机制拼合）

| | 慢速滑动 | 快速滑动 |
|---|---|---|
| fling | 无，或极短（低于最小 fling 速度） | 有，且行程长 |
| 手指抬起后 | 立刻静止 | 进入长惯性，可能撞界 |
| 滚动回调 | 停止后窗口自然成立，此时确实静止 | **撞界后回调冻结，但惯性未停** |
| 守卫判定 | 与真实状态一致 ✔ | **与真实状态背离** ✘ |
| `addView` 落地时机 | 用户确实停手之后 | **可能落在惯性空转期** |
| 观感 | 流畅 | 卡住 / 被打断 |

⇒ 慢速滑动的"停手"就是真停手，窗口判对了；
快速滑动制造了一个**"守卫以为已停手、实际未停"**的重叠区，`addView` 就落在这里。

### 2.3 可能的放大器（非根因，但会让它更容易发生）

1. **内存压力降档**（见 §1 例外）：`siteTabBatch` 8→4，chip 队列排空时间翻倍，
   "队列还有货"的窗口变长 ⇒ 撞上惯性空转期的概率升高。
2. **`needScroll` 门槛**（事实 A）：搜索早期 chip 少时本来就拖不动，
   与"快滑被打断"叠加，用户感受统一归为"卡住不跟手"。
3. 左栏重绘本身：40 个 chip 每个含背景 drawable + 文本 + 选中态 + 指示器，
   单帧重绘有基本开销；快速滑动更容易撞上后台尖峰（建 chip、图片解码、logcat 输出）。

## 3. 问题③：右栏"松手后到第几个停下，有明显顿挫感"

### 3.1 已确证的代码事实

**事实 E —— 惯性停止的瞬间，同帧连做三件重活。**

`FastSearchActivity.kt` L285-300：
```kotlin
override fun onScrollStateChanged(rv: RecyclerView, newState: Int) {
    scrollPauseActive = newState != RecyclerView.SCROLL_STATE_IDLE
    if (scrollPauseActive) {
        scheduleImageWindow(IMG_WINDOW_REFRESH_MS)
    } else {
        if (pendingResults.isNotEmpty() && !flushScheduled) scheduleFlush()
        cancelOutOfWindowImages()        // ① 取消越界在途下载
        scheduleVisibleImageAudit()      // ② 可见项审计
        prefetchAroundVisible()          // ③ 可见±6 预取
    }
}
```
其中 ③ 的实现（L1304-1332）是**一个同步 for 循环**，对范围内每个未预取过的 URL
依次执行 `checkReplaceProxy` → `prefetchedUrls.add` → `countPrefetchStart` →
**`Picasso.get().load(u).fetch()`**（一次 dispatcher 入队），上限 `IMG_PREFETCH_BUDGET = 200`，
循环末尾还有一次 **`System.out.println`**（在 Android 上是**同步写 logcat**，真机上有可观开销）。

⇒ IDLE 那一帧（或紧随其后的几帧）会出现**负载尖峰**：若干次 Picasso 入队 + 若干次字符串处理 +
一次同步日志。这与"明显顿挫"的时间点吻合。

**事实 F —— 惯性期间图片是"全速不下闸"的。**

L302-307 `onScrolled` 是**空实现**，注释写明「滑动中**不取消任何下载**」。
⇒ fling 期间所有可见项照常发请求、照常解码，解码队列在 fling 结束时正好处于**积压峰值**，
紧接着撞上事实 E 的尖峰。

**事实 G —— 惯性结束后的取消动作会误伤"正好停进屏幕"的图。**

`cancelOutOfWindowImages()` 在 IDLE 时执行，取消窗口外请求。
注释自己记录了这条副作用（L304-306）：被取消的图若来自复用缓存就不再重绑、会永久停在灰图。
虽然已把取消限制在"停稳"时做，但**停稳瞬间的可见范围正好包含刚滑进来的那一批**，
取消/保留的边界判定本身也在这一帧发生。

### 3.2 需要实测确认的一项（不敢下定论）

布局里两个网格都开了 **`app:tv_selectedItemIsCentered="true"`**（L162、L173），
这是 `com.owen:tv-recyclerview` 的**焦点项居中**特性。该库源码不在仓库（Maven 依赖），
无法静态确认它是否在**触摸滑动**路径上生效：

- 若只在**焦点变化**（D-pad / 点击选中）时触发 → 与触摸 fling 无关，可排除；
- 若在**滚动停止**时也会对选中项做一次居中校正 → 会额外产生一次 `smoothScroll`，
  那正是"松手后停到第几个、然后又顿一下"的完美解释。

⇒ **此项待验证**（最省事的验证：临时去掉 `tv_selectedItemIsCentered` 对比手感；
或抓一次 fling 的 `computeScroll`/`scrollTo` 日志看停止后有无二次滚动）。

## 4. 判定小结

| # | 用户问题 | 判定 | 性质 |
|---|---|---|---|
| ① | cj 档位会不会拖慢两侧 | **不会**。中/高档取值 = 改造前写死值，逐字相同 | ✅ 确证 |
| ①附 | 唯一例外 | 运行期内存压力降档 → `siteTabBatch` 8→4（只影响左栏 chip 创建速度） | ✅ 确证（需查日志是否已触发） |
| ② | 左栏快滑卡住不跟手 | **fling 撞界后滚动回调冻结 → "停手窗口"误判 → `addView` 落进惯性空转期**；叠加 `needScroll` 门槛与 fling 边界差一个视高 | ✅ 代码链确证（§2.1 A–D） |
| ③ | 右栏松手后顿挫 | **IDLE 同帧三件重活（取消+审计+预取）+ fling 期间图片全速导致解码积压** | ✅ 确证（§3.1 E–F） |
| ③附 | 是否还有居中校正 | `tv_selectedItemIsCentered` 在触摸路径是否生效 | ⚠️ 待验证（外部依赖） |

**共同点**：②③ 都发生在**"手势结束"这个时间点附近**，且都是**"后台本该错开的工作，撞在了用户刚停手的那一刻"**。
换句话说，不是两侧的列表本身慢，而是**收尾动作与用户操作撞车**。

## 5. 建议的验证方式（只验证，不改代码）

为把 §2、§3 从"代码链成立"推到"真机复现"，最小成本的取证：

1. **查是否已降档**：日志搜 `MemoryGuard` / `onLowMemory` / `tier=`。这一步能直接排掉 §1 例外。
2. **左栏快速滑动时看帧埋点**：现有 `帧耗时[本轮]` 会打出最差帧与其阶段标签
   （`stage()` 已覆盖 `建站点栏`）。若快速滑动的最差帧标签命中 `建站点栏`，且发生在手指已抬起之后，
   则 §2.2 的"守卫误判"链条得到真机证据。
3. **右栏 fling 结束前后对比**：现有日志已有 `图片预取：本批=N 累计=…`。
   若该行的时间戳与顿挫发生时点重合，则 §3.1 事实 E 得到证据。
4. **`tv_selectedItemIsCentered` 对照**：此项需改代码才能对照 ⇒ 留到方案阶段。

> 按纪律，本轮**不出优化方案**。上面的验证项做完、结论收敛后，再谈"要不要动、动哪一处"。
