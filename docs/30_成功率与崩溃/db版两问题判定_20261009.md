## 一、问题 A：搜索页一直显示加载中

### 代码级根因

`FastSearchActivity` 的 SUB_FAIL 态**没有出口**：

```kotlin
private fun enterSubFail() {
    phase = Phase.SUB_FAIL
    showLoading()                       // ← 先盖上加载中
    if (!subReloadTried) { subReloadTried = true; reloadSubNow(); return }
    showSubFailDialog()                 // ← 只有这一条路弹出对话框
}
```

而对话框的「取消」只是把对话框藏掉：

```kotlin
override fun right() { subFailDialog?.hide() }      // → 回到「加载中」，phase 仍是 SUB_FAIL
```

**为什么回到加载中就再也出不来**：
- `onWaitTick()` 开头就是 `if (phase != Phase.S1 && phase != Phase.S3) return`（975-983 行）⇒ **SUB_FAIL 不再被任何节拍驱动**
- `enterSubFail()` 也**不排任何定时任务** ⇒ 没有重试、没有空态、也不再弹窗
- 搜索看门狗此时早已失效（日志里整段**没有一条「搜索超时」**）

⇒ **「取消」之后就是永久加载中**（只能返回上一页）。

### 日志时间线（你的实测）

| 时刻 | 日志 | 含义 |
|---|---|---|
| 17:34:46.560 | `搜索轮次：S2 可搜站点=40 …` | 换源前，正常 |
| 17:34:54.535 | `S2 可搜站点=0 且站点池为空但有订阅地址 ⇒ 订阅未加载成功` | 池已清空 ⇒ 首次进 SUB_FAIL（`showLoading` + 同址重拉，**要等 3 次请求超时**） |
| 17:35:06.034 | 同上 | 用户点了重试，又一轮加载中 |
| 17:35:08.723 | `SUB_FAIL 同址重拉仍失败 msg=订阅内容异常：…` | 这条之后才弹对话框 |
| 17:35:43.343 | `S2 可搜站点=40` | 换回可用源，恢复正常 |

**要点**：这条路径**只在池被清空后才存在**。db 之前，换源失败时池里还是旧源站点 ⇒ 可搜站点=40 ⇒ 压根进不了 SUB_FAIL。**所以是 db 把它暴露出来的，不是 db 写坏了它。**

## 三、真 bug：带 `//` 行注释的订阅配置 100% 被判"内容不是订阅配置"

### 证据链（五步，每一步都有据）

**第 1 步** — 日志里 `XYQTVBox.json` 被判失败的样本，开头长得**像合法配置**：

```
样本={     "wallpaper": "https://wp.upx8.com/api.php",     "spider": "https://fastly.
```

**第 2 步** — 我把这个地址**下载下来验证**：HTTP 200，**24,820 B**，开头正是上面那段 ⇒ 确实是一份真配置。

**第 3 步** — 它是一份**带行注释的配置**：文件里有 **35 处** `//`，例如：

```json
        //磁力资源区
        //{"key": "csp_Mp4Mov","name": "🧲Mp4电影","type": 3,"api": "csp_Mp4Mov", ...},
```

**第 4 步** — `json.loads` 在**第 1984 字符**处就失败（`Expecting value`），与注释位置一致。

**第 5 步** — 定位到代码里那段逻辑，**四行代码互相咬死**：

| 位置 | 代码 | 后果 |
|---|---|---|
| `L1SubUrl.stripInvisible:70` | `if (c <= ' ') continue;` | **把换行 `\n` 也一起删了** |
| `L1SubContent.cleanJson:184-195` | 只删块注释 `/* */`，**明确放弃处理 `//`** | 注释里写着理由：「换行已被 stripInvisible 删掉，`{//说明\n"sites":…}` 实际是 `{//说明"sites":…}`，**注释与正文已粘死、无法区分边界**」 |
| `L1SubContent.looksParsable:235` | 字符串外遇到 `//` 或 `/*` ⇒ **直接 return false** | 「宁可漏认，绝不误认」 |
| `L1SubContent.toJson` → `pickJson:96` | `(hasSubKey ‖ selfContained) && looksParsable` | `looksParsable` 为 false ⇒ **返回 null** |
| `ApiConfig.parseJson:754-759` | `toJson` 返回 null ⇒ 抛 `订阅内容不是配置` | 报错文案就是它 |

⇒ **凡是带 `//` 行注释的订阅配置（这类"线路规则"文件很常见的写法），100% 装载失败。**

> ⚠️ 这一段**不是 db 引入的** —— `L1SubContent` / `L1SubUrl` 本轮**一个字都没动**。
> 它在 cv/da 上也一样失败，只是那时**失败被"沿用旧源"掩盖了**，所以看不见。

### 修法 + 离线实测

**改法（两处，都很小）**：
1. JSON 净化路径**保留换行**（地址规范化那条路仍用原 `stripInvisible`，不动）
2. `cleanJson` 里补一条**字符串感知**的「`//` 删到行尾」—— 换行现在还在，边界可界定

**在真文件上的实测（离线模拟，未改工程代码）**：

| 样本 | 现行 | 修法后 |
|---|---|---|
| **`XYQTVBox.json`**（本例，24.8 KB） | ❌ **NOT_SUB** | ✅ **OK — 解析出 48 个站点** |
| 用户原有可用源 `data.json`（23.5 KB，41 站点） | ✅ OK | ✅ OK（**结果完全一致**） |
| 无注释的干净配置 | ✅ OK | ✅ OK（**结果完全一致**） |

⇒ **对一个源从"必然失败"变成"成功 48 站点"，对本来就成功的源零影响。**

# 【修订 · 2026-10-09 19:11】D3 用例推翻了我上面的一条结论

## 用户新报：D3（把源换回可用源后）搜索页一直显示加载中

### 真机日志铁证（dc 版，19:10 时段）

```
19:10:45  搜索轮次：S2 可搜站点=40  站点池定论=true 池签名=41|...   ← 好源（gooooddayy，40 站点）的池在用
19:10:47  L1Sub: 拉取配置失败 地址=https://9877.kstore.space/one.json 异常=404 or 5xx
          L1Sub: 换源装载失败 地址=9877… 池归属=https://gooooddayy.github.io/boxURL/data.json ⇒ 清空前源站点池
19:10:53  又一次 9877 失败 ⇒ 再清（此时已空）
19:10:56  搜索轮次：S2 可搜站点=0 且站点池为空但有订阅地址 ⇒ 订阅未加载成功 ⇒ 加载中
```

### 根因：**迟到的失败回调，清掉了当前可用源的池**

db 的判据只比了两件事：`本次地址 != poolUrl ⇒ 清池`。**漏了一件事**：
**本次失败的地址，是否还是用户当前用的地址？**

装载是异步的，而且失败会指数退避重试（`attempt 0/1/2`，间隔 1.5s + 3s，横跨约 4.5 秒以上）。
用户在这几秒内完全可能已经切到别的源 —— 于是：

1. 用户从坏地址 A 切到好地址 B，**B 装载成功**，池 = B（40 站点），`poolUrl = B`
2. **A 的迟到回调**（还在重试链里）此刻才失败 ⇒ 判据：`A != poolUrl(B)` ⇒ **清池**
3. 池被清 ⇒ 搜索"可搜站点=0 ⇒ 订阅未加载成功" ⇒ **界面一直加载中**（D3 现象）

⇒ **一个已经被放弃的地址，清掉了当前可用源的池。**

### 这条同时修订我上面的结论

我在上面写过「**没有任何地址时好时坏** ⇒ 不存在正常源变差 ⇒ 未发现 db 造成的成功率下降」。
**那条结论不完整，必须更正**：

- 按地址统计只能看到"每个地址各自的成功率"，**看不到"池被别人清掉"**——
  好源 `gooooddayy.github.io/boxURL/data.json` 自己的装载一直是成功的（4 次），
  但它的**池**在 db 版会话里被别的地址的失败清掉过至少 4 次：
  ```
  17:34:52  池归属=gooooddayy… 被 地址=XYQTVBox.json   清空
  17:35:49  池归属=gooooddayy… 被 地址=XYQTVBox.json   清空
  17:39:12  池归属=gooooddayy… 被 地址=www.饭太硬.net/tv 清空
  17:41:18  池归属=gooooddayy… 被 地址=www.饭太硬.art/tv 清空
  ```
- ⇒ **用户"正常源也显示加载失败 / 成功率变低"的体感里，确实有一部分是 db 引入的真回归**：
  不是好源装载失败，而是**好源的可用状态被别的地址的迟到失败清掉了**。
- ⇒ 判断口径也要补一条：**按地址统计答案有限** —— 还要看「池归属」的变迁史
  （`池归属=X ⇒ 清空` 这一行的 `X` 是不是当前地址）。

### 修法（dd 批）

给判据加一条前置条件 —— **本次装载必须仍然是"当前地址"的装载**：

```java
private static boolean isCurrentLoad(String apiUrl) {
    if (apiUrl == null) return false;
    return apiUrl.equals(L1SubUrl.normalize(Hawk.get(HawkConfig.API_URL, "")));
}
```

- 两个失败出口（网络重试用尽 / 内容异常）：**不满足 ⇒ 不清池、不报错**（用既有 `-1` 约定让调用方不弹提示）、
  **也不做缓存回退**（回退会把被放弃的源装进池）。只留一行日志（含"当前地址="，便于事后核对判据）。
- `dropPoolIfUrlChanged` 自身也加同一条防御（任何未来调用方都安全）。
- 判据不变的部分：**当前地址**装载失败且地址变过 ⇒ 照样清池（db 口径保持）。

### ⚠️ 残余风险（本轮未改，先记录）

**迟到的「成功」**仍会 `parseJson` 装池（把被放弃源的站点装进池）。它比迟到失败罕见得多
（要求一个已在失败的地址在切换后反而成功），且**能自愈**：当前地址装载成功会覆盖，
当前地址失败时 `dropPoolIfUrlChanged`（当前地址、地址变过）会把它清掉。
若真机上再出现"池归属对不上当前地址"，再补这一条。
