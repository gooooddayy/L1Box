## 二、逐项详述

### S1 · 冷启首搜：把"固定 5 秒预算"抬到 20 秒

**现象**：进程刚起来就搜索 → 提示「正在初始化播放源，自动重试…」→ 最终给空态。

**依据（本轮硬数据）**

| | 失败那次 | 成功那次 |
|---|---|---|
| 距进程启动 | **+7.7s** | **+4.7s** |
| 搜索前是否已有首页数据 / jar | **都没有** | **都有**（+3.2s / +4.66s） |
| `站点池定论` | **false** | **true** |
| 结果 | 失败 | 首条 2046ms / 命中 60 |

⇒ 决定成败的是「**config 与 jar 有没有就绪**」，而**就绪时间不可预测**（实测 4.7s ~ 13s+）。
固定 5 秒预算天生会踩空。

**改动点（一行常量）**
```
READY_RETRY_MAX = 10 → 40        // 500ms × 40 = 20s（原 500ms × 10 = 5s）
```
等待循环本身是 **handler 非阻塞式**（`postDelayed` 后 return），**不会 ANR**。

**潜在 bug 与预防**

| 风险 | 预防 |
|---|---|
| 池子永不就绪 ⇒ 白等 20s 才报错 | 保留上限；超时后**空态文案改为「未获取到播放源，请检查订阅或稍后重试」**（与"确实没有这个关键词"区分开） |
| 用户已退出搜索页，等待回调还在跑 | ✅ **已有守卫**：`readyRetryRunnable = Runnable { if (!isFinishing && !isDestroyed) searchResult() }`，无需新增 |
| 用户干等 20 秒没反馈 | 可选：等待期间复用现有 loading（已有），或加一行"正在初始化播放源…" |

**待定**：要不要在等待期间给进度提示？（见第五节问题 1）

### S2 · 自动重搜的"等待计数"空转 —— 让重搜真的等

**依据（代码 + 日志双证）**

日志显示三次轮次的时间是 `45.684 / 46.348 / 47.005`，**间隔只有 0.66s**，且三轮 `等待次数` 都是 **10**：

```
搜索轮次：可搜站点=0 站点池定论=false jar装载序号=0/0 等待次数=10 自动重搜=0
搜索轮次：可搜站点=0 站点池定论=false jar装载序号=0/0 等待次数=10 自动重搜=1
搜索轮次：可搜站点=0 站点池定论=false jar装载序号=0/0 等待次数=10 自动重搜=2
```

原因在代码：`readyRetry` **只在 `search()`（用户手动发起）里清零**（第 421 行），
而自动重搜是**直接重入 `searchResult()`** ⇒ 计数仍是 10 ⇒ `readyRetry < READY_RETRY_MAX` 立即为假
⇒ **一轮都不等**，只花掉 600ms 延时。

**改动点**
```
把 readyRetry = 0 从 search() 移到 searchResult() 入口
```

> ### 🔴 2026-09-22 17:30 更正：上面这个改法**有坑，已作废**
>
> 照上面那样写在 `searchResult()` **入口**会**无限等待**：等待重试本身就是
> `readyRetryRunnable → searchResult()`（第 431 行），每次重入都把计数清零
> ⇒ `readyRetry < READY_RETRY_MAX` 永远为真 ⇒ **只要 `isSitePoolSettled()` 一直是 false 就永远出不来**。
> 唯一出口退化成"池子定论变 true"，`AUTO_RESEARCH_MAX` **拦不住它**（那是另一条路）。
>
> **正确改法：把 `readyRetry = 0` 放在「自动重搜的调度处」（第 505~514 行 `verdictEmpty()` 里
> `autoResearches++` 那一支），而不是 `searchResult()` 入口。**
> 即：只在**新一轮开始**时清零，绝不在**本轮自旋重试**时清零。
>
> 改对之后自然有界：手动轮 5s ＋ 自动① 0.6s+5s ＋ 自动② 0.6s+5s ≈ **最长 16s**。
>
> **✅ 17:51 补测更新**：实测就绪可达 **+16.5s**（+1.9s 起搜的那次），16s 窗口只剩 **2s 余量，太薄**
> ⇒ **S2 单改不够，S1 要一起做**。且**抬高上限不会牺牲速度**——上限只在"池子尚未定论"期间生效，
> 池子一定论（含有站点、以及"0 站点"的**明确空态**）就立刻停等（`FastSearchActivity.kt:647`）。

⚠️ **必须只移 `readyRetry`，`autoResearches = 0` 要留在 `search()` 里。**
原作者在第 419~421 行留了注释：「不在 searchResult() 里清是因为那也是自动重搜的入口 —— 清在那儿等于自动重搜失效」。
**这条注释指的是 `autoResearches`**（清在那儿会永远为 0 ⇒ 无限重搜）；`readyRetry` 移过去是安全的。

**效果**：手动轮等 5s → 自动轮各再等 5s，总等待 ≈ **16s**（受 `AUTO_RESEARCH_MAX = 2` 限死，**不会无限**）。

**潜在 bug 与预防**

| 风险 | 预防 |
|---|---|
| 无限重搜 | `AUTO_RESEARCH_MAX = 2` **保持不动**；`autoResearches` 仍只在用户手动时清零 |
| 最长 3×5s 让用户等太久 | 与 S1 合并考虑：S1 抬高单轮上限后，建议**总预算共享**（例如总上限 20s），而不是 3×20s=60s |

> **S1 与 S2 的耦合**：S1 只管单轮等多久，S2 管"重搜时还等不等"。
> 两个都改 ⇒ 冷启首搜最长等约 20s 且**真的在等**；只改 S1 ⇒ 仍然只有第一轮在等（5s→20s，够用但只有一次机会）。

### S3 · 假计时埋点（纯观测，零行为）

**依据**：失败那次打印 `总耗时=7ms`，**但实际等了 5 秒**。

原因：`roundStartMs = SystemClock.elapsedRealtime()` 写在 `searchResult()` 里（第 609 行），
而 `searchResult()` 是**自动重搜的重入入口** ⇒ 每次重入都把起点重置 ⇒ 读数只反映"最后一小段"。

**改动点**
```
search()      : roundStartMs = 0L                    // 用户按下搜索 = 计时起点
searchResult(): if (roundStartMs <= 0L) roundStartMs = SystemClock.elapsedRealtime()
```
（`printRoundSummary` 第 455 行已有 `if (roundStartMs <= 0L) return` 守卫，不用动）

**效果**：自动重搜轮报出的 `总耗时` 变成「**从用户按下搜索算起**」的真实总耗时。
**风险：零。**

### P1 · `errReplay()` 缺"重新取链"档

**依据**：上一轮（15:09）完整时间轴，见 `20_播放器/播放中途404_兜底链缺重新取链_20260922.md`。

**本轮状态**：**未复现**（5 个源、连续 5 分钟，`出链=0`、`404=0`、`ExoPlaybackException=0`）
⇒ 触发条件是**源站中途失效**，属**低概率但确定性缺陷**。

**根因回顾**：`errReplay()` 的三档兜底（回退原始直连 / 换 http↔https / 换 IJK）**全都在同一条死链上折腾**，
而"重新取链"`autoRetry()` 在全工程**唯一调用点**是"有其它已解析地址"那一支 ⇒ 本例一次都没重取，白等 11.3s。

**改动点**：按错误签名分档 —— **仅当「播放已开始之后」且「签名 = 404/410 或 `errorCode=2004`」时，先试一次 `autoRetry()`**。

**三个约束缺一不可**

| # | 约束 | 为什么 |
|---|---|---|
| 1 | 起播前的 404 不加 | 那时链接刚取，重取没意义 |
| 2 | 只认"地址没了"类签名 | 超时 / 解码失败 / 容器不支持，重取也白搭 |
| 3 | **预算基准回溯到本次 404 的时刻** | 不能用 `mEpisodeStartAt` —— 否则播了 10 分钟的片子会立刻判"预算用尽"而整档跳过 |

**潜在 bug 与预防**

| 风险 | 预防 |
|---|---|
| 最坏等待从 64s 拉到 96s（原作者 `errorFinal` 注释已警告） | 靠约束 3 把这次重取限定在"地址失效"一种签名下，其它签名完全不受影响 |
| 重取也失败 ⇒ 报错更晚 | 重取耗的**是同一个预算**，不额外新增等待时间 |
