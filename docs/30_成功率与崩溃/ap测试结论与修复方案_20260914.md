## 二、严重回归：458 次"拒载"（本版引入，功能级倒退）

```
加固 jar 内部 loader 绑定失败，已拒载其站点（避免原生闪退）   ← ap: 458 次
```

| 版本 | 拒载 | 加载成功 | 启动次数 |
|---|---|---|---|
| ak | **0** | 260 | 11 |
| al | **0** | 268 | 28 |
| am | **0** | 98 | 15 |
| **ap** | **458** | 41 | 18 |

每会话 13~17 次拒载，仅 2~4 次成功。**被拒载的站点是彻底不可用**（失败结果不进 `classLoaders`，每次访问都重试，所以消息计数被放大）。

### 根因（两处缺陷叠加）

**缺陷 ① 判据偏宽**：`ProtectedInitJar.Signals.family()` 的第 ④ 条兜底
`nativeRef && processRef`（既引用 `System.load*` 又引用 `Runtime.exec`/`ProcessBuilder`）会把**普通 jar** 判成家族；运行时 `probeFamily` 也偏宽。普通 jar 被送进手动受控路径。

**缺陷 ② 手动路径把"绑不上"当致命**：`bindDexLoader` 调 `DexNative.getLoader(...)`，失败即 `return false` → `loadClassLoader` 里 `success=false` → **整个 jar 被拒载**。
栈实证它为什么失败：`DexNative.getLoader` 内部会走 `InitOrigin.init:65 → ProxyOrigin.init:69 → okhttp → 127.0.0.1:8964 ECONNREFUSED`（该 jar 自己的本地代理还没起来）。

**次序反了**：日志 `PanDebug` 显示 jar 自身流程是
`GoProxyManager.startBlockingForInit`（exec + `waitHealth ok`，**每次随机端口** 35660 / 27849）**在先**，`getLoader` 需要它；我们把 `bindDexLoader` 排在 `startGoProxyOnce` **之前**。

> 批次一方案注释里写的"多判家族的代价只是网盘源降级"——**与实际不符**。实际代价是整个 jar 被拒载、站点消失。这是方案设计的错误假设。

## 三、搜索结果"补全停止"根因与修法

**触发**：搜索结果页 → 进详情页 → 返回 → 再进详情页，反复几次后结果不再补全。

**根因**（`FastSearchActivity.kt`）：进详情页时对搜索池执行 `shutdownNow()`（第 145、169 行）。
`shutdownNow()` **只返回"还没开跑"的排队任务**，已经在跑的任务被打断后**永远不会回来**。
`onResume()`（第 103-113 行）只重投 `pauseRunnable`——也就是"排队余量"，**列表为空时整个不做任何事**。

用户恰好在结果开始出现时点击 → 那一刻队列往往已经空了 → **这一轮在飞的全部站点被永久丢弃**。反复几次后剩余站点全部消失 → 补全停止。

附带两个让它"静默"的细节：
- 每个搜索 lambda 里 `catch (_: Throwable)` 吞掉异常且**不递减 `allRunCount`**；
- `allRunCount.set(pauseRunnable.size)` 把计数重新基准化，于是页面仍会正常"收尾"，只是结果少了一块，没有任何报错。

**修法（推荐，最小且无损）**：进详情页时**不要拆掉搜索** —— 删掉两处 `shutdownNow()` 与 `onResume` 的重投逻辑，让本轮搜索在后台自然跑完（已有 30 秒看门狗封顶）。`flushSearchResults()` 本来就只拦 `isFinishing || isDestroyed`，暂停期间结果照样落地，返回时看到的就是完整列表。

## 四、另外两个必须说清的事实

1. **批次二的"装载复用"本轮零命中**（`复用命中=0`、`受控接力=0`）。因为"退出"= 划掉应用 = **进程被杀**，每次都是新进程，进程内复用表用不上。所以批次二**没有兑现任何提速**；它只在"同进程内配置重载 / 切线路"时生效。
2. **一加系统的日志限流**：`LOG_FLOWCTRL: LOGS OVER PROC QUOTA(420) ... DROPPED` 共 **125 次**，应用自身日志被大量丢弃（SpiderLog 每 15 秒约 2 万行）。这既让"用日志路标验收"不可靠（本次改用系统侧 dropbox / exit-info 才拿到硬证据），本身也是该修的噪声源。

## 五、修复计划（一批出包）

| # | 改动 | 目标 |
|---|---|---|
| F1 | 判据分级：`familyType` / 静态 `Init+DexNative` / 运行时 `probeFamily` 命中 = **确认加固**；仅第 ④ 条启发式命中 = **疑似** | 不再把普通 jar 拖进手动路径 |
| F2 | 手动路径次序改为**先起代理、再绑 loader**；仍绑不上时按 F3 处理 | 让持有者 jar 真正能绑上 |
| F3 | **疑似** jar 绑不上 → 回退走 jar 自己的 `Init.init(Context)`（这批 jar 本来就没有加固 SDK、不会启动 Go 代理、不产生互杀链）；**确认加固** jar 绑不上 → 维持拒载降级，并**释放代理闸门**让后续 jar 可接管 | 站点恢复可用，且不给真家族 jar 开危险口子 |
| F4 | 每次拒载/回退打印 jar key + 具体失败点（getLoader 抛异常 / 返回类型不符 / 找不到字段） | 下一轮可精确核查 |
| F5 | 删掉进详情页的 `shutdownNow()` 与 `onResume` 重投 | 修"补全停止" |
| F6 | SpiderLog 加开关（默认只在调试构建打开） | 消除日志限流，恢复可观测性 |

**验收口径不变**：冷启动首搜 + 退出重进首搜各 5 轮，`Fatal signal 6` = 0、`JNI DETECTED ERROR` = 0；外加**新增一条硬指标**——`加固 jar 内部 loader 绑定失败` 次数须回到 **0**，且加固 jar 的网盘源可用。
