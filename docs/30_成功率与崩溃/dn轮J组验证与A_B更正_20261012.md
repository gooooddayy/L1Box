## 二、⚠️ 一处更正：我先前那个「后台 60 秒 409 → 200/119」的 A/B **不干净**

核对日志时发现这台 ROM（Oplus/ColorOS）**在应用退到后台约 10 秒后就会把它冻结**：

```
I/OplusHansManager( 3080): freeze uid: 10512 com.github.tvbod.osc pids: [...] scene: LcdOn
I/OplusBinderProxy( 3080): proxyBinder uid: 10512 ... proxy: true calling: OFreezer
```

冻结之后主线程**完全不调度** ⇒ 无论新旧版本，后台的唤醒都会被系统归零。这带来两个后果：

1. **我先前那个 A/B 的 60 秒窗口里，绝大多数时间都是"已冻结"状态**，量到的差异混进了"启动后收尾工作"和"冻结时机"的抖动 ⇒ **不该按"−51%"那样解读**。
2. **在这台手机上，本次改动几乎没有可观测收益** —— 因为冻结已经替它把后台唤醒清掉了。

### 重做严格对照（各版本：启动 → 空闲 25 秒 → HOME → 逐 5 秒窗）

| 版本 | 前台空闲 5s | 后台窗1 | 后台窗2 | 窗3~6 |
|---|---|---|---|---|
| dm（旧：无条件 250ms 自续期） | 454 | **133** | 47 | 0 / 0 / 0 / 0 |
| dn（新：仅前台自续期） | 425 | **79** | 读数不可取（`/proc` 读空） | 0 / 0 / 0 / 0 |

- 方向一致（79 < 133），但**单样本、窗口只有 ~10 秒（之后就被冻结）⇒ 不足以给出精确数字**，我不当作有效量化。
- 再测一次"搜索页在前台 → HOME"的场景（复现一次卡顿式活动）：后台前 10 秒出现过 893/704 次/5秒。查证这是**在途搜索的收尾**（日志里正在跑 `搜索稳定收尾 / 搜索补全守卫 / 搜索等待 S5`），并被冻结在 10 秒处截断。
  **这不是本次改动引入的**：本次只删掉**每秒 4 次**的 250ms 定时任务，算术上不可能产生 800+ 次/5秒。
  **也不是帧循环漏了**：同一场景里埋点正常打出「前台页面已消失：兜底轮询停摆」，而该日志只在 `resumedCount` 真的归零时才打 ⇒ 计数没泄漏 ⇒ 帧循环也已停。

### 更正后的准确表述

> 本次改动删掉的是：**应用在"没有前台页面"期间、每秒 4 次的主线程空转唤醒**。
> - 在这台 ROM 上：**收益被系统冻结掩盖**（约 10 秒后就什么都不会跑），每个后台会话最多省 ~40 次唤醒 ⇒ **体感与电表都测不出来**。
> - 在**没有激进冻结机制的设备/ROM**（老 Android、电视盒子 —— 也正好是本项目的主要受众，且盒子通常长期通电不关机）上：旧代码会**一直**每 250ms 转下去，新代码则**一次都不转**。
> - 价值是**结构性**的：改完后应用在后台没有任何周期性调度。风险为零、前台逐拍行为不变。

## 四、J1 视觉项确认 + 「退后台还在跑搜索」这个新问题：**不值得修**（21:15 补充）

### 4.1 J1 视觉项

用户 21:15 确认：**没有突然冒出的第三方横幅/弹窗** ✅
（与日志侧的旁证一致：期间 0 次「已移除 jar 弹窗」＝没有需要清扫的弹窗。）
⇒ **J1 三条件全部通过，dn 的 J 组收口。**

### 4.2 这个"新问题"到底是什么

退到后台时**不取消在途搜索**，搜索会继续跑完。表现：退后台后到被系统冻结前的 ~10 秒里，主线程仍以帧率级被调度，但**几乎不出帧**。

### 4.3 实测代价（同一台机、同一操作：启动 → 进搜索页 → HOME）

| 场景 | 退后台后 **9 秒内**进程 CPU |
|---|---|
| A 空闲首页 → HOME | **320 ms** |
| B 搜索在途 → HOME（第 1 次） | **1,740 ms** |
| B 搜索在途 → HOME（第 2 次） | **2,480 ms** |

⇒ 差值 **~1.4 ~ 2.2 秒 CPU**，**一次性**。
换算电量：单核满载按 ~1.5W 估，2 秒 ≈ 3 J ≈ **电池容量的 0.003%**（以 15Wh 计）⇒ **电表与体感都测不出来**。

⚠️ **流量这一项我没测到可信数值**：本机是 Android 13，`/proc/net/xt_qtaguid/stats` **不存在**，`dumpsys netstats` 里也**没有该 uid 的记录** ⇒ 不编数字。
仅有的间接证据：实测的几次里，退后台那一刻搜索已经 `已回=40/40`，紧接着 `搜索补全：源无变化，跳过`（1 秒内收工）⇒ 后台主要在做**解析/缓存**，不是在发新请求。

### 4.4 为什么它是有界的（三重界定）

| 界定 | 依据 |
|---|---|
| ① 搜索自身硬上限 | `FastSearchActivity.SEARCH_TIMEOUT_MS = 30000L`；补全守卫 `40×500ms = 20s` 上限 ⇒ **到点必收工** |
| ② 系统冻结 | Android 12+/ColorOS 把 cached 应用冻结（本机退后台 ~10s）⇒ 直接把窗口截断 |
| ③ 日志实证 | 本机实测退后台 1 秒内补全守卫即判定「源无变化，跳过」并结束 —— 事实上更短 |

### 4.5 结论：**不值得修**，只留观察判据

**不建议修的理由**

1. **代价测不出来**（~2 秒 CPU、一次性），而"修"要有代价（见下）。
2. ⭐ **这个"不取消"是对的、也是故意的**：用户搜到一半切出去看一眼消息，回来结果已经好了。取消它＝用户回来看到空态 / 要重搜 —— **拿一个真实的体验倒退，换 1.4 秒 CPU**。
3. 多数设备上它本来就被冻结截断 ⇒ 收益≈0。
4. **与 dn 改动无关**（dn 只删掉每秒 4 次的定时任务，算术上不可能产生 800+ 次/5 秒），是既有行为。

**若哪天要收，两种方案都不划算**

| 方案 | 内容 | 判断 |
|---|---|---|
| 甲 | 退后台即取消在途搜索 | ❌ 体验倒退（回来要重搜） |
| 乙 | 退后台只"不再发新一轮"，已发出的回调照收 | ⚠️ 要动搜索状态机、风险中等，**收益测不出来** ⇒ 不划算 |

**留下三条观察判据（下次若命中其一，才回头处理）**

1. 搜索在后台跑**超过 30 秒**（说明上限没生效）；
2. 日志里「搜索补全」**反复出现**而不是「源无变化，跳过」（说明补全守卫在无界重启）；
3. 退后台期间**流量明显**（弱网下 40 个站点的请求全在后台发）—— 这一项本机测不到，需要换一台能读流量统计的设备再看。
