## 二、A 组：让搜索"快、准、且一定收敛"

### A-1 判据② 从伪判据改成真判据

**证据**（bu 清单三·补·洞 5）：`FastSearchActivity.kt:1069 roundSiteCount = siteKey.size` 与 `:1070 roundAsked = siteKey.size` **赋的是同一个值**，`roundAsked` 从不按回调计数 ⇒ `问全=true(40/40)` 恒真。它本想回答的"这一轮有没有站点没被问到"**根本测不出来**。

**修法**：
- 删 `roundAsked`，新增 `roundDone`（本轮**实际完成回调**的站点数，在 `searchData()` 里自增，含空结果回调）；
- 新增 `roundEndedByTimeout`（在 `finishSearchByTimeout()` 置 true，发起时置 false）；
- 判据② 改成：
  `askedAll = !roundEndedByTimeout && roundDone >= roundSiteCount && roundSiteCount > 0`

**为什么两段都要**：`allRunCount` 归零（正常收尾）在代码上**等于**"发起的站点都回来了"——这是硬事实；而超时收尾**必然**有站点没回来。两者取"与"，既拿到真数据，又不会被迟到回调污染（迟到回调会让 `roundDone` 偏大，但它是上一轮的，`roundEndedByTimeout` 这一道挡得住）。

### A-2 池签名撤出 `loadSeq`，换站点 key 集合指纹

**证据**：bu 真机 `18:58:23 池未变=false(41|true|4|true|false -> 41|true|8|true|false)` ⇒ 站点数、池来源、主 jar 全没变，**变的只有 `loadSeq`**；而同一时段"没有任何一条 jar 装载成功日志"。⇒ 判据③ 恒假 ⇒ S3 每 1 秒又起一轮 30 秒。

**修法**：
- 新增 `poolKeySig()`：`getSourceBeanList()` 的 key 排序拼接取 `hashCode()`（纯内存读，41 个短串）；
- 签名改为 `站点数|定论|主jar定论|key指纹|池来源` —— **`isPoolFromCache()` 仍放最后一段**（闸门 `:1302` 的断言锚的是行尾，不能动顺序）；
- `loadSeq` **保留**在 `printRoundSummary` 里（"本轮装载增量"是诊断硬指标），只是不再参与判据。

**语义依据**：签名要回答的是"池**内容**变了没"；装载活动不改变池内容。"jar 装上了 ⇒ 站点变可搜"这件事由**判据⑥（本轮新面孔被跳过）**覆盖 —— 装不上会被 `skipNull` 记账 ⇒ 新面孔 ⇒ 重搜一轮；装上了那次搜索本来就有结果。两个方向都不会漏。

### A-3 两处漏计改走 EventBus

**证据**（洞 6）：`SourceViewModel.getSearch` 的 `:529`（`getSource(key)==null`）与 `:610`（类型不在 {0,1,3,4}）只 `searchResult.postValue(null)`；而结果实际派发走 EventBus（`json()/xml()` 的 `:983/:996/:1030/:1043` 与 `onError` 的 `:576/:606` 都是 `EventBus.post(TYPE_SEARCH_RESULT, …)`）；**全工程该 LiveData 无观察者**。⇒ 该站点永不回调 ⇒ 计数漏一格 ⇒ 只能等 30 秒看门狗。冷启时池正从缓存池切网络池，`getSource(key)` 落空概率最高 —— 与"只有冷启立刻搜才这样"完全一致。

**修法**：两处 `searchResult.postValue(null)` → `EventBus.getDefault().post(new RefreshEvent(RefreshEvent.TYPE_SEARCH_RESULT, null))`（与同文件既有写法逐字一致，不新增通道）。

### A-4 停滞检测（只对 0 结果生效）

**动机**：看门狗 30 秒是"最坏情况上限"，但对**已经卡死**的那一轮，用户要白等 30 秒。真机旁证：A2 那轮 30 秒里有 **22 秒几乎零日志**（只有 jar 自己每 5 秒重试一次）。

**修法**：新增 `STALL_QUIET_MS = 10000`：
- `searchData()` 每次回调刷新 `lastProgressMs`（**含空结果回调**）；
- 每秒一拍的 `stallRunnable`（纯内存读、零网络）：`在途 > 0 ∧ 结果为空 ∧ 静默 ≥ 10 秒` ⇒ 打埋点 + `finishSearchByTimeout()`；
- **只在 0 结果时生效** —— 有结果时不提前，让慢站点继续补（"结果条数"一个字不少）。

**为什么 10 秒**：实测正常轮次 2~8 秒收尾、首条 64ms~2.4s；10 秒静默已经远超"任何站点在工作"的形态，而不是"慢"。

### A-5 S3 兜底出口（"部分站点未响应"）

**必要性**：A-1 让判据②变真之后，"有站点卡死"会让 S3 一直等一个**永不到来的池变化** ⇒ 又变成无限转圈。所以必须给一个**诚实的、非空态的**结论。

**修法**：`onWaitTick` 的 S3 出口，在"新面孔跳过"检查之后加一支：
- `roundDone < roundSiteCount` ⇒ `showEmpty()` + `ToastUtils.showLong("部分站点未响应，未找到结果，请稍后重试")`，埋点写明 `已回 X/Y`；
- 措辞刻意**不是**「暂无数据」：真空态才配那四个字。

## 三、D 组：转发端点（外部播放器 + 投屏）

### D-1 m3u8 分片重写

**为什么必须重写而不是"把 base 换回上游"**：换回上游 = 分片由播放器直连 ⇒ 站点没下发的 Referer 又丢了 ⇒ 回到 403 那条老路（D1 最初的病根）。所以分片**必须继续走转发**，但地址得是**绝对的**。

**修法**（只在 `code == 200 ∧ 无 Content-Range ∧ Content-Length ∈ (0, 8MB] ∧ 像 m3u8` 时）：
1. 全量读上游清单（实测 197KB）；
2. 非 `#EXTM3U` 开头 ⇒ 一字不改，原样回；
3. 逐行处理：
   - 普通 URI 行（非 `#` 开头）⇒ 用**上游清单 URL** 解析成绝对地址；
   - `#EXT-X-KEY` / `#EXT-X-MAP` / `#EXT-X-MEDIA` / `#EXT-X-I-FRAME-STREAM-INF` 的 `URI="…"` ⇒ 同样重写（这份清单没有，但别的源有）；
4. 重写目标 = `http://<来源 Host>/l1play?[t=<同一个码>&]u=<urlencode(绝对分片)>&h=<urlencode(请求头)>`：
   - **Host 取请求的 Host 头** ⇒ 本机自动是 `127.0.0.1:9978`、电视自动是 `192.168.x.x:9978`，不需要判断"我是谁"；
   - 投屏那条**复用同一个一次性码**（不带 `h`，头从登记里取）；
5. 改写过 ⇒ 用改写后的字节长度重新构造定长响应；**不改写 ⇒ 照原路**（chunked / 超限 / 206 都不碰）。

**解析规则**（纯字符串，不用 `URI.resolve` —— 清单里的地址常含 `|`、空格、中文，`URI` 会抛）：
`http(s)://` 开头 ⇒ 自身；`//` 开头 ⇒ 补 scheme；`/` 开头 ⇒ 补 `scheme://authority`；其余 ⇒ 拼 base 的**目录**（base 先剥掉 `?query`）。任一环节出意外 ⇒ **返回 null ⇒ 原样不重写**（退化，不是报错）。

**已指向本机的不重写**（`127.0.0.1` / `/l1play`）⇒ 防自嵌套。

### D-2 投屏：分片带上同一个码

**修法**：`servePlayForward` 的 token 分支里，**请求自带 `u` 时以它为准**，没有才用登记的那条地址；请求头仍一律取登记里的（电视根本不带 `h`）。放行条件不变（必须持有有效码），码的 12h 过期与"最多在册 8 条"都不动。

### D-3 Accept-Ranges 不再谎报

上游给了才回（两处：HEAD 与 GET）。实测上游对 Range 请求回 **200 + 全量、无 `Content-Range`、无 `Accept-Ranges`** ⇒ 它本来就不支持拖动，硬写 `bytes` 只会让播放器按"可拖"去算位置。
