## 一、搜索结果页两侧滑动更丝滑

### 原因（09-28 日志＋代码实锤）

| # | 根因 | 证据 |
|---|---|---|
| 1 | **滑动中结果仍在落地**：`SEARCH_FLUSH_MS=120ms`（`FastSearchActivity.kt:77`）攒批 `addData`（`:1073`），270 条结果要在 ~15s 内持续插入列表 ⇒ 滑动中反复 `notifyItemRangeInserted`＋新 item 绑定，与手势抢主线程 | 09-28 判定：L1Box 整场仅 1 次 38 帧掉帧（恰在回调高峰）⇒ 不是渲染崩坏，是"落地与滑动抢主线程" |
| 2 | **图片下载/解码不避让滑动**：滑动中每绑定一个新 item 就 `into()`，解码回调在主线程落地 | `FastSearchAdapter.java:38-48` |
| 3 | 左侧站点竖栏（`DslTabLayout` VERTICAL）为自绘 ViewGroup：`scrollTo`＋每帧 `invalidate` 全量重绘（`DslTabLayout.kt:1757-1776`），40 个 tab 全量子 View | 它自身开销有限，卡更可能来自主线程被 1/2 占用 ⇒ **不首选动库** |

### 方案（F 组）

| # | 改动 | 落点 |
|---|---|---|
| F1 | **滑动中暂停落地**：`mGridView.addOnScrollListener`——DRAGGING/SETTLING 期间 flush 只攒不通知；回 IDLE 一次性落地。护栏：攒满 60 条或静默 2s 强制落一次（防"一直滑永远不更新"） | `FastSearchActivity.kt` flushSearchResults 一带 |
| F2 | **图片避让滑动**：搜索页图片统一 `.tag("fast_search")`；DRAGGING `pauseTag`、IDLE `resumeTag`（Picasso 内置能力） | `FastSearchAdapter.java` ＋ F1 同一监听器 |
| F3 | 列表缓存加厚：`setItemViewCacheSize(6)`（默认 2），`setHasFixedSize(true)` 已有（`:207`） | `FastSearchActivity.kt:207` 一带 |

**验收**：滑动跟手不滞；埋点看 L1Box 掉帧 ≥30 帧应 ≈0；结果条数不因暂停落地而变少（270 口径）。
**二期留观**：F1~F3 后左侧栏若仍卡，再动 DslTabLayout 绘制（一处改动覆盖搜索页＋首页分类栏）。

## 二、搜索页图片缺失不显示

### 原因（分层，一层已修、一层盲区）

| 层 | 结论 |
|---|---|
| 地址类 | **bv 已修**（`trim`＋`checkReplaceProxy`，`FastSearchAdapter.java:39`）——这层不再是主因 |
| 观感类 | **placeholder 与 error 是同一张图**（`:46-47` 都用 `img_loading_placeholder`）⇒ "加载失败"与"加载中"长得一样，用户看到的都是"缺失" |
| 盲区 | Picasso release 下**零日志** ⇒ 失败构成（403 防盗链／超时／空图）无法判定。图床防盗链 403 是常见病因，但没有数据不能定刀 |
| 挤兑类 | 一次命中 270 张图全量入队（4 解码线程＋下载队列），滑出屏幕的也在排队 ⇒ 慢，但会陆续出 |

### 方案（G 组）

| # | 改动 | 说明 |
|---|---|---|
| G1 | **error 占位图分开**：失败用一张显式"加载失败"灰图 | 用户第一次能区分"还在加载"和"这个图死了" |
| G2 | **图片失败统计埋点**：`MyOkhttpDownLoader` 聚合计数，搜索收尾时打一行 `图片加载：成功=N 失败=M 失败域名=[a:3,b:2]` | 一轮实测就能看清失败构成，二期按域名定刀 |
| G3 | 滑动 pause/resume | ＝F2，同一份改动 |
| G4（二期） | 按 G2 数据定向：某域名 403 → 按域名白名单补 Referer/UA（**只补图片链、按域名，不全局**——播放链"外站 Referer 403"血泪不适用于图片，但也不能盲加） | 等 G2 数据 |

**验收**：搜索页静止 1~2 分钟后，图位要么出图、要么显示明确的"失败图"；日志出现统计行。

## 三、详情页选集被截断为 4 行

### 原因（子代理逐行实锤，一处写死）

- `activity_detail.xml:393`：选集网格 `mGridView`（RecyclerView，3 列）**`layout_height="126dp"` 写死**；`DetailActivity.java:178` 注释明写"显示三行"的设计意图。
- 外层是 `ScrollView`（`activity_detail.xml:25-27`），而 RecyclerView 自己内部滚动 ⇒ 嵌套滚动冲突，外层永远滚不到"被截断"的部分。
- dp 是绝对值 ⇒ **手机/平板看到的行数完全一样**，与屏幕尺寸无关 —— 正是"所有设备都截断"的原因。

### 方案（H 组）

| # | 改动 | 说明 |
|---|---|---|
| H1（首选） | `126dp → wrap_content` ＋ `android:nestedScrollingEnabled="false"` | 选集**全部展开**，由外层 ScrollView 统一滚动；内容多页面就长，任何屏幕都完整可见、自然自适应 |
| H2（备选） | 改为屏幕高度 35% 上限＋保留内部滚动 | 若嫌长剧集页太长再用；与"完整可见"诉求稍弱 |

**风险评估**：300 集影片＝300 个轻量 TextView 按钮一次性绑定，无压力；"展开全集"底部弹窗是独立控件（`AllVodSeriesBottomDialog`，spanCount 本就自适应），不受影响、不需要动。
**验收**：集数多/少的影片各测一部＋平板尺寸，选集全部可见无截断。

## 四、播放失败（直接失败／1m/s 后失败）

### 原因（子代理全链路实锤：13 条置败路径已清点）

| 症状 | 机理 |
|---|---|
| 很多源直接播放失败 | 主路径＝①取链失败（`FETCH_WATCHDOG_MS=15s` 超时／站点接口空）→ errorWithRetry；②内核 `STATE_ERROR` → `errReplay()` 兜底链（备选地址→重取→回退直连→http/https 变形→IJK/Exo 降级→再重取）**全试尽** → errorFinal。**关键缺陷：错误码被全工程丢弃**（IjkPlayer 丢弃 what/extra；Exo 只打日志）⇒ 403/404/编码不支持/超时**全部无差别走同一条链**，既多等无效档，也无法从日志分类"很多源"到底是哪种死法 |
| 显示 1m/s 后仍失败 | 速度显示（`VodController.java:245-268`，每秒写 UI）与判死**零耦合（刻意设计，防误杀慢源）**。"有速度"＝分片在下载，但 prepare/首帧始终不成功（分片 403、清单中断、编码打不开）⇒ 最终内核 error 或 32s 起播看门狗判死 → 兜底链试尽（本集预算 `EPISODE_RETRY_BUDGET_MS=70s`）→ errorFinal |

**判死秒数现状（纪律核对，全部不动）**：起播看门狗 20s＋唯一一次延长 12s（判死点 32s）、本集预算 70s、取链看门狗 15s、重取预算 8s、重取次数 2。

### 方案（I 组，分两期——先看见，再动手）

| # | 期 | 改动 |
|---|---|---|
| I1 | 一期 | **错误码透传＋分类埋点**：Exo `onPlayerError.errorCode`／Ijk `what/extra` 带出到 `errReplay`，打埋点 `播放失败：code=<错误> 阶段=<取链/起播/缓冲> 站点=<名> 走到=<兜底第几档>`。**只加可见性，不改任何判定行为** |
| I2 | 一期 | **兜底档去重**：同 URL 同类错误已试过的档直接跳过（bo 的 P1 已有 404/410/2004 分档基础，扩成通用签名）⇒ 救不了的少等无效档、更快到下一档，**省下的时间留给可能有用的档** |
| I3 | 二期 | **等 I1 数据定向**：403 为主 → 播放链按域名补 Referer/UA；解码为主 → compatFallback 提前；清单类 → m3u8 重写已有基础上扩展 |

**明确不做**：判死秒数改动；自动换线路（纪律）。
**验收**：一期出包后，你复现"直接失败"和"1m/s 后失败"各几次 ⇒ 日志能报出**失败构成分布**，二期才有的放矢。
