**分类合计**：A 源站空返回 **2** / B 网盘·代理 **2** / C 非 http 地址 **3**（同一 token，跨 2 个站点）。

### 三类根因的证据与"改前会不会好"

**A 源站空返回**：`取链 reason=站点未返回播放信息 ms=-1` —— 站点（jar）压根没给播放地址。播放器层拿不到地址，改内核/超时/看门狗都无效。改前同样失败。

**B 网盘源代理**：地址是 `http://127.0.0.1:9978/proxy?...`，即**加固 jar 的本地代理**。净化预取报 `IOException`（代理里没持有者）→ 属 aq 域（代理持有者机制），播放层不碰。改前同样失败（改动前净化不存在，同样直接把这个地址丢给播放器）。

**C 非 http 地址**：`Ksvideo-aed463fa76ffb834f1aa33814f230f50bfd49c88ba0dce664678…`
- 全仓（含 assets）搜不到 `Ksvideo` ⇒ **不是应用内置协议，是站点返回的自定义地址**；
- 关键证据：**同一站点、同一剧集、同一集数，2 分钟内两次请求给出不同结果**——21:17:21 苹果"超级无敌4K#0"给的是 `https://onvideo-safety.ssrcdn.com/...`（284ms 就绪）；21:19:43 同一位置给的是 `Ksvideo-…`（必失败）⇒ **源侧多线路轮换，混进了本应用播不了的地址**；
- 代码级对比：改动前后**主起播路径都没有 scheme 校验**（唯一的 `!url.startsWith("http") return null` 在 JSON 解析分支，改前改后一字未变）⇒ 改前同样会把它丢给播放器。

## 四、为什么"感觉比改播放器前出错更多"

四条，都能落到证据上：

**① 失败是真的——但不是新增的失败，是新增的"计数器"。**
本轮 43 次点播确实失败 7 次（83.7%）。这些站点/地址在改前也是失败的，只是改前没有埋点，**没有任何人知道失败了几次**。现在能数出来了。

**② 失败的界面表现从"有动作在跑"变成"停在错误上"。**
改动前 `setTip()` 里藏着这段（`git show HEAD` 已核）：
```java
if ("视频播放出错".equals(msg)) {
    if (!retriedSwitchPlayer) {
        ToastUtils.showShort("播放出错,正在尝试切换播放器");
        retriedSwitchPlayer = true;
        mController.mPlayerBtn.performClick();   // 自动弹播放器按钮
    } else { /* 提示里给"切换播放器"链接 */ }
}
```
改前失败时界面在**切播放器**（全应用只发生一次），错误被这轮动作盖住了；改后按第二批口径**取消了自动切播放器**（自动切换只准内置、不弹菜单），失败就**明明白白停在提示上**。同一件事，改后更像"出错了"。

**③ 到提示的等待变长了。**
改动前 `errReplay()` 只有一行（`errorWithRetry`），失败 → 静默重解析一次 → 提示；
改动后 `errReplay()` = 去重 → 回退原地址 → 变形重试 → 内置降级 IJK → 出链失败 → 提示 → **再静默整轮重试** → 再提示。
同一个播不了的片子，改后要多走 1~3 次内部尝试，**用户感知的"卡着不出结果"时间更长**（本次 Ksvideo 那三次每次都是两轮）。

**④ 一条既有缺陷把"1 次失败"放大成"长时间假死"。**
取链失败走的是 `errorWithRetry(err, finish=true)` → 只弹 2 秒 Toast，**不关 `setTip("正在获取播放信息", true, false)` 的 loading 浮层** ⇒ 提示一闪而过，界面继续转圈。Rebo ep1/ep3 两次就是这个表现（改前代码相同，非本批引入，但它是"感觉错更多"的最强放大器）。

## 五、判定与诚实边界

- **本轮不达标**（83.7% < 95%），不能因为"根因不在播放器层"就宽松口径。
- **无退化**：11 次净化命中全部正常起播、18 次补 Referer 全部正常起播 ⇒ au 那次 C1 回归确认未复发；没有任何一次失败可归因到本批改动（回退/变形/降级/看门狗都没把能播的片子弄坏）。
- **新发现 1 个真缺陷（本批引入，影响小）**：`retryVariantUrl()` 的守卫是 `isLocalHlsUrl(url) = url.contains("/l1.m3u8")`，**只挡了净化端点，没挡 `/proxy`**，于是对 `127.0.0.1:9978/proxy` 也做了 http↔https 变形，生成必然失败的 `https://127.0.0.1:9978/proxy`（#14）。本轮它只浪费一次尝试、没改变结果，但属于确定写错的逻辑。
- **诚实缺口**：看门狗 32s 终裁本轮仍未被观测（两次都在 18s / 28.8s 被切走）；场景 C 依然不可测 ⇒「空转终裁 / 重新武装 / 90s 预算 / 变形回原地址」**仍是机制论证 + 闸门断言，没有真机空转证据**。
