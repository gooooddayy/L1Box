# as 方案落地：冷启动首搜"暂无数据"的真根因与修法

日期：2026-09-14　版本：`L1Box_v1.1.1_release_20260914as.apk`
上一版：ar（`7c8c4f0c9b53b08e6cd54361b5043fda`）

---

## 一、用户实测反馈（ar 版）

> "冷启动首搜这个还是会出现没有数据的情况。两次都出在仙剑奇侠传这个名称，
> 但是这次点击搜索后可以正常工作了。"

拆成三条事实：

1. 冷启动后**第一次**搜索，仍偶发空态（页面文案是"暂无数据"）。
2. **手点第二下就正常** —— 说明站点本身没问题，只是"还没准备好"。
3. ar 相比 aq 有改善（不必再退回首页），但**没治本**。

结论先说：**ar 的修法是错的**。那次我给搜索侧加了一个"站点池未定论就先等一等"的守卫，
但同一批代码里，我自己又把守卫的前提**提前置成了真**，等于白加。

## 二、取证：这不是猜，是代码级闭环

### 2.1 先确认用户看到的到底是哪个空态

`app/src/main/res/layout/loadsir_empty_layout.xml` 的文案就是 **"暂无数据"** ——
与用户口述的"没有数据"逐字对应，确认是 LoadSir 的空态，而不是别的提示。

### 2.2 硬指标（ar 测试窗口 20:06~21:49，21 次冷启动）

| 指标 | ar | 说明 |
|---|---|---|
| `Fatal signal 6` / JNI 错误 | **0 / 0** | 防崩专题稳住了 |
| dropbox native crash | **无新增** | 系统级互证 |
| 加固 jar 拒载 | **0** | ap 是 458，aq/ar 已归零 |
| 手绑成功 / 交还自身入口 | 11 / 8 | 两条腿都在用 |
| killall | 14 | 代理换届正常 |
| 连 `127.0.0.1:896x` 失败 | **14560 行 ≈ 7280 次** | **良性**：见 2.4 |
| `自定义爬虫代码加载成功` | 40 | jar 装载有结论 |
| **`WexProgress: 正在初始化本地代理`** | 28 | jar 自己的初始化横幅（已被宿主清扫） |
| **`App99.searchContent → NullPointerException`** | 63 | **根因二的实证** |

**防崩这条线可以结案**：0 崩溃、0 拒载、0 遗漏初始化。

### 2.3 真根因链（全部可在代码里逐行核对）

```
冷启动
 └─ HomeConfigLoader 读 assets/home_config.json     ← assets，瞬间完成
     └─ parseHomeJson(): sites 数组是**空的**
         └─ homeSiteList 为空 → if (!homeSiteList.isEmpty()) 不成立
             └─ mHomeSource 保持 null（新进程）
                 └─ getHomeSourceBean() 返回 emptyHome 存根（new SourceBean()）
                     └─ isSearchable() = (searchable != 0) = **false**   ← int 默认 0

 同时：订阅是**网络请求**（日志实测"从本地缓存加载"0 次 ⇒ 每次冷启动都重新拉）

 用户此刻点搜索
 └─ searchRequestList = sourceBeanList(仍为空) + [emptyHome]
     └─ 循环里 !bean.isSearchable → continue  → **siteKey 为空**
         └─ 本该"先等一等"…… 但 ar 在 loadLocalHomeConfig 出口
            已无条件 sitePoolSettled = true
             └─ 守卫失效 → 立刻 showEmpty() → **"暂无数据"**

 几秒后订阅落地 → parseJsonInternal 填满 sourceBeanList → 用户手点第二下 → 正常
```

**每一环都有代码或构建产物佐证：**

- `home_config.json` 的 `sites` 为空 —— 项目自己的预检脚本就打印：
  `(提示) sites 为空——首页内容由订阅站点提供，空源显示"添加订阅源"引导（正常）`
- `parseHomeJson()` 只写 `homeSiteList` / `mHomeSource`，**从不写 `sourceBeanList`**
- 但搜索页取的是 `getSourceBeanList()`（+ 首页源）→ **两者不是同一个池子**
- `getHomeSourceBean()` 的兜底 `mHomeSource == null ? emptyHome : mHomeSource`
  （顺带排掉了一个更坏的可能：若这里返回 null，`remove(home); add(0, home)` 会把 null
   塞进列表，Kotlin 的 `for (bean: SourceBean in ...)` 会直接 NPE。实测应用侧 0 次
   `FATAL EXCEPTION`，与此一致）
- `SourceBean.isSearchable()` = `searchable != 0`，而 `new SourceBean()` 的 int 默认值是 0

**所以这是一次 100% 确定的竞态**：只取决于"用户手指"和"订阅响应"谁先到。
用户说"有时候"、"两次都出在仙剑奇侠传"—— 关键词无关，只是他每次都搜这个片名。

### 2.4 根因二：搜索与 jar 初始化撞车（独立存在，同样会造"假空"）

ar 日志里 63 次这样的栈：

```
NullPointerException: Attempt to invoke interface method 'int java.util.Map.size()'
  on a null object reference
    at java.util.HashMap.putMapEntries(HashMap.java:493)
    at com.github.catvod.spider.App99.G(Unknown Source:166)
    at com.github.catvod.spider.App99.searchContent(Unknown Source:41)
    at com.github.catvod.spider.BaseSpiderGuard.searchContent(Unknown Source:2)
    at com.github.tvbox.osc.viewmodel.SourceViewModel.getSearch(SourceViewModel.java:536)
    at com.github.tvbox.osc.ui.activity.FastSearchActivity.searchResult$lambda-16(FastSearchActivity.kt:556)
```

**jar 自己的 `searchContent` 在配置/代理未就绪时抛异常**（它内部拿 null map 构造 HashMap），
被 `SourceViewModel` 的 `catch (Throwable)` 吞掉并回一条空结果 —— 站点就被**静默记成 0 条**。
如果这一轮恰好只有 jar 源参与，页面同样落到"暂无数据"，再搜一次（jar 已热）就好了。

同类还有一条**看起来像 bug、其实是良性**的噪音，别被它带偏：

```
Failed to connect to /127.0.0.1:8964 / 8965 / 8966 …（7280 次，ECONNREFUSED）
    at com.github.catvod.spider.ProxyOrigin.init
    at com.github.catvod.spider.DexNative.getLoader(Native Method)
```

这是 jar 在**逐端口探测它自己的旧端口段 8964~9031**。而宿主实测：
`GoProxyManager.waitHealth try=1, ok=true, host=http://127.0.0.1:39715/`
—— **活代理在随机高位端口**，8964 那批本来就不该有人在听。属既有结论"jar 内部出站
走 HTTP、连不上自己的代理是良性的"再一次被印证。

## 三、as 的修法（5 处，全部是机制性修正，不是打补丁）

### ① `ApiConfig.loadLocalHomeConfig()`：定论标志条件化（治根因一，这是主刀）

```java
// 内置首页配置只填 homeSiteList/mHomeSource，**不填 sourceBeanList**；
// 有订阅时必须把定论留给 parseJsonInternal（解析完）或重试用尽那两个出口。
if (Hawk.get(HawkConfig.API_URL, "").isEmpty()) sitePoolSettled = true;
```

**语义修正**：`sitePoolSettled` 的含义从"某个配置解析完了"改成
"**搜索能看到的那份站点池**有结论了"。这是 ar 失败的根源，也是这一版最关键的一行。

### ② `JarLoader`：新增装载序号（治根因二）

```java
private static final AtomicLong LOAD_SEQ = new AtomicLong();
public static long loadSeq() { return LOAD_SEQ.get(); }

private DexClassLoader loadJarInternal(...) {
    try { return doLoadJarInternal(...); }
    finally { LOAD_SEQ.incrementAndGet(); }   // 成功/失败/命中复用都算"有结论"
}
```

搜索侧发起时快照，收尾时比对。用 `finally` 是刻意的：**失败同样意味着"撞上了"**，
那次 0 结果一样不可信。static 是因为主 loader 与 home loader 两个实例都要记进同一本账。

### ③ `FastSearchActivity.verdictEmpty()`：0 结果统一裁决，假空自动重搜

把原来散在三个出口的 `showEmpty()` 收敛成一个裁决点：

```
不可信 = 站点池尚未定论  ‖  本轮期间有 jar 装载落定
   不可信 且 未超上限 → 保持 loading + Toast「正在初始化播放源，自动重试…」→ 自动重搜
   否则               → showEmpty()（真空态）
```

**这就是用户"手点第二下"的自动化**：上限 2 次，重搜时 jar 已热，第二次基本必成；
源真的没结果时不至于无限转圈。

### ④ 等待预算 2 秒 → 5 秒

`READY_RETRY_MAX` 4 → 10（×500ms）。ar 的 2 秒在弱网下拉订阅不够。
等待期间界面停在 loading，**不会先闪一个"暂无数据"再变出结果**。

### ⑤ 文案与配套

- 新增 Toast `正在初始化播放源，自动重试…` 并**加进 `ToastSweeper.HOST_TEXTS`**。
  ⚠️ 这个白名单是**允许列表**（`isHostToast` 里 `text.contains(host)` 命中才放行），
  不登记就等着被当 jar 弹窗移除。注意别与 jar 横幅那条"正在初始化本地代理"混了，两者只差两个字。
- 自动重搜会**重入** `searchResult()`，所以 tab 与站点名表改为在 `searchResult()` 内部重建
  （原来只在 `search()` 里清，重入会叠加"全部显示"、残留上一轮站点名）。
- `onDestroy` 清掉新的定时任务。

### ⑥ 回归闸门新增 W 节 13 条断言

锁死：定论标志不得无条件置位、`emptyHome` 兜底不得删、装载序号必须自增、
0 结果必须走裁决（≥3 处调用）、不可信判据的写法、等待预算、Toast 必须进白名单。

## 四、验证口径与新增路标

日志里现在有两行**贯穿每轮搜索**的路标（`I/System.out`）：

```
搜索轮次：可搜站点=N 站点池定论=true/false jar装载序号=X 自动重搜=N
搜索收尾：0 结果但与初始化重叠（站点池定论=... jar装载序号=X->Y），自动重搜第 N 次
搜索收尾：0 结果且判定为真空（...），给出空态
```

**这样下一次不需要再靠推测**：直接看"可搜站点"是不是 0、"定论"是不是 false、
"装载序号"有没有变，就知道空态是哪条路径造成的。

## 五、诚实边界

1. **根因一已修且可静态证**（`sitePoolSettled` 的语义修正 + `emptyHome` 不可搜 + assets 无 sites
   —— 三者任一不成立，结论就不成立；三者都已逐行核对）。
2. **根因二未被"消灭"，只是被"兜住"**：jar 在代理未就绪时抛 NPE 是它自己的内部时序，
   宿主无法从外部消除；as 的做法是**不把它的后果当结论**（0 结果 → 自动重搜）。
3. **弱网极端情况**：订阅响应超过 5 秒，仍会给空态 —— 但此时它确实是"还没到"，
   用户再点一下仍然有效，且不会再出现"必须先回首页"那种死结。
4. **本次仍未碰**：结果缓存、慢源分档超时（新风险面，留给独立批次验证）；
   `DetailActivity` 站点快捷搜索的同类缺陷（另一特性，不混批）。
5. **一个可再优化的点**（未做，等验证后决定）：订阅落地其实是有回调的，
   若能加一个"站点池已就绪"事件，搜索侧就能做到**事件驱动、零轮询**，
   把最坏 5 秒的等待也省掉。当前版先保"绝不假空"，不引入新的事件通道。
