## 一、这批修的都是「失败链走错路」，与具体站点无关

前三项是上一轮真机对照里抓到的，第四项是复核时发现的机制缺陷，第五项是构建前补的，第六七项是历史遗留与证据质量。

| # | 症状（改前） | 根因 | 修法 |
|---|---|---|---|
| **1** | 起播卡住时界面**永久转圈**，既不报错也不换路 | 看门狗把「网速 > 0」当"有进展"解除保护。实测存在「持续下数据却始终不出画面」的源（准备中 / 位置 0 / 46KB每秒），它把保护永久解除 | 真进展只看**离开准备中**或**位置推进**；「有数据无画面」不属于进展，但也不立刻判死（会误杀慢源）——只延长观察一次（12 秒）再终裁 |
| **2** | 判死 → 降级重播 → 又不出画面时，**再没人接管** | 看门狗有 `mWatchdogFired` 一次性标记，`armStartWatchdog` 不重置 → 只有第一次会响 | 每次起播都重置标记与轮次。安全性来自降级链自带额度（回退直连 1 次 / 变形 1 次 / 内置降级 ≤2 档），额度用尽即终止 |
| **3** | 变形重试（http↔https）把地址改坏后，**后续降级拿这个死地址去播** | `retryVariantUrl` 会把 `mPlayingUrl` 换成同址改协议的地址；`compatFallback` 又直接用它重播（例如 http 端口被写成 https，必不通） | 变形前记下原地址，降级一律回到**变形前**的地址 |
| **4** | 同一次起播的失败被处理**两次**，降级额度凭空少一半 | 播放器换源/释放后仍可能滞后报一次 `error` → 再走一遍降级链（实测同一集出现间隔 0.25 秒的两轮） | `errReplay` 按起播时刻去重：同一次起播只处理一次 |
| **5** | 每档降级都空转时，用户要盯着转圈**最坏约 160 秒** | 判死 → 降级 → 再判死 → 再降级，每轮 32 秒，没有总预算 | 本集自动重播设 **90 秒总预算**，超了直接给提示（换集 / 手动点重试才重新给满） |
| **6** | 真失败**一条都没记**；取链超时耗时写死 `-1` | 「兜底试尽」出口只记 `stage` 没记 `fail` | 改为 `fail` 并带上真实耗时；取链看门狗记真实起点；净化失败补粗归因（区分本机代理地址 / 远端） |
| **7** | 本地 HLS 端点可能读到空内容 | `RemoteServer.m3u8Content` 是裸静态字段：写方是 OkGo 回调线程、读方是 NanoHTTPD 工作线程，无任何同步 | 加 `volatile` |

## 二、为什么第 1 项不能"简单地把 speed>0 去掉"

去掉 `speed > 0` 会误杀**真的还在慢慢加载**的源（那是正常的慢，不是坏）。所以设计成两条独立路径：

| 情形 | 改前 | 改后 |
|---|---|---|
| 无数据、无画面（20s） | 复核 10s → 30s 判死 | **不变**（原行为保留） |
| 有数据、无画面（20s） | 判定"有进展"→ **永久放行** | 延长观察 12s → **32s 判死** |
| 复核时发现有数据 | —— | 按上行再放宽一次（30s → 42s） |
| 位置推进 / 已离开准备中 | 解除 | 解除（**不变**） |

即：**把"永久转圈"变成"最多 32~42 秒"，同时不动"真进展"的判定**。慢源仍然会被放行（只要位置动或已就绪）。

## 三、闸门

`check_l1box_regressions.sh`：

- **X 节 B3 那条断言本身是错的**（它固化的正是这次的漏洞：「网速 > 0 也算解除」），已改写为「真进展 = 离开准备中或位置推进」，并加 `mustnot` 禁止「`pos > 0 || speed > 0`」这个组合再出现。
- 新增 **Z 节 13 条**：降级必须回到变形前地址、不得直接拿 `mPlayingUrl` 重播、同一次起播只处理一次失败、三个失败出口都要留痕、`m3u8Content` 必须是 `volatile`、本集预算三段。

**验证过防线有效**：X 节那条错误断言在改动前确实让闸门报错（`!!` 退出码 1），说明新增断言不是摆设。

## 五、诚实边界

1. **限速代理只影响 Exo 路径**（ffmpeg/IJK 不读系统代理）。但 Exo 是默认播放器，正是要测的那条路径。
2. **限速代理对设备回环地址（127.0.0.1）无效** —— 那个"本地 HLS 服务"跑在设备自己身上，代理到不了。脚本遇到这种请求会直接 502 并在日志标出，便于区分"代理造成的影响"与"被测行为"。
3. **32 秒判死对"真的需要 40 秒才起播"的源是损失**。权衡：永久转圈更差；且判死后走的是降级重播（还会再试），不是直接判失败。
4. **90 秒预算不是起播超时**：它只在判死这条路上检查，已经在播、或位置在推进的播放不会被它打断。
5. 本批**不碰加固 jar 装载**、不新增线程、不新增用户可见入口。
